# DbDataKit.Knowledge.Index

The knowledge index on a state database (plan 27a KN07 and KN08: words on every engine, vectors where the engine can hold them). `DbDataKit.Knowledge` holds items, chunks, scope and the access filter and needs no server; this library keeps the chunks of a channel's items in the `knowledge` module of `DbDataKit.State` (`KnowledgeModule`, `KnowledgeStore`) and finds them by their words.

- **`StateKnowledgeIndex`** (one per channel): `Put(item, chunks, source, version)` writes an item and its chunks in one transaction, replacing what was there; an item whose hash did not change is not written again. `Remove`, `Status`.
- **`SearchAsync(question, caller, catalog)`** finds the chunks that have any of the question's words, applies `KnowledgeAccess.Visible` to each item at the time of the question (so an access change takes effect at once, with no rebuild) and assembles the hits as `KnowledgeSearch` does: per item at most three chunks, adjacent ones joined, with the title, the heading path, the source and the version.
- **The engine's own text search**, made on first use and always derivable from the chunks: SQLite FTS5 (bm25), PostgreSQL `tsvector` with a GIN index on an expression (`ts_rank_cd`, configuration `simple`: no stemming, any language), and a portable term match (a count of the question's words) where an engine has none, which is SQL Server. SQL Server's full-text feature is an optional install this suite does not require; the term match is what it gets, and it is honest about being basic.
- **A question** is its words (lower case, letters and digits, the words that mean nothing left out, at most twelve), searched by *any* of them and ranked by how well a chunk matches; no character of a question reaches the engine's query language.
- **`LineageSubjectCatalog`** (plan 27a KN02): the catalog of subjects read from a `LineageGraph` (semantic models with their measures and dimensions, apps, integrations, Store models, connections), `Gone` for what an earlier answer had and this one does not, and `CompositeSubjectCatalog` to ask it beside another catalog.
- **`GeneratedSync`** (plan 27a KN12): keeps the items `GeneratedKnowledge` renders for a published definition in the index: only changed text is indexed again, a measure that is dropped is retired, a retired definition takes its items, and items of other definitions or typed by people are never touched.
- **Vectors are a module of their own** (`knowledge_vectors`, `requiresFeatures: [Vector]`, in `DbDataKit.State`): a module that needs an engine feature refuses to exist without it and words must be found on every engine. It is the embedding model's id and dimension per channel and the vectors of the chunks in a table per dimension (PostgreSQL `vector(n)` with HNSW through pgvector, SQL Server 2025 `vector(n)` with `VECTOR_DISTANCE`); SQLite and SQL Server 2022 have no vector index here.
- **`KnowledgeEmbedder`** (per channel) is the background step that gives chunks their vectors: only the chunks that have no current vector for the bound model (new, or whose text changed; the chunk's hash says which), in batches, a chunk the model refuses recorded with the reason and tried three times, a provider that is down told in the run without using up the chunks' attempts, and when a model was bound after another, the switch to the complete new index in one step. It never runs while an item is saved: `Put` writes words and chunks and calls no model.
- **`FindAsync(question, caller, catalog, mode, resolver)`** searches by `Words`, `Vectors` or `Both` (the rankings fused by reciprocal rank, k = 60) under the same access filter. Where meaning is not available (no vector module, no ready index, no embedding model) it answers by words and says why in `Note`. The `EmbeddingResolver` finds the generator for the model the ready index was made with, so a model change keeps answering from the old index until the new one is complete.

Tests: `DbDataKit.State.Tests/KnowledgeIndexTests.cs` and `KnowledgeVectorTests.cs` (SQLite always where it can; SQL Server 2025 and PostgreSQL with pgvector when `DBDATAKIT_TEST_SQLSERVER` and `DBDATAKIT_TEST_POSTGRES` name them).
