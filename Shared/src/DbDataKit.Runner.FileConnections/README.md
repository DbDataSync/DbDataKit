# DbDataKit.Runner.FileConnections

File connections as the sources of the runner's file trigger (plan 27a IX07). `ConnectionFileSource` is the trigger's `IFileSource` over an `IFileStore` of `DbDataKit.Connections.Files` (SFTP, FTPS, SMB, S3, Azure Blob): it opens the store when a look starts and the trigger engine lets it go when the look ends, so a trigger holds no connection between looks; it lists the files that match the trigger's pattern oldest first, and reads them. `ConnectionFileSources` is the `IFileSourceProvider`: it finds the source of a slot by the connection the slot is **bound to in the task's release channel** (a delegate `(task, slot) -> ConnectionDefinition?`, which the runner's binding store and the connection files answer; or an opener that makes the store itself), and leaves any other slot to a fallback such as the local folders of `LocalFileSources`.

- **A file seen twice runs once:** the engine hashes each new-looking file with a bounded buffer and asks the task's ledger by content, so a re-sent file, or the same content under another name, is recognised whatever the source.
- **A partly written file is not taken:** the listing leaves out names that mean "being written" (`.part`, `.tmp`, ...: the store's own `WriteAsync` writes through `.part`), and the engine leaves a file modified within its settle time (`FileSettle`, 2 seconds by default) for the next look. The server's modified time is compared with the runner's clock: a server clock far ahead makes files look just written (they are taken once the skew has passed), one far behind defeats the settle time (the ledger still stops a second run, a half file could run once).
- **The source follows the channel's binding:** a slot bound to one connection in `prod` and another in `test` reads each in its own channel; the test channel never reads production's folder.
