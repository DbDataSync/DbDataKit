# DbDataKit.Lineage

The lineage graph of the suite (plan 18, G01-G03), built by each server from what it knows about its own objects and joined by identity in the console.

- **Nodes** (`LineageNode`): a dataset, a column, a job, a semantic member, a serving object, a consumer. A node says when its upstream is unknown (`UnknownUpstream`), so "nothing flows here" and "we do not know" are different.
- **Edges** (`LineageEdge`): `replicates`, `derives`, `copies`, `binds`, `serves`, `extracts`, `reads`, `promotes`, each at `column` or `table` granularity and each `declared`, `derived` or `observed`. The graph refuses a cycle.
- **Two layers**: design lineage is what a definition says can flow (replaced whole when a definition changes); run lineage (`EdgeRun`) is what did flow, kept per edge and pruned by the server's retention.
- **Identity** (`LineageIdentity`): a dataset or column is named from its `connection/1` definition (engine, normalized server, port, database, schema, table; the dialect's case rule), in the shape of an OpenLineage namespace and name, so two products that spell one server differently still meet in one node.
- **Run tables** (`RunTables`): the tables a run read and wrote, as the dataset lines of the Runner Kit's `run.Lineage(reads, writes)`; the Runner keeps them and its `RunnerDataChanges` sends the writes as `data.changed` (plan 24a UC13). Sync's drain names a pass's tables with it.
- **Store** (`LineageStore`, the `lineage` module `LineageModule.Module`): per server, on `DbDataKit.State` (SQLite, SQL Server, PostgreSQL), with a version that changes whenever the design graph changes.
- **Queries** (`LineageQueries`): `Impact` (downstream), `Provenance` (upstream) and `Path`, each bounded in depth, reporting the gaps they ran into.
- **The contract guard** (`ContractGuard`, plan 21 CH06): before a column is dropped, renamed away or retyped, `Consumers` walks the graph downstream from the column (and from its table, for a consumer that reads only the table) and returns each published consumer or semantic member with its **channel** (the node's property `channel`; a node with none is production's). `Check` turns that into refusals that name consumer and channel and the escape (`<consumer>@<channel>` allowances, `gateway:<name>` for a paired server whose lineage could not be read), and says which allowances it used so the caller records them. The Gateway emits one consumer node per channel a dashboard, report or app instance is published in (`name~channel` for the channels other than production, with `channel` on the node). The callers reach a Gateway's graph through `GatewayLineageClient` (`DbDataKit.Serving.Notify`: the pairings the server publishes with, its own signed token with the Publisher role, which the Gateway lets read `GET /api/v1/lineage`): Build's apply (`--allow-consumer`, DDB-444) and the Store's contract step (`allow_consumer=`).
