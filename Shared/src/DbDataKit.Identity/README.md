# DbDataKit.Identity

The identity home (plan 13a U13): who people are and what they may do, for every server, console and app of an install. A component, not a host: the serving layer hosts it (plan 20, O06), and `dbdatakit identity run` (U15, in `DbDataKit.Server`: `IdentityHost`) runs it on its own with the shared sign-in, its own state and directory.

- **`HomeSchema`**: the tables, over `DbDataKit.State`'s users, credentials and sessions: groups, members, role assignments, OpenID Connect clients, authorization codes, signing keys. SQLite, SQL Server and PostgreSQL by the state dialect.
- **`HomeDirectory`**: groups, and roles assigned to a user or a group on a server, on one Build project of a server, or in an app. What a user holds is the union of their own and their groups'.
- **`OpenIdProvider`** and **`MapOpenIdProvider`**: discovery, JWKS, `authorize`, `token`, `userinfo`, `end-session`. Authorization code with PKCE (S256 only), ES256 id tokens and access tokens; **refresh tokens** (scope `offline_access`; the `refresh_token` grant reads the roles again, rotates the token on each use, revokes the family when a used token comes back or the user is disabled, and expires 12 hours after the sign-in); the **token exchange** (RFC 8693, `grant_type=urn:ietf:params:oauth:grant-type:token-exchange`, plan 26 AP19): a client the host of the home named (`IdentityHomeOptions.AppHosts`; none is named by default) trades a refresh token of its own that is still the one in force, for the access token of one app instance (`audience=app:<instance>`, or a preview `app:<instance>~<channel>`): the audience is the instance, the roles are the person's on it, the scope is `IAppGrants` narrowed by them (`AppScope.Narrow`), the client is the instance's; the refresh token is not used up and none is issued, and `invalid_target`, `access_denied`, `unauthorized_client` and `invalid_grant` say why not (`OpenIdClient.ExchangeForAppAsync` is the relying party's side); **OpenID Connect RP-Initiated Logout** (`end_session_endpoint`: the id token hint names the person, every refresh token of theirs is revoked, the host's `EndSession` callback ends its own session, and the browser goes back only to a `post_logout_redirect_uri` the client registered). `sub` is the home's user id; `groups` and `dbdata_roles` (`server:<id>`, `server:<id>/<project>`, `app:<id>`) carry what the home says. The host signs the person in (its session) and tells the endpoints who that is.
- **Addresses** (plan 13a U16): the id token carries `email` with `email_verified`, true only for an address an administrator entered at the home (the state store's `EmailKey`); a client links people on the address only when it is verified. `OpenIdClient` reads it into `HomeIdentity.EmailVerified` (a JSON `true` and nothing else), and `FederatedUsers` hands it to `AccountLinker` (`DbDataKit.State`), which joins the sign-in to the local or Windows account that holds the address.
- **`SigningKeys`**: ES256 keys, the private half protected by the host's `ISigningKeyProtector` (there is no default, so there is no unprotected key); rotate, retire.
- **`OpenIdClient`** and **`FederatedUsers`** (U14, U17): the relying party and what a console keeps for people who sign in through the home: the mirrored user, the home's last word on their roles, and per session the protected refresh token. `RefreshAsync` asks again when the interval has passed; the roles lapse after the interval plus a grace when the home cannot be asked.
- **`HomeTokens`**: the request for the console's token to a server (plan 13 T01) with the home's user id as the subject and the roles the home holds for that user there.

- **External groups** (plan 13a U18): `HomeDirectory.MapExternalGroup` maps an Entra group (the id token's `groups` claim) or a Windows group to roles on a server, a Build project or an app; `ExternalSignIns.SignIn` finds or makes the home user for an upstream sign-in (U16's rules) and records the groups the sign-in carried, replacing the last ones. What a person holds is their own assignments, their groups' and their external groups' mappings added together. `OpenIdClient` validates ES256 (the home) and RS256 (Entra) id tokens.

- **Directory attributes** (plan 22a GP04, D4): `HomeDirectory.MapExternalGroupToAttribute(source, group, attribute, value)` maps the same external groups U18 records (`ExternalSignIns.SignIn` -> `SetExternalGroups`; there is no second path) to an attribute and a value, in the table `attribute_mapping` (identity module version 7, additive: `CompatibleWithPrevious` is 1). Attributes are **multi-valued**: a person in two groups that give `region` a value each holds both, a value two groups give is held once, and a person holds only what their last sign-in's groups map to (leaving a group at the provider drops the value at the next sign-in; removing a mapping drops it at once). Names are lower case letters, digits and underscores (at most 64), values non-blank text of at most 200 characters. The admin API lists and edits them (`GET`/`POST` `attribute-mappings` `{"source","group","attribute","value"}`, `DELETE attribute-mappings/{id}`; the same again changes nothing). Not built: a command (`identity map-group` is for roles) and a screen (U18's admin command, route and screen are still open), and only group values are mapped, not other directory claims (a department claim would have to be fed as a group value).
  - **The claim `attrs`**: the home's id token and `userinfo`, and the console's token to a server (`HomeTokens`, `ConsoleTokenRequest.Attributes`, `ValidatedToken.Attributes`), carry a JSON object of attribute name to a non-empty array of strings, each value once, names and values in ordinal order: `"attrs": {"cost_centre": ["4711"], "region": ["east", "west"]}`. A person with no attributes has **no claim** (not an empty object), so their tokens are as before the claim. A reader that does not know `attrs` is unaffected (additive; a console built before reads the same `sub`, `groups`, `dbdata_roles`, `roles` and `projects`). A reader that knows it refuses a claim that is not an object of arrays of strings (the console token validator answers `MissingClaim`, `OpenIdClient` an `OpenIdClientException`) instead of reading it as none, because attributes will decide what a person may see. `OpenIdClient` reads it into `HomeIdentity.Attributes`; a serving host copies `ValidatedToken.Attributes` into `ServingCaller.Attributes` (`DbDataKit.Serving.Abstractions`), which stays separate from the single-valued `Claims`. The home's access token (`at+jwt`) does not carry it.

- **Upstream sign-in at the home** (plan 20 O06b, `UpstreamSignIn`): `IdentityHomeOptions.Entra` (an `EntraUpstream`: the tenant's issuer, the home's app id and secret, whether its addresses are trusted) makes the home a confidential OpenID Connect client of an Entra tenant: `/identity/upstream/entra` sends the browser there, `/identity/upstream/entra/callback` (the redirect URI to register) checks the RS256 id token with `OpenIdClient`, hands it to `ExternalSignIns` and starts the home's session. `IdentityHomeOptions.Windows` adds `/identity/upstream/windows`, negotiated (`AddNegotiate`): the SID (else the Kerberos name) is the credential, the UPN the address, the group SIDs (and on Windows their `DOMAIN\group` names, or on Linux an LDAP lookup's role claims) the groups. The sign-in page offers each one that is configured; a refused sign-in, an unknown state, a token that does not check out, an account conflict or a disabled person signs nobody in and the page says why (403).

- **Personal access tokens and service accounts** (plan 13a U20, `AccessTokens`): a token is `ddk_<id>_<secret>`, shown once, kept as a SHA-256 hash; a person's lasts `AccessTokenPolicy.DefaultLifetime` (90 days, or the install's lower maximum) unless asked otherwise and never more than `MaxLifetime` (at most 365 days); a service account (a home user with no credential, `ServiceAccounts`) may have one that never expires. `Verify(userName, token)` takes the person's address, the service account's name or the user id with it, and refuses a revoked or expired token, another person's name and a disabled user. The home registers it as the shared `IPasswordCredentials`, so `SessionAuthenticationHandler` signs a request with `Authorization: Basic` in as that user, with the same id as any other way in. `/api/access-tokens` is a person's own list, make and revoke at the home (a request signed in with a token cannot make another). Administration at the command line: `service-account-add`, `-list`, `-remove`, `token-create` (a service account's), `token-list` and `token-revoke` (anyone's).

- **The admin API** (plan 13a U21, `IdentityAdminApi`): people, groups, role assignments, app clients, external group mappings, tokens and service accounts, transport-agnostic (a host passes the method, the path under `/api/v1/identity/`, the body and whether the caller holds admin), for the management API of whatever hosts the home: the Gateway's management listener, `dbdatakit identity run`'s. `HomeDirectory` gains `Assignments`, `RemoveAssignment`, `MembersOf`, `RemoveGroup`; `OidcClients.Remove` (its refresh tokens revoked).

A group of homes on one SQL Server or PostgreSQL state (plan 20 O02b) works behind any balancer: an Entra sign-in in progress, a passkey ceremony's challenge and the management tokens used are in the state (`OneTimeValues`), each used once.

Entra's group overage (more than 200 groups: the token has no `groups` claim) is left to the tenant: its administrator limits what the app registration sends with `groupMembershipClaims`, and the home calls no Microsoft Graph (13c D25). Not here yet: the serving layer forwarding a home that runs on its own (O07).

**Decisions that shape what a person holds** (the owner's, 2026-10-31; `docs/architecture.md`, 13c D24 to D26, D30, D31):

- A person's external groups (Entra, Windows) are the groups of their **last sign-in through that source** and count until the next one: nothing expires and signing out does not clear them, so a person removed from an Entra group keeps the mapped role until they sign in through Entra again (their session's refresh asks the home, which still has the old groups). A lifetime can be added if a tenant needs one.
- An Entra sign-in links to an existing account on the token's UPN (preferred, it is usually the canonical address) or `email`, because the Entra source is built with `trustEmail: true`; every other OpenID source links only on a verified address (U16's rule). A tenant that lets people set their own mail attribute must not be trusted that way.
- The admin API is the management API of whatever hosts the home (the console's screens through its relay; `dbdatakit identity run`'s commands stay).
- Signing keys: a home that runs on its own keeps the framework key ring in its `dataprotection/` directory, so a backup or a move takes the state **and** that directory (a copy without it fails to start with a cryptographic error). The serving layer's home protects the keys with `KeySigningKeyProtector` and a key in its secret store (`dbdatakit:gateway:identity:signing-keys`), because the instances of a group share one state. `ISigningKeyProtector` is where a key from outside would go.
## Not yet run on a real host

Everything above runs in CI with stand-ins (`UpstreamSignInTests` with a fake that signs RS256 tokens, `HomeIdentityTests` with a fake Windows logon). Two checks need an environment no CI job has (GitHub's Windows runners are not domain-joined), and are open until someone runs them and writes the date and the result here:

- **A domain-joined Windows host:** a real negotiated identity carries the `ClaimTypes.Upn` claim that `WindowsSignIn.ResolveOnWindows` reads and signs in to the account that holds that UPN; its group SIDs reach `ExternalSignIns`; the Gateway's `WindowsAccountValidator` resolves a Windows logon to the home account.
- **An Entra tenant:** an id token with a `groups` claim (the app registration's `groupMembershipClaims` limiting it) signs in through `UpstreamSignIn` and maps to roles.

## Decisions that bind sign-in (owner, 2026-10-25 and 2026-11-02; folded from the old plan 16)

- **One identity home per install**, a shared component (this package) hosted by the serving layer by default and runnable on its own (`dbdatakit identity run`). Other consoles hold no users: they are OpenID Connect clients of the home, keep only their own settings and a **ceiling** per server from their pairing, and a person is the same user everywhere, so audit names agree. Roles are assigned once, at the home.
- **App users are home users who administer nothing**: they hold app roles only. An app instance is an OpenID Connect client of the home; its access token's **audience is the instance** and its scopes come from the approved manifest (the models it names and the operations on each: read, write, change request), so the token is never wider than the person narrowed by the manifest. The serving layer's modules check audience and scopes. Sandboxed apps get the token from the shell, which gets it from the apps host, which trades the person's refresh token for it at the home (below, token exchange); the host signs nothing.
- **One list of people.** The Gateway's own users with passwords and its password-checked Windows accounts are retired (a configuration that still lists them is refused with a message naming the file); pass-through database credentials stay, the database being the authority. Clients that cannot open a browser use **personal access tokens** (a revocable secret per person, used as the password; 90 days by default, at most a year, the maximum lowered per install) and **service accounts** for unattended work (a service account's token may last longer or not expire, and is always listed and revocable). Product servers keep no sign-in of their own: a person reaches a back-end server only through a console's token whose subject is the home's user.
- **Excel, per path.** WebDAV: Office forms-based sign-in (MS-OFBA) with the home's own page, or a user name and personal access token. XMLA and MDX: HTTPS with Windows or user name and token; native TCP is not built. Power Query (feeds, saved queries, OData): Windows, user name and token, and where the install uses Entra, **Entra's own tokens accepted directly** on those endpoints, the person linked by UPN and given the home's roles (the one place a token the home did not issue is accepted). None of these has been seen in Office yet: the Excel VM recordings record each. The slices are plan 20 O15 to O17.
- **No consent prompt**: publishing an app instance, with plan 26's approvals, is the consent; an app's about page shows the models and operations its manifest uses, who published it and who approved it.
- **Sessions** last 12 hours from sign-in by default and do not extend in use; an optional idle timeout is off by default; an administrator sets both per install in `server.yaml` (a session of 1 to 24 hours; `SessionSettings`). Fixed in code: the home's access token 10 minutes, the role re-check inside a session 5 minutes (10 more when the home cannot be asked), the console's token to a server about 5 minutes.
- **Report servers embedded in apps: Windows end to end.** The browser signs in to the report server with the person's Windows identity; the report server's origin is an approved `frame` exception of the instance; off the domain the app shows a link. Kerberos constrained delegation through the serving layer is the later step (plan 26 AP17, plan 32 section 9e).
