# DbDataKit.State.Api

The state endpoints every server product's management API has (plan 29b, C05), so a console can see a server's state and prepare a move of it (`state move`, C04; the screens, C06).

It is a project of its own because it needs `DbDataKit.State.Cli` (the read-only inspection `state show` uses) and so `DbDataKit.State.Engines` and its two database providers: `DbDataKit.Web` must not reference those drivers, and every server product already references `State.Cli`. The product registers it with `<DbDataKitReference Include="State.Api" />`.

* `GET /api/v1/state` (viewer): product, software version, management API version, engine, connection (secret references as written, never resolved; the SQLite file), the registry table, where each effective setting came from (`sources`: flag, environment, file, default), each module with its place (schema, prefix, file), the version in the binary, the version in the registry and what is pending, `pending_migrations`, `instance` (this instance's module versions), `instances` (the live instances, from the product's `IInstanceDirectory`; empty when the product keeps no instance table; each with `software_version`, `module_versions` and `definition_formats` (the previous and current format of each kind of published definition it reads, plan 24a UC01), the versions its binary has, as its instance row records them: absent for a row an older binary wrote), and `maintenance`. Read-only: it opens nothing for writing, creates and migrates nothing. A state that cannot be read is still answered (`read: false`, `error` names the fix). The last answer step replaces any literal credential of the connection string. Last export and verify times are left out: nothing records them.
* `GET /api/v1/state/maintenance` (viewer): `enabled`, `idle`, `since`, `reason`, `inflight`.
* `POST /api/v1/state/maintenance` (admin), body `{"enabled": true, "reason": "moving the state"}`: the reason is needed to enter. While it is on, `MaintenanceMiddleware.UseMaintenance` answers every request with 503, `Retry-After: 30` and `{"error", "maintenance": true, "reason", "since", "retry_after_seconds"}`, except the state endpoints, `/health*`, `/version`, `/management/` (pairing) and requests of an administrator. Requests are counted while answered, and `idle` is true when none is left and the product's own work (`MaintenanceGate`'s `work`, such as plans a scheduler runs) is done. Nothing is persisted: a restart leaves maintenance (a move needs the restart anyway).
* `GET /api/v1/state/move` (viewer) and `POST /api/v1/state/move` (admin), where the product passes `Move: true` (it has a settings file the state writer can write: the Store, the Gateway and Build; not the console, whose own move is the command line, plan 29b QM3; there the calls are 404): the server moves its own state to another database, on the machine that has the settings file and the secret store (plan 29b, C06). Body `{"engine": "postgres|mssql", "connection": "Host=...;Database=...;Username=...;Password=secret:NAME", "schema": null, "prefix": null, "dry_run": false}`: the connection takes secret references only (a password written out is 400) that the server resolves in its own store; `dry_run` runs the preflight alone (the target opens, is empty, is not the server's own database, the settings file can be written; a reference the server cannot resolve answers 400 with `reason: secretmissing` and the `secret set` command). The server has to be in maintenance and idle or the call is 409 (it never freezes itself), a target that holds modules is 409, a viewer 403. A real move answers 202 and runs `StateMoveService` (export, import, both verifications, then the settings, with the previous file kept as `<settings>.before-state-move`) in a task of the server; `GET` reads `state` (`none|running|succeeded|failed`), `step`, per-table progress, `error`, `kept` (what was left as it was), and on success `restart` and `way_back`. Maintenance stays on; nothing is restarted; a failure leaves the settings unchanged. Audited as `state.move` (started, ok, failed, refusals); no secret is in an answer or the audit. The server's own instance row (the Gateway's lease) does not count as a live user of the database for its own export (`SnapshotOptions.IgnoredInstances`); other live instances still refuse it.
* The console's own wizard calls are audited by the console as `state.connection.save`, `state.connection.remove`, `state.move.check` (the preflight) and `state.move.start`, who and which call, never a body (`ConsoleAuditTrail`); the server audits the same move as `state.move` and the maintenance switch as `state.maintenance`.
* Every change is audited as `state.maintenance` (who, through which console, the reason; never a secret) through the product's `IAuditLog`, and a refusal (a role that is not enough, a body that is not valid) too. A change that cannot be audited is not kept.

The identity home's own host (`dbdatakit identity run`) registers them under its management prefix (marked anonymous: the token check is their authentication, the home's session policy is for people at the home); its state settings are read from the `state:` section of its `server.yaml` in the shared order. `Move: true`, its audit is `management-audit.log` beside `server.yaml`.

## What a product does

```csharp
var gate = new MaintenanceGate(onEnter: reason => /* stop claiming */, onLeave: () => /* claim again */, work: () => running);
app.UseMaintenance(gate, context => /* is this request an administrator's */);   // after the authentication it reads
app.MapState(new StateManagement(new StateManagementOptions(product, program, "the server", () => stateTarget, modules, scope, gate, audit, instanceId, version, instances)));
```

`MapState` reads the console's token that `UseManagementAuthentication` validated; a product that signs people in (the console) passes a function that makes a `StateCaller` from the session. A product with its own dispatcher (the Gateway, whose local channel shares it) calls `StateManagement.HandleAsync`. The audit is `StateAuditSink` where the state has the `audit` module (console, Gateway), else a `FileAuditLog` (Store, Build). `IInstanceDirectory` is the seam for the instances sharing a state: the Gateway's `serving_instance` (it records its software and module versions); the default is empty.
