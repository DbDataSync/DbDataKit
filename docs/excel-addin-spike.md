## Manifests

Two formats exist and an add-in may need both.

| | Add-in only manifest (XML) | Unified manifest for Microsoft 365 (JSON) |
| --- | --- | --- |
| Root | `<OfficeApp xsi:type="TaskPaneApp">` with `Id`, `Version`, `ProviderName`, `DisplayName`, `Description`, `IconUrl`, `Hosts` (`Workbook` is Excel), `DefaultSettings/SourceLocation`, `Permissions`, `AppDomains`, `VersionOverrides` for ribbon buttons | `manifest.json`: `id`, `version`, `manifestVersion`, `name`, `description`, `developer`, `icons`, `validDomains`, `webApplicationInfo` (Entra app, for SSO), and an `extensions` array with `requirements`, `runtimes`, `ribbons`, `autoRunEvents` |
| Where it works | the format of every client, including the perpetual Office on Windows that the unified page says cannot take the JSON one (read by implication from that page; the [XML manifest overview](https://learn.microsoft.com/en-us/office/dev/add-ins/develop/xml-manifest-overview), 2025-11-06, gives the elements; the clients it lists were not read: unverified) | Excel, Word and PowerPoint on Windows version 2501 or later and on Mac 16.103 or later, both with a Microsoft 365 subscription, and on the web; **not** perpetual Office on Windows, iPad or mobile (read, [Unified manifest overview](https://learn.microsoft.com/en-us/office/dev/add-ins/develop/unified-manifest-overview), 2026-10-14) |
| Status | the original format | general availability for Word, Excel and PowerPoint announced 2026-07-16 (read, [Microsoft 365 Developer Blog](https://devblogs.microsoft.com/microsoft365dev/unified-manifest-for-office-add-ins-now-ga/)); the overview page's own sample still shows `"manifestVersion": "devPreview"` and the `vDevPreview` schema, so which schema version to write is **unverified** until the current schema page is read |

What each needs to be sideloaded:

- **XML, Windows:** the manifest in a shared folder trusted as a catalog in the Trust Center (or the registry script), then Insert, My Add-ins, Shared Folder (read, [network share](https://learn.microsoft.com/en-us/office/dev/add-ins/testing/create-a-network-shared-folder-catalog-for-task-pane-and-content-add-ins), 2026-06-09). Not a production deployment route.
- **XML, Mac:** copy the file into `~/Library/Containers/com.microsoft.Excel/Data/Documents/wef`, restart Excel, Home, Add-ins (read, [Mac sideload](https://learn.microsoft.com/en-us/office/dev/add-ins/testing/sideload-an-office-add-in-on-mac), 2026-05-07).
- **XML, Excel on the web:** the manifest is stored in the browser's local storage, so clearing the cache or changing browser means sideloading again; there is a manual route for a Microsoft account and another for a Microsoft 365 tenant (read, [web sideload](https://learn.microsoft.com/en-us/office/dev/add-ins/testing/sideload-office-add-ins-for-testing), 2025-12-03). The menu steps themselves were not read: **unverified**.
- **Unified:** `npx office-addin-debugging start <manifest.json> desktop` (zips the manifest and its icons, sideloads, starts a localhost server), the Microsoft 365 Agents Toolkit (`atk install --file-path <zip>`), or an upload through the Teams app store. Sideloading on Windows also sideloads on the web. Not supported from a network share; not iPad (read, [sideload with the unified manifest](https://learn.microsoft.com/en-us/office/dev/add-ins/testing/sideload-add-in-with-unified-manifest), 2026-04-21). Whether the `atk` and Teams routes need a Microsoft 365 tenant account was not stated on the page: **unverified**.
- **Central deployment** (what an administrator does for everyone): the Integrated Apps page of the Microsoft 365 admin center, which takes the unified manifest (read, same blog post). Whether the XML manifest is also accepted there was not re-read: **unverified**.
- Every URL in the manifest must be HTTPS (read, XML overview: "all URLs on the resources section must use HTTPS"). Navigation to another domain from the pane opens a browser window outside the pane on desktop unless the domain is in `AppDomains` (XML) or `validDomains` (unified) (read, both overviews).

**Recommendation for the suite:** the add-in is a generated artifact, not a hand-written file. The suite should produce the XML manifest first (widest reach, the same file for Windows, Mac and the web, no dependence on a still-moving schema) and the unified one from the same template when an administrator wants Integrated Apps. Origin, ids and names are filled in from the console's public address. In XL02 the manifest is a published format registered open in `docs/formats.json`, with a row in `docs/ui-editors.md` for the console screen that shows it and its install steps; this spike registers nothing.

## Sign-in

Facts about Office (all read):

- Office runs a task pane in an iframe on the web, and Entra, Google and others refuse to show their sign-in page in an iframe. Office's answer is the **dialog API**: `Office.context.ui.displayDialogAsync` opens a separate browser or webview instance, nonmodal, 80 percent of the screen by default (`height` and `width` as percentages). Its first page must be on the **same origin** (protocol, host and port) as the pane; it may then redirect anywhere; the page that finishes the sign-in calls `messageParent` (with `targetOrigin` when it is not on the pane's origin); the pane receives `DialogMessageReceived`. One dialog per pane at a time. The dialog shares no storage with the pane (not `sessionStorage`; `localStorage` sharing is unreliable, and not at all in Safari on the web), so a token travels in the message. Pass the message as a string. A dialog on another origin that sends `Cross-Origin-Opener-Policy: same-origin` fails with error 12006 on the web ([auth with the dialog API](https://learn.microsoft.com/en-us/office/dev/add-ins/develop/auth-with-office-dialog-api), 2026-01-08; [dialog API](https://learn.microsoft.com/en-us/office/dev/add-ins/develop/dialog-api-in-office-add-ins), 2026-09-28).
- **Legacy Office SSO** (`getAccessToken`) hands the pane a token for the Microsoft account or work account Office is signed in with. The page now points to **nested app authentication** (NAA: MSAL.js `createNestablePublicClientApplication`, a single-page-application redirect `brk-multihub://<origin>`, plus a normal redirect for the task pane page on the web) as the replacement. NAA supports Microsoft accounts and Entra work accounts, not B2C; Word, Excel, PowerPoint, Outlook and Teams are the brokers. Both need an Entra app registration, and the add-in's `webApplicationInfo` names it ([legacy SSO](https://learn.microsoft.com/en-us/office/dev/add-ins/develop/sso-in-office-add-ins), 2026-02-02; [NAA](https://learn.microsoft.com/en-us/office/dev/add-ins/develop/enable-nested-app-authentication-in-your-add-in), 2025-12-15). Microsoft says to keep a fallback sign-in because SSO fails on some Office versions (legacy page).
- In a custom function that does not share the pane's runtime, sign-in uses `OfficeRuntime.displayWebDialog` and `OfficeRuntime.storage` (10 MB, unencrypted, shared between runtimes) to pass the token ([custom functions authentication](https://learn.microsoft.com/en-us/office/dev/add-ins/excel/custom-functions-authentication), 2026-07-10; [JavaScript-only runtime](https://learn.microsoft.com/en-us/office/dev/add-ins/excel/custom-functions-runtime), 2025-10-22).

What the suite's identity home can do with them (code read: `Shared/src/DbDataKit.Identity/README.md`, `OpenIdEndpoints.cs`, `DbDataKit/src/DbDataKit.Server/ConsoleFederation.cs`, `Shared/src/DbDataKit.Web/Auth/Controllers/AuthController.cs`):

| Way | Windows, Mac, web | Through the identity home? | Needs |
| --- | --- | --- | --- |
| **Dialog to the home's own sign-in, authorization code with PKCE** | designed for all three (read) | **yes**: `/identity/authorize` and `/identity/token` exist, a client may be public (`identity client-add --public --redirect <uri>`), and the sign-in page offers passkeys, Entra and Windows as the install configures them | a registered public client whose redirect is a page on the add-in's origin; **CORS on `/identity/token` and `/identity/userinfo` for that origin (none exists today: no CORS code in the console, the home or the feeds listener)**, or the add-in served from the home's own origin; the add-in's origin in `AppDomains`. Whether a passkey prompt or Windows (Negotiate) sign-in works inside Office's dialog webview on each platform: **unverified**, and the first thing to try |
| **NAA with MSAL** | Windows, Mac and the web (read) | **no**: the token is Entra's, and the home accepts none (plan 20 O15 to O17 would accept Entra tokens directly on the Power Query endpoints only; not built). The home does exchange tokens (RFC 8693) but only a refresh token of its own for an app instance | a Microsoft Entra tenant, an app registration, and a new exchange of an Entra token for a home token. Quiet for the person, but only where the install uses Entra. A later optimization, not the base |
| **MSAL in the pane** (popup) | on the web the popup is blocked as an iframe issue; the dialog route above is what Microsoft documents (read) | same as NAA | not recommended |
| **The console's own session cookie** | no | n/a | the console's session cookie is `SameSite=Strict` for a local or passkey sign-in and `Lax` after the home, and the console answers no CORS, so a pane on another origin cannot use it; whether a desktop pane's webview even shares the browser's cookies was not found: **unverified** |
| Personal access token typed in the pane | all | yes (a token of the person) | no browser needed, works where the dialog does not; weaker experience; useful as the fallback Microsoft asks for |

Token life with the home: the access token lives 10 minutes; a refresh token (scope `offline_access`) ends 12 hours after the sign-in; roles are read again on refresh (identity README). **Recommendation:** the pane holds the tokens in memory only (a runtime with `lifetime: long`, which stays alive while the workbook is open (read, [shared runtime](https://learn.microsoft.com/en-us/office/dev/add-ins/develop/configure-your-add-in-to-use-a-shared-runtime), 2026-07-30), keeps them across pane closing), refreshes through the home, and asks the person to sign in again after 12 hours. Putting a refresh token in `OfficeRuntime.storage` would make it readable by anything on the add-in's origin, unencrypted: decide with the owner before doing it.

The hello pane does exactly the first row: `taskpane.js` opens `dialog.html` (same origin), which builds the PKCE request and sends the dialog to the home; the home redirects to `auth-done.html`, which hands the code to the pane with `messageParent`; the pane trades it at `/identity/token` and shows the name from `/identity/userinfo`. Until the home answers CORS it stops at the token call with the browser's error: that is the first finding to confirm, not a defect of the scaffold.

## How the pane reaches the suite

- **HTTPS everywhere** (read above). For localhost, Microsoft's tool `office-addin-dev-certs install` creates a development CA and a `localhost` certificate under `~/.office-addin-dev-certs` and trusts the CA; the certificate lasts 30 days by default (read, the package's README on npm, version 3.0.1 of 2026-09-24; file names `localhost.crt`, `localhost.key` read in the package). `docs/examples/excel-hello/serve.sh` serves the folder with `http-server` using them. Whether Excel on the web and on Mac accept that CA without more steps: **unverified**. The suite's own listeners already use HTTPS with their own certificates (`docs/suite-listeners-and-auth.md`).
- **Office's script:** the pages load `office.js` from `appsforoffice.microsoft.com`. An install with no internet access cannot do that, and whether Microsoft allows a copy on the install's own server was not found: **unverified**; decide before promising the add-in to offline installs.
- **Host the add-in's files as a small static site of the console (for example under `/office/`), not as an app of the apps host (plan 26).** The apps host shows an app in a sandboxed shell with an opaque origin and `frame-ancestors 'none'` unless embed origins are set (`Shared/src/DbDataKit.Apps.Host/AppShell.cs`), and the dialog rule needs a stable origin; Excel on the web frames the pane, so the origins Excel uses would have to be allowed (their list: **unverified**). The console's host and the home are separate origins today (the home on its own listens on 8482), which is why the CORS above is needed; serving the add-in under the home or console removes it for sign-in but not for calls to other servers.
- **What the pane calls:** a published front-end agent and the semantic and feeds routes, as the person, with the home's access token as `Bearer` (the feeds listener already accepts an access token, a personal access token or Basic: `docs/bi-tools-on-semantic-models.md` R2). Every call from the pane or a custom function crosses origins: each server it calls must answer CORS for the add-in's origin, or the console relays (`ConsoleRelay.cs`) the call.
- **The workbook is a surface:** plan 27's rule stands; Excel recalculation and the person's access rules decide what a function or refresh returns.

## Custom functions

Read, from the pages listed under "Sources" (dates there):

- A function is JavaScript or TypeScript with JSDoc tags (`@customfunction`, `@param`, `@returns`, `@volatile`, `@streaming`, `@cancelable`); a webpack plugin makes the JSON metadata file; names allow `A-Z a-z 0-9 _ .` and a namespace prefixes them. The manifest names the metadata file and, in the unified form, a runtime whose action type is `executeFunction`. The add-in needs **read and write document permission** (`ReadWriteDocument`, or `Document.ReadWrite.User`): read-only can show `#BUSY!`.
- Two runtimes. The **JavaScript-only runtime** (default) has no DOM, no `localStorage`, `OfficeRuntime.storage` for state, and **simple CORS only** (same-origin or GET, HEAD, POST with simple headers, no cookies). The **shared runtime** (`lifetime: long`, requirement set SharedRuntime 1.1) is the task pane's browser runtime: DOM, full CORS, Office.js, state shared with the pane; Microsoft recommends it. The dialog never shares a runtime.
- A function that fetches data returns a Promise; Excel shows a busy value until it resolves. **Streaming** functions (`@streaming`, a `StreamingInvocation`) push values repeatedly; **cancelable** ones are told when Excel cancels (recalculation, a referenced cell edited). **Volatile** functions recalculate on every calculation. Results are `scalar` or `matrix` (a two-dimensional array that spills); a matrix result can be asked the addresses of its inputs.
- **Batching** is Microsoft's pattern for a remote service: collect the calls Excel makes in one calculation and send one request, because every cell calls separately (page: batch custom function calls).
- Platforms: not on iPad or on volume-licensed perpetual Office 2021 or earlier on Windows; CustomFunctionsRuntime 1.5 needs Windows 2504 or Mac 16.96 (the table of requirement sets, 2025-10-17). Coauthors are asked to load the add-in and then share results.
- The Excel JavaScript API itself: on the web a request or response is limited to **5 MB**, and a range read to five million cells on every platform ([performance](https://learn.microsoft.com/en-us/office/dev/add-ins/excel/performance), 2026-06-02).

**Unverified:** any limit on how long one function may run, how many calls one calculation may make, the cell count of a returned matrix, whether one request may be cancelled by Excel on a slow query, and what the person sees when the home's token has expired in the middle of a calculation (the sign-in dialog cannot be opened from a calculation: the function must return an error that says to open the pane; Microsoft's docs show `displayWebDialog` for this, whose behaviour was not tried). These decide XL03.

**What plan 14 R7 gives this:** nothing yet. R7 is MDX and XMLA for PivotTables, deferred; its recording forwarder (`Shared/tools/DbDataKit.Tools.XmlaForwarder`) has never been run against Excel (plan 14a: "never run against Excel"; no recordings exist anywhere in the repository). It is the wrong channel anyway: a PivotTable speaks XMLA to a data source, an add-in speaks HTTP from JavaScript. The one overlap is the Windows VM with Excel that R7 asks the owner for: the same machine runs the checklist below.

## A table that remembers its query

All Excel JavaScript API, so ExcelApi requirement sets apply (the pages were read for tables and settings; custom XML parts only from a documentation search result, so those are **unverified** in detail).

- A table is created with `worksheet.tables.add(...)` and named by setting its `name` after creation; its `onChanged` event reports edits; it can be written from JSON (read, [tables](https://learn.microsoft.com/en-us/office/dev/add-ins/excel/excel-add-ins-tables), 2026-06-03).
- **Where to store the query id:** the add-in's **workbook settings** (`context.workbook.settings`, scoped to this workbook and this add-in; read, [workbooks](https://learn.microsoft.com/en-us/office/dev/add-ins/excel/excel-add-ins-workbooks), 2026-06-03), keyed by the table's name, holding the query id (a saved or verified query's name and version, never the SQL and never data). Or a **custom XML part** (`workbook.customXmlParts.add(xml)`, ExcelApi 1.5, found by id or namespace; unverified). Recommendation: **settings keyed by table id**, with a custom XML part (namespace `urn:dbdatakit:query:1`, one element per table) only if the settings turn out not to survive a copy of the workbook. A renamed table or a table copied to another workbook loses the link; the add-in must say so rather than guess.
- **Refresh** reads the id for the table, runs the query as the person who is signed in now (their token, their rules), and rewrites the rows; it never reuses the earlier person's access. A workbook opened where the add-in is not installed shows the last copy and nothing else.
- The workbook is a copy: the 5 MB web limit means a refresh writes in chunks, and a result larger than a few hundred thousand cells needs a limit shown to the person (the number is **unverified**: measure on the web).

## Owner decisions (2026-11-12)

- **Manifest:** the XML manifest first; the unified JSON manifest later, if at all.
- **Hosting:** a static site of the Gateway or the identity home, not the console (end users are kept out of the console). Served from the home's own origin, the add-in needs no CORS on the home's token and userinfo routes; served from the Gateway, the home must answer CORS for that origin. XL02's first slice picks one.
- **Tokens:** no refresh token in `OfficeRuntime.storage`; tokens stay in memory and the person signs in again after 12 hours.
- **Sign-in:** no passkeys in the add-in; Windows and Entra sign-in automatically where Office's dialog allows it.
- **Platforms:** Windows first; Excel on the web second (not a priority); Mac last.
- **Offline installs:** nice to have, not required, and not worth much effort (self-hosting `office.js` is the open question).
- **Still open:** a Windows machine with Excel, a Mac and an Excel-on-the-web account for the one-day check.
