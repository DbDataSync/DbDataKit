# Testing app publishing end to end

How to walk an app through its whole life on one machine: write, validate, publish, approve, run, navigate, update, roll back, revoke, remove. [apps.md](apps.md) is the design as built; [plans/26-app-publishing.md](plans/26-app-publishing.md) holds the work that is left. This page is the audit of what a tester can do **today** (2026-11-08, `main` plus the slices AP20 to AP24 and AP26), a script to do it, and the gaps.

## Prerequisites

* Docker with Compose, a browser (Chromium, Edge or Chrome) and a checkout of this repository. A passkey is needed to sign in: a platform authenticator, a security key, or Chromium's virtual authenticator (DevTools, WebAuthn).
* About ten minutes for the first build (the quickstart's five images). Everything is self-signed: accept the browser's certificate warning for `localhost`, on 8817 (the identity home) and 8818 (the apps host).
* The sample apps in [DbDataGateway/templates/apps](../DbDataGateway/templates/apps/README.md): `territory-notes` (a code app over the Store model `territories`), `front-portal` (a declared portal) and `territory-views` (an app of views only).
* Without Docker: run a Gateway yourself with `modules: [flightsql, identity, apps]` (see the Gateway's README, "Modules") and replace the `DP` and `DS` shorthands below with `dotnet dbdatagateway.dll` and `dotnet dbdatastore.dll`. The Store's half (steps 1 and 2) needs a PostgreSQL for the model's tables.

## Manual script

Run from the repository root. Two shorthands:

```
DC="docker compose -f dist/compose/quickstart.yml -f dist/compose/quickstart-apps.yml"
DP="$DC exec -T gateway dotnet /app/dbdatagateway.dll"        # the Gateway's command line, on its own data directory (/data)
```

## The audit

The question for each step: what does a tester use today, does it work, what is missing.

| Step | Today's path | Works end to end? | Gap / what blocks a tester |
| --- | --- | --- | --- |
| Write an app, code | AP23: `apps init --template territory-notes --dir <folder> [--name]` makes a folder from the sample (inside the program, no network); an app folder is `app.yaml` (`app/1`) and the files the host serves; plain JS speaks `postMessage {dbdata:"app/1"}` to the shell | yes (run by `AppsModuleTests`, `AppsBuildTests`, `apps-host.spec.ts`) | no documented SDK of the message protocol beyond the sample and `apps.md` |
| Write an app, build step | AP23: `apps build --src --out [--entry] [--no-minify] [--offline] [--bun]` over `BunAppBundler` (`bun install --ignore-scripts` when there are packages, `bun build`), Bun found by `BunLocator` (the pinned, hash-checked `.bun/<rid>` from `scripts/fetch-bun.sh`, `--bun`, `DBDATAKIT_BUN`, the PATH), then `AppValidator` on the result | yes: `AppsBuildTests` build the sample source tree with an injected bundler (no Bun needed) and, where Bun is installed, with the real one | a package install fetches from the registry unless `--offline` or a package store is set; with `--store <folder>` (or `apps.packageStore`) nothing is installed, the build runs with no network where the machine can make a namespace for it, and an import outside the library and the allow-list (`apps.allowedPackages`) is refused by name (plan 22a GP33; docs/apps.md says what that guarantees) |
| Write an app, declarative | a **portal** of `kind: portal` with `views/home.yaml` (text, links, tiles), `front-portal` is one; an **app of views only** (AP25): `view-spec/1` files (grid, form, detail, dashboard) over a Store model, `apps init --template territory-views --dir <folder>`, which `apps validate` checks against the manifest (and the model, when the Store's schema is given) with file, line and column | yes (Gateway tests `AppsBuildTests`, `AppsModuleTests`; `ViewsAppTests`; the renderer's vitest suite; the pages were also driven in a real browser under the app's policy, see below) | the Playwright story for it is not written (it needs the identity home, the Store and PostgreSQL, like `apps-host.spec.ts`); a view cannot mix with a code page in one app (GP34); no semantic-layer widget |
| Validate | `dbdatagateway apps validate --dir` (manifest, files it names, root-relative paths, addresses of other hosts with file and line) | yes | advice only: the host's policy is what enforces |
| Publish a version | the Apps screen's **Publish a version…** (choose the built folder or paste a manifest; the Gateway checks it first, `POST /api/v1/apps/check`, and says the version it would be; `PUT /api/v1/apps/<name>`), or `dbdatagateway apps publish --dir [--note]`, which writes `app/<name>` into the Gateway's state; the serving host reads it within `definitionPollSeconds` | yes, locally and (AP26) remotely: `--to <address or paired name> [--code] [--client-name] [--client-dir]` over the management API as a paired server client with the publisher role (the same pairing as the Store's and Build's; the certificate is pinned) | the local verb records the OS user name; the remote one records the **paired client's name**. A client with the publisher role can publish a new version of any app (apps carry no owner stamp yet, unlike data sources and models) |
| Create the instance | `apps instance-save --name --app [--pin] [--bind] [--setting]`, or the Apps screen's **New instance** and **Edit** (app, version or follow, title, settings, one binding per model the version uses; `PUT /api/v1/app-instances/<name>`) | yes; `--to` as above; the screen in the Gateway tests `AppsScreenTests` and the stories `gateway-apps-editors*.spec.ts` | roles are not set here: `identity assign --user --app <instance> --roles ...`, a second tool and an id lookup (`identity user-list`) |
| Approve (AP15) | `apps approve --path` (before publishing), `--hash --app`, or `--app --version`, or the Apps screen (the exact files of a chosen folder before publishing, or a published version, ticking the outside origins the manifest asks for); approver is a home user with the Approver role on the server | yes (Gateway tests; `AppsRemoteTests` for `approve --to`, which needs a pairing with the approver role of its own, so one client key cannot both publish and approve; the Playwright story, not run here) | the approver must exist at the identity home with a role on the **server id**, which is easy to miss (step 4); the Apps screen approves a published version too (AP24b) |
| Run: address, sandbox | `https://<host>:8818/apps/<instance>/`; shell page plus sandboxed frame; policy from the manifest's egress | yes | subdomain and custom domain are not built (AP08, not blocking: the subpath is the address) |
| Run: token, storage, data | shell hands the home's 10 minute token for the instance (a refresh-token exchange at the home) and storage over `postMessage`; data route `/apps/<instance>/_data/api/v1/models/...` answered in process from the group's published models | yes with a published model (the Store must publish it; step 2) | the quickstart had no way to run any of this: AP22 (compose override) closes it. The host's tokens are the home's (AP19) |
| Run: semantic data | the manifest's `semantic: [name]` is accepted and scoped | not exercised here | no sample and no Playwright case for a semantic call from an app; not checked end to end |
| Navigate | `apps nav-save`, `nav-list`; the shell header lists a set's members the person may open; portals; `/apps/catalog`; `?launch`, `?embed` | yes (Gateway and Playwright tests) | home dashboard, image and table blocks and per-block roles are built (AP30); the portal's switcher and search are open (plan 26 leftover AP13) |
| Update | `apps publish` again; unpinned instances follow, pinned ones stay | yes | the apps host's sessions are per instance and in memory (AP05 leftover): a restart signs people in again |
| Roll back | AP20: `apps list --app`, `apps rollback --app [--to n]`; `instance-save --pin` per instance | yes (unit, Gateway test, and the Playwright story, not run here) | an instance's own settings roll back only by saving again |
| Revoke | `apps approval-revoke --id --by`, or the Apps screen's Revoke (AP24a: `POST /api/v1/app-approvals/<id>/revoke`, the approver role) | yes | the command line has no `--to` form of it yet; both need `--by` a home user with the Approver role |
| Remove | AP20: `apps remove`, `instance-remove`, `nav-remove` (the record and the storage stay); the Apps screen removes an app or an instance (AP24a: `DELETE /api/v1/apps/<name>`, `/app-instances/<name>`) | yes | a retired instance's app storage is not deleted (no verb); that is deliberate here |
| See it in the console | Servers (Gateway ready), the Gateway's Apps screen (AP24: apps, versions, instances with the version each runs and its address, navigation sets, approvals; serve an older version, pin, approve, revoke, remove) and its Identity home screens (people, roles, clients) | yes (Gateway tests `AppsScreenTests`, vitest, and the Playwright story `gateway-apps.spec.ts`, run once in the session that wrote it) | the screen does not edit a navigation set (command line, or `--to` from another machine); an approver must be a home user who holds the Approver role on the **server id** |
| Start the host in the quickstart | AP22: `dist/compose/quickstart-apps.yml`, `quickstart/apps-bootstrap.sh` | configuration run locally; containers not built here | before AP22 the quickstart's Gateway ran Flight SQL only |
| A sample app | AP21, AP23: `DbDataGateway/templates/apps` (`territory-notes`, `territory-notes-src` to build, `front-portal`, `territory-views`) | yes, validated and published by Gateway tests; the source tree is built by `AppsBuildTests` | none |

## Automating it

`DbDataKit/tests/DbDataKit.Server.Web.Tests/tests/apps-host.spec.ts` is the Playwright story: it starts a Gateway (`identity` and `apps`) and publishes a model from the Store's command line, enrols Ada with a passkey (virtual authenticator), runs the sandboxed app in the frame (token, rows, storage, the page that cannot read cookies or reach another host), navigation, the catalog, embedding, two portals, then a trusted portal that is refused without an approval, approved by a second person, run, audited and revoked. AP20 adds the end of the lifecycle to it: a second version the unpinned instance follows, a rollback, the refusal to remove a mounted instance and the 404 of a removed one. Needs `DBDATAKIT_TEST_E2E_PG` (a PostgreSQL), the built Gateway and Store, and `npm ci`; the ports 8511 to 8515 are its own. The story was **not run in the session that wrote AP20** (it was run on 2026-11-12, plan 26 AP27, and passes: its one fix was the check of the frame the browser refuses, whose address is empty in this Chromium) (no browser job, PostgreSQL or Store build there); its syntax was checked. It does not use the quickstart's compose files or the sample apps, which the Gateway test `The_sample_apps_validate_publish_and_run_as_instances` covers up to publishing.

`apps-policy.spec.ts` (plan 26 AP27, ports 8651 to 8653; needs the built Gateway only, no PostgreSQL or Store) is the browser-side story of the egress policy: three instances ask for the identity home's origin as an outside address; the sandboxed one and the trusted one approved for nothing are blocked by the browser, the trusted one an approver approved it for reaches it, and each about page lists the origin as in force or as asked for and not approved (AP31). The views-app story (a list, an edit, a refused row, a dashboard) is `apps-authoring.spec.ts` (GP34).

**The stories of the apps host, all run on 2026-11-12 (plan 26 AP27) and green:** `apps-host.spec.ts` (needs PostgreSQL and the Store), `apps-authoring.spec.ts` (the same), `apps-policy.spec.ts` (8651 to 8653), `views-apps-embed.spec.ts` (AP17, 8661 to 8664: an approved report origin is framed, an unapproved one is a link and not in the policy, a report that does not answer shows the link after 15 s), `views-apps-addresses.spec.ts` (AP08, 8671 to 8673: a subdomain added in the instance editor routes by `Host`, a wrong name is refused in the Gateway's words, removal stops the routing, Verify of a custom domain shows the DNS challenge record; it also needs the console), `apps-home-blocks.spec.ts` (AP30, 8681 to 8683: a portal home's dashboard block is a frame for a person with the role and absent for one without, a role-gated line, a table, an image) and `apps-sessions.spec.ts` (AP29, 8691 to 8693: the same cookie opens an app after the Gateway process is restarted). How they were run without the whole CI fixture set: the recipe in `docs/ci-lessons.md` ("running one console spec locally with a trimmed config"): an untracked `playwright.local.config.ts` that starts only the console (and the built Gateway and Store the stories start themselves), `TEST_WORKER_INDEX=0`, Chromium of `/opt/pw-browsers`, `--trace off`; `DBDATAKIT_TEST_E2E_PG` for the two that need a PostgreSQL.

## Known gaps

Blocking a tester today: none that the script above does not get around. Remote (`--to`) covers `publish`, `instance-save`, `rollback`, `list` and `approve`; `nav-save`, the removals, `approval-list` and `approval-revoke` still run on the Gateway's own machine at the command line (the Apps screen does the removals, the revoke and the navigation sets through the management API). Not blocking: AP08 (subdomain and custom-domain bindings: built; what is left is plan 26's), AP17 (embedded report servers: the Windows run), Z13b (the migration contract step).

What was not checked: the compose files were not built or started (the container image build is long and the disk of the session small); the same configuration (environment variables, the client registration) was run on a built Gateway directly and the home and the apps host answered, the samples were published and served under the sandbox policy. The Store pairing and model publication in `apps-bootstrap.sh` follow the commands of the Playwright story and were not run. The ServerId lookup in step 4 and the exact text of some messages in steps 11 to 13 follow the code and the tests, not a run.
