# CI lessons

Every CI problem that has cost time more than once, how to recognise it, and the fix. Read this before you push; add a problem and its fix **in the same commit that fixes it**, so the next person does not find it again.
The CI runners are small (two cores, Windows and Linux), run many jobs at once, and the test engines are containers, so most of these are about time, files and order.

## Before you push (the short list)

1. Build **every project that references what you changed, including the test projects of other products** (Build's `DbDataBuild.Tests.Conformance`, Sync's `TaskRunner.Tests`, the console's server tests). A merge from `main` that moves or renames a type breaks them silently: a green build of your own project proves nothing about them.
2. Run the new and the affected tests on **SQLite, SQL Server and PostgreSQL** (`eval "$(testenv/testenv.sh env dbdatakit)"` in the same shell command as the test run; each command starts a fresh shell). A test that is "skipped" on an engine you did not set up has not run.
3. Think Windows: does the test delete a directory that holds read-only files (cache, artifact views)? does it read a file a running server still has open? does it use `/` or `:` in a path? See the Windows section.
4. If you touched `Directory.Packages.props`, a `.csproj`, a publish target or the Dockerfile: `dotnet publish` the console and start it (`dotnet dbdatakit.dll server run --listen https://localhost:<port>` must print "The console is on").
5. If you added a Playwright spec: the specs run **one at a time in the order of their file names**; see the Playwright section.
6. `python3 -I -m unittest discover -s scripts/tests` and the `scripts/check_*.py` (`check_duckdb_cache.py` among them: a job or Dockerfile that needs DuckDB uses the cache, see "GitHub release downloads fail") (agent worktrees under `.claude/worktrees` make two of those fail on a machine that has them; that is not a CI problem).
7. Delete your `bin`/`obj` (and any `node_modules`) when you finish: the disk of a session is small and a full disk fails builds in confusing ways.

## Recognise it, fix it

### Windows

| Signature | Cause | Fix |
| --- | --- | --- |
| `UnauthorizedAccessException: Access to the path '<hash>' is denied` in a test's `Dispose`/cleanup, `Directory.Delete(recursive)` | the artifact cache stores objects read-only; Windows will not delete a read-only file | delete with `ArtifactTestSupport.DeleteTree(path)` (DbDataKit.Runner.Tests), never `Directory.Delete` on a tree that held cache objects |
| `IOException: The process cannot access the file '...state.db' because it is being used by another process` when a test reads files under the data directory | a plain `File.ReadAllText` needs exclusive-enough access; the running server holds the SQLite file | open with `new FileStream(path, FileMode.Open, FileAccess.Read, FileShare.ReadWrite \| FileShare.Delete)` |
| a memory-limit test sees no kill / a freshly started child is killed at once | job-object kills are silent; the memory watchdog sampled at once | the watchdog's first sample is after one interval (`MemoryWatchdog`); the limit test forces the watchdog |
| a read-only-directory test fails | Windows has no read-only directory semantics | skip it on Windows (`OperatingSystem.IsWindows()`), say why in the test |
| noise: "SQL Server '.\SQLEXPRESS' is not reachable" lines in the Windows job | tests that need a local SQL Server are skipped there | not a failure; look for `failed` lines |

### Timing (two-core runners)

| Signature | Cause | Fix |
| --- | --- | --- |
| a test needing "the next thing within N seconds" fails only in CI; log says "This runner was silent for 00:00:5x (the lease is 00:00:30)" | the whole process stalled (thread pool starvation, many jobs on the machine) longer than a 30 s lease | the DbDataRunner tests raise the thread pool minimum (`TestProcess.cs`) and run one at a time; the scheduler renews its own running items before it releases expired leases (`RenewOwnLeases`). A second record of one run (`Sequence contains more than one element` on a runs query) means this area again |
| `Two_runners_activating_at_once_migrate_once` fails with `NotReady` instead of `AlreadyDone` | the second runner read readiness after the first had activated (activation resets the instance states) | `PackageActivator.ActivateAsync` looks at the head again before answering `NotReady` |
| `Assert.False(activation.IsCompleted)` or `Waited 60 seconds for the hold on new runs` in `A_run_in_flight_finishes_on_the_old_version…` | the in-flight `lingers` task was a fixed 12 s of wall clock; when staging the new version is slow (a stalled runner) it ended before the activation started its hold, so the activation finished at once and the hold was never there to see | `lingers` takes the input `release_file` and runs until that file exists (five minutes at most); the test creates the file after it has seen the hold and the 1.5 s of waiting. Never wait for "a task that is long enough": give the task a signal the test controls. The task process has a cleared environment, so the channel is an input of the run request (`{"inputs": {"release_file": "..."}}`), not an environment variable |
| `the run of lingers is recorded 2 times` (or `Sequence contains more than one element`) in `A_run_in_flight_finishes_on_the_old_version…`; the log says "This runner's lease ... ran out and the item was taken again ... while the earlier attempt still ran here" | the runner's own tick gave back (`ReleaseExpired`) the lease of an item whose run was going on in the same process: the process stalled longer than the 90 s lease (attempt 1 had run 49 s against a 30 s lease in the loaded reproduction), and a stall between the tick's renewal and its release, or a tick that started late, left the lease expired when the release ran. The item went Pending, the same loop claimed it again as attempt 2 and the first record ended Interrupted/Cancelled | the scheduler passes the items it is running itself (record not finished, lease not lost) to `ModuleWorkQueueStore.ReleaseExpired(except)`, which never releases them: no timing involved. Only another worker's expired lease is taken over, and a record that lost its lease or ended (also when its task process is gone) is not protected. Test: `A_tick_that_finds_the_lease_of_an_item_it_runs_itself_expired_leaves_it_alone_even_when_nothing_renewed_it`; `A_loop_that_stops_renewing_loses_its_item_to_another_loop…` still holds because the taking loop is not running the item |
| `IncompatibleServerException: 127.0.0.1:<port> did not report a management API version` in a publish/pair test (`PublishApiTests.A_publisher_uploads_only_a_changed_file…`), after a very slow test (2+ minutes) | Kestrel's own `408 Request Timeout` (`RequestHeadersTimeout` 15 s, `DbDataKit.Hosting`): a process that stalls longer than that gets the answer from Kestrel itself, which is written before any middleware runs, so `UseManagementApiVersion` cannot put the version on it. The server never started the request. Shown by `KestrelsOwnRequestTimeoutAnswerIsWrittenBeforeTheMiddlewareAndHasNoVersion`; that a stall of this length produces it in the full test is inferred (a reproduced stall made pairing fail with a closed connection instead, the same family) | `ManagementVersionHandler` sends a request once more when the answer is a 408 without the version header (the request was never started, so it is safe to send again); a second such answer, or a 408 that carries the version, is passed on as before. Do not make the version header optional |
| `Cancel` or "body started" tests flaky | the test cancelled before the body ran | cancel when the body signals it started (a `TaskCompletionSource`), never after a fixed delay |
| two tests pick the same free port | `FreePort` handed the same number twice | `FreePort` never repeats a port in a process |
| `address already in use` (`IOException` from Kestrel, `HttpListenerException` from an `HttpListener`) in one test of a full run (`PasskeyChallengeTests.A_captured_response_signs_nobody_in_again`), gone on a re-run | the helper looked a free port up (`TcpListener` on port 0, read the port, stop it) and the server bound it later; another test's client or server took it in between | a server that can take `UseUrls("http://127.0.0.1:0")` binds the port itself: read the address from `app.Urls` after `StartAsync` (Identity tests, `AccessTokenTests`, `ExternalGroupTests`, `IdentityHomeHostingTests`); one that needs its address before it starts (`HttpListener` prefixes, an issuer given to a provider, a port in a child process's arguments) wraps the whole start in a loop of up to 5 that looks a new port up when the bind fails (`AuthenticatedGitServer`, `ExporterTests.StartListener`, `OpenIdFlowTests`, `ViewsModuleTests.StartAsync`); `git grep -n "FreePort\|GetFreePort\|TcpListener(IPAddress.Loopback, 0)"` before adding a helper |
| `DBP-140 Gateway:Identity:Port ... The identity home has its own port; it is the management API's here. (Choose another port than 3xxxx.)` in `GroupStateTests` (seen once, in a full Gateway run) | the test's own `FreePort` released the port it found, so asking twice in a row can return the same number | the helper keeps the ports it handed out and never repeats one (as the others do); copy that when you write a new helper |
| `Assert.Empty() Failure: Collection was not empty` on `Assert.Empty(await h.RunsAsync())` in `WebhookTests.A_bad_signature_is_answered_401…` (SQLite and MsSql, only in CI) | the webhook receiver stored a refused body as a waiting inbox item (`taken_by` NULL) and set it aside with a second statement (`RefuseInboxItem`); the trigger engine's sweep (`SweepWebhooks`, at its tick) that looked in between saw a waiting webhook and queued a run for the task. Inferred from the code, not reproduced: 0 failures in 20 loaded runs (`taskset -c 0` plus 6 busy loops) before the fix on SQLite, SQL Server and PostgreSQL, the window is a few milliseconds | `ProgressStore.Receive(..., refusedBy: ProgressStore.RefusedBySignature)` writes the item already set aside, in the one insert; the receiver uses it. Test: `A_refused_webhook_is_stored_already_set_aside_and_is_never_visible_as_waiting`. The assertion now prints the runs and the server log. Any "store, then mark" of a row another loop polls has this window: write the final state in the insert |
| `an export browser is still running after the deadline` in `DbDataKit.Views.Export.Tests` (once, not on a re-run) | `ExporterTests` counts the `dbdatakit-export-` processes before and after an export, and a second test class (`SvgExportTests`) started its own browser in parallel | every test class of that project that starts Chromium is in `[Collection("chromium")]`, so they run one after the other |
| a deadlock victim (SQL Server 1205, PostgreSQL 40P01/40001) in a state store test | concurrent takers of one inbox | the dialects' `ShouldRetry` covers them; a new store operation that takes rows concurrently needs the same retry |
| `SqliteException: SQLite Error 5: 'database is locked'` from `SqliteStateDialect.TableExists` <- `StateMigrator.Apply` <- `PayloadStore.Get` <- `DefinitionPublisher.FindPayload`, after minutes (`StagingServerTests`, SQLite row) | `FindPayload` called `PayloadStore.Get` (a connection of its own) while its own reader on the same file was open. On SQLite (rollback journal) a writer waiting to commit holds the pending lock: it refuses the new reader and waits for the old one, which waits for the new one; only the 5 s busy timeout breaks it, and the retry loops of both sides repeat it. `DefinitionPublisherTests.Looking_up_a_stored_file_never_waits_for_a_writer_on_the_same_sqlite_file` stalled for 92 s before the fix (that first regression test was a stress/timing test, a writer in a tight loop and a 2 s bound, and it failed on the Windows runner at 10 s with the fix in place; it was replaced by `Looking_up_a_stored_file_never_opens_a_connection_while_another_one_holds_a_lock_on_the_same_sqlite_file`, which does not time anything: `StateDatabase.ConnectionOpened` probes for a lock each time a connection is opened) | read the rows to the end and close the reader before asking another store anything; never open a second connection to the file while a reader or transaction of the first is open |
| `SqliteConnectionUnderLockException: A state connection was opened on '...' while an earlier connection of this thread holds a read/write lock on it` in any test of State, Scheduling, Runner, Identity, Lineage, Web, State.Engines, State.Api or State.Cli (the guard below), or the `database is locked` stall above in a new place | the same pattern as the `FindPayload` row: a store opened a second state connection (a store method of its own, `PayloadStore.Get`, a `new XStore(database)`) while a reader or a transaction of its first connection on the same SQLite file was still open. The audit of every store, module, runner and product found no other site (the one near miss, `StepStore.FindOwnedCompletePayload`, held a connection open without a lock and now closes it first). **The guard**: `DbDataKit.State.Tests/SqliteLockGuard.cs` is linked into those test projects; a module initializer sets `StateDatabase.AnyConnectionOpened`, each connection a thread opens is remembered with its stack trace until it is closed, and a new connection on the same file asks the thread's still-open ones for their transaction state (`sqlite3_txn_state`: an open reader or a transaction that has read or written is not 0). A hit throws from the open with both call sites in the message, and `SqliteLockGuardFixture` (an assembly fixture) reports one a catch-all swallowed. Nothing is timed or probed over a second connection, and other threads' connections are never looked at, so a concurrent writer is no false positive (an `await` that hops threads between the two opens is not seen) | materialize and close first (read the rows to a list, dispose the reader and command, then call the other store); never pass a store its own connection to "save" an open. A test whose point is a connection under a held lock (`StateSqliteFilesTests`) says so with `using var _ = SqliteLockGuard.Allow();`; a new test project that uses `StateDatabase` on SQLite links the file (`<Compile Include="..\DbDataKit.State.Tests\SqliteLockGuard.cs" Link="SqliteLockGuard.cs" />`) and gets an `InternalsVisibleTo` in `DbDataKit.State.csproj` |

### Playwright (console)

| Signature | Cause | Fix |
| --- | --- | --- |
| `ENOENT ... FIRST-RUN.txt` in `first-run.spec.ts` or `identity-home.spec.ts` | a spec that ran earlier invited the first administrator (`user invite`), which uses the first-run invitation up | the specs run in the order of their file names with one worker; `first-run` and `identity-home` need a console with no user, so a spec that invites an administrator must sort **after** `identity-home` (`monitoring`, `inventory-connections`...). | `ENOENT ... FIRST-RUN.txt` in `identity-home.spec.ts` although its Gateway is "up" (the failure is immediate) | a fixture server added to `playwright.config.ts` took a port a spec starts its own server on (8497 and 8498 were the identity-home spec's home and console): the spec's health check was answered by the OTHER server, so it believed its own Gateway was running | before choosing a port, `grep -n "<port>" playwright.config.ts tests/*.ts`; ports 8481 to 8499, 8511 to 8519 and 8520 to 8523 are in use (8516 to 8519 are `gateway-apps.spec.ts`'s Gateway, 8520 to 8523 `gateway-apps-editors.spec.ts`'s), 8501 and 8502 are the inventory story's, 8503 and 8504 the runner-publishing story's runner and Build server, 8531 is the quality story's Sync server (`qualitySync`) |
| `apps publish` of a trusted portal fails in `apps-host.spec.ts` ("asks to be trusted and has no approval for these exact files"; then `FIRST-RUN.txt` missing) | AP15 made the publish of a trusted app need an approval by a home user with the Approver role; a story that makes any user (a service account is one) before Ada enrols has no first-run invitation | the story makes grace (a service account holding `approver` on the server's `instanceId`, from `config/server.yaml`) **after** Ada enrols, approves the files by `--path`, publishes, revokes, then approves by `--app --version` as before |
| a Playwright story passes with a mocked relay and fails against the real servers: after the first publish of a NEW app (or the first create of any new thing) the detail the screen should open is "not found" (`gateway-apps-editors.spec.ts`, `version-row-1`) | the screen selected the new item before its list was refetched; an effect that drops a selection the list does not contain cleared it. The mock's first story only published a version of an app that was already listed | select after the invalidated queries have refetched (`await invalidateQueries` first); a mocked story must also create a new item, not only change an existing one |
| a story asserts on a row of a thing made at the command line (`instance-save` behind the screen's back) and fails with "element(s) not found" after 5 s (`gateway-apps-editors.spec.ts`, `instance-row-views`) | the Apps screen reads its lists every ten seconds and not on focus; a change made outside the screen shows up on the next poll, longer than an assertion's default 5 s | wait with a timeout of 20 s for anything made by the command line (or reload); what the screen itself changed is refetched before its notice shows, so needs none |
| a new fixture server never starts | every server in `playwright.config.ts` needs its own port and its own directory under the temp folder; the `webServer` entry needs `url`, `reuseExistingServer: false`, a timeout | copy an existing entry; ports in use are listed in the config |
| a click on a chart (a bar, a mark) does nothing in `views-interact`, though the SVG is drawn and visible | `VegaChart` embedded two specs into one element when the tile's box changed while the first embed was still on its way; the first, already cancelled, finished last and drew a dead picture over the live one | each draw has its own mount element, removed on cleanup (`VegaChart.tsx`); a story that clicks a mark retries until the page changed (`clickBar`) |
| `monitoring.spec.ts` (or another spec) fails with `Error: no such table: ChangeWatermarks` (or `ChangeCheckHistory`) while seeding Sync's state database | a slice moved a stored table onto the shared state modules (E14 and E15: the position is the `watermark` checkpoint of `runner_progress`, the source checks are `change_check`) and the spec still wrote the old table with `node:sqlite`; nothing in the product build touches the spec, so only the browser job sees it | grep `tests/` of every product for the old table name when a slice moves a table; the spec writes the new tables (`dbdatakit_runner_progress_main_checkpoint_head` and `_part`, `dbdatakit_sync_state_main_change_check`; times as `yyyy-MM-ddTHH:mm:ss.fffffffZ`), or better calls the product's own API when it has one |
| a Runner test passes on Linux and fails on the Windows job with `Assert.Single() Failure: The collection was empty` on the runs a scheduler should have started (`RuntimeTests`) | the test published runtime packages for `linux-x64`, but its scheduler took the platform of the process (`win-x64` on Windows) and found no runtime for its own platform, so no run started | a test that publishes for a platform gives the runner under test the same platform explicitly (`SchedulerHarness.NewScheduler` defaults to linux-x64); never rely on `RuntimePlatforms.Current` in a test |
| `OpenIdFlowTests.An_end_session_request_with_a_hint_that_is_not_this_homes...` (or another forged-token test) fails once with a redirect it should not give | the test forged a token by replacing the LAST characters of its signature with `AA`; the last base64url character holds padding bits, so about one run in 256 the forged signature decodes to the original and the token is valid | forge a signature by changing its FIRST character to a different valid one (`ForgedSignature` in `OpenIdFlowTests`); any test that tampers with encoded data must change bits that are certainly used |
| the console's `first-run.spec.ts` fails at `getByTestId('user-analyst')` (a Gateway user made on the Identities screen) | P13 retired Gateway users (`PUT /api/v1/users/*` answers 410), and the spec still drove the screen that made one | a slice that retires a feature greps every Playwright spec (`git grep -n <testid> -- '*.spec.ts'`) and the screens that offer it; the spec now has no Gateway-user step. The Identities screen still draws the retired users editor (task: remove it with a screen for a data source's groups) |
| `monitoring.spec.ts` (or another spec) fails with `Error: database is locked` while seeding a running server's `state.db` with `node:sqlite` | the spec wrote into the file of a running Sync server; the state database is not in WAL mode, so a second writer is refused at once when the server's own scheduler or heartbeat holds the lock, and `node:sqlite` waits for nothing by default | `PRAGMA busy_timeout`, every row in one `BEGIN IMMEDIATE` transaction, retried when the lock is still not ours (never a sleep as synchronisation); the same applies to any spec that seeds a live server's SQLite file |
| `SyntaxError: Unexpected end of JSON input` on `(await request.get('/api/instances')).json()` in a console story | the test fixture `request` is an API context of its own: it holds no session cookie, so the console answered 401 with no body; the signed-in cookie is in the browser context | use `context.request` (or `page.request`) after `signInNewAdmin`, as `runner.spec.ts` and `monitoring.spec.ts` do; never the bare `request` fixture for a call that needs the signed-in person. A story that has never run for real also says nothing of its seeded table names: check them against a started server |

### GitHub release downloads fail (the DuckDB engine)

The pinned DuckDB archives (`duckdb.pin`) come from github.com/duckdb/duckdb/releases, which now and then answers `502`/`504` or drops the connection for hours. Before the cache, every job that needed the engine downloaded it and went red together (`duckdb-pin-*`, `solution`, `dotnet`, `playwright`, `compose`, `flightsql-e2e`, `conformance`, `unit`, `test`, `image`, `runtime-package`, `views-export`).

How it works now, and what to keep true when you add a job:

- **The action `.github/actions/duckdb-cache`** restores `.duckdb-archives/` from the Actions cache (key `duckdb-<os>-<arch>-<rids>-<hash of duckdb.pin>`; `rids` is the host's platform unless the action is given `rids:`), runs `scripts/fetch-duckdb.sh --archives .duckdb-archives <rids>` (a hit finds every archive current and downloads nothing; a miss downloads, with retries, and the action saves the folder right away so a later failure of the job does not lose it), and sets `DUCKDB_RELEASE_BASE=file://<workspace>/.duckdb-archives` for the rest of the job. `setup-product` uses it unless it is given `duckdb: 'false'`; a job that opts out and still needs the engine (or runs a Docker build, a compose file, `publish.sh`) puts the action before the first such step.
- **Every consumer reads `DUCKDB_RELEASE_BASE`**: `fetch-duckdb.sh` and `.ps1`, and `DbDataSync.Libraries.DuckDbEngine` (the .NET downloader of the Sync tests and of `internal build-catalog-cache`; `DBDATASYNC_DUCKDB_ENGINE_SOURCE` still wins there). The sources are tried in order: `DUCKDB_RELEASE_BASE`, the pin's `BASE`, then `DUCKDB_RELEASE_BASE_FALLBACK` or the pin's optional `BASE_FALLBACK` (a second source that serves the same archive names; none is set, because DuckDB publishes these archives nowhere else, so nothing is invented: mirror the five archives, then add `BASE_FALLBACK=` to the pin). Every copy, from any source, is checked against the archive hash in the pin and the library inside it against its own, so a cache can neither hide a changed pin (the key has the pin's hash) nor serve a changed byte.
- **Downloads retry**: curl `--retry 8 --retry-all-errors` with growing waits (1 s doubling), three rounds per source; the PowerShell script does the same with `Invoke-WebRequest`; `DuckDbEngine` retries 5xx/408/429 and connection errors six times (1, 2, 4, 8, 16 s). A final failure says `checksum mismatch or no copy of <archive> ... from any source: <every url>` and names the Actions cache key that had no copy.
- **Docker builds** cannot see the runner's cache, so the cache folder is inside the build context (`.duckdb-archives/`, in no `.dockerignore` of an image that uses it) and the Dockerfiles of Build, Gateway and Sync `COPY duckdb.pin .duckdb-archive[s] /duckdb-archives/` (the pattern matches nothing in a local build, which then downloads as before) and run their fetch with `DUCKDB_RELEASE_BASE=file:///duckdb-archives`. No build flags, so compose files, `docker build` and `build-push-action` all work unchanged.
- **`scripts/check_duckdb_cache.py`** (run by the `package-versions` job; test in `scripts/tests`) fails a workflow job that needs the engine without the action (or a `DUCKDB_RELEASE_BASE` of its own) before the first such step, a Dockerfile that fetches DuckDB without the context folder, and an action that lost the pin hash in its key.

## Working in a session (not CI, but it costs the same time)

- `dotnet test --project ...` can fail with `Handshake failures` here: run the built executable instead. Microsoft.Testing.Platform projects take `--filter-class "*Name"` and `--filter-method "*Name*"`; the xunit v3 in-process runner takes `-class` and `-method`.
- Never chain `sleep` in a command; wait with a `Monitor` until-loop.
- A job that reports "failed with 1 error(s)" has an error line named `failed` above it; search for the test name, not for "error".
- `DbDataConsole.Servers.Tests` fail with "dbdatabuild.dll is not built" until `dotnet build` has run for `DbDataBuild/src/DbDataBuild.Cli`, `DbDataGateway/src/DbDataGateway.Server` and `DbDataSync/src/DbDataSync.Cli` (they start the built programs). Sync's `ChangeReaderFirstPassContractTests.EveryDeclaredProofNamesATestThatExists` fails until `DbDataSync.Drivers.MsSql.Tests` and `.Postgres.Tests` are built (it reads their assemblies). A build that says `libduckdb.so is missing` needs `scripts/fetch-duckdb.sh linux-x64`; none of these is a code problem.
- When one failure shows up in two pull requests, it is not those pull requests' failure: fix it once, in the batch, and add it here.
