# CI lessons

Every CI problem that has cost time more than once, how to recognise it, and the fix. Read this before you push; add a problem and its fix **in the same commit that fixes it**, so the next person does not find it again.
The CI runners are small (two cores, Windows and Linux), run many jobs at once, and the test engines are containers, so most of these are about time, files and order.

## Before you push (the short list)

1. Build **every project that references what you changed, including the test projects of other products** (Build's `DbDataBuild.Tests.Conformance`, Sync's `TaskRunner.Tests`, the console's server tests). A merge from `main` that moves or renames a type breaks them silently: a green build of your own project proves nothing about them.
2. Run the new and the affected tests on **SQLite, SQL Server and PostgreSQL** (`eval "$(testenv/testenv.sh env dbdatakit)"` in the same shell command as the test run; each command starts a fresh shell). A test that is "skipped" on an engine you did not set up has not run.
3. Think Windows: does the test delete a directory that holds read-only files (cache, artifact views)? does it read a file a running server still has open? does it use `/` or `:` in a path? See the Windows section.
4. If you touched `Directory.Packages.props`, a `.csproj`, a publish target or the Dockerfile: `dotnet publish` the console and start it (`dotnet dbdatakit.dll server run --listen https://localhost:<port>` must print "The console is on").
5. If you added a Playwright spec: the specs run **one at a time in the order of their file names**; see the Playwright section.
6. `python3 -I -m unittest discover -s scripts/tests` and the `scripts/check_*.py` (`check_duckdb_cache.py` and `check_native_cache.py` among them: a job or Dockerfile that needs DuckDB uses the cache, see "GitHub release downloads fail"; `check_env_names.py`: every environment variable name starts `DBDATAKIT_`; `check_secret_names.py`: every secret name starts `dbdatakit:`, never `dbdata:`; `check_product_name.py`: the product is `DbDataKit`, never `DbDataConsole` or `DbDataKitConsole`) (agent worktrees under `.claude/worktrees` make two of those fail on a machine that has them; that is not a CI problem).
7. Delete your `bin`/`obj` (and any `node_modules`) when you finish: the disk of a session is small and a full disk fails builds in confusing ways.

## Recognise it, fix it

### Windows

| Signature | Cause | Fix |
| --- | --- | --- |
| `UnauthorizedAccessException: Access to the path '<hash>' is denied` in a test's `Dispose`/cleanup, `Directory.Delete(recursive)` | the artifact cache stores objects read-only; Windows will not delete a read-only file | delete with `ArtifactTestSupport.DeleteTree(path)` (DbDataKit.Runner.Tests), never `Directory.Delete` on a tree that held cache objects |
| `IOException: The process cannot access the file '...state.db' because it is being used by another process` when a test reads files under the data directory | a plain `File.ReadAllText` needs exclusive-enough access; the running server holds the SQLite file | open with `new FileStream(path, FileMode.Open, FileAccess.Read, FileShare.ReadWrite \| FileShare.Delete)` |
| a memory-limit test sees no kill / a freshly started child is killed at once | job-object kills are silent; the memory watchdog sampled at once | the watchdog's first sample is after one interval (`MemoryWatchdog`); the limit test forces the watchdog |
| a read-only-directory test fails | Windows has no read-only directory semantics | skip it on Windows (`OperatingSystem.IsWindows()`), say why in the test |
| a test that edits a stored config file by `Replace("key: value\n", ...)` changes nothing on Windows (`Assert.Throws() Failure: No exception was thrown`) | the file is written with the platform's line ending, CRLF on Windows, so the text with `\n` is not in it | edit by pattern (`Regex` with `\r?\n`) or normalise the text first, never match a line ending literally |
| `KeyPermissionException: The secret key file '...\\secrets\\keys\\active' has an access list that lets others in (unexpected grant to NT SERVICE\\<service>; missing grant for <admin>)` from `dbdatakit instance add` (or another elevated command) in the Scoop install | the service made the key ring with its own account; the elevated command line checked it against {itself, SYSTEM, Administrators} | the default identities of a key ring and a secret store are those plus the accounts of the services registered on the data directory (`WindowsServiceAccounts`), and an elevated administrator's own account counts through the Administrators group (`AclHelper.Verify`), so the files look the same whoever made them first; nobody else is ever allowed |
| `The module 'knowledge_vectors' needs the engine feature 'vector' ... SQL Server 2022` in the `state-older-engines` job | the module needs SQL Server 2025's vector type and refuses 2022 by design | the tests of a module with a newer engine feature skip on the engine that lacks it (`KnowledgeVectorTests.OpenVectors`) |
| `error TS2366: Function lacks ending return statement` in `views-editor/src/editing.ts` (every web build and image) | a union (`WidgetType`) gained a member in a work-in-progress commit and a `switch` over it did not | add the case with the member; never push a union change without building the console (`npm run build -w @dbdatakit/console`) |
| `'proxy' is not a command` from `dbdatastore` (a spec, test or script) | the noun is `gateway` since the rename (`scripts/rename_proxy_to_gateway.py`); callers in specs, tests, `dist/compose` scripts and usage texts kept `proxy` | after a rename, grep the specs, `dist/` scripts and the messages for the old word, not only the code |
| on Windows only: a test of an unreachable local port expects `Network` and gets `Timeout`; `Export` of a loaded certificate throws `Key not valid for use in specified state`; a 204 answer with a body hangs 20 s | Windows retries a refused connection for about 2 s; a PFX loaded without `Exportable` cannot be exported; a 204 has no body | tests give a connect timeout well above 2 s, load test certificates `Exportable`, and send no body with 204 |
| `A_statement_leaves_a_record...` fails with `"members"` where `"complete"` is expected | a members list (parameter choices) was recorded with the answer's own status word `members` | a run record's status is how the statement ended (`SemanticServing.Write` takes the answer's status only for `explained`, `unsupported` and the like, never `members`) |
| `System.IO.IOException: The configured user limit (128) on the number of inotify instances has been reached` in a Gateway test (linux) | many in-process hosts each hold a file watcher | the Gateway linux job raises `fs.inotify.max_user_instances` (a test that builds a configuration disposes it) |
| a locally trimmed Playwright config pairs twice, or the first-run code from a spec is refused | workers re-evaluate `playwright.config.ts`, so its setup (pairing, writing the scratch settings.yaml) runs once per worker, and a second pairing invalidates the code of the first | guard the setup with an environment variable (set it on the first evaluation, skip the setup when it is set) |
| the console image build fails in `vite build` with `[plugin dbdatakit-module-docs] ... the docs folder /src/DbDataKit/docs does not exist` | a module's docs folder (its `dbdatakit.docs.dir`) is not copied into the web stage of `DbDataKit/Dockerfile` | every docs folder a module registers is copied there (`COPY DbDataKit/docs`) |
| a spec that expects an empty Audit list for a filter fails | the console is shared by every spec: earlier specs left rows (paired servers) | prove a filter by what it hides (the row this spec made), not by an empty list |
| `The_checked_in_output_schema_is_current` / `TheCheckedInOutputSchemaIsCurrent` fails after a verb's output gained a property | the golden `schemas/output.schema.json` of the Gateway or Sync was not regenerated | run the test with `UPDATE_GOLDEN=1` and commit the file |
| a state module's conformance test fails with `plan_run.exit: 'exit' is a ...` | the column name is a reserved word on SQL Server or PostgreSQL (`exit`) | name columns `exit_code`, `user_name`, never a keyword |
| a job that builds `DbDataBuild/src/DbDataBuild.Cli` fails with `DuckDb.Native.targets: The DuckDB engine '.../.duckdb/linux-x64/libduckdb.so' is missing` | the job set up its product with `duckdb: 'false'` | a job that builds Build (or anything that references the DuckDB targets) lets `setup-product` fetch the engine (`duckdb: 'true'`) |
| `SHA256SUMS does not list the win-x64 zip of suite member dbdatakit (dbdatakit-v<version>.1-win-x64.zip)` in the update step of the Scoop e2e | PowerShell variable names are not case-sensitive: `function Bind([string]$version)` hid the script's `$Version`, so `$version -ne $Version` was never true and the second version was bound to the first version's sums | a parameter never differs from a script variable only by case (`$forVersion`) |
| the Scoop e2e (`suite-install-windows`, `dist/tests/suite-scoop-e2e.ps1`) ends with `Exception: ... throw "dbdatakit-full: this package registers services..."` at the per-user install step, after `ERROR 'dbdatakit-full' isn't installed globally` from the cleanup | Scoop runs a manifest's hook in the caller's PowerShell process, so a hook's `throw` (the manifest's refusals) escapes a `Native` wrapper that only reads exit codes and ends the script | `Native` catches the exception, writes it to the command's file and returns a failing code; assertions read the text |
| a PowerShell step fails with `Exception: ...ps1:4` right after `dotnet-install: Installation finished` (`suite-install-windows`) | `if ($LASTEXITCODE -ne 0) { throw }` after `& dotnet-install.ps1`: a `.ps1` is not a program, so `$LASTEXITCODE` is unset (null is not 0) | check the result (the runtime's folder exists), never `$LASTEXITCODE`, after a script; only after a native command |
| `Assert.Equal() Failure: Strings differ` with `\r\n` in Expected and `\n` in Actual, only on Windows, where the expected text is a C# raw string literal compared with a file the product wrote | the source file is checked out with CRLF (`autocrlf`), so a raw literal in it has CRLF; the product writes LF | normalise the literal in the test: `literal.ReplaceLineEndings("\n")` (`StoreModelsTests`) |
| a cached object loses its read-only attribute after a view was removed (Windows), or a view cannot be made on a volume without links | a view's files are hard links of the objects (`FileLinks`), and the read-only attribute belongs to the file, not to a name: clearing it to delete a view's link clears it for the object | `ArtifactCache.DeleteView` deletes a link with `FileLinks.TryDeleteIgnoringReadOnly` (POSIX delete semantics, ignore read-only) and only falls back to clearing the attribute; a link that is refused (another volume, no link support, NTFS's 1023 links per file) is a copy (`HardLinkViewTests`); written without a Windows machine, so the first run of the `windows` job of `dbdatarunner-ci.yml` is its proof |
| noise: "SQL Server '.\SQLEXPRESS' is not reachable" lines in the Windows job | tests that need a local SQL Server are skipped there | not a failure; look for `failed` lines |
| a test asserts a path in a JSON error body (`Assert.Contains("connections/twice.yaml", body)`) and fails only on Windows | the body is JSON, so a Windows path arrives as `connections\\twice.yaml` (the backslash is escaped); `Replace('\\', '/')` leaves `//` | normalise both: `body.Replace("\\\\", "/").Replace('\\', '/')` (`ManagementGrantsTests`); look for the same assumption in any test that reads a path out of a response body |
| `NullReferenceException` on `detail["channels"][0]["staged"]` after a stage-mode publish through the embedded runner, only on Windows; and `UnauthorizedAccessException: Access to the path '<sha256>' is denied` in `Dispose` | (1) the runner's staging follower activates a staged version nobody objects to within a few moments, so a slow runner reads the channel after that and `staged` is already null (`active` is 1); (2) the artifact store's files are read-only on Windows, and the cleanup caught only `IOException` | (1) assert the version is held either way (`staged == 1` or `active == 1`); (2) catch `IOException or UnauthorizedAccessException` when a test deletes a runner directory that held artifacts (`EmbeddedRunnerTests`, `ConsoleRunnerTests`) |
| `Assert.NotEqual() Failure: Values are equal, Expected: Not 0` on the exit code of `label remove os:linux` (`GroupTests.A_restarted_runner_keeps_its_administrator_labels...`), only on Windows | the test named a literal OS label; the runner reports `os:windows` there, so removing a label nobody has is a no-op that exits 0 | name the label the runner reports (`LimitCapabilities.Detect()[LimitCapabilities.Os]`); a test that names a platform-dependent value computes it |
| `dotnet publish -r win-x64 --self-contained false -p:PublishSingleFile=true` of `DbDataRunner.Server` fails with `NETSDK1151` (Linux: `NETSDK1150` once the other side changes): the referenced `DbDataKit.Runner.TaskHost` is (not) a self-contained executable | single-file implies a self-contained publish for the program, while the task host, reached through a reference with other global properties, is evaluated the other way round (which way depends on evaluation order, so Linux and Windows differ); the reference only orders the build and the task host is published framework-dependent by the program's own target | `<ValidateExecutableReferencesMatchSelfContained>false</ValidateExecutableReferencesMatchSelfContained>` in the program's csproj (Runner.Server, Console.Server); run both publishes, with and without `PublishSingleFile`, one after the other |
| `dbdatarunner service doctor` fails with `[FAIL] dir.Data: ... Administrators lacks 16; System lacks 16` right after `service install` (Windows) | `FileSystemAclService.FromFileSystemRights` never read back `AccessRights.Full` (bit 16: ChangePermissions and TakeOwnership), so an `(F)` ACE came back as Modify | the mapping sets the bit when both are present (`FromMask`, tested on every platform with the icacls masks) |
| `[FAIL] dir.InstallRoot: ... binaries are writable by Users` in `service doctor` on a hosted Windows runner | the install root inherits its parent's ACL (as Program Files does, where Users only read) and `D:\a\_temp` gives Users write access: the doctor is right | `service-e2e.ps1` cuts the inheritance of the install directory first (`icacls /inheritance:r`, Administrators and SYSTEM full, Users read and run) | Also: `service install` applies its directory specs again and puts the inheritance back, so lock the directory down (`icacls /inheritance:r`) right before each `service doctor`, not before the install.
| a published `dbdatarunner` (or the console) exits at start with `FileNotFoundException: Could not load file or assembly 'Microsoft.Data.Sqlite'` and the Application log shows `StateDatabase.SqliteConnectionString` | the publish output lacks `Microsoft.Data.Sqlite.dll`: the task host is published with the same file name, and when its files are added to the publish list BEFORE `ComputeResolvedFilesToPublishList`, the SDK's file-conflict resolution drops the program's own copy; `dotnet build` and `help` do not show it | add the task host files `AfterTargets="ComputeResolvedFilesToPublishList"` (as the console does); `service-e2e.ps1` checks the file is beside the exe |
| `Assert.Equal() Failure: Expected "succeeded", Actual "running"` on `status.tasks[0].last_run.outcome` of a task that is due every second (RunnerServerTests, slow Windows runner) | a single read of the status can land while the next run has already started | poll for a snapshot whose last run has finished and assert on that snapshot (`h.WaitAsync`), never on one read of a task that runs on a short schedule |

### Timing (two-core runners)

| Signature | Cause | Fix |
| --- | --- | --- |
| a test needing "the next thing within N seconds" fails only in CI; log says "This runner was silent for 00:00:5x (the lease is 00:00:30)" | the whole process stalled (thread pool starvation, many jobs on the machine) longer than a 30 s lease | the DbDataRunner tests raise the thread pool minimum (`TestProcess.cs`) and run one at a time; the scheduler renews its own running items before it releases expired leases (`RenewOwnLeases`). A second record of one run (`Sequence contains more than one element` on a runs query) means this area again |
| `Two_runners_activating_at_once_migrate_once` fails with `NotReady` instead of `AlreadyDone` | the second runner read readiness after the first had activated (activation resets the instance states) | `PackageActivator.ActivateAsync` looks at the head again before answering `NotReady` |
| `Assert.False(activation.IsCompleted)` or `Waited 60 seconds for the hold on new runs` in `A_run_in_flight_finishes_on_the_old_version…` | the in-flight `lingers` task was a fixed 12 s of wall clock; when staging the new version is slow (a stalled runner) it ended before the activation started its hold, so the activation finished at once and the hold was never there to see | `lingers` takes the input `release_file` and runs until that file exists (five minutes at most); the test creates the file after it has seen the hold and the 1.5 s of waiting. Never wait for "a task that is long enough": give the task a signal the test controls. The task process has a cleared environment, so the channel is an input of the run request (`{"inputs": {"release_file": "..."}}`), not an environment variable |
| `A_plan_run_with_parallel_3_ends_with_the_same_data...` on SQL Server fails with "three pauses of 3 s one after another took 00:00:07" (or 5) | SQL Server 2025's `WAITFOR DELAY '00:00:03'` returns early on some hosts (1.6 s measured in a micro-VM, its own `SYSUTCDATETIME` agrees; about 2.4 s on a CI runner), so a fixed 9 s lower bound is wrong | the test takes its bound from the `run_log` start and end of the three `pre_load` hooks (`PauseTotalAsync`), never from the requested delay; a test of a pause measures it |
| `the run of lingers is recorded 2 times` (or `Sequence contains more than one element`) in `A_run_in_flight_finishes_on_the_old_version…`; the log says "This runner's lease ... ran out and the item was taken again ... while the earlier attempt still ran here" | the runner's own tick gave back (`ReleaseExpired`) the lease of an item whose run was going on in the same process: the process stalled longer than the 90 s lease (attempt 1 had run 49 s against a 30 s lease in the loaded reproduction), and a stall between the tick's renewal and its release, or a tick that started late, left the lease expired when the release ran. The item went Pending, the same loop claimed it again as attempt 2 and the first record ended Interrupted/Cancelled | the scheduler passes the items it is running itself (record not finished, lease not lost) to `ModuleWorkQueueStore.ReleaseExpired(except)`, which never releases them: no timing involved. Only another worker's expired lease is taken over, and a record that lost its lease or ended (also when its task process is gone) is not protected. Test: `A_tick_that_finds_the_lease_of_an_item_it_runs_itself_expired_leaves_it_alone_even_when_nothing_renewed_it`; `A_loop_that_stops_renewing_loses_its_item_to_another_loop…` still holds because the taking loop is not running the item |
| `IncompatibleServerException: 127.0.0.1:<port> did not report a management API version` in a publish/pair test (`PublishApiTests.A_publisher_uploads_only_a_changed_file…`), after a very slow test (2+ minutes) | Kestrel's own `408 Request Timeout` (`RequestHeadersTimeout` 15 s, `DbDataKit.Hosting`): a process that stalls longer than that gets the answer from Kestrel itself, which is written before any middleware runs, so `UseManagementApiVersion` cannot put the version on it. The server never started the request. Shown by `KestrelsOwnRequestTimeoutAnswerIsWrittenBeforeTheMiddlewareAndHasNoVersion`; that a stall of this length produces it in the full test is inferred (a reproduced stall made pairing fail with a closed connection instead, the same family) | `ManagementVersionHandler` sends a request once more when the answer is a 408 without the version header (the request was never started, so it is safe to send again); a second such answer, or a 408 that carries the version, is passed on as before. Do not make the version header optional |
| `Cancel` or "body started" tests flaky | the test cancelled before the body ran | cancel when the body signals it started (a `TaskCompletionSource`), never after a fixed delay |
| two tests pick the same free port | `FreePort` handed the same number twice | `FreePort` never repeats a port in a process |
| `address already in use` (`IOException` from Kestrel, `HttpListenerException` from an `HttpListener`) in one test of a full run (`PasskeyChallengeTests.A_captured_response_signs_nobody_in_again`), gone on a re-run | the helper looked a free port up (`TcpListener` on port 0, read the port, stop it) and the server bound it later; another test's client or server took it in between | a server that can take `UseUrls("http://127.0.0.1:0")` binds the port itself: read the address from `app.Urls` after `StartAsync` (Identity tests, `AccessTokenTests`, `ExternalGroupTests`, `IdentityHomeHostingTests`); one that needs its address before it starts (`HttpListener` prefixes, an issuer given to a provider, a port in a child process's arguments) wraps the whole start in a loop of up to 5 that looks a new port up when the bind fails (`AuthenticatedGitServer`, `ExporterTests.StartListener`, `OpenIdFlowTests`, `ViewsModuleTests.StartAsync`); `git grep -n "FreePort\|GetFreePort\|TcpListener(IPAddress.Loopback, 0)"` before adding a helper |

### GitHub release downloads fail (the DuckDB engine and the Build native library)

The pinned DuckDB archives (`duckdb.pin`) come from github.com/duckdb/duckdb/releases, which now and then answers `502`/`504` or drops the connection for hours. Before the cache, every job that needed the engine downloaded it and went red together (`duckdb-pin-*`, `solution`, `dotnet`, `playwright`, `compose`, `flightsql-e2e`, `conformance`, `unit`, `test`, `image`, `runtime-package`, `views-export`).

How it works now, and what to keep true when you add a job:

- **The action `.github/actions/duckdb-cache`** restores `.duckdb-archives/` from the Actions cache (key `duckdb-<os>-<arch>-<rids>-<hash of duckdb.pin>`; `rids` is the host's platform unless the action is given `rids:`), runs `scripts/fetch-duckdb.sh --archives .duckdb-archives <rids>` (a hit finds every archive current and downloads nothing; a miss downloads, with retries, and the action saves the folder right away so a later failure of the job does not lose it), and sets `DUCKDB_RELEASE_BASE=file://<workspace>/.duckdb-archives` for the rest of the job. `setup-product` uses it unless it is given `duckdb: 'false'`; a job that opts out and still needs the engine (or runs a Docker build, a compose file, `publish.sh`) puts the action before the first such step.
- **Every consumer reads `DUCKDB_RELEASE_BASE`**: `fetch-duckdb.sh` and `.ps1`, and `DbDataSync.Libraries.DuckDbEngine` (the .NET downloader of the Sync tests and of `internal build-catalog-cache`; `DBDATAKIT_TEST_DUCKDB_ENGINE_SOURCE` still wins there). The sources are tried in order: `DUCKDB_RELEASE_BASE`, the pin's `BASE`, then `DUCKDB_RELEASE_BASE_FALLBACK` or the pin's optional `BASE_FALLBACK` (a second source that serves the same archive names; none is set, because DuckDB publishes these archives nowhere else, so nothing is invented: mirror the five archives, then add `BASE_FALLBACK=` to the pin). Every copy, from any source, is checked against the archive hash in the pin and the library inside it against its own, so a cache can neither hide a changed pin (the key has the pin's hash) nor serve a changed byte.
- **Downloads retry**: curl `--retry 8 --retry-all-errors` with growing waits (1 s doubling), three rounds per source; the PowerShell script does the same with `Invoke-WebRequest`; `DuckDbEngine` retries 5xx/408/429 and connection errors six times (1, 2, 4, 8, 16 s). A final failure says `checksum mismatch or no copy of <archive> ... from any source: <every url>` and names the Actions cache key that had no copy.
- **Docker builds** cannot see the runner's cache, so the cache folder is inside the build context (`.duckdb-archives/`, in no `.dockerignore` of an image that uses it) and the Dockerfiles of Build, Gateway and Sync `COPY duckdb.pin .duckdb-archive[s] /duckdb-archives/` (the pattern matches nothing in a local build, which then downloads as before) and run their fetch with `DUCKDB_RELEASE_BASE=file:///duckdb-archives`. No build flags, so compose files, `docker build` and `build-push-action` all work unchanged.
- **`scripts/check_duckdb_cache.py`** (run by the `package-versions` job; test in `scripts/tests`) fails a workflow job that needs the engine without the action (or a `DUCKDB_RELEASE_BASE` of its own) before the first such step, a Dockerfile that fetches DuckDB without the context folder, and an action that lost the pin hash in its key.

- **The Build native library has the same arrangement** (`DbDataBuild/scripts/polyglot.pin`, the polyglot-sql FFI archives from github.com/tobilg/polyglot): the action `.github/actions/native-cache` fills `.native-archives/` (key `native-...-<hash of polyglot.pin>`; `rids:` as for DuckDB), `DbDataBuild/scripts/fetch-native.sh [--archives <dir>]` reads `POLYGLOT_RELEASE_BASE` (a `file://` folder, `file:///D:/a/...` on Windows, or https) before upstream's address, retries like `fetch-duckdb.sh`, and still checks every archive against the SHA-256 recorded in the pin (never one fetched from the release). `DbDataBuild/Dockerfile` copies `.native-archive[s]` and builds with `POLYGLOT_RELEASE_BASE=file:///native-archives`. `scripts/check_native_cache.py` is its check; the `native-pin-linux` and `native-pin-windows` jobs of `repo-checks.yml` exercise the cache on both platforms.

## Working in a session (not CI, but it costs the same time)

- A Build test or project fails with `DDB-620` naming `connections/<name>.yaml` and "`extensions.gateway.allow_writes` is not something a definition carries": a project's connection file never carries `allow_writes` or `allowed_directories` (a publish replaces the whole file on the Gateway, those two included; plan 13c D19). Take the line out of the connection file; the same goes for `groups` and `everyone` inside `extensions.gateway` (they are `grants`). A Gateway test that needs a writable data source writes the file by hand on disk.
- A fresh `git worktree` cannot build the Gateway or Build: `DuckDB.Native.targets ... libduckdb.so is missing` (link or copy the main checkout's `.duckdb` folder to the worktree root; it is ignored by git) and `libpolyglot_sql_ffi.so` missing for Build (`DbDataBuild/native/linux-x64/`, from `scripts/fetch-native.sh` or a copy of the main checkout's folder; `cp -r .../native/* native/` into a missing folder copies the content, not the folder).
- `--artifacts-path /dev/shm/..` keeps the disk free, but a few tests find the repository by walking up from the test binary (`CommandTimeoutChokepointTests`, the `InvariantTests` of `DbDataKit.Transfer.Tests`): they fail only there, run them from an in-tree build.
- `dotnet test --project ...` can fail with `Handshake failures` here: run the built executable instead. Microsoft.Testing.Platform projects take `--filter-class "*Name"` and `--filter-method "*Name*"`; the xunit v3 in-process runner takes `-class` and `-method`.
- The Docker daemon of a machine is shared by every session on it: another session's `testenv.sh down` removes the containers under a suite that is running (it hangs, or fails with a database that is gone). If a run misbehaves for no reason in the change, `docker ps` before anything else, and bring the engines up again; one stack at a time.
- Never chain `sleep` in a command; wait with a `Monitor` until-loop.
- A job that reports "failed with 1 error(s)" has an error line named `failed` above it; search for the test name, not for "error".
- `DbDataKit.Server.Servers.Tests` fail with "dbdatabuild.dll is not built" until `dotnet build` has run for `DbDataBuild/src/DbDataBuild.Cli`, `DbDataGateway/src/DbDataGateway.Server` and `DbDataSync/src/DbDataSync.Cli` (they start the built programs). Sync's `ChangeReaderFirstPassContractTests.EveryDeclaredProofNamesATestThatExists` fails until `DbDataSync.Drivers.MsSql.Tests` and `.Postgres.Tests` are built (it reads their assemblies). A build that says `libduckdb.so is missing` needs `scripts/fetch-duckdb.sh linux-x64`; none of these is a code problem.
- `dotnet build --artifacts-path /dev/shm/...` (a small disk) moves the test host away from the repository, so Sync tests that walk up to `DbDataSync.slnf`, `schemas/` or `docs/` (`SyncCliTests`, `DocsCommandDriftTests`, `LauncherTests`) fail with `was not found above`: symlink `DbDataSync.slnf`, `schemas` and `docs` into the artifacts folder, or build in place. The Playwright config reads the products' `bin/Debug/net10.0` folders: symlink them to the artifacts' `bin/<project>/debug` and leave the links untracked (`git add` the paths you mean; a symlink named `node_modules` is not ignored by `node_modules/`).
- When one failure shows up in two pull requests, it is not those pull requests' failure: fix it once, in the batch, and add it here.
