# Plan 28c: Sync and Build on the runner

Status: **in progress** (proposed 2026-11-07; audited against the code 2026-11-11: E01 to E05, E06a to E06e, E07 to E15, E19, E20, E23, E24 and CW01 are built, E14, E16, E18 and CW02 partly; **not built:** E25 to E37 (section 12: the Runner connection store audited and sliced, 2026-11-12), E06f (a CI split, recorded only), E17 (Sync's state on the target: Sync does not reference `DbDataKit.Tracking`), E21 (optional) and E22 (the old paths `ProcessSupervisor`, `BuildScheduler`, the loopback state and the old schema code are all still in the code)). [Plan 28](28-runner.md) section 8 says *what* moves (engines as published runtimes, schedulers, state, logins);
[28a](28a-runner-slices.md) rows R21 to R24 left it as "L, split by a plan of its own". This is that plan: what exists to build on (read in the code,
named), the decisions made while planning, the questions only the owner can answer (each with the default work continues on), and the slices E01 to E22
that replace R21 to R24. Same shape and rules as 28a and [29a](29a-state-slices.md): one slice, one branch `suite/e<nn>-<short-name>`, one pull request,
"done" is a test, the status goes in the slice's row in the same change. Where a name below is marked *to build*, it does not exist yet.

The state half of this plan builds on plan 29 section 4a and the slices Q20 (progress store, done), Q21 (the `tracking` follower library, done), Q22 and Q25
of [29a](29a-state-slices.md). Nothing here changes what the owner decided on 2026-11-04 (plan 28 decisions 5 to 7 and section 8; Sync's and Build's primary is
the target); it says how, and where the code makes a decision harder than the plans assumed (section 3, "Found in the code").

## 1. What exists to build on

### 1.1 The runner, as built (R01 to R18)

Gaps in the runner found while writing this plan, which the engines need and which are not in R01 to R20 (slices E02, E04):

1. **A connection slot is never resolved.** `TaskStart.ConnectionHandles` carries names only, the protocol has no call that turns a handle into a login, and `RunnerScheduler` does not fill
   the handles from `definition_binding` (no use of `ConnectionHandles` under `DbDataKit.Runner/Scheduler`; the kit's `SlotOpener` is supplied by whoever hosts the job and `RemoteJobHost`'s caller gives none). Sections 6 and E02.
2. **A package cannot name a runtime outside itself.** `PackageLaunch.Command` is a path inside the package or a program on the runner. An engine published once and used by many definition packages needs a reference
   from a launch to another package's active version (E04).
3. **Only the kind `integration` exists** (`DefinitionKinds`; R15 registered it, `RunnerPackages` holds its validator).
4. R19 (console screens for runners) and R20 (embedded runner) are not marked done in 28a; E10 and E12 assume R19's pause and run-now screens and say so in "Needs".

## 3. Decisions made while planning

Marked **default** where the plan picks one so work can go on; the owner may change any of them in the slice that is wrong.

| # | Decision | Why |
| --- | --- | --- |
| ED1 | **Both engines are published as runtime packages and their definitions as separate definition packages**, not one package per definition with the engine inside. A definition's manifest names its runtime (`launch.runtime`, E04, done) and a version range. | upgrading the engine must not mean republishing every replication set and project; content addressing already makes a shared file free, but the *activation* of 40 packages for one engine upgrade is the cost, not the bytes |
| ED2 | **No new definition kind in the runner: the existing `integration` kind carries both**, its manifest generated by the back end (a replication set: tasks `drain`, `reload`, `verify`, `reconcile`; a Build project: one task per scheduled or manual refresh plan). A kind is added only when a validator the `integration` one cannot express appears (default: none). | R15's registry, stage, activate, bindings, signatures and the progress migration are all keyed by kind; `package/1` already has tasks, schedules, slots, limits and a progress declaration. The kinds `replication` and `build-plan` that plan 30 section 5 foresaw are labels the console may show, not new code paths |
| ED3 | **Both engines start as the `Executable` launch kind**, with a runner entry compiled into the engine (a `[RunnerTask]` job on `RemoteJobHost`, *to build*), not through `TaskHost`. | Sync's library loader binds client libraries into the **default** load context on purpose (`LibraryRegistry` doc); `TaskHost` loads a package into its own `AssemblyLoadContext`, which would split `SqlConnection` types. Build's executable is one self-contained file with natives that unpack beside it. Neither is a plain assembly package; both still speak the protocol through the kit |
| ED4 | **The unit of a run is what runs in one process today:** one **drain of one replication** (Sync) and one **refresh plan** (Build). Sync's lanes and consumers stay inside the process. | a process per mapping pass is the overhead phase 8 refused; one process per plan is Build's D12 |
| ED5 | **Rows never go through the runner.** The protocol carries only what `IRunnerState` and `Report` carry today: claims, marks, positions, counts, outcomes and log lines. A test counts bytes of a 1,000,000-row replication across the socket and fails above a bound (E03). | a gRPC hop per row would be the bottleneck of the whole suite; the engine already talks source to target directly |
| ED6 | **Move one object at a time, never flip a product.** Each replication and each refresh plan has exactly one scheduling owner (`old` or `runner`), a recorded setting; a switch is audited, waits for the old owner's run in flight, and can be undone. | a double scheduler runs a replication twice (watermark races) or writes a warehouse twice; the one-owner record is the guard |
| ED7 | **Shadow runs only for decisions, never for writes.** In `observe` mode the runner computes what it *would* queue and records it beside what the old owner did; no engine runs. A write-path shadow is refused: it would load a target twice. | a Build refresh or a Sync pass changes a target; the only safe comparison is of the schedule decisions and, in tests, of results on copies |
| ED8 | **A task's package view is read-only; an engine writes to the run's scratch and the runner's data directory only.** Build's extraction base (`DOTNET_BUNDLE_EXTRACT_BASE_DIR`) is set **by the runner's executor** (not by the engine's entry: a single-file executable unpacks before any of its code runs) to `<data>/cache/runtimes/<runtime>@<version>`, outside the views, shared by runs of the same version and written once (E05); Sync's script cache, journal, secret key and verification files go to scratch or to payloads. | `ArtifactCache` views are 0444/0555 symlinks; a first-start unpack or a cache write beside the executable would fail or, worse, write into the shared object |
| ED9 | **Provisioned-column reports and verification results are run outputs, not config writes.** `ReportProvisionedTargetColumns` becomes a payload in the run's outputs; the Sync back end reads it and, as an authoring change with a commit, updates the mapping's column cache; the next publish carries it. Until then the engine re-reports each pass (as it already does when a report is lost). | a published definition is immutable; the run must not write into the config repository, and `IRunnerConfig`'s own doc says the report is recurring and loss-tolerant |
| ED10 | **ODBC and a JDBC image are not packaged where they cannot be.** ODBC drivers are runner capabilities (labels `odbc:*`, R12 `requires`); the IKVM image and jars are artifacts of the replication set's `driver-libraries` part. | Microsoft's ODBC driver and unixODBC are machine installs (CLAUDE.md's test engines say the same); IKVM's image is plain files |
| ED11 | **Credentials reach an engine as environment secrets resolved by the runner for the run**, in the form the engine already reads (`DBDATAKIT_SECRET_...` for Sync's `EnvSecretProvider`, `DBDATAKIT_BUILD_<CONNECTION>_<READ|WRITE>` for Build); a `ResolveConnection` call for kit users follows. Never in a package, argv or a file. | both engines already accept environment logins (`ChildProcessCommandRunner` sets them per child); the kit call is the cleaner end state, not a prerequisite |
| ED12 | **Sync moves in three steps, each shippable:** (S1) the runner is the process supervisor only; (S2) the runner is the scheduler too; (S3) state moves to modules. Build moves in two: scheduler and runner, then state follower. | each step has an undo and a test; S1 alone already removes `ProcessSupervisor`'s limits and logging code and proves packaging |
| ED13 | **A durable queue stays only where it is needed:** bulk-load and reload segments (a batch spans hours and crashes). Ordinary passes are planned inside the drain, as units (`BeginUnit`/`EndUnit`) with no durable row. Segments are units of a `reload` task run; a crash retries the run as an attempt chain, which skips finished units (28b: units skip within an attempt chain only). | `scheduling`'s queue stays for what outlives a process; fewer rows for the common case (today every pass is a `WorkQueue` and `TaskRuns` row) |
| ED14 | **Sync's `both` is per target driver capability.** Where the writer can put a state row in the same transaction as the data (the SQL engines), the target holds the primary and the unified copy follows; where it cannot (Flight SQL targets, descriptor drivers without transactions, DuckDB files), the mode is `state` and the console says why. | Sync keeps no state on targets today; target-primary is a new capability per writer (section 5.3), and the owner's default (target primary) cannot be met by a writer that cannot commit it atomically |
| ED15 | **A clean break for Sync's old state, owner decision 2026-11-07 (QE3).** No `state convert` command. The old state file is refused at start with a message naming the file and the ways to recover; the old file is left untouched. Recovery does not mean a full reload: a replication can **replay changes from the earliest position the source still has** (the log or change-tracking retention), and a table whose position is no longer available is reloaded alone. Build converts nothing (its tracking is rebuilt by the follower from zero). | plan 13's rule is a clean break; the owner judged the recovery options (replay from the earliest available change, a per-table reload) enough, so a conversion path is not worth building. **Supersedes** the conversion in E15 and section 5.4 (read those as: the refusal message and the replay-from-earliest start, not a converter) |
| ED16 | **The write-login constraint is relaxed, owner decision 2026-11-07 (QE6).** Build may keep its write login for person-driven flows (`deploy --apply`, `ack`, seeds); E21 stays optional and plan 20 principle 3 is not amended. It is re-evaluated later. **The condition is ED17: administrators and operators can always see which connections exist where and which process uses each.** | the constraint cost a larger design for little gain now; what matters is that nobody has to guess where a login is used |
| ED17 | **A connection and usage inventory.** Every product reports its connections (name, kind, engine, host, database, the secret *reference* never the value) and for each the **processes that use it** (the server, a runner and its group, a task or replication by name and version, a person-driven flow) and which login role (`read`, `run`, `write`) the use needs. The console shows one table across the paired servers and runners; an operator can ask "where is this connection used?" and "what does this task connect to?". | with logins allowed to stay where they are (ED16) the answer to "where does this secret live and who can use it" has to be a screen, not a search |
| ED18 | **Deployment lineage.** Lineage (plan 18) records, for each published definition, **where it is deployed and on which version**: package, channel, definition kind and name, the active version and the previous one, which runners (group and instance) have it ready or active, when and by whom it was activated or rolled back, and the runtime version it runs on (QE1). A run's record names the definition version it ran, so "which version produced this table" and "which tasks run version N" are both answerable. These are nodes and edges of the plan 18 graph, not a separate store. | the runner already holds the pieces (`definitions` module events, the instances list with `module_versions`, `package_version` on a run); the graph needs them as one answer |

**Found in the code, changing what plans 28 and 29 assumed** (each is addressed by a slice, and each is a reason the owner may want to see section 8):

- Sync's connection has **one** credential; "the back ends keep read logins" needs a second one that does not exist (E20).
- Build's tracking tables are **not all append-only** (`ddl_log`, `run_log` updated in place; `object_info`, `metadata_dependency` rewritten), while the Q21 follower copies by a growing ordering key (E16 settles each stream).
- Sync has **no state on targets**, so "primary: target" is new work in each writer, not a move (E17, ED14).
- The runner **cannot yet resolve a connection slot** (gap 1 above, E02).
- Sync's engine **writes beside its own repository** (ED8, E06).
- Sync's due-ness depends on a **source round trip** (the polling gate), so its scheduler is not a cron (E11).

## 4. Published engine runtimes

### 4.1 What a runtime package is

A **runtime package** is a `package/1` manifest with no tasks of its own (the validator allows zero tasks when `runtime: true`, E04, done), whose files are the engine and its natives, and whose `launch` is an executable. A **definition package** is an ordinary `integration` package whose names `launch.runtime: {name, range}` (E04, done); the runner materializes the definition's view and the runtime's view and starts the runtime's executable with the definition's directory as the working directory and `DBDATAKIT_PACKAGE_DIRECTORY` (`RunnerProtocolNames.PackageDirectoryVariable`, exists) pointing at it.

| | `dbdatasync-runtime` | `dbdatabuild-runtime` |
| --- | --- | --- |
| Launch | `Executable`: `dbdatasync-engine` (the TaskRunner with a runner entry, *to build* E06) | `Executable`: `dbdatabuild` with a runner entry (`[RunnerTask("refresh")]` calling `CliApp` with `connection refresh <connection> <plan> --project <view>`, E05) |
| Contents | the TaskRunner and its project closure: `DbDataSync.Core`, `.Drivers.*` (MsSql, Postgres, MySql, Oracle, DuckDb, Flight SQL, Generic, Jdbc, Descriptor), `.Libraries`, `.Scripting` (Roslyn: a script compiles at run time; the compiler cache goes to scratch), `.Verification`; per RID | the self-contained single-file executable of `scripts/publish.sh` (runtime, tool, polyglot library, DuckDB), per RID |
| Not in it | client libraries (`Npgsql` and the others are excluded from the build by design), JDBC jars, customer drivers, ODBC | nothing: Build has no customer-supplied code beyond the project's own load scripts, which are definition files |
| Size | to measure in E06; the budget test (below) records it | measured in E05: 286 MiB for linux-x64 (one file; the polyglot archives are about 150 MB each but the shared library is the part used, the DuckDB engine is one library) |
| Versioned by | the Sync release (`ProductInfo`), `built_against` the runner protocol, kit major and .NET major (`BuiltAgainst`, checked by `RunnerContracts` at stage) | the Build release, same |

Artifact sizes against the cache and the 512 MiB cap: each file is an artifact, so the cap applies to the largest single file. The Build single-file executable is the one at risk (a self-contained file with two natives); **E05 fails if any artifact is above 400 MiB** and records the size per RID, and the fallback is the framework-dependent publish plus natives as separate artifacts (the runner is .NET and has the runtime; `requiresDotnet: 10.0` is already in both `dist.json` files). The cache keeps every active and previous version's objects and evicts the rest (`ArtifactCache.EvictAsync`), so two runtime versions side by side (N and N-1) cost the sum of their *distinct* files. The runtime's files are stored once however many definitions use it.

### 4.2 N and N-1 (plan 24)

- The runner keeps the **active and previous** version of each runtime per channel (the `serving` pointer already holds active, previous and staged), and a definition's range pins which it may use. A definition built for runtime 3.x on a runner whose active runtime is 2.x **fails staging** naming the runtime and range, the same refusal `RunnerContracts` gives a package built against a contract the runner lacks.
- A runtime upgrade is **activated per channel**: stage the new runtime, every instance prepares it (materialize, hash), then activate; **runs in flight finish on the old runtime** (`PackageActivator` waits for runs of the *package* in flight, and E04 extends the hold to the dependents of a runtime), the next run of each dependent definition starts on the new one. Rollback is `Rollback` on the runtime, which restores the previous pointer; progress needs no migration (a runtime has no progress declaration).
- The runtime's contract with its definitions is the **definition formats**: Sync's `task.yaml`/mapping formats and Build's `rendered/` file formats are versioned by their own `<name>/<n>` rule; a definition in a format the active runtime does not read is refused at stage naming the file (plan 13's clean-break rule, not a silent failure at run time).

### 4.3 What a definition package is

| | Sync: replication set | Build: project snapshot |
| --- | --- | --- |
| Files | `config/connections/*.yaml` (no secrets), `config/replications/<name>/task.yaml` and `table-mappings/*.yaml` (with the cached target columns), `config/scripts/*` with locks, `files/` (jars), the `driver-libraries` part (`libraries/*/library.csx`, `library.lock` and the restored `lib/` closure with natives per RID, `drivers/*`) | `dbdatabuild.yml` and its folder files, `rendered/<connection>/loads.yml`, `rendered/<connection>/refresh/<plan>.yml`, the load scripts, resolvers and hooks they name by hash |

| Size | small (YAML) except `driver-libraries` (tens of MB with IKVM and native providers) | small (YAML and SQL) |

Publishing is plan 30's API (`PUT /api/v1/definitions/integration/{name}` with artifacts by hash, `expected_version`, stage then activate, bindings per channel, signatures when required); the back end is paired as a Publisher with `OwnerScope`. Plan 21's promotion applies unchanged: the same version to the next channel, bindings the channel's own.

### 5.1 Sync's tables, module by module (E14, E15)

| Sync table (`Migrations.cs`) | Goes to | How |
| --- | --- | --- |

**Watermarks as a declared checkpoint** (ED12 step S3, E15). The declaration (in `package/1`'s `progress`, read by `ProgressMigration.Plan`, generated by the Sync back end for each replication set):

```
checkpoint: watermark      per: [mapping, source_table]
  parts: position (text)            # ChangeWatermarks.Watermark, opaque: hex LSN, decimal version, time text
         position_time (time)       # WatermarkTimeUtc
         intent (text)              # ReadIntent; default "Changes"
         hold (text)                # ReadHold; default "None"
         pending_position (text), pending_position_time (time), pending_batch (text)   # a captured initial load awaiting promotion
```

`SetWatermark` (after the target write commits) becomes an `Advance` in the same protocol call that closes the **unit** (a mapping pass or segment), with the unit's outcome; a refused `Advance` (another writer got there first, `row_version`) is the same condition `LocalRunnerState` meets today when two passes overlap. `PromotePendingLoad` is one `Advance` moving the pending parts to `position` and clearing them; `ClearWatermark` is a rewind with the actor named. `checkpoint_history` replaces nothing Sync has (it has none) and gives the console its first "rewind a mapping to Monday". A new Sync version that changes this declaration is migrated by the runner at activation (R18), losses confirmed, rollback restoring from history.

The one honest limit: the progress store and the **target** are two databases, so `Advance` after the target commit is at-least-once, the semantic Sync has today ("only ever called after the target write has committed"). `both` with the target primary (5.3) is what closes it for writers that can.

### 5.2 Build's tracking: streams for the follower (E16)

Build's primary stays `target` (owner, 2026-11-04) and the tables, their DDL and layout 9 do not change. The follower (Q21, `TrackingFollower`) copies each **stream** into the `build_tracking` module of the group's state, under the connection's identity (server and database as they really are, plan 18 section 4: *to build* the identity string in E16, Q21's open item), idempotently. Each stream needs an ordering value that only grows and a row key; where a table is updated or rewritten, the stream is defined over what is stable:

| Table | Stream | Ordering key | Row key | Note |
| --- | --- | --- | --- | --- |
| `schema_version` | yes | `first_seen_utc` (ticks) | `object_name\|first_seen_utc` | append-only; `TrackingClock.NextUtc` makes it strictly increasing per process |
| `migration_log` | yes | `applied_utc` | `plan_id\|applied_utc` | one insert per event (`MigrationAsync`) |
| `block_log` | yes | `created_utc` | `block_id` | an acknowledgement is its own insert carrying `ack_*`, no update in the code |
| `operation_interval` | yes, after a layout change | none stored today (`interval_id` is a GUID) | `interval_id` | layout 10 adds `recorded_utc` to this table (default); until then it is copied by joining to its `run_log` rows' `started_utc` |
| `ddl_log` | **no, as an append stream**: rows are updated with `status` and `hash_after` | `executed_utc` | `ddl_id` | the follower copies a row when its status is final (`ok`/`failed`); a row left `started` by a crash is copied as `started` after the run that owns it is over (`apply --resume` settles it), and re-copied on a status change by comparing the row hash (E16 adds a per-row hash to the stream for updated tables) |
| `run_log` | same as `ddl_log` | `started_utc` | `run_id\|step_id` | updated at the step's end (`status`, `rows_affected`, `shape_hash_end`, `ended_utc`, `duration_ms`) |
| `metadata_document` | yes (the `metadata_current` view is derived) | `recorded_utc` | `subject_kind\|subject\|recorded_utc` | append-only |
| `object_info`, `metadata_dependency` | **snapshot, not stream**: deleted and rewritten per subject | `recorded_utc` for `object_info` | key columns | derived from `metadata_document`; the copy is **rebuilt from the copy's own documents** rather than copied (`metadata_dependency` has no timestamp at all) |
| `refresh_plan_member`, `plan_store` | yes | `stored_utc` for `plan_store`; `plan_id` order for the members (written once with the event) | `plan_id\|position`, `plan_id` | written once, never updated |
| `tracking_version` | no | | | the layout record; kept as one row per source identity |

Known limit carried from Q21 and made explicit: divergence compares positions and keys, not content, so a restored target that reuses keys and ordering values for different rows is not seen; the per-row hash E16 adds for the two updated streams narrows it for those, not for the append-only ones.

Where the follower runs: **after every refresh task** (a step of the runner entry, bounded by a time budget, never failing the run: `TrackingRunResult.Error` is a warning) and from a **small `catch-up` task** of the Build project package on a schedule, so a copy that was down catches up without a refresh. `TrackingSettings` (`mode: target|state|both`, `primary`) are Build's settings and `server.yaml`, default `both` with `primary: target`, as plan 29 section 4a.2 decided.

### 5.3 Sync's state on the target (E17)

Sync writes no state to targets today. For `both` with a target primary, a writer driver (`IChangeWriter`) must, **in the transaction that applies a unit**, upsert the unit's position into a `dbdatasync` state table of the target (replication, mapping, source table, position, position time, intent/hold, run id) *to build*, per dialect through the shared dialects. Then the position moves atomically with the data, which is **stronger than today** (no at-least-once window for that target), and a restored target rewinds the watermark with the data, which is what the owner wanted. The progress store holds the follower's copy. Writers that cannot (Flight SQL targets, DuckDB files, descriptor-built drivers with no transaction, JDBC targets whose driver declines) run `state` mode (ED14). The follower for Sync is the same `TrackingFollower` with a stream `watermark` over the target table (ordering key: a position counter the writer increments, row key: the key parts), identity as for Build. This is the largest single piece of new code in this plan after the engine move; it comes after the move works with `state` mode (E14 and E15), so the move is never held up by it.

| Credential | Today | After |
| --- | --- | --- |
| Build **read** login (catalog and tracking read; previews, `plan`, `diff`, `report`, `history`) | `ServerSecrets` `dbdatakit:build:connection:<c>:read` in the Build server's store | stays |
| Build **write** login (refresh, apply, ack, seeds) | `...:write` in the same store, handed to a child as `DBDATAKIT_BUILD_<C>_WRITE` | scheduled and run-now **refresh**: bound on the runner per channel (E19). Interactive `deploy --apply`, `ack`, seeds: stay in Build until E21 (ED16) |
| Sync credential | one per connection, `CredentialSecretRef` | two roles, **`read`** (metadata browsing, connection tests, previews, provisioning previews: stays in Sync) and **`run`** (reading sources and writing targets in a drain: on the runner); a connection may bind both to one secret, since an administrator may only have one login (plan 28 section 5: simple options, the administrator decides) (E20) |
| State database logins | the engine reaches state through the API's loopback endpoint | the runner owns the state login (`state grants`, Q23); the engine process holds none (DR5) |

How a slot resolves on the runner (E02): a manifest slot (`ConnectionSlot(name, kind)`) is bound **per channel** by `definition_binding` to a `connection/1` (plan 13 W13) whose secrets are references into the runner's secret store (`DbDataKit.Secrets`), never values in a package. When a task starts, the scheduler fills `TaskStart.ConnectionHandles` from the bindings (names). For a run the executor then **injects the resolved logins into the child's environment** in the form the engine reads (ED11): for Sync one `DBDATAKIT_SECRET_<NAME>` per connection of the replication (so `SecretStore.Open`'s `EnvSecretProvider` finds `dbdatakit:sync:connection:<name>` unchanged), for Build `DBDATAKIT_BUILD_<CONNECTION>_<READ|WRITE>` per slot role (`LoginEnvironment.Name`). A package's slot declares `env: sync-secret` or `env: build-login` (*to build*; the injection format is a registry in the runner, not free text, so a package cannot make the runner write an arbitrary variable). The same facts are what the `ResolveConnection` call (*to build*, protocol `v1` addition, kit `Slot<T>.OpenAsync`) returns to a kit job, as a short-lived grant held in memory. Tests: the resolved secret is in `/proc/<pid>/environ` of the child and not in `argv`, the scratch directory or the run log (the R06 test pattern, extended to the injected variables).

The staging check refuses a version whose slot has no binding in the channel, naming the slot (R15 already refuses a promotion with an unbound slot).

### 7.2 Pause, run now and monitoring (M11)

- **Run now.** The runner's `POST /api/v1/tasks/{package}/{channel}/{task}/run` (R10, `RunnerControl.RunNow`, audited) with `inputs`; Sync's "trigger", reload and verification requests and Build's `.../schedule/{connection}/{plan}/run` call it from the back end with the caller's identity as `by`, and the back end answers with the run id. A Sync request that computes segments (`BulkLoadService`) sends them as an input payload (an uploaded payload id, so the input stays small).
- **Pause and resume.** The runner's `.../pause` and `.../resume` (`job_pause`, who and when). The back ends keep their own pause endpoints, which for a runner-owned object **forward** to the runner (they are paired; a Publisher may not pause, so the back end's client needs the Operator role, an owner question: QE5) and answer 409 naming the runner for an object the runner does not own.
- **Monitoring.** The console's monitoring view (M11) already lists Sync replications and Build plans from each product's schedule endpoint; after a cutover the **same row** carries `owner: runner` and the runner's last run (R19's screens), so a failed Build run and a lagging Sync replication still appear together (the M11 test). `ReplicationLagReading` stays in Sync (it reads the checkpoint through the `runs`/progress modules after E15).
- **Notifications.** Run failures are raised by the runner (`DbDataKit.Monitoring`); Sync's lag and Build's `expected_every` stay with their products (they judge a thing the runner does not know).

### 7.3 Migration path with both side by side (ED6, ED7)

Per object (a replication; a refresh plan), a recorded **owner** setting in the back end's settings and mirrored in the runner (`old` default, `runner`, plus `observe`):

1. **Publish and stage** the runtime and the definition to the runner's channel; every instance prepares them (E04, E07, E08). Nothing runs: the manifest's schedule is *inactive* until activation, and `owner` is still `old`.
2. **Observe** (`owner: observe`). The runner's scheduler evaluates the object's schedule against a *copy* of `job_state` and writes `decision` rows (would queue at T) without starting anything; the back end compares them to its own (Build: `BuildScheduler`'s queued times; Sync: the planner's due mappings for continuous mode, with a tolerance of one tick). A difference is a finding in the console. This is the only shadow (ED7).
3. **Cut over one object** (`owner: runner`): the back end pauses the object in its own scheduler, **waits for the run in flight** (Build: the item's lease; Sync: the worker process, as `PackageActivator` waits), copies the schedule position (E09, E12), sets the owner, and activates the package's schedule. The first scheduled run is on the runner. The switch is audited with who and why.
4. **Per-object rollback**: set the owner back. The back end resumes its scheduler from the position the runner left (the reverse copy), the runner's task is paused. State for Sync in S1 and S2 is still Sync's own, so rollback needs nothing else; after S3 (state on modules) the previous release reads its own old state file, which ED15 leaves untouched and which holds the positions of the day of the switch: rollback loses the positions made since (the mappings re-read from the old ones, which the merge writers take as a repeat), and the switch page says so before it does anything.
5. **A whole product** is only ever "every object cut over"; the back end's own scheduler stays in the code until E22 and is simply idle, behind the same `--scheduler` opt-in Build already has.

Results are compared, not trusted: for a few objects the owner can run old and new against **copies** of the target (Build: a second tracking connection and a scratch schema; Sync: a second target) and diff the outputs with the existing comparison (Build's `connection compare`, Sync's verification). That is a test technique (E01, E03, E09 and E12 use it), not a production mode.

## 11. Risks

- **Windows paths and read-only views.** `ArtifactCache` makes a view of hard links on every system (before R-links: symlinks on Linux, copies on Windows), directories carry a read-only attribute that does not stop file creation there, and its Windows behaviour is untested (R05). Build's first-start unpack and Sync's cache writes make this concrete: E05 and E06 run the Windows path in CI and the "no write into the view" test must be meaningful on Windows too. Long paths: a view path plus a deep `config/replications/<name>/table-mappings/` tree plus IKVM's image under `libraries/ikvm/lib` may exceed 260 characters; the cache's view directory name is kept short (`<version>-<id>`) and E06 tests a long replication name.
- **Native libraries in the cache.** Natives are per RID and must be loadable from a read-only, possibly symlinked path: some loaders resolve symlinks and look for neighbours (DuckDB, IKVM's `libikvm`, the polyglot library), and a copy-on-Windows view duplicates 100+ MB per run unless views are shared per version. E04 decides that a runtime's view is **shared by every run of that version** (read-only, created once), not one per run; the per-run view stays for definitions only. A hash-pinned `DuckDbEngine` source and the polyglot pin are verified at publish, not downloaded on the runner (the runner must work offline).
- **JDBC through IKVM.** The IKVM image is large, loads into the default context, is never unloaded, and its JRE image is per RID; running many JDBC drains on one runner multiplies resident memory, and the **watchdog samples a process, not its tree** (R07 "Remains"), though IKVM is in process so the number is right. A JDBC-heavy replication needs a `MemoryMb` limit above the default; E06 measures it and the manifest generator sets it.
- **ODBC is not packageable.** A runner without the driver cannot run the replication: the label and `RoutingCheck` make the activation refuse naming the label (R12), but the failure is found at stage, which needs a live runner with the label; a group whose only ODBC runner is down cannot activate. Plan 28 question 7 already says a version whose label no runner has does not activate; E06 adds the probe (QE12).
- **The cost of an extra process hop and of gRPC.** Today the worker already is a child process of the API and speaks HTTP to it; the runner adds a scheduler, a materialization (cheap after the first run: hard links) and a protocol socket, but **not on the rows** (ED5). The real exposure is the *frequency* of small calls: Sync's `IRunnerState` is called per pass and per log batch (`LogBatchRequest`), so `Report` must batch (the `RemoteRunnerState` buffer carries over) and `SetWatermark` per unit must not become one `Advance` per row batch. E03 and E11 bound both: bytes across the socket, and calls per 10,000 rows; the bound is a test, not a hope.
- **Sync's planner and the runner's cadence.** The runner's tick is 5 s like Sync's, but a continuous replication that stays alive between passes holds a lease and a slot; a runner with 300 replications needs `Concurrency` per instance and per-package limits tuned, and the lease heartbeat (30 s) is slower than Sync's `StateGraceSeconds` model. E11 measures a runner with 50 continuous replications, one mapping each, against the supervisor.
- **State moves are the hard part (plan 28 decision 7), and two are new code, not moves.** Target-primary for Sync (5.3) needs a transactional state row in every writer, which does not exist; Build's tracking is not append-only (5.2) and needs a layout 10 and a per-row hash. Both are scheduled **after** the engine move works in `state` mode, so a late discovery there does not stall the migration. If E17 shows a writer cannot do it cheaply, that writer stays `state` (ED14) and the owner's default is amended in the plan, in that pull request.
- **Two schedulers, one object.** The whole safety of the migration is the one-owner record. The failure mode is a replication run twice, or a warehouse refreshed twice. The guards are: the owner setting, the pause-and-wait in the cutover, the resource claim on `package:<package>` plus Sync's per-mapping `Resource`, and tests that start both and assert one run. A back end restored from a backup that has an older `owner` setting is the residual risk; the runner's mirror of the setting is authoritative and a mismatch is a console finding.
- **Interactive flows that quietly need the write login.** Build's `deploy`, `ack`, seeds and Sync's provisioning write from the back end; claiming "the write login left Build" before E21 would be false. ED16 and QE6 say so, and E19's test asserts which secrets remain.
- **The runtime/definition split adds a version matrix.** A definition's range, the channel's active runtime and the runner's N and N-1 interact (a definition promoted to a channel whose runtime is older). The staging refusal names runtime, range and channel; the console's versions screen (plan 30) shows the dependency like `depends_on`. If this proves too heavy, QE1's alternative (the engine in every package) is a one-line change in the generator and costs only activation time.
- **Scope.** E01 to E22 is 11 L and 11 M slices, on the order of eighteen weeks of one person's work end to end, and E17 and E21 are optional by decision. The first value, a scheduled Build refresh with a real publish, is four slices away; the plan is built so that stopping after any milestone leaves both paths working.

### 12.3 The smallest design

1. **Keep the store, add no table for connections.** A back end sends a definition to a runner with the **administrator's pairing code** (the `secret send` pattern), through one new client call and one shared composition (`RunnerTargets`); a Publisher still cannot put a copy by itself (QE14).
2. **A channel target is three existing facts**: a copy, a login, a binding of the write slot in that channel (confirmed by IX17 when it equals production's). `channel target create|drop|list` (Build) and the trial run (Sync) are verbs over them; no second override record exists.
3. **A Gateway starts a task as a paired client of the Runner**: its own `runners.json` and key (the shape of `gateways.json`, one shared file class), the pairing made by the console's Link (the mirror of what it does for `data.changed`), one new runner route `POST /api/v1/start/{package}/{channel}/{task}` that only a paired server client with Operator may call and only for a **grant** an administrator wrote on the runner, and a status read of the runs that client started. The person is the run's `by`; `Via` names gateway, app and link.
4. **The report-catalog host is the console's embedded runner** (system task `report-catalogs/read`, on channel `system`, in the console's process): sources are the console's `report-catalog` connections bound per channel (`bindings.yml`, a new section `catalogs:`), the sink is a client of plan 30's route into each paired Gateway as the console's identity with the Publisher role and an owner stamp, and the snapshot carries the report server's open address so the Gateway needs no connection.
5. **Finish ED17 where the data already is**: the runner's inventory reads engine, host and database from the copy or file and lists copies nobody uses; the console's table shows the copy's version against the console's file beside the use.
