# Plan 26: app publishing, what is left

Status: **in progress**. What is built (where code runs, trust and egress, app storage, subpath addresses, navigation sets, portals, the catalog and embed, app instances, Store model instances) is described in [docs/apps.md](../apps.md). This plan holds only unbuilt work. Slice ids AP03 to AP18 and Z12 to Z14 stay cited from code; their done rows are in git history.

| AP08 | **Subdomain and custom-domain bindings.** An instance has one primary address and any number of others, each a binding an administrator adds. One listener routes by `Host` and path from a table of bindings in the group's shared state (a binding change is a published change, not a restart); TLS picks the certificate by name (SNI: a wildcard for subdomains, a supplied certificate for a custom domain through the secret store); a name is verified before it is accepted; each binding is registered as a redirect URI of the instance's OpenID client when added and removed when removed; behind a reverse proxy `X-Forwarded-Host` and `X-Forwarded-Prefix` are trusted only from listed addresses; a subdomain label is the instance name and reserved names are refused. This is also what makes `origin: own` and a trusted portal's own domain possible | AP05 | L | one host serves two names with two certificates; removing a binding removes its redirect URI; an unverified name is refused; declaring `origin: own` with no domain bound to the instance fails publication naming the setting |
| AP17 | Report servers embedded with Windows sign-in (plan 16, "Sign-in decisions" item 10): an app embeds an SSRS or Power BI Report Server report by its URL; the report server's origin is an approved `frame` exception of the instance; off the domain the frame is replaced by a link that opens the report on the report server | AP05, AP14 | M | Playwright: an unapproved report origin is blocked by the policy and an approved one is framed; with Windows sign-in failing, the person sees the link, not a password prompt; on a domain-joined Windows host with a report server (the Windows CI job, or recorded on the Excel VM) the report renders signed in as the person |
| AP19 | **Move the apps host onto the identity home's app tokens** (the host half of plan 16, "Sign-in decisions" item 1; was 13a U19). The home's half is built: `OidcClients.RegisterApp` (one public PKCE client per instance), `OpenIdProvider` with `IAppGrants` (an access token whose `aud` is `app:<instance>`, `dbdata_roles` the person's roles on the instance, `dbdata_scope` the manifest's scope narrowed by `AppScope.Narrow`), `AppTokenValidator` and `AppAccessToken.Allows`. The host still brokers `AppTokenBroker` tokens signed by its own key, and `AppDataGateway` validates those. To do: the shell broker does a **refresh-token exchange per instance client** at the home; a **JWKS verifier** lets a host that does not run the home validate the home's tokens; an **`IAppGrants` implementation over `AppInstanceStore`** says what the approved manifest allows (null when no approved version runs); the manifest gains a **`change request` operation** beside read and write (today a write scope's change request is the Store's rule on a write) | AP05, 13a U13, U19 | M | the O08c data test passes with the home's token and no `AppTokenBroker`; instance B's validator refuses instance A's token; a model or operation the manifest does not name is refused; a write scope for a person who may only read gives no write; the console's and other clients' tokens are unchanged |

## Leftovers of built slices

- **AP25** (built, on top of GP06): an app of `views/*.yaml` only (no `entry`) renders in the apps host. The host generates the page at `_app/` (`ViewsApp.Document`) with the specs as a JSON element in it (`views.json` too) and serves its own runtime, `views-app.js` and `.css` (`ViewsRuntime`, from `apps-views` beside the Proxy; a Proxy without it answers 503 naming the build). The runtime is the new workspace `DbDataKit/web/view-app`: `ViewApp` and a screen per kind on `@dbdatakit/store-ui` (field controls, the Store client, violations; a refusal is drawn against its attribute) and `@dbdatakit/visuals` (`VegaChart` for a bar or a line, `DataTable`); data through the app's own data route with the shell's token. Built as a sandboxed document under the app's policy, not on the host's origin as the row said: the YAML is data and the runtime is the host's, so it needs no more reach than a code app. The data route gained `GET .../models/<model>/schema` (`AppDataRoute.Schema`, `GroupStoreApi.Schema`, `ModelSchemaJson` moved to `DbDataKit.Store` and used by the DbDataStore server too), limited to the entities the manifest lists. `@dbdatakit/visuals` compiles its validators on first use, not on import (Ajv needs `unsafe-eval`, which an app's policy refuses). Sample `territory-views` (`apps init --template territory-views`, `publish-samples.sh`), step 6a of [apps-testing.md](../apps-testing.md). Tests: `ViewsAppTests`, `AppSiteTests`, `AppDataGatewayTests`, `AppsBuildTests`, `AppsModuleTests`, the `GroupStateTests` schema read (needs SQL Server or PostgreSQL), and vitest in `view-app` and `visuals`; also driven in Chromium against the built runtime under the apps policy. Left: the Playwright story (list, edit, a refused row, as the row asks; it needs the identity home with a passkey, the Store and PostgreSQL, like `apps-host.spec.ts`), reading rows in the browser (up to 2000 an entity; filter, sort and paging are client side until the Store has a query), a composite key (a view addresses a row by one attribute), semantic-layer widgets, views next to code pages in one app (22a GP34), the theme message from the shell (charts follow the person's colour scheme only).
- **AP24b** (built): the Apps screen of the Proxy's screens in the console (`DbDataKit/web/proxy`: `AppsPage.tsx`, the list logic in `apps.ts`, the rail item **Apps** at `/apps`), over the AP24a routes through the console's relay (which passes every Proxy call; the person's token carries their roles, the Proxy decides). Sections: **Instances** (the version each runs, followed or pinned, with a chooser and Apply; trust and the approval standing; an Open link to the address on the apps host, or the path when the Proxy serves none; Remove), **Apps** (the version served and its publisher, instances, Remove; **Versions and data access** opens the versions table: Serve this version (the rollback), Approve for a trusted version with no standing approval, Data access: the models and what each entity may do, outside addresses, storage, publisher, approval), **Navigation sets and portals**, **Approvals** (hash, approver, time, what it was for, standing or revoked; Revoke). Every button that is off says why, from the `caller` flags and the data: the Approver role on this server, a different person than the author, the portal that mounts an instance, the instances an app still has; a removal the store refuses shows its message. The approver is named in a field above the approvals (the signed-in person at first; the Proxy checks that the identity home knows them and holds the role). Tests: `apps.test.ts` and `AppsPage.test.tsx` (vitest), `proxy-apps.spec.ts` (Playwright; its own Proxy on 8516 to 8519, no Store or PostgreSQL; sorts after `identity-home`). Left: the screen does not publish a version or make an instance (the command line, or `--to`), and edits no navigation set.
- **AP24a** (built): the Proxy's routes for the console's Apps screen, in `ProxyApps` and audited like the AP26 ones. Reads for a viewer or publisher (so also an administrator; this widens `GET /api/v1/apps`, which needed the publisher role): `GET /api/v1/apps` (now with title, trust, kind, publisher and instances), `GET /api/v1/apps/<name>` (every version: who published it and when, whether it serves, the content hash, the approval standing for its exact bytes, and the manifest's "about" data of AP18: models and operations, outside origins, storage, roles), `GET /api/v1/app-instances` (the version each runs, pinned or following, and what the app serves now; whether it runs as its manifest asks; the address on the apps host when the Proxy serves one, else only the path; the portals that mount it; the navigation sets that list it), `GET /api/v1/app-navigation`, `GET /api/v1/app-approvals`. Every answer carries `caller` (`can_publish`, `can_approve`, `you`) so a screen can say why a button is off; the roles are enforced on each call, never by a screen. Changes: `DELETE /api/v1/apps/<name>` and `DELETE /api/v1/app-instances/<name>` (publisher or admin; the store's AP20 refusals come back as `409` with its message, a name that is not served as `404`), and the new `POST /api/v1/app-approvals/<id>/revoke` (`{"by"}`; the approver role like approving, and `by` a user of the identity home who holds the Approver role on the server id; audited as `app approval-revoke`). A person of a console who names no `by` is the named approver (the home still has to know them); a paired server client must name one. Left: `nav-save` and the navigation removal have no route. Tests: `AppsScreenTests`.
- **AP26** (built): `apps publish|instance-save|rollback|list|approve` take `--to <address or paired name>` (`--on` for `rollback`, whose `--to` is the version) with `--code`, `--alias`, `--client-name` and `--client-dir`: the Proxy's management API (`PUT /api/v1/apps/<name>`, `POST /api/v1/apps/<name>/rollback`, `PUT /api/v1/app-instances/<name>`, `GET /api/v1/apps`, `POST /api/v1/app-approvals`; `ProxyApps`) called by a paired server client the way the Store and Build call it (pinned certificate, token signed with the client's own key). The roles are the pairing's: publisher (or admin) for the first four, approver for approvals (a second client; `--by` is still a home user with the Approver role, not the author). The author recorded is the paired client's name. Left: the other verbs (`nav-save`, the removals, `approval-list`, `approval-revoke`) have no remote form; an app has no owner stamp, so any publisher client may publish a new version of any app; the person of a signed-in console is not passed (the token names the client). Tests: `AppsRemoteTests`.
- **AP23** (built): `apps init --template <territory-notes|territory-notes-src|front-portal> --dir [--name]` copies a sample that is inside the program, and `apps build --src --out [--entry] [--no-minify] [--offline] [--bun]` runs `IAppBundler` (Bun found by `BunLocator`: the pinned, hash-checked `.bun/<rid>`, `--bun`, `DBDATA_BUN`, the PATH; a missing Bun is said with the pin and `scripts/fetch-bun.sh` named) and the built-in checks on the result. `--offline` installs nothing and is refused for a source whose packages are not already in `node_modules`; the allow-listed vendored mirror (plan 22a GP33) is still open. Tests: `AppsBuildTests`, `BunLocatorTests`.
- **AP20 to AP22** (the first testable cut, built): the lifecycle's last steps at the command line (`apps list`, `rollback`, `remove`, `instance-remove`, `nav-remove`), the sample apps (`DbDataProxy/templates/apps`) and the quickstart override that serves the identity home and the apps host (`dist/compose/quickstart-apps.yml`). The script that uses them is [docs/apps-testing.md](../apps-testing.md), which also lists what a tester still cannot do.
- **AP05**: sessions shared across a group (`AppSessions` is in memory per instance, so a person signs in again at another instance); the apps host gives a trusted portal no shared shell script (it carries its own).
- **AP07**: browsers that block third-party cookies by default ask the person to sign in inside a frame; a portal on such a browser links with `?launch`.
- **AP09**: an administrator-set cap in configuration (the 50 MB is a constant); previews' throwaway copy (plan 21); an app on its own origin calling the storage API directly.
- **AP11 / AP13**: the shared controls (`@dbdatakit/store-ui`) applying a `theme` message (the Playwright app applies it by hand); the portal header's switcher and search parts (drawn as nothing); slot sizes fixed by the shell (declared sizes would be a manifest addition).
- **AP12**: dashboard blocks from the semantic layer in a portal home (the extension point is `HomeBlock`; the loader refuses a `dashboard` key today), images, tables, per-block roles, `slots.home` combined with a view; the Playwright story.
- **AP14**: a sandboxed app cannot be given origins (approvals exist only for trusted apps); per-instance lists distinct from the version's approval; the policy shown on the instance's page (the about page lists what the manifest asks, not what is approved); the Playwright cases for browser enforcement.
- **AP15**: the approval label on a change request a trusted app proposes (the audit row of a write has it); `--hash` cannot check that the app asked to be trusted (the gate at run still allows only what the manifest asks).
- **AP16**: the Playwright story in `apps-host.spec.ts` (unapproved fallback with the reason, approved portal on the host origin with the `_audit` row naming Ada, the version and the approver, revoked falls back) is written and has not been run; it needs PostgreSQL, the built Proxy and Store and `npm ci`.
- **Z12b**: `scope: shared` entities in `column` mode (held once, readable by every instance, writable through `default`); a token scoped to instances; migrating a model between modes.
- **Z12**: per-instance roles for the Store (the roles are the home's `app:<instance>` ones).
- **Plan 22 section 1** says builds run offline from vendored packages with an allow-list; AP01's bundler runs `bun install --ignore-scripts` (it fetches from the registry). Before the apps host ships, the bundler gets an `offline` mode that installs only from an allow-listed, vendored mirror.
- Plan 21 gets instances as a second axis beside channels (a promotion carries the app version; the model instance a channel binds to is channel configuration).
