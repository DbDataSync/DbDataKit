## Parked

Low priority, kept as one paragraph each and not scheduled; pull one into a plan with slices when someone asks.

- **RDL reports without a report server (was plan 16 section 2a).** Our own report spec (plan 32) is the first step and SSRS and PBIRS are embedded or read through plan 32 section 9e. If RDL files must be rendered by the suite itself, **Majorsilence Reporting** (open-source RDL engine, Apache 2.0, about 237,000 lines of C#, .NET 8 and 10, exports PDF, HTML, Word, Excel, CSV; data can be pushed in with `DataSet.SetData` so a semantic query under the user's identity feeds it; its RDL coverage is partial, it refuses matrices, gauges, sparklines, maps and `Lookup`, so a sample of real reports must go through its `rdl-doctor` first, and render on Linux and Windows with pushed data, before anything is promised; its own data providers stay off and the code-loading features `<Code>`, `<Classes>` and `<CodeModules>` are refused for reports from users or agents). **FastReport Open Source** (MIT, banded and pixel-perfect documents, does not read RDL) is the alternative if the spike fails; the unofficial decompiled `ReportViewerCore` is not recommended (licence and maintenance risk).
- **Verifying the Arrow Flight SQL ODBC driver on a report server (route R3, `docs/bi-tools-on-semantic-models.md`).** Metadata calls, parameter binding, types, TLS and sign-in on SSRS and PBIRS recorded as tests; needs the Windows machine the Excel and SSAS work already needs.
- **Published semantic views written in semantic SQL (route R1).** The plain case, a Build view model, works today; `semantic/published/*.sql` with one-source and fixed-grain checks waits for a report-server user (plan 14a Q15).

## Suggested order

1. **Quick security fixes in place** (not shared work): Sync library install validation (SECURITY H1), Gateway read-only/pass-through/TLS key (H2-H4).
2. **00 + CI baseline** in the hub, then **04 Part A** (already in flight) as the first shared package.
3. **05 phase 1** (lexer + quoting) and **01 phase 1** (extract strict YAML): both small, both immediately fix known gaps.
4. **02** abstractions, then **06** (needs 02 and 05); **03** phases 1-3 in parallel (Gateway install hardening).
5. **05** dialect/type model, then **07** phase 0 (written strategy comparison) and onward.
6. **08** phases 1-2 (signed manifest + updater core) once 03 exposes `/version` and drain; service swap after 03 phase 4.

Parallelisable: 01, 02 and 05 have no dependencies on each other; 03 and 04 can proceed independently once 02/05 minimums exist.

## Cross-cutting conventions for all shared packages

- Independent SemVer per package; public API baselines (`PublicApiAnalyzers`); changelog per package.
- Central package management, SourceLink, deterministic builds, nullable on, warnings as errors in new projects.
- Each package ships a README with the API contract; consumers should not need to read internals (agent-friendly).
- Strangler migration: adapters in products first, delete duplicates only after parity tests; never a big-bang rewrite.
- Each plan's conformance/golden tests live with the package and run in the hub's `contract.yml` against all three products.
- Security acceptance criteria in each plan map to `docs/security-review.md` findings and are verified by tests, not review alone.
