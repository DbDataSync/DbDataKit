# Plan 30: one way to publish, what is left

Status: **in progress** (audited 2026-11-09, re-audited 2026-11-12: PB01 built; PB05 built for the runner's versions and, through the Gateway's management API, for the serving kinds, with the runner's and the Gateway's models screens; PB02 built for the runner and the Gateway (the library with a per-kind hook, the runner's routes on it, the Gateway's mount and its hooks for the serving kinds, the client library, Build's `ProxyPublisher` on it; the apps command and the Workspace publish are not moved), PB03 built except the approver's second signature (signatures, the trust store, the Publishers screens, instances verifying at preparation, the runner on the trust store), PB04 not built; PB06 built: the library, the runner's command and the console's action). What is built (the `definitions` module with stage and activate, bindings per channel, per-instance status, the registry of kinds, artifacts by hash, signatures and the shared HTTP API for the runner's `integration` kind, `dashboard` and `report` through the registry) is described in [docs/publishing.md](../publishing.md). This plan holds the unbuilt work: the serving side still publishes through per-kind endpoints. Direction decided by the owner on 2026-11-04 and kept below as the decisions the slices serve. Runner-side slices are in [plan 28a](28a-runner-slices.md) (R15 to R19, built for the `integration` kind).

## Decisions (owner, 2026-11-04), still binding

1. **One publish API** for every kind and every target, with a registry of kinds. The per-kind endpoints (`PUT /api/v1/data-sources/{name}`, `/api/v1/semantic-models/{name}`, the apps command's own publishing) are removed when the shared API covers them (a clean break that names the route).
2. **Artifacts are content-addressed payloads**, apps included; **stage, then activate**; **bindings per channel**, outside the version; **per-instance applied status**.
3. **Versions are kept until an administrator prunes them**, through an API and a screen that show what is active, staged, previous, each instance's status and what pruning would remove.
4. **Promotion between groups** (test group to production group) is a deploy of the same version to the other group: artifacts are sent by hash, bindings are that group's own. **No activation at a set time** for now.
5. **Code is published compiled, with its source**; the compiled code runs, recompiling on the instance is an option, off by default. **Signatures:** the publisher signs the manifest (Ed25519, as the update system signs releases), each group keeps a trust store of publishers per kind, every instance verifies at preparation, **approvals of trusted code are signed too** (a second signature with the approver's key from the identity home); required by default, an administrator may allow unsigned versions for a kind as a recorded choice. **Packages** are published as the whole `.nupkg` closure by hash, so a runner needs no feed. Built for the runner; the serving side is below.
6. **Apps are published file by file** (the manifest with a list of files; only files the target lacks are sent) and **served from a local disk cache** filled when the instance prepares the version (hash and signature checked), with an in-memory index, compressed copies of text files and the hash as `ETag`; the state database is not read to serve a file.
