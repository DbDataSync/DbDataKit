# Release notes: what has changed behaviour since the last release

Written as each slice of plan 13 lands, so the first suite release does not rely on anyone's memory. Each entry says what to do about it. Add
to it in the pull request that makes the change; a release moves the entries into its notes and empties this file.

## DbDataSync

- **Secrets are in a new store and are set again.** Connection passwords and the state database's password were in the operating system's
  credential store (through `ClrKernel.Core.Secrets`) under `dbdatasync:...` names. They are now in an encrypted file store, `secrets/` under
  the repository root, under `dbdata:sync:...` names, and nothing is imported. Set each connection's password again (save the connection
  with its password, or `dbdatasync secret set dbdata:sync:connection:<name> <value>`) and the state database's
  (`dbdata:sync:config:stateConnectionString`). `secrets/` is added to the repository's `.gitignore`; back it up with its key. Names are
  lower-cased, so two connections whose names differ only in case share a password. The environment fallback is now
  `DBDATA_SECRET_DBDATA_SYNC_CONNECTION_<NAME>` (was `DBDATASYNC_SECRET_DBDATASYNC_CONNECTION_<NAME>`); `DBDATASYNC_SECRETS_FILE` is gone. (A04, A05)
- **Connections are `connection/1` files, and the old form is refused.** `config/connections/<name>.yaml` is now the shared connection format that the Proxy and Build use: `schema: connection/1`, `name`, `engine`
  (`sqlserver`, `postgres`, `mysql`, `oracle`, `duckdb`, `flightsql`, or a driver id), `address` (host, port, database) or `connection_string`, `auth` (`sql` with `user` and
  `password_secret: secret:dbdata:sync:connection:<name>`, `integrated` or `none`), `timeouts`, and Sync's own settings (`segmentOrder`, `properties`, `scripts`, `hooks`, `testQuery`, and `database` with a `connection_string`)
  under `extensions.sync`. A repository that still has the earlier files (`driverType`, `host`, `authMode`, `schemaVersion`) fails to load its connections, with a message that names every such file and the new form
  (`dbdatasync config check` and the Connections page show it). **Rewrite each file by hand, or delete it and create the connection again**; nothing is converted, and the stored passwords keep their names so none needs setting again.
  A connection name must now start with a letter and be at most 64 characters (it was any letters and digits). The API and the screens are unchanged. See `DbDataSync/docs/configuration.md`, "Connection files". (E01)
- **Every config file needs a `schemaVersion`, and unknown keys are an error.** (Connection files carry `schema: connection/1` instead, see the entry above.) A file without one, or with an older one, is refused with a
  message naming the file. The retired per-stage `parallelism` keys under `reader` and `writer` in a replication's `task.yaml` are refused,
  naming each key: delete them. (A02, A03)
- **Column types for some engines changed.** Oracle `uuid` stays `varchar2(36)`. Oracle `NUMBER(n,0)` up to 18 digits is read as an integer
  type. MySQL's time-zone timestamp is created as `timestamp(s)` (it ends in 2038). Postgres creates `timestamp(6) with time zone`.
  DuckDB's unsigned integers are read as the next wider signed type. (A07)
- **The command line has new names.** `dbdatasync serve` is `dbdatasync server run`, `setup` is `server setup`, `config cert|secret|library|driver ...` are `cert`, `secret`, `library` and `driver` (`config check|get|set`
  stay), and `health` is `health check`. The old forms exit 2 and print the new one. The Windows service, the systemd unit and the Docker image run `server run`, so **run `service install` again** on an
  existing installation (a service still registered with `serve` cannot start), and update container health checks to `health check`. `invite`, `update`, `launcher` and `tool` are unchanged for now. (C06)
- **SQL Server and PostgreSQL connections verify the server certificate by default.** The built-in `TrustServerCertificate=true` is gone: SQL Server connections are encrypted (`Encrypt=Mandatory`) and the
  certificate is checked, and PostgreSQL uses `SSL Mode=VerifyFull` (Npgsql's default was `Prefer`, which did not verify). A server with a self-signed certificate needs `TrustServerCertificate=True` in the
  connection string or in the connection's properties; a PostgreSQL server without TLS needs `SSL Mode=Disable` (or `Require`, which encrypts without verifying). `Encrypt`, `SSL Mode` and `Root Certificate` in a
  connection string or in properties are still honoured. A connect timeout in properties still wins. Any other property the shared policy reserves (credentials, host and database keys, `Application Intent`,
  `Multi Subnet Failover`, `Options`, `Search Path`, command timeouts) is now refused with a message naming it; put it in the connection string instead. (A08)
- **Sync commands accept `--format json`.** `server`, `service`, `cert`, `secret`, `library`, `driver`, `config` and `health` print one JSON document (`schema`, `command`, `exit_code`, `ok`, `data`, `messages`, `errors`); an unknown command now exits 2 with "'x' is not a command" (it was 1 with "Unknown command 'x'"). (C07)
- **The Docker image serves https on 8443, not plain http on 8080.** Like the Build, Proxy, Store and console images, it makes a self-signed certificate in the volume (`tls/dbdatasync.pfx`) on its first start and serves
  `https://0.0.0.0:8443`; its health check is `dbdatasync health check --url https://127.0.0.1:8443`. A client, script, port mapping (`-p 8080:8080`) or health check that used `http://localhost:8080` gets a refused
  connection: use `-p 8443:8443` and `https://` (`-k`, or trust the certificate; a console pins it when it pairs, and a Sync server on https now announces itself to a console, so `dist/compose/sync.yml` pairs the two).
  The image no longer sets `DbDataSync__App__AllowInsecureHttp=true`. To run behind a proxy that ends TLS, override the entrypoint to `dotnet /app/DbDataSync.Cli.dll server run --url http://0.0.0.0:8080` and set
  `DbDataSync__App__TrustedProxies` (the command is in `docs/install.md`). A server started with an `https://` address and no configured certificate now makes the managed one (`dbdatasync cert new-self-signed --file`'s file) instead of
  failing at the first request; if it cannot, it exits 1 with a message naming `tls/dbdatasync.pfx`. (L08)
- **Database errors show a fixed message and the engine's code, not the driver's text.** A failed connection test, run, preview, provisioning step or reconcile now reports for example
  `The login was rejected. [sqlserver 18456]` or `The server could not be reached. [postgres 08006]`; a run's stored error detail is empty for a driver failure. The driver's own text, with
  secrets scrubbed, is written to the server log. Set `Diagnostics:DriverDetails` to `true` (environment `Diagnostics__DriverDetails=true`) to append it to the response and keep it in the run
  detail again. Sync's own validation messages are unchanged. (A10)
- **MySQL, MariaDB and Oracle connections are verified and encrypted by default.** Like SQL Server and PostgreSQL before them, they are built by the shared composers. MySQL and MariaDB now use `SSL Mode=VerifyFull`
  unless the connection string or `properties` name another `SSL Mode` (`None`, `Preferred`, `Required`, `VerifyCA`); `SSL CA` is the root certificate. An Oracle connection given as a host, port and service name is written as
  `tcps://host:port/service`; put `Encrypt` = `false` in `properties` for a listener that has no TLS. A connection string is still the base and its own data source (an alias, a descriptor, a wallet) is not rewritten.
  Credential, host, port, database and timeout keys in `properties` are refused with a message naming the key (Oracle's `Data Source` included). Failures from these engines now show the shared classified message. (A09)
- **`dbdatasync ui mcp` serves the commands that read to an agent** (Model Context Protocol on standard input and output). Each command that only reads is a tool that returns its `--format json` document; `--allow-writes` also offers the ones that change files. Secrets cannot be set and installed libraries cannot be loaded through it. (C08)
- **Sync's settings are in `server.yaml`, and the old settings files are refused: set the server up again.** `dbdatasync server run` reads `server.yaml` in the repository root (the file `server pair` already keeps the server's
  identity and paired clients in), the environment and the command line, and nothing else. The `dbdatasync.config.yaml` of earlier releases and any `appsettings.json` (or `appsettings.<environment>.json`) in the repository
  root, in its `config` folder or beside the executable are no longer read and not converted: the server, `server setup` and `config check` stop with a message that names the file. Sync no longer ships an `appsettings.json`, so
  after upgrading over an old installation **delete the `appsettings.json` left beside the executable**. To set up again: move the old file away and run `dbdatasync server setup`, or write the `DbDataSync:` settings by hand in
  `server.yaml` (the key names are in `docs/configuration.md`; many were renamed in an earlier release, so the old file cannot be copied as it is). The migrations that rewrote old key names and pointed at the per-user folder
  earlier releases used as the default are gone, so an install still in that per-user folder is refused the same way (name the folder you want with `--repo`, or set up at the machine-wide default). Environment variables
  and command-line flags are unchanged. (E04)
- **Sync has no sign-in of its own to set up: `dbdatasync invite`, `FIRST-RUN.txt` and `Auth:Passkeys:*` are gone.** People and invitations are the dbdatakit console's (`dbdatakit user invite`), and the console reaches
  a Sync server with a signed token (`dbdatasync server pair`). `dbdatasync invite` now exits 2 and says so. The server no longer writes `FIRST-RUN.txt` (delete one an older install left in the repository root) and
  `server setup` no longer offers passkeys or "Reissue invite"; `config check` no longer has a "First admin" line, and its "Auth" line says the server is signed in at the console. The settings
  `Auth:Passkeys:Mode`, `Auth:Passkeys:RelyingPartyId`, `Auth:Passkeys:RelyingPartyName`, `Auth:Passkeys:Origins` and `App:AlternateUrls` (which only widened the passkey origins) are removed and **refused**: a `server.yaml`,
  environment variable (`DbDataSync__Auth__Passkeys__...`) or command-line flag that still sets one stops `server run` and `config check` with a message that names the setting. **Delete those settings before
  upgrading.** Windows group sign-in (`Auth:Windows:*`) and network trust (`Auth:Network:*`) are unchanged, for a client that calls the API directly. Passkeys registered with the old server sign-in stay in the state database and are not used. (X05)
- **Changing a user's role, or disabling a user, now works when the state store is on SQL Server or PostgreSQL.** It failed with a syntax error on those two engines (SQLite was unaffected). (U04)
- **MySQL, MariaDB and Oracle table columns are read by the shared catalog readers.** MySQL and MariaDB column types now carry the full engine type (`bigint unsigned`, and MariaDB's `bigint(20) unsigned`; `text` instead of `text(65535)`), so an unsigned column is no longer mistaken for a signed one. Oracle reports the same types as before. (A12)
- **Work that was waiting in the queue is cancelled when the state database is upgraded, and a bulk load that was waiting must be asked for again.** The work queue and the run lock are now the shared ones (`DbDataKit.Scheduling`), so the first start after the upgrade replaces the two old tables. A run that was still queued is marked Cancelled with "Cancelled when the work queue was upgraded; ask for it again."; scheduled passes are queued again by the scheduler on its next tick, so only an on-demand reload or an initial load that had not started needs doing again. Runs that were running keep their record and are settled by the startup reconciliation as after any restart. Stop the workers before upgrading if you can. (M03)
- **New: whether a reload's segments run one at a time or together is a setting.** `segmentOrder` (`oneAtATime`, the default and what Sync has always done, or `together`) can be set on a connection (the one the mapping writes to), a replication or a table mapping, and a bulk load request may carry it; the most specific wins. Nothing changes until it is set; there is no screen for it yet. (M03)
- **New: `dbdatasync server pair|clients|unpair`, so a console can manage this server.** `server pair` makes a single-use code; a console pairs with it (`dbdatakit instance add`) over https, pinning this server's certificate, and then calls the API with a short-lived signed token that names the person. The token's roles become Sync's two (administrator where it holds admin, viewer where it can read), limited by the ceiling the pairing code carried; pairing and unpairing take effect on the next call. The clients are listed in `server.yaml` in the repository root, which is also where this server's instance id is kept. Behind a proxy that ends TLS, set `DbDataSync:Management:CertificateFingerprint` to the fingerprint the proxy presents. Signing in to Sync itself is unchanged. (U08)
- **Passkeys now work in a browser.** The options sent to the browser spelled two values with the C# names (`PublicKey`, `None`) where WebAuthn needs `public-key` and `none`, so `navigator.credentials` refused them. They are now sent as the passkey library writes them. If you could not register a passkey on a Sync install, this was why. (U07)
- **`Microsoft.AspNetCore.Authentication.Negotiate` is 10.0.13** (GHSA-vrrp-6v32-2p8g, an elevation-of-privilege fix). Rebuild and redeploy to take it. (U07)
- **The table picker no longer lists the engine's own tables.** For SQL Server and PostgreSQL connections the list of tables in the mapping editor comes from the shared catalog reader: base tables of every schema, without views and without system objects. Before, a SQL Server database that uses change data capture also offered `dbo.systranschemas`, and PostgreSQL offered the `pg_catalog` tables. Nothing else about a mapping changes; a mapping that names one of those tables still runs. (A11)
- **Sync no longer serves a web app: its screens are the console's.** Open `dbdatasync server run`'s address in a browser and you now get a plain-text
  message instead of the screens: `/` answers 200 with it and any other address except the API (`/api`, `/hubs`, `/version`, pairing) answers 404 with the same
  words, so an old bookmark is told what changed. Add the server to a `dbdatakit` console (`dbdatasync server pair` on the server, then the console's Servers page or
  `dbdatakit instance add <address> --code <code>`) and open it there, at `/servers/<id>`; Sync's own sign-in screen and its users and invitation pages are the console's now. To have
  the message name the console, set `DbDataSync:Console:Url` (environment `DbDataSync__Console__Url`, or `DBDATAKIT_CONSOLE_URL`) to its address. The API, the realtime hub, `/version`, health and
  pairing are unchanged. The docs that were served at `/docs/*.md` by the server are in the console now (its Docs entry, and each Sync screen's Docs link, at `/docs/sync`). Packages and the container image no longer
  carry `wwwroot`; `tools/install-local-tool --no-spa` and `-p:SkipWebBuild` are gone. (U11)

- **A load into SQL Server or PostgreSQL that used to store a reinterpreted value now fails.** Sync's staging refuses, before writing, a value whose type the
  target would store as something else, with a message naming the table, the column, its type and the value's type (never the value): `Staging into public.invoices: column 'Due' (date) cannot take a value of type System.Int32 from the source ...`.
  The pairs: PostgreSQL `date` from `int` or `ushort` (stored as days since 2000-01-01), `time`, `timestamp` and `timestamptz` from `uint` or `long` (microseconds since 2000-01-01), `text` and
  `character varying` from `byte[]` or a stream (the bytes as characters); SQL Server `tinyint`, `smallint`, `int` and `bigint` from a character (its code point, `'a'` as 97), and SQL Server `varchar` and `nvarchar` from a `DateTime` or `DateOnly` (the client formats the date as text such as `03/17/2024 09:41:22`: lossy, and dependent on the culture of the machine that runs Sync; decided 2026-10-30). **To fix a date sent into a text column,** add a Transform to the mapped source column that formats the date or time as the text you want (for example `yyyy-MM-dd HH:mm:ss`). **To fix the others,** change the mapped source
  column, or its `Transform`, to a type the column takes (a date or timestamp for a date column; `CAST(... AS ...)` or a conversion in the Transform; text for a text column). What is still stored as before:
  anything that is only a question of the value, such as `1.5` into an integer column (rounded on SQL Server, truncated on PostgreSQL), a number out of range, a string that parses as a date or a number, and a
  string too long for its column. Cost: one type comparison per cell, as before; no change in speed. (A14b)
- **Package hashes of scripts are pinned in the configuration repository.** A `.csx` script's `#r "nuget: Id, 1.2.3"` packages are recorded, with their SHA-512, in `scripts/<name>.lock` beside the script (a library's are in `libraries/<id>/library.lock`
  already, and a compiled driver's in `drivers/<id>/driver.lock`; same file format). A configuration repository without lock files keeps working: the first time a script with packages is compiled (validated, saved, tested or run) its lock file is created, and saving the script
  commits it; a lock file created by a run is not committed by Sync, so **commit the new `scripts/*.lock` files** of an existing repository. From then on a package whose bytes differ (another machine, or the feed changed under the same id and version) is refused with a message naming the package, the version
  and the lock file; if the change is expected, delete that package's line from the lock file and validate again. A stored package that matches its pin needs no network. The lock reader is strict: a key other than `schema` and `packages` stops the load,
  naming the file and the key. Deleting a script deletes its lock file. (S12)

## DbDataBuild

- **A copy now stops on two values it used to let through.** A copy converts values with the shared converter, and writes them with the shared bulk writers. A `DateTime` that has a time of day, copied into a column the model declares `DATE`, used to lose its time silently; it is now an error that names the column. A string longer than a declared `VARCHAR(n)` is refused at the copy, naming the column, where the destination used to refuse it. Declare the type the origin really holds (`TIMESTAMP`, a longer `VARCHAR`) or cut the value in the read. Nothing else changes: the same rows arrive in the same tables, and the statement log is as before. (B08)
- **`dbdatabuild ui web` is gone.** The DbDataKit console replaces it: run `dbdatabuild server run --project .` (loopback by default), pair a console with it and open the project there. Scripts that started `ui web` fail with an unknown command. The MCP server's `show` tool still serves its page. (R09)
- **Login variables are `DBDATA_BUILD_<CONNECTION>_<READ|WRITE>`.** The old `DBDATABUILD_*` names are not read, and the
  `secret:dbdata:build:connection:...` fallback is gone. A connection name with characters other than letters and digits has underscores in
  its variable (`my-dw` is `DBDATA_BUILD_MY_DW_READ`). A connection with no variable set is DDB-501, naming the variable. (B02)
- **Connections are files, `connections/<name>.yaml`, and a `connections:` in `dbdatabuild.yml` is refused.** Each is a `connection/1` document (`schema: connection/1`, `name` equal to the file name, `engine` the driver alone, optional `dialect` and `access: readonly`, and the tool's own settings under `extensions.build`: `version`, `parameters`, `max_parallel`, `tracking`, `title`, ...). A project whose `dbdatabuild.yml` still has `connections:` stops with `DDB-621` naming `dbdatabuild.yml` and every connection in it; nothing is converted. Move each entry: `shop: { engine: readonly postgres, parameters: { store_id: E01 } }` becomes `connections/shop.yaml` with `engine: postgres`, `access: readonly` and `extensions: { build: { parameters: { store_id: E01 } } }` (keywords of the old `engine` other than the driver are `access` and `dialect`). A file that is not right is `DDB-620` naming the file and line; a connection file holds no address, login, TLS or timeout setting, and the login is still `DBDATA_BUILD_<NAME>_<READ|WRITE>`. The five templates are rewritten, so a project made from one before needs the same move. `dbdatabuild project agent-kit` writes `schemas/connection.schema.json`. (E03)
- **The statement log has a new line format, and still holds the values.** `.dbdatabuild/statement-log/*.jsonl` is written by the shared write gate's log: each parameter of a line is `{"name":..., "type":..., "hash":..., "value":...}` where it was `{"Name":..., "Value":...}`. The `value` is still the value in the clear, as before (nothing was changed to hashes; `hash` is an extra, salted per run, that matches equal values within a run). The file is created readable by its owner only on Linux and macOS. The lines for a lock and for the rollback after a failed statement have the kinds `Lock` and `Control`, and the rollback line has no text. Tools that read these files by the old keys need the new ones; retention (`retention.statement_logs_days`) is unchanged. (B06, B07)
- **New: `dbdatabuild server`, a Build server a console can manage.** `server run` serves the projects registered with `server project add|remove|list|pull` (a folder, or a git repository the server clones and keeps at a branch) over HTTPS with a management API; a console pairs with a single-use code (`server pair`, `server clients`, `server unpair`). The API runs the project's commands (all but `ui ...`), each in a child process, for a caller whose signed token carries the role the command needs: viewer reads, author changes the project's files, operator refreshes data, approver applies a plan to a target, admin changes the tracking tables. A plan applied through the API is recorded in the tracking tables (`migration_log.applied_by`, `ddl_log.invoker`) as the person and their console ("Ada via Main console"). `server run --read-only` offers only the commands that change nothing. Nothing is on unless you start it; the command line and the other interfaces are unchanged. `dbdatabuild secret set|list|delete|check|rotate-key|export|import|protect --repo <server directory>` keep the server's logins (`dbdata:build:connection:<connection>:read|write`), which reach each command as `DBDATA_BUILD_<CONNECTION>_<READ|WRITE>`; the read and write logins are separate and one never stands in for the other. `service install|uninstall|status|start|stop|restart|doctor|unit` register `server run` with Windows or systemd, and `health check` is what the container image's health check runs. The image is `DbDataBuild/Dockerfile` (build it from the repository root). (R01, R02, R04, R05, L02)
- **New: `server run --scheduler` runs refresh plans that declare a `schedule:`.** Off unless asked. A plan runs as `connection refresh <connection> <plan>` using the connection's stored **write** login, so a scheduled plan on a connection with no stored write login fails and the server's log says so. A schedule added to a project is not run at once, and times missed while the server was down run once. (M08)
- **New: a project can have a git credential, and a push shows the pull request link.** A remote that needs a login (GitHub, Azure DevOps, GitLab, HTTPS with an access token as the password) is reached with one credential per project, used for every author's push and for the server's own clone and pull. Store the token in the server's secret store under `dbdata:build:git:<name>` (`dbdatabuild secret set dbdata:build:git:sales`, prompt or stdin; the value is the token, or `<user>:<token>` when the provider wants a particular user name, otherwise the user is `oauth2`), then `dbdatabuild server project add sales --git <https address> --git-credential sales`, or add `git_credential: secret:dbdata:build:git:sales` to the project's entry in `build/projects.yaml`. Nothing changes for a project without one. The token is never returned, logged or written outside the encrypted store (it is not in the remote's address or `.git/config`); a refused push names the credential, and a missing secret names itself and the command that sets it. SSH keys are not supported for now. After a push the Edit tab shows an "open a pull request" link for a remote at github.com, dev.azure.com (or `*.visualstudio.com`) or gitlab.com; any other remote shows none. (W12)
- **`connection status` and `connection monitor` decide overdue and slow by exact time** (the shared health rules) where they compared whole seconds, so a run that began 3600.5 seconds ago is now overdue under `expected_every: 1h`. (M09)
- **Build secures its connections the way every product does: encrypted, certificate verified, unless the connection file says otherwise.** A SQL Server or PostgreSQL login string from `DBDATA_BUILD_<NAME>_<READ|WRITE>` used to be taken as written, so `Encrypt=False` or `TrustServerCertificate=True` in it was enough. Now the connection file's `tls:` block is applied over the string, and a file with no `tls:` (or a connection named after its engine with no file) encrypts and verifies. A server with a self-signed certificate needs `tls: { trust_server_certificate: true }` in `connections/<name>.yaml` (and one without encryption `tls: { encrypt: false }`); the keys are `encrypt`, `verify`, `trust_server_certificate` and `ca_file`, and the connection file's schema lists them. Without it Build reports a TLS or certificate failure when it connects. A read login also asks for read-intent and is named `dbdatabuild-read` (write: `dbdatabuild-write`) as before. ODBC, DuckDB and Flight SQL logins are unchanged. (B02)

## DbDataProxy

- **The console shows a Proxy.** A Proxy paired with the console opens inside it: overview, data sources (edited as their `connection/1` files), users and sign-in, the certificate, activity (sessions, running queries with cancel, limits, lockouts, failures) and the history of the configuration. The Proxy now reports its product as `dbdataproxy`, as the other servers do. The JWT claim mappings can be edited there too (the key, authority and audience stay in `proxy/auth.yaml`). (P08, P09)
- **The console shows where a Build connection stands and deploys.** A project opened in the console has Compare (two tables by counts and digests), Status (the objects the models declare and whether they exist, drift, what a deploy would do), Plans (write a deploy plan, read every step, dry-run it, then approve and apply it; risky and destructive steps need to be allowed in the page) and Sample (the models run on generated rows). Applying needs the `approver` role, so pair a Build server with the console using `--max-role viewer,author,operator,approver` for administrators to approve there. (R08)
- **New: a management API for a console (off unless asked for), and `server pair|clients|unpair`.** `management: { enabled: true }` in `server.yaml` opens an https listener on port 8816 (loopback unless `management.address` says otherwise) that is never the Flight port; a console pairs with a single-use code from `dbdataproxy server pair` and then reads the server's identity, its effective configuration (secrets masked, with where each value came from) and validates a candidate configuration without writing it. `management.localChannel` also answers the command line on this machine. `server.yaml` gains `instanceId` and `pairedClients`, which the pairing verbs write; leave them to the verbs. (P03)
- **Proxy's settings are YAML files, and `appsettings.json` is refused.** The settings are in the `config` folder of the data directory: `server.yaml`, `proxy/auth.yaml`, `proxy/users.yaml` and one `connections/<name>.yaml` per data source (keys in camelCase, except the data sources, which are `connection/1` files with snake_case keys and the proxy's own settings under `extensions.proxy`; `config.example/` beside the executable shows each file). A data source file in the earlier layout (`provider:`, `connectionString:`, no `schema:`) is refused with a message naming it: rewrite it as a `connection/1` file, with the password as `auth.password_secret` (a reference such as `env:ERP_DB_PASSWORD`) instead of in the connection string. An `appsettings.json` in the data directory, its `config` folder or beside the executable stops the server (exit 2) with a message that names it; nothing is converted, so move the `Proxy` section's keys into the new files and delete the old one. Environment variables and the command line override as before. `config check|show --file` takes a config folder or the path of its `server.yaml`. (P01)

- **Parameterised queries work from the Apache .NET Flight SQL client.** A prepared-statement handle was random binary data, which that client turns into a string and back, so the proxy no longer recognised it and answered `NotFound: Unknown or closed prepared statement`. Handles are now 32 hexadecimal characters; clients need no change. (A18)
- **The executables are lower case.** `DbDataProxy.exe` is `dbdataproxy.exe` and the 32-bit worker `DbDataProxy.Worker.exe` is `dbdataproxy-worker.exe` (`worker\dbdataproxy-worker.exe`); the Docker image runs `dbdataproxy.dll`. The
  Windows service is registered as `dbdataproxy` by default (the service control manager ignores case, so `service install` updates an existing registration in place, and its virtual account is the same one).
  A script, a shortcut, an `ExecStart` or a `worker` setting that names the old file must be changed. The data directory is still `DbDataProxy`. (C03)
- **The command line is `dbdataproxy <noun> <verb>`, and there is no default command.** Running `dbdataproxy` with nothing prints the help and exits 2; `dbdataproxy server run` runs the proxy. The Windows service,
  the generated systemd unit and the Docker image now run `server run` (re-run `service install` to update an existing service, which adds the argument to its command line). Renamed: `hash-password` is
  `secret hash` (the password comes from a prompt or standard input, no longer an argument), `protect-secret` is `secret protect`, `query` is `query run`, `--healthcheck [url]` is `health check [--url url]`,
  and `install`/`uninstall` are `service install`/`service uninstall` (the MSI and `install.ps1` call the new forms). The old forms are not commands. Anything that starts the proxy with options only
  (`dbdataproxy.exe --Proxy:Listen:Port=9000`) must say `server run`. (C04)
- **`dbdataproxy ui mcp` serves the commands that read to an agent**, the same way. Secrets and `query run` (which returns rows) are never offered. (C08)

- **New: semantic queries.** A `semantic:` section in `server.yaml` names catalogs (semantic models) and the data source for each of their sources; a client then sends a JSON semantic request or semantic SQL as a statement with `x-datasource: semantic:<model>` and gets the combined result as an Arrow table, with the engine's status, warnings and remaining steps in the schema metadata. The scans run as the signed-in client against the mapped data sources, under the same access, classifier and limits as their SQL. SQL Server, PostgreSQL and DuckDB sources; Analysis Services (DAX) sources run on Windows when the model gives their connection (`ssas:` under the model; the connection is the server's, not the caller's, so the access rules of the data sources do not apply to it). Nothing changes for a server with no `semantic:` section. (J10)
- **New: publish semantic models to a running Proxy.** `PUT /api/v1/semantic-models/<name>` (administrator, or a paired Build server for its own models) validates the catalog and its source mapping, keeps every version, switches atomically and rolls back with `POST .../rollback`; published models survive a restart. Also fixed: a catalog source with several fact tables ran its second and later facts against a data source of the wrong name. (J13)
- **New: Build publishes a semantic model to a paired Proxy.** `POST /api/v1/projects/{project}/proxies/{proxy}/publish-model` (approver) sends the connections the model reads as read-only data sources and then the model; the Proxy keeps versions and rolls back. (J12)
- **Changed: Sync's database picker on SQL Server** lists only databases the login can open (the shared catalog reader's rule); it used to list every database after the four system ones. (A11)
- **The Proxy serves PostgreSQL (`engine: postgres`).** A data source of `engine: postgres` takes an Npgsql connection string (`Host=...;Database=...`; the `address:` form stays SQL Server only) and answers queries, catalog metadata and parameters like the others, with the read-only classifier (the PostgreSQL deny list: `COPY`, `DO`, `pg_read_file`, `lo_import`, `dblink`, `set_config`, and the rest) and the concurrency limits applied, and a source that cannot write also sets `default_transaction_read_only=on` on its session. It can pass the caller's own database credentials through (`pass_through: true`). TLS is `SSL Mode=VerifyFull` unless the string says otherwise; a string with `SSL Mode=Require` or `Disable` is named in the startup warning like a SQL Server opt-out. Behaviour to know: a `?` is a marker, so PostgreSQL's `jsonb` `?` operator must be written `jsonb_exists(...)`; an array column arrives as its JSON text; a `numeric` wider than .NET's `decimal` fails the query (cast it). Build's publish now accepts PostgreSQL connections, and the console's Build Publish page says so; `fabric` connections are still refused with the 409 that names the engines a Proxy serves (plan 13a, P12, which records why). Nothing to do for an existing install: no setting changes. (P12)
- **The Proxy serves an upstream Flight SQL server (`engine: flightsql`).** The data source's connection string is the Flight SQL login value Build already uses (`grpc+tls://host:port;token=...`, or `;user=...;password=...`, with `header.x-datasource=<name>` to choose a data source of an upstream Proxy), read by the shared `DbDataKit.Connections.FlightSql` client. It is read only (`allow_writes` is refused at load), takes no pass-through credentials, and a statement is checked with the ANSI deny list; the read-only classifier and the concurrency limits apply as for any source. `token_command` and `token_env` are **refused** in a Proxy data source (a program or variable the data source's author named must not run or be read on the Proxy's host); put the token in `token=` as a secret reference. Metadata is read with `INFORMATION_SCHEMA` queries on the upstream server. Build's publish now accepts Flight SQL connections whose login follows that rule and refuses others in a sentence before anything is sent. (P12)

- **New: `dbdataproxy datasource adopt <name> <client id or name>`** hands a data source made by hand, or by another client, to a paired server client (a Build server), the same call as `POST /api/v1/data-sources/{name}/adopt`, over the running proxy's local channel (`management.localChannel: true`); the audit line names the operating-system user. `--format json` works. A new `GET /api/v1/clients` (administrator) lists the paired server clients. The console's Proxy data sources page shows who manages each data source and has a Hand over button, and the Build Publish tab's adopt offer has a button for administrators. (T13)

## dbdatakit (the console)

- **New: the `dbdatakit` console.** One web interface for the DbData servers, a separate program from them: `dbdatakit server run` serves it over https (a self-signed certificate it makes in its directory; `--listen https://localhost:8480` by default), the first administrator redeems the invitation in `FIRST-RUN.txt` by making a passkey, and `dbdatakit user list|invite` manage who can sign in. `dbdatakit instance add <address> --code <code>` pairs it with a server (the code is made on the server with `server pair`); `instance list|remove|rotate-key` manage the pairings, and the Servers page shows each server's state. Calls to a server go through the console's `/relay/<server>/api/...`, which signs a short-lived token naming the person. Nothing is on unless you start it. (U07, U12, U08)
- **Staging loads go through the shared bulk writers; nothing to do.** SQL Server's `SqlBulkCopy` staging and PostgreSQL's binary `COPY` staging now run in `DbDataKit.Transfer.SqlServer` and `DbDataKit.Transfer.Postgres`.
  The staging tables, their names, their columns, the error text for a value `COPY` cannot write, and the speed (measured within noise of before, see `DbDataSync/architecture/benchmarks/staging-baseline.md`) are unchanged; no file, log
  or wire format changes. One difference: SQL Server `date` and `time` values that a source delivers as `DateOnly` and `TimeOnly` are converted to `DateTime` and `TimeSpan` by the shared writer before `SqlBulkCopy` sees them. (A14, A15)
- **A staged value of a type the target column never takes now fails with one message.** On the SQL Server and PostgreSQL bulk staging paths, a value whose type the target engine refuses for every column of that kind (a `Guid` into an `int`
  column, a `DateTimeOffset` into `varbinary`) fails before it is written, with `Staging into <table>: column '<name>' (<declared type>) cannot take a value of type <type> from the source ...`, naming the table, the column and the type, never the value.
  Before, the same run failed with the provider's own message. What is stored and what is refused is unchanged for every value measured (the 1,900-cell tables in `DbDataSync/architecture/staging-value-types.md`); a run that failed still fails, a run that
  succeeded still succeeds; only the text and the exception type (`StagingValueException`) differ. (A14a)
- **Sync scripts are `.csx` files.** A script `config/scripts/<name>.cs` with an `entryType` in its manifest is no longer read: Sync stops with a message naming the file. Rename the code to `<name>.csx`, remove `entryType:` from `<name>.yaml`, and end the script with an expression that is the implementation, **with no semicolon after it**: `new MyTransform()`. A script may now `#r "nuget: Id, 1.2.3"` packages and `#load` other scripts of `config/scripts/`. (S07)

- Servers can announce themselves to a console (`DBDATAKIT_CONSOLE_ANNOUNCE_URL`, `DBDATAKIT_ADVERTISE_URL`) and wait to be confirmed (`dbdatakit instance pending|confirm|reject`); the console takes announcements on a private plain-http port (`--announce-listen`, `DBDATAKIT_CONSOLE_ANNOUNCE_LISTEN`) that must not be published. `dist/compose/build.yml` runs a console with a Build server this way. The Servers page of the web app lists the waiting servers (name, address, when each last announced) with a Confirm and a Reject button each, for administrators; Confirm pairs with the certificate the server presents, so confirm only a server you recognise.

- The console's and the Proxy's state database can live on SQL Server or PostgreSQL: `--state-engine` and `--state-connection` (or `DBDATAKIT_CONSOLE_STATE_ENGINE` and `_CONNECTION`) for the console, `state:` in `server.yaml` for the Proxy. SQLite stays the default. Give each its own database; the password is a secret reference.
- **A console with an identity home refreshes roles inside a session and ends the home's session at sign-out.** The home's OpenID provider now issues refresh tokens (scope `offline_access`) and has an end-session endpoint (`end_session_endpoint` in discovery). A console signed in through a home asks it for the person's roles again every 5 minutes (a removed role applies without a new sign-in; the console's ceiling still lowers them), keeps the last roles for 10 more minutes when the home does not answer and then grants no role on any server, and signing out of the console sends the browser to the home to end their session there (which ends their other consoles' sessions at their next refresh). Register the console's `<public address>/` as a post-logout redirect address of its client at the home so the browser comes back. Local users are kept and unaffected. Two new state tables are added by append (`RefreshTokens`, `OidcClientLogout` at the home; `FederatedSessions` at the console); nothing to migrate. (U17)

- **The identity home maps Entra and Windows groups to roles (component only).** `HomeDirectory.MapExternalGroup` gives everyone whose last sign-in through a source (`entra`, `windows`) carried a group the roles you map it to on a server, a Build project of it or an app, added to what they hold otherwise; a removed mapping removes the role. Groups are compared ignoring case. **Nothing to do yet:** no host performs the Entra sign-in or administers mappings (serving layer, O06), so no install has mappings. The home's schema gains `GroupMappings` and `ExternalMemberships` (a new schema entry, appended; created at the next start). An unmapped group gives nothing. A person removed from an Entra group keeps the role until their next sign-in through Entra (open question D24). `OpenIdClient` now also accepts RS256 id tokens. (U18)
- **One account per person across every way of signing in; a new account needs an email address.** The address is the account's key (a Windows account's is its user principal name, `user@domain`), compared without regard to case: a local passkey user, a Windows account and a person who signs in through the identity home with the same address are one user (the same roles, and the same user id in a server's audit). A sign-in that would take an address another account already holds is refused with a message. **What changes for you:** (1) an invitation for a new user must say whose it is: `dbdatakit user invite --email <address>` (or `--user <id>` to give an existing user another way in), `dbdatasync invite --email <address>`, `POST /api/invites` with `email`, and the Users page asks for it; before this an invitation made without one now fails with a message naming `--email`, and the person's own entry at redemption is no longer used (only the first-run invitation, which nobody made, keeps what is typed, for display). (2) **Existing users keep signing in and keep their roles**, but their addresses were typed by whoever redeemed the invitation and nobody checked them, so none is matched on: the Users page marks them "unverified", and `dbdatakit user set-email --user <id> --email <address>` (or the Set button) sets the address an administrator vouches for; until then such an account is not joined to a Windows account or the home, and the same person signing in that way gets a second account. (3) A Windows account whose domain gives no user principal name cannot be a new account (a `DOMAIN\user` name is never turned into an address); one that already has an account signs in by its SID as before. (4) A person the identity home knows, whose verified address a local or Windows account holds, becomes that account **under the home's user id** (their passkeys, Windows accounts and sessions move with it), and then holds what the home gives them on every way in. The state database gets two new columns (`Users.EmailKey`, `Invites.Email`) and a unique index when the product starts; older databases are upgraded in place, nothing is rewritten. (U16)
- Publishing a Build connection to a Proxy works for every engine the Proxy serves (SQL Server, ODBC, DuckDB), not only SQL Server; a connection of another engine is refused with a message. A Proxy administrator can hand a data source made by hand to a paired Build server with `POST /api/v1/data-sources/{name}/adopt`; the Build console gains a Publish tab. A publish the Proxy refuses no longer leaves its login stored there, and a re-publish does not replace the stored login unless the Proxy accepted the data source. (T12)
- **New: the console's Connections page lists every connection and copies one to another server.** `/connections` lists the connections of each Sync server and the data sources of each Proxy (asked through the relay), and *Copy to...* creates a copy on another server (or on the same one under another name) as the signed-in person: the file is the same `connection/1` file everywhere, with `name` changed, `managed_by` and another product's `extensions.<product>` left out, and a password reference the target is to hold (a password is never copied). The target validates it with its own strict loader; what it refuses is shown with the line of each fault and nothing is written, and a name the target already has is a conflict, never overwritten. Sync takes a typed password for the copy (sent to that server only, stored under the copy's own reference). `POST /api/connections/copy` is the console's call. (E05)
- **New: Sync serves a connection as its file.** `GET /api/connections/<name>/file` (viewer) and `PUT /api/connections/<name>/file` (administrator; a whole `connection/1` file, the version it is based on, an optional password) read and write a connection as the file it is kept in, with the same strict checks as a file on disk and a save. Nothing changes for the existing `/api/connections` calls or the screens. (E05)
