## 2. The widget, and what is shared

1. **One widget vocabulary, one document, several layouts.** A widget is `{id, type, title, encodings, query, ...type options}`. A document (a `dashboard/1` or a `report/1`: two kinds on one shared core, section 3) holds a `widgets` map **once** and a list of **layouts** that place widget ids; the **widget schema is part of one shared core schema** that both kinds reference. The same map is what an assistant's inline answer, a portal home block, an app page and a pinned tile hold. **Layout is never part of a widget**: a layout places widgets and may set only the allowed per-layout options (section 3.1); it never changes a widget's type, encodings, query or formats.
2. **A widget carries a declarative query that matches what it draws** (owner, 2026-11-08; replaces "names a result and never computes"). `encodings` say what is drawn (a chart's x, y, color, column, row, tooltip; a matrix's rows, columns, values; a metric's value and compare; a table's columns). `query` says what to ask, in one of these forms:
   - `{semantic: {model, request}}`: a semantic request as `docs/semantic/query.md` defines it (`measures`, `attributes`, `filters`, `order`, `limit`, `segments`, `totals`, `timezone`);
   - `{semantic: {model, sql}}`: semantic SQL;
   - `{saved: name, params}`: a saved query (J26, J27), run as the viewer;
   - `{store: {model, entity, filter, sort, limit}}`: rows as they are (a table or an unaggregated chart);
   - `{ref}`: an already run result (an assistant's answer; no query).

   **Where computation lives:** in the query, on the server, under the viewer's permissions. **Not** in the chart spec: Vega-Lite `aggregate`, `bin`, `timeUnit`, `calculate`, `filter` transforms and expressions stay refused (the subset has none), so plan 16 section 2a's rule becomes **"no computation in the chart spec"**. A binned axis is a grain of an attribute in the request; a share is a catalog measure or a transform entry of the request; a metric's comparison is a second measure of the same request (previous period). Parameter values enter through J25's binding (`{param: name}`), so the same rows and request hash as the literal form hold.
3. **The query is derived from the encodings (`mode: derived`, the default) or hand-written (`mode: explicit`).**
   - **Derived:** the document holds the encodings and the parts a person chooses beside them: `model`, `filters`, `segments`, `order`, `limit`, `totals`, `timezone`, `params`. `DeriveRequest(widget, catalogRoles)` is a **pure function** (in `DbDataKit.Views`, .NET, because the request runs there) that returns the request: every encoded field that the catalog says is a **measure** goes to `measures`, every other encoded field to `attributes` (in encoding order, duplicates once); a chart's `column` and `row` are attributes; a matrix's `rows` and `columns` are attributes and its `values` measures, `totals.rows`/`columns` become `totals` (`subtotal_by`, `grand_total`) so the result holds the total rows the matrix shows (QIS's `totals_missing` cannot happen); a metric's `value` and `compare` are measures with no attribute; a table's columns split the same way; an encoding `sort` becomes `order` (and a sort by a measure adds it to the request); a missing `limit` takes the widget type's default (metric 1, chart 500, table 100, matrix 10,000) and **never** more than the request's 10,000. The result's fields are then named exactly as the encodings name them, so **what is drawn and what is asked cannot drift**: a field well changed in an editor changes the request in the same step.
   - **Golden tests:** `conformance/views/derive/` (built as that path, DBR03) holds pairs (widget JSON, catalog roles JSON, request JSON) for every type and every encoding (x=dimension, y=measure, color=dimension; y=two measures; a time attribute with a grain; a stacked bar; a matrix with column limit and totals; a metric with compare; a table with a sort on a measure); the .NET test compares byte-for-byte; the TypeScript editor, when it exists, ports the function and runs the same pairs. Roles come from the model's catalog (the descriptor already says measure or attribute, and `x_kind`).
   - **What a hand-written query may override:** everything about the request: it may use ad hoc aggregates, transforms, segments and `sql`, a saved query, or a Store read. The one rule is the **binding check**: every encoded field must be an output of the query (by logical name or alias), and the query must be a valid semantic request for its model. In explicit mode the document says `mode: explicit` so a reader and the editor know the encodings do not drive the request. An explicit `sql` is allowed only where the published model allows semantic SQL for the author (an administrator setting; the decision in section 12).
   - **Binding check, two levels:** at load, a **shape check** (encoded fields are named in the query: derived by construction, explicit by output names found in `measures`/`attributes`/aliases or a saved query's declared signature); at publish and at `app validate`, a **catalog check** against the model version the document depends on (the request validates through the engine's validator: `unknown_field`, `attribute_not_placed` and the other server codes surface as diagnostics with the document's file and line).
4. **The widget types** (the first set; adding one is a format change, section 10):

| Type | Encodings | Notes |
| --- | --- | --- |
| `metric` | `value`, optional `compare`, `format` (named presets plus the catalog's `x_format`), `label` | no sparkline in `/1` (decided: later, in `/2`) |
| `chart` | a QIS chart view's `mark` and `encoding` (the Vega-Lite subset, **unchanged**) | the engines, not the spec, set the size in a dashboard |
| `matrix` | a QIS matrix view (`rows`, `columns`, `values`, `totals`, `sort`, `column_limit`), **unchanged** | repeats header rows when a report splits it |
| `table` | `columns` (field, label, format, align, `width` hint) and `sort` | over `DataTable`; a total row is a row of the result |
| `text` | markdown, the **same safe subset as the portal home** (no raw HTML, no image or link by outside URL), `{{params.name}}` substituted as text | no query |
| `image` | a raster (png, jpeg, webp) held **in the definition's artifacts by hash** (plan 30 payloads), size capped | no URL, **no SVG** (it can script) |
| `control` | edits one **parameter**: `select`, `multiselect` (values listed by J25 under the viewer's access), `date`, `daterange`, `number`, `toggle`, `text` | no query beyond the values list |
| `embed` (**reserved**, refused by `/1` loaders until DBR19) | an external report server's report in a frame (AP17) or a link | dashboards only |

5. **Relation to the existing documents: reuse the QIS view schema, extend with an envelope, supersede only GP06's inline dashboard.**
   - **QIS view documents (0.3) are not changed.** A `matrix` or `chart` widget's encodings *are* the view schema's `$defs`; `ViewRenderer` stays the one place a matrix or chart becomes data, and a QIS view still "arranges rows a result already has": the widget adds the query that produced them. No stored-format change for the semantic library.
   - **`view-spec/1` loses its `dashboard` kind** (GP06 is unreleased and open, so rule 2 of the freeze rule allows editing it): `Dashboard`, its `widgets` and aggregates go; grid, form and detail stay (entity views over the Store, GP34). **A file under an app's `views` is dispatched by its `kind`**: `grid`, `form`, `detail` are `view-spec/1`; `dashboard` is read by the `dashboard/1` loader and `report` by the `report/1` loader (both on the shared core); each format has its own `schemaVersion`. `AppValidator` and `AppChecks.ViewSpecs` run the dashboard and report loaders and check queries against the manifest (a `semantic` model must be listed under `semantic`; a `store` read needs `read` on the entity under `models`).
   - **The Store question is answered:** GP06's `count` or `sum` by an attribute is a **semantic request over a model** whose source is the Store's entities (plan 21 already reads entities through the store module for semantic queries), so the aggregate is computed by the engine under the viewer's access; the Store gets no aggregating read, and the host computes nothing. An app that wants a quick chart over an entity needs a (small, generated or hand-written) semantic model of it (decided, section 12).
   - **Rendered form:** `rendered-view.schema.json` gains a sibling, `rendered-widgets` (a map of widget id to a rendered matrix or chart, `metric`, `table`, `text`, `image`, `control`, or an error **per widget**), so one failing widget never fails the page.
6. **Three layout types, one pipeline.** To show a document: (a) **select the layout** (section 3.2); (b) resolve parameters; (c) **resolve the widgets the layout places, as the viewer** (derive the request, run it, section 5), in parallel, with limits (a widget no layout in play places is not run); (d) render matrix and chart through `ViewRenderer`; (e) give the **rendered widgets** and the **layout** to its engine: `reflow`, `canvas` (both fit one page) or `flow` (the browser's paged media).

| Shared by the two engines | Separate |
| --- | --- |
| the document, the widget vocabulary and schema, layout selection, encodings and the derivation of queries, parameters and their binding, resolution as the viewer, limits and errors, theme tokens (`--sui-*` and the chart palettes, light and dark), the widget renderers (`@dbdatakit/visuals`), formats and number presets, the result cache, audit | the **layout data** of each type, the **layout code** (`layoutReflow`, `layoutCanvas` in TypeScript; browser CSS flow and paged media for `flow`), **export** (one page for a fit layout; paged PDF for `flow`), interaction on screen (cross-filter and drill work in reflow and canvas; a flow has parameters and links, and nothing interactive in print) |

## 3. The document, its layouts and the two fit layouts

### 3.1 Two kinds on one shared core: `dashboard/1` and `report/1`

**Decided (owner, 2026-11-08; overrides my recommendation of a single `board/1`):** **two kinds**, `dashboard` and `report`, so that **searching, browsing and creating can say what a document is intended to be**: the catalog (plan 31) lists and filters by kind, the create flows start from "new dashboard" or "new report", agents' tools name the kind and the registry (plan 30) lists and filters by kind.

**The shared core.** Everything below is **one core**, defined once and used by both kinds' loaders: `widgets` (section 2), `parameters`, **`layouts`** (the three types `reflow`, `canvas`, `flow` and their placement data), the **selectors** (`when`), the per-layout `widget_options`, and the rules of 3.2 and 3.3. In code it is one JSON Schema file of `$defs` (`core.schema.json` in `@dbdatakit/visuals`, referenced by both kind schemas) and one set of core types and checks in `DbDataKit.Views`. **Each kind keeps its own rules and keys on top of it:**

| | `dashboard/1` | `report/1` |
| --- | --- | --- |
| **default layout** (`default: true`) | must be `reflow` or `canvas` (a fit layout) | must be `flow` |
| **layouts allowed** | **any of the three types**, so a dashboard may carry a `flow` print layout (and several fit layouts) | **any of the three types**, so a report may carry fit layouts for the screen (a canvas summary for a wall, a reflow for a phone) |
| **kind-specific keys** | `refresh` (auto-refresh), `kiosk` defaults | `strict` (an over-width block refuses the export), `limits` (pages, rows), `cover` defaults; `refresh` is refused (a report is a run) |
| **what an export uses when no layout is named** | a layout for `print` or `export` if there is one (its `flow` print layout), else the default layout as one page (3.6) | its `flow` layout (the default, or one for `print` or `export`) |
| **what the catalog, create flow and registry say** | kind `dashboard` | kind `report` |

The two loaders are the shared core loader plus the kind's rules; a document of one kind never needs the other kind's loader, and the apps validator, the registry and the catalog dispatch on `kind`.

**How the core is versioned (the freeze rule).** The shared core is versioned **with the kinds**: one constant, `ViewsFormat.Current`, in `DbDataKit.Views` is the number of both. **A new widget type, query form, layout type or selector condition bumps both kinds to `/2` in one change** (and a test fails if the two kind schemas stop referencing the same core file or the two kinds' numbers differ). A document is written in the **lowest number that can say it** (rule 4 of the freeze rule), so a document that uses nothing new stays `/1` on a program that reads `/2`. A key that only one kind has (say a new `report` key) is that kind's change but, to keep one number, bumps both; this is a deliberate simplification. **In `docs/formats.json`** (when UC02's checker exists): **two entries, `dashboard` and `report`, with the same `version_source`** (the constant) and each listing its own kind schema and loader **and the core schema file** in `files`, so a change to the core is a change to a frozen file of both; there is **no `core` entry** because the core is not a file format of its own. That the checker accepts two entries with one version source is **not verified** (it is a draft on `work/fq01-fq06`); if it forbids it, the fallback is a `core` entry that both reference.

```yaml
schemaVersion: 1
kind: dashboard                     # dashboard | report: the kind the document is intended to be
title: Sales today
parameters: [{name: region, type: string, for: customers.region, many: true, default: []}]   # J25 definitions
refresh: {every: 5m}                # dashboard only; the server's floor applies (default 15 s)
widgets:                            # defined once
  revenue: {type: metric, encodings: {value: orders.net_revenue, compare: orders.net_revenue_prev}, query: {model: sales, filters: [...]}, label: Revenue}
  by_region: {type: chart, mark: bar, encodings: {x: customers.region, y: orders.net_revenue, color: products.category}, query: {model: sales, order: [[orders.net_revenue, desc]], limit: 20}}
  regions: {type: control, parameter: region}
layouts:                            # at least one; exactly one has default: true
  - name: desk
    type: reflow                    # reflow | canvas | flow
    default: true

    tiles: [{widget: regions, x: 0, y: 0, w: 4, h: 1}, {widget: by_region, x: 0, y: 1, w: 8, h: 4, min: {w: 320, h: 200}}, {widget: revenue, x: 8, y: 1, w: 4, h: 2}]
  - name: wall
    type: canvas
    when: {width: {min: 1700}, medium: screen}
    canvas: {width: 1920, height: 1080, unit: px}     # unit px (default) | mm | in (96 px per inch)
    overflow: scale                 # scale | scroll; min_scale: 0.5; max_scale: 4
    tiles: [{widget: revenue, x: 40, y: 40, w: 400, h: 180}, {widget: by_region, x: 40, y: 260, w: 1200, h: 700}, {widget: logo, x: 1700, y: 20, w: 180, h: 60, layer: 1}]
  - name: phone
    type: canvas
    when: {width: {max: 600}, orientation: portrait}
    canvas: {width: 390, height: 900}
    overflow: scale

  - name: print
    type: flow                      # the report engine (section 4)
    when: {medium: [print, export]}
    page: {size: A4, orientation: portrait, margins: {top: 20, right: 15, bottom: 20, left: 15}}
    header: {left: "{title}"}
    footer: {center: "Page {page} of {pages}"}
    sections: [{title: Summary, blocks: [{row: [{widget: revenue, span: 6}]}, {widget: by_region, height: 80}]}]
```

**Rules of the core (both kinds).**
- **A layout has a `name` (unique), a `type` and the placement data of its type, a `when` selector (optional) and `default: true` (exactly one layout).** The data of other types is refused (`grid` and `tiles` in cells with `reflow`; `canvas`, `overflow` and `tiles` in canvas units with `canvas`; `page`, `header`, `footer`, `cover`, `sections` with `flow`). **Two layouts may be of the same type with different sizes** (two canvases, a phone canvas and a wall canvas; or two reflow grids) and may differ in the widgets they show.
- **A widget no layout in the document places is refused** (dead). **The default layout must place every widget** (refused otherwise), so a full view always exists. **Any other layout may omit widgets**, silently, with one exception: a layout that omits a `control` whose parameter is `required` without a default is refused for that layout. A widget a layout omits is **not resolved** when that layout is shown (no query runs for it).
- **A layout may restyle a widget only through `widget_options` (and the placement hints of its own type)**: `density` (`compact | comfortable`), `show_title`, `legend` (`show | hide`), a tile's `min`, `layer`, `span`, `height`, `keep`. It **cannot change a widget's type, encodings, query, formats or parameters**, so every layout shows the same numbers. The validator refuses any other key.
- **Kind rules** (the table above) are checked by the kind's loader: the default layout's type, the kind-specific keys, and that a `report` has a `flow` layout.

### 3.2 Selecting a layout: `when` and `selectLayout(doc, context)`

`when` is a **selector**; its conditions are ANDed and an omitted condition matches anything:

| Condition | Meaning |
| --- | --- |
| `width: {min, max}`, `height: {min, max}` | the **container's** size in CSS pixels (the viewport minus chrome for a page; the block's box in a portal home or a pinned tile) |
| `orientation: portrait \| landscape` | height above or not above width |
| `aspect: {min, max}` | width divided by height of the container, for a canvas that suits a shape |
| `medium: screen \| print \| export` (one or a list) | where it is shown: a screen, the browser's print, or an export (PDF) |
| `default: true` | not a condition: the layout used when no selector matches |

`selectLayout(doc, context)` is a **pure function** (context: width, height, medium, an optional layout name) with the same goldens in .NET and TypeScript: (1) a **named layout** (URL `?layout=print`, an export option, a subscription's setting) wins; an unknown name is refused naming the layouts the document has; (2) otherwise the layouts whose `when` **matches** are the candidates, where a condition on a dimension the context lacks (an export has no viewport width) **does not match**; (3) the **most specific** candidate wins (the most conditions); ties go to **document order**; (4) with no candidate, the **default**. **Switching** (a window resized across a selector, a phone turned) keeps the parameters and the resolved results of widgets both layouts place, and resolves a newly placed one. **How an aspect mismatch behaves:** selection never measures a canvas against the container; a `scale` canvas letterboxes, so authors who care write `orientation` or `aspect` selectors (question 19). The validator warns on two layouts with equal selectors (the later is unreachable) and on a `width` range with `min` above `max`.


### 3.3 Reflow layout: `layoutReflow(layout, box)`

1. **The fit rule.** The dashboard fills its **container** (the viewport minus the host's chrome; a box for an embedded one: a portal home block, a pinned tile). CSS grid with `minmax(0, 1fr)` tracks, **no page scroll and no tile scroll** at any size at or above the smallest layout. A table or matrix that does not fit its tile **shows what fits and says so** ("12 of 40 rows") with an action that **maximizes the tile** to the whole container, where the widget scrolls. Nothing is hidden silently.
2. **Tile minimums** (CSS pixels; a tile may raise them): metric 160 x 88, text 160 x 56, control 180 x 56, chart 280 x 180, table 320 x 200, matrix 360 x 220. `layoutReflow(layout, box)` is a **pure function** returning the placed tiles and any violation. The layout was already chosen by its selector (3.2), so there are no breakpoints inside a layout (a narrow viewport gets a layout of its own); if a tile would be **below its minimum** in this box it uses the **compact stack** (one column in document order, minimum heights, the page scrolls: the only place a reflow dashboard scrolls; phones). The validator lays each reflow layout out at the sizes its selector allows (or 1920 x 1080, 1366 x 768 and 390 x 844 for a layout with none) and warns when a tile is below its minimum there.
3. **Density is the renderer's decision, not the document's.** Each tile is told its pixel box (`ResizeObserver`; an explicit box in tests) and picks a class `xs`, `s`, `m`, `l`: a metric drops its label, then its comparison; a chart drops legend, then axis titles, then thins ticks, and is drawn **at the box size** (the renderer sets size and `autosize: fit`; the spec's `width`/`height` are ignored in a dashboard); a table shows the rows that fit; a matrix truncates columns first. `density: compact | comfortable` pins it.

### 3.4 Canvas layout: `layoutCanvas(layout, viewport)`

A **fixed design**: the author places tiles on a canvas of a stated size and the host shows that picture.

1. **`canvas: {width, height, unit}`** (px by default; `mm` and `in` are converted at 96 px per inch for print-sized canvases; limits 320 to 8,000 px per side) and **`overflow`**:
   - **`scale`** (default for canvas): the whole canvas is scaled **uniformly** to fit the viewport, keeping the aspect ratio, centred and **letterboxed** on the theme's background; `max_scale` (default 4) caps up-scaling, `min_scale` (default 0.5) is the smallest scale: **below it the canvas stays at `min_scale` and scrolls**, so text stays readable on a small screen.
   - **`scroll`**: native size (scale 1) with scrollbars; `min_scale`/`max_scale` are not allowed.
2. **`layoutCanvas`** is a pure function of the layout and the viewport: it returns the scale, the offset, the scrolled size and the placed tiles (in canvas units, unchanged by the scale).
3. **The validator checks** (all at load, with file and line, per canvas layout): every tile lies **inside the canvas**; **no two tiles overlap unless they have different `layer`** (an integer, drawn in ascending order; for a logo over a banner or a text over a chart); each tile is at least its type's **minimum at scale 1** (the canvas is the native size, so the minimums above apply unchanged); `min_scale <= max_scale`; canvas size in range; a `layer` only in a canvas layout.
4. **Density at scale.** Density is decided from the tile's **canvas box**, never from the screen, because the whole canvas is scaled as one picture (a CSS transform of the canvas element; charts are drawn as SVG so they stay sharp, to verify for `VegaChart`'s renderer): the same picture at every size, no re-density, text scales with it. A maximized tile (below) leaves the canvas and is laid out as a single tile at the viewport size, with reflow density.
5. **Phones:** a phone gets **its own layout by selector** (a phone canvas or a reflow layout, as in the example); with none, the default layout is used and a canvas scales to `min_scale` and scrolls. Per-breakpoint canvases are just several canvas layouts (decided by the owner, 2026-11-08).

### 3.5 The same in every layout

1. **Parameters and filters:** the document's `parameters` (shared by all layouts) (J25 definitions); a `control` widget edits one; values live in the **URL query string** (a dashboard is a link that carries its filter); only the widgets that use a changed parameter resolve again.
2. **Cross-filter:** a chart or matrix may say `on_select: {set: region, from: customers.region}`: selecting a bar sets the parameter exactly as a control would (a parameter binding, not a computation).
3. **Drill:** `drill: {to: {dashboard|report|view: name}, with: {region: $customers.region}}` uses GP06's link vocabulary (`$field` of the clicked row, `$params.name`); the target's required parameters must all be given (a check); a drill to a report opens its screen view.
4. **Maximize** a tile (full container; the widget scrolls) and **refresh**: `refresh.every` re-resolves, the client pauses when the tab is hidden, adds jitter, never goes below the server floor (a setting, 15 s) and shows "as of hh:mm" per tile; a failed refresh keeps the last rows marked stale; results use plan 24's opt-in cache keyed on access-rule values, channel and version, and a request hash tells that nothing changed.
5. **Kiosk and wall mode:** `?mode=kiosk` hides the host's chrome; **wall mode is a canvas layout with `overflow: scale`** in kiosk (a `wall` layout selected by a width condition, or named with `?layout=wall`; a reflow layout in kiosk is just chrome-less). Rotation of several dashboards (`?rotate=a,b&every=60`) is a host feature, not a document key.
6. **Layout in export and snapshot** (section 3.6).

### 3.6 Which layout an export or snapshot uses

1. **A named layout wins** (`export?layout=print`, a subscription's `layout`, the exporter's option). Delivery names the layout it wants (a scheduled report says `layout: print`); with no name:
2. the **medium** `export` is the context, with no viewport size: the layouts whose selector matches `export` (or `print`) are candidates, **a `flow` layout declared for print or export is chosen when there is one** (for a `report` that is its default or its print layout; for a `dashboard`, its print layout), else
3. **the default layout, as one page:** a **canvas** at its own size (`@page` size = the canvas in its unit, margin 0, scale 1), a **reflow** laid out at the chosen page size by `layoutReflow` (box = the printable area). Both go through the Chromium exporter (4.5) from the same HTML the screen shows (`?print=1`).
4. A `report` always has a flow layout (its default; the `report/1` loader refuses otherwise); a `dashboard` with no print layout exports as in 3.


## 4. The flow layout (`type: flow`): the browser lays it out

**The decision (owner, 2026-11-08):** we build **no layout or pagination engine of our own** and run **no Node at runtime**. A `flow` layout is compiled to **HTML and CSS for a browser**, and the browser's own flow layout and paged media do the paging. On screen it scrolls; to PDF, headless **Chromium** prints it, driven from .NET. **A `flow` layout is the default layout of a `report` and the print layout a `dashboard` may add**; it is the same code either way.

```yaml
# a layout of type flow, inside `layouts:` (the widgets and parameters are the document's)
- name: print
  type: flow
  default: true                     # for a report; a dashboard's print layout says `when: {medium: [print, export]}`
  page: {size: A4, orientation: portrait, margins: {top: 20, right: 15, bottom: 20, left: 15}}   # mm; size A4 | A3 | Letter | Legal | {w, h}
  header: {left: "{title}", right: "{params.region}"}        # text with {title} {page} {pages} {asof} {viewer} {params.x}
  footer: {center: "Page {page} of {pages}"}
  cover: {parameters: true}         # a first page listing parameters, "as of" and the viewer; optional
  sections:
    - {title: Summary, break: before, blocks: [{row: [{widget: revenue, span: 4}, {widget: orders, span: 4}, {widget: margin, span: 4}]}, {widget: by_region, height: 80}]}
    - {title: Detail, blocks: [{widget: lines, repeat_header: true}, {pagebreak: true}, {widget: notes}]}
  widget_options: {by_region: {density: comfortable}}
```

### 4.1 How the document becomes paged HTML

| Document | HTML and CSS |
| --- | --- |
| `page` | `@page { size: A4 portrait; margin: 20mm 15mm }` (Chromium honours it with `preferCSSPageSize`) |
| a section, `break: before | after` or `pagebreak` | `break-before: page`, `break-after: page` |
| `keep: true` (default for `metric`, `chart`, `image`, a section title with its next block) | `break-inside: avoid`, `break-after: avoid` on a title |
| `text` | `orphans: 2; widows: 2` |
| `table` and `matrix` | a real `<table>`: the header rows in `<thead>` (`display: table-header-group`, **repeated on every page**), each `<tr>` with `break-inside: avoid`, so a table splits between rows and never inside one; **totals are the last `<tbody>` row, not `<tfoot>`**, because Chromium repeats a table footer group on every page and totals belong where the result puts them: once, at the end. No per-page subtotals or "carried forward" in `/1` (computations; open question 4) |
| a `row` block of spans | a 12-column CSS grid, `break-inside: avoid` by default |
| `chart` | the widget's SVG drawn **in the browser** by `VegaChart` (the existing visuals path, vector in the PDF), at a declared `height` (mm) and the content width |
| header and footer | **Chromium's header and footer templates** (4.5) or `@page` margin boxes (below) |
| `cover`, the parameters list | a first page of HTML |

A table wider than the content width uses `table-layout: fixed` with the columns' `width` hints and wrapping; **columns are never dropped**. Because we have no metrics of our own, an over-wide block is **detected after layout in the browser** (`scrollWidth` larger than the content width) and reported: a warning on screen, a refusal in export when the report says `strict: true`.

### 4.2 On screen

The same HTML in a **scrolling column** the width of the page, with **page-break guides**: dashed lines at the printable height of a page. The guides are **approximate** (breaks move to avoid splitting a block; the PDF is exact), and the screen says so. A **Print preview** button opens the exact PDF from the exporter in the viewer (when export is available), and the browser's own Print works on the same HTML with the print stylesheet (`@media print`, `@page` from the report), as a person's fallback when no exporter is installed.

### 4.3 What the browser gives and what it does not (stated honestly)

- **Good:** floats-free block flow, tables that split, repeating `thead`, `break-*`, `orphans`/`widows`, named page sizes, vector SVG charts, real text shaping and fonts, accessibility tags (`generateTaggedPDF`) and an outline (`generateDocumentOutline`) from the headings.
- **Page numbers:** `{page}` and `{pages}` come from Chromium's header and footer templates (`pageNumber`, `totalPages`) through the DevTools protocol (4.5: PuppeteerSharp). **CSS `@page` margin boxes** (the other way to number pages) (`@bottom-center { content: "Page " counter(page) " of " counter(pages) }`). are an alternative, but **whether the pinned Chromium supports page margin boxes is not verified** (believed to have shipped in Chromium 131, late 2024); DBR15 verifies it against the pinned build, and the plan relies on the header and footer templates, using margin boxes only if they work. Header and footer templates do not inherit the page's CSS (they need their own inline font size and font); the exporter writes them from the report's `header` and `footer` and substitutes `{title}`, `{params.x}`, `{asof}`, `{viewer}` itself.
- **Not guaranteed:** the **same page breaks across Chromium versions**, and across hosts **when a document uses a host font** instead of the bundled set. With the bundled fonts (the default) and the same pinned Chromium, breaks are the same on every host. Mitigation in 4.6.

### 4.4 Where exports run, and what has to be installed

A PDF needs a Chromium (or Edge) on the host that makes it. Options, with the recommendation:

| Where | For | Cost |
| --- | --- | --- |
| **The serving layer's `views` module host** | interactive "Download PDF", print preview | Chromium on every host that enables `views` export |
| **A runner task** (plan 28) | **scheduled and subscription delivery** (GP17), batch exports | Chromium on the runner host; a task runs in a process of its own, which suits a browser child |
| **The console** | nothing: it serves no data (it calls the module through the relay) | none |

**Decided (owner, 2026-11-08): Chromium on export hosts is accepted, pinned.** `DbDataKit.Views.Export` is a library with one `IReportExporter`; the **module** uses it for interactive exports and a **runner task** (`views-export`, a first-party package) for scheduled ones. **Export is off by default** and turned on per host by `views.export` (`mode: pinned | system`, `path`); the module's `/health` says "export unavailable: no browser" otherwise, and the screen view and the browser's own Print keep working. **`pinned` is the default and the supported mode:** a `chromium.pin` at the repository root names a **Chrome for Testing** version and, per rid (`linux-x64`, `win-x64`), the archive's SHA-256 and the executable's, fetched by `scripts/fetch-chromium.sh` and `.ps1` into `.chromium/<rid>/` (DBR15a, the pattern of `bun.pin` and `duckdb.pin`); the exporter's `LaunchOptions.ExecutablePath` points at it and **nothing is downloaded at run time**. **`system` mode** (an installed Microsoft Edge or Chrome on Windows) stays **allowed but unsupported for page-break guarantees**: it auto-updates, so the exporter records the browser version in the audit row and the PDF's metadata. Honest costs: Chromium is about 150 to 300 MB installed (not verified for the pinned build); it is **not in the MSI or zips of the products that do not export**; the products that do (the serving layer host with `views`, the runner host) get it as a **`dist` component** (the pinned archive, hash-checked at build and at install, installed beside the product) and, for containers, an **image layer** that copies the pinned build and installs the shared libraries it needs (nss and so on, not fonts: Playwright's `--with-deps` list is the reference; a build that runs `apt-get` fails on the cloud proxy's 403, so the layer takes a package set that is already in the base image or is pulled whole, as CLAUDE.md says for testenv). The export component also carries the **small bundled font set** (4.6, "Fonts"), so a Linux container with no fonts at all still exports correctly; host fonts are needed only for documents that name them. The browser is launched **without a sandbox exception only where the platform needs one** (root in a container needs `--no-sandbox`; the exporter says so in its log), with a throwaway profile, **no network except a loopback address** (`--host-resolver-rules="MAP * ~NOTFOUND, EXCLUDE 127.0.0.1"` or request interception denying the rest), and the HTML is served to it from a one-shot random loopback path with **the rendered widgets embedded as JSON**, so the page needs no token and calls nothing.

### 4.5 The .NET exporter (no Node)

- **Decided: PuppeteerSharp (MIT, to be confirmed) over the DevTools protocol, with a pinned Chromium.** PuppeteerSharp is a .NET port of Puppeteer that speaks CDP itself: **no Node**. `BrowserFetcher` is **not used at run time** (it downloads a browser; ours is the pin): `LaunchOptions.ExecutablePath` points at the pinned executable, `Headless` on, throwaway `UserDataDir`, the flags of 4.4. The exporter: launch, `Page.navigate` to the one-shot loopback page, wait for the page's own **ready signal** (`window.__reportReady`, set after the charts are drawn and fonts are loaded; an event wait with a deadline and a cancellation token, never a sleep), then `PdfAsync` (`Page.printToPDF`) with `DisplayHeaderFooter`, `HeaderTemplate`, `FooterTemplate` (classes `pageNumber`, `totalPages`, `title`, `date`), `PreferCSSPageSize`, `PrintBackground` and margin options, plus tagged PDF and outline where the library exposes them. **Whether the current PuppeteerSharp supports all of that, targets net10.0, reports timeouts and cancels, and runs a Chrome for Testing binary from `ExecutablePath` with no download is not verified and is the first work of DBR15** (section 14).
- **Fallback, documented:** a **minimal DevTools client of our own** (`--remote-debugging-pipe` or a loopback WebSocket, a few hundred lines, no dependency) if PuppeteerSharp fails that check; the exporter sits behind `IReportExporter`, so the swap touches nothing else.
- **Considered and not chosen:** **Playwright for .NET**: bundles and starts a **Node driver**, the dependency the owner ruled out. **CefSharp / CEF**: embeds Chromium in-process, Windows-first and Linux support unverified, heavy native packaging for a server. **QuestPDF**: its licence changed in July 2026 to source-available, free only under USD 1M revenue and excluding public and publicly traded companies, and it is code-first layout, not HTML, so our widgets would need a second renderer. **The browser's command line** (`--print-to-pdf`): no header and footer templates, no ready signal (only a virtual-time guess), exit codes for errors. **Commercial HTML-to-PDF engines** (and Majorsilence or FastReport from plan 16): licences or a second chart system, and they do not read our widgets. **Own paginator**: rejected by the owner (section 4).
- **Charts in print** are `VegaChart`'s SVG drawn in the page by the browser, so the print path **is** the screen path. `chartToSvg` stays for **non-browser contexts only** (an email body, an agent's transcript); the report path does not use it. The Y05 text in the visuals README is updated: Chromium is now used, for PDF, behind the exporter.
- **Data exports stay in .NET:** CSV and xlsx of a widget's resolved rows (ClosedXML is already a dependency of `DbDataKit.Semantic.Extraction`), so the file equals what is shown.

### 4.6 Determinism, CI and limits

- **Pin the version.** The one pinned Chrome for Testing build is what CI, the install component and the images use; the exporter's golden tests run only on it. **Tests compare structure, not pixels:** the PDF's page count, each page's extracted text, the outline and the embedded fonts, with a PDF text reader as a test dependency (PdfPig is a candidate, licence **not verified**). A Chromium upgrade is a reviewed change to `chromium.pin` that regenerates the goldens; a break moving on a bump is expected and is the review's job, not a defect.
- **A CI job that fetches the pin and runs the exporter tests:** `scripts/fetch-chromium.sh` on the Linux runner (and `.ps1` on the Windows job), then the exporter tests with `DBDATA_TEST_CHROMIUM` pointing at `.chromium/<rid>/`; they **fail, not skip,** in that job (plan 11 CI04's rule) and skip elsewhere with the skipped count in the summary. The pin itself is checked by a `chromium-pin-linux` job in `repo-checks.yml` like `duckdb-pin-linux` (every rid's archive and executable download and match their hashes; the PowerShell script on Windows). In cloud sessions Playwright's Chromium under `/opt/pw-browsers` can stand in for a local run (`system` mode with a path), but it is not the pinned build, so its output is not compared with the goldens. A Windows job also runs a smoke test with the installed Edge in `system` mode.
- **Limits:** rows per table (default 100,000), widgets per document, pages (default 500, read from the PDF and refused over the limit with a message), a **deadline** for the whole render (an injected value in tests; no real waiting), memory of the browser process (the platform's job-object or cgroup limit; **not verified**), one browser per export, at most N at once per host.
- **Fonts: a small bundled set, plus host fonts an administrator lists (owner, 2026-11-08, revised).**
  - **The bundled set:** a curated **sans, serif and monospace family**, a few weights each (regular, bold and their italics), **open licences only (SIL OFL)**, shipped as WOFF2 with the export component, **roughly 5 to 10 MB (an estimate, not measured)**. Recommendation: **Noto Sans, Noto Serif and Noto Sans Mono** (one design family and one licence, broad Latin, Greek and Cyrillic coverage); Inter for the sans and Liberation (OFL since 2.x) for a metric-compatible-with-Arial option are the alternatives. **The licence check of the exact files (and their reserved font names) is unverified work of the font slice, DBR15b.** CJK, Arabic and Hebrew are **not in the set** (CJK fonts are tens of MB per weight): documented, not promised.
  - **Loaded by the export page itself:** the report's HTML declares `@font-face` rules for the bundled files, served from the **same one-shot loopback origin** as the page, under the aliases `DbDataKit Sans`, `DbDataKit Serif` and `DbDataKit Mono`; the ready signal waits for `document.fonts.ready`. **Nothing is installed into the operating system**, so the result is **identical on Windows and Linux**. The screen view of a `flow` layout loads the same files from the `views` module, so screen and print agree (fit layouts on screen keep the console's UI font).
  - **The font stack is a theme token** whose **last members are the bundled families**: `--font-sans: <allowed host fonts, if any>, "DbDataKit Sans", sans-serif`, likewise serif and mono. A document picks `sans`, `serif` or `mono` for its text (a `theme.font` choice in the shared core), so output is deterministic by default.
  - **A document may name a font that is not bundled only if an administrator lists it** in `views.export.fonts.allowed` (family names); the loaders and the publish check refuse any other name, naming the allowed ones. A listed font that is **missing on the export host falls back to the bundled family** and the export result carries a **warning** naming the missing font (not a failure).
  - **Font-presence check at exporter start covers only the host fonts the administrator has promised**, in `views.export.fonts.required` (default empty): the exporter loads a probe page in the pinned browser that sets each promised family and asks which platform fonts it used (the DevTools `CSS.getPlatformFontsForNode`, **through PuppeteerSharp's CDP session, not verified**); if one is missing **it refuses to start, naming the font and the package that provides it** (for example `fonts-noto-cjk` on Debian and Ubuntu, package names per release to be confirmed), and `/health` says "export unavailable: fonts". With nothing promised the check has nothing to do, because the bundled set is verified by hash (below).
  - **The bundled files are verified by hash like the Chromium pin, in a separate `fonts.pin`** with `scripts/fetch-fonts.sh` and `.ps1` (the pattern of `bun.pin` and `duckdb.pin`: one archive per upstream release, each file's SHA-256, no per-rid entries because fonts are the same everywhere), **not** an entry in `chromium.pin`. Why separate: fonts and the browser change at different times and for different reasons, a font update should not re-pin Chromium (or the reverse), and the goldens depend on both, so each pin is its own reviewed change. The files are fetched at build or install time into the export component, never at run time; they are **not committed to git** (5 to 10 MB of binaries; the pin and the licence texts are).
  - **Tests:** the export page's `@font-face` files match the pin's hashes (a changed byte is refused at startup and in the pin script test); a report on a **Linux image with no fonts installed** exports with the bundled fonts and the PDF's embedded-font list names only `DbDataKit` families; a document naming an unlisted font is refused; a document naming a listed font absent on the host exports with the bundled family and a warning; a promised-but-absent family (`DbDataKit Missing Font` in the test) refuses to start with a message naming it.
  - **Page-break determinism, plainly:** with the **bundled default and the same pinned Chromium, page breaks are the same across hosts**; **host fonts are best effort** (another host's font version can break pages elsewhere), and the audit row records the browser version and the fonts used.

## 5. Where it lives, who runs it, who sees what

1. **One library renders, where a definition is published decides who serves it.** `DbDataKit.Views` (new, .NET: loaders, `DeriveRequest`, resolution, `ViewRenderer` calls, limits, export orchestration) is hosted by (a) a **serving module `views`** for the published kinds `dashboard` and `report` (a module of plan 20's serving layer, enabled per instance with `modules:`; REST in J28's listener design, the same tokens), and (b) the **apps host** for documents inside an app version, called with the app's **scoped token**, which narrows. The **console** serves nothing (it calls the module through the relay once J28 gives it a query path; until then the Views page shows fixtures, as Y03 does). A dashboard without an app is `/views/d/<name>` on the serving layer.
2. **Published definitions** are kinds in plan 30's registry (`DefinitionKinds`: validator = the loader plus the catalog check, `FormatOf` = `schemaVersion`, `DependsOn` = `semantic-model@v`, saved queries, image payloads). Channel-aware (plan 21), staged and activated, rolled back like any kind.
3. **User-owned dashboards** (built while exploring, or "pinned" from an assistant's view or a saved query): `UserViewStore` in the serving group's **state database** next to J27's `SavedQueryStore`, same shape (owner, share to `user:`, `group:`, `*`, history, expected-version conflicts, restore). A user dashboard may only ask what the person can already run; sharing shares **no data**. **Promote** = export the document as a file for a Build project or an app source, then publish through plan 30.
4. **A widget runs as the viewer.** Its derived or written request goes through the serving core's services (`IServingQueries`; the Store module for `store` reads) with the viewer's `ServingContext`, so **access, limits, audit and lineage are the host's** and the cache key includes the access-rule values. A subscription runs as the subscriber (plan 22 section 5, GP17). **Access rules (plan 22 section 2, GP01, GP02, GP10 to GP15) are deferred by the owner (QG2, 2026-11-07)**; nothing here waits for them, and when they land they plug in **below** the widgets, at the serving core's row and column rules, so no widget, dashboard or report knows a rule. Two checks for that day: a hidden or masked column reaches a `table` or `matrix` as the core gives it, and a **total comes from the filtered query** (the derived request asks for `totals`), never from a precomputed number.
5. **A widget that fails** (denied, timeout, engine refusal, a missing model) renders an error tile with the server's code and words; the rest draws. A report with a failed widget **exports with the error block in its place and says so on the cover**; a subscription that cannot render sends nothing and tells the owner (GP17).

## 7. Agents

An agent writes a **document as data** (a `dashboard/1` or a `report/1` of the kind it was asked for, or a `widgets` map to pin), never code. With encodings that drive the query it need not write a request at all: it states the fields it wants drawn and the filters, and `DeriveRequest` makes the request. The **same strict loaders and the catalog check** validate it and return diagnostics with path and line, so a bad draft is corrected in the loop. Safe by construction: closed schemas, no URLs, the Vega-Lite subset with no transforms, a markdown subset, a request that is validated by the engine and run as the viewer. A draft is saved as a **user dashboard** by the person's approval (plan 16), published only through plan 30. Tools (provisional): `views_validate`, `dashboard_draft`, `report_draft`, `layout_add` (a layout for an existing document: a print layout for a dashboard, a phone canvas for a report), `view_pin`. An agent may write the **widgets once and a print layout** for a dashboard in one step. **Evaluation uses the scripted fake chat client** (plan 25 section 2): a scripted conversation drafts a dashboard from a model's description, gets a diagnostic (an encoded field that is not in the model), fixes it, and the approved draft equals the golden document; a draft with a URL image, raw-HTML text, a custom Vega expression or an `aggregate` transform is refused by the same validator as a human's; an explicit `sql` is refused where the author may not use it; a denied approval stores nothing. The agent runtime is plan 16's and is not built (not verified), so DBR20 waits for it.

## 8. Authoring: what comes first

The visual editor follows the first viewing slices at once (section 9a). **First: files.** A dashboard or report is a YAML or JSON file in an app's source (`views/`) or in a Build project (`dashboards/` and `reports/` beside `semantic/`, validated by `project validate`, published with the model they depend on, through plan 30), with `app validate` and `dashboard validate` and `report validate` commands (one `Validate` call in `DbDataKit.Views`, as `AppValidator` has) and the JSON Schemas for editors. **Second: the user store** (DBR12): pin what you build. **Then the editor (owner, 2026-11-08: ready to test soon; slices DBR22 to DBR29 and the milestones of 9a):** field wells that write `encodings` and so the request (`DeriveRequest` ported to TypeScript against the shared goldens), a layout list with a drag grid for reflow, a canvas editor with snapping, a flow preview from the paged HTML and a selector test ("show me the layout for 390 x 844"); it writes the same files, so nothing in the engines changes. Dashboards and reports are definitions, not Store entities.

## 13. Risks

- **Page breaks vary with the Chromium version, and with host fonts when a document uses them.** With the bundled font set (the default) and the same pinned Chromium, breaks are the same on every host (the owner's decision, 4.6). Mitigation: a pinned build in CI and a `pinned` mode; the bundled set verified by hash (`fonts.pin`); structure-only tests; a version bump of Chromium or of the fonts is a reviewed change that regenerates the goldens. A document that names an administrator-listed host font gets best effort only; the audit row records the browser version and the fonts used.
- **A browser on the server is heavy and an attack surface.** Mitigations: export off by default, a pinned, hash-checked build, loopback-only HTML with the rendered widgets embedded (no token, no data call), no network but loopback, a throwaway profile, a deadline, memory and concurrency limits, a closed widget language (no script from a document), `--no-sandbox` only where a container forces it and logged. Install size and the extra component are real costs (accepted, question 3). **PuppeteerSharp is a dependency we do not control:** if it stops tracking Chromium's protocol or net10.0, the fallback is the minimal own client behind `IReportExporter`.
- **A derived query can be expensive.** A chart with a high-cardinality dimension asks for it; the request's `limit` (required, at most 10,000), the widget type's defaults, the host's row and time limits and the result cache bound it; the editor, when it exists, warns on a dimension's cardinality (the catalog may say).
- **Derivation drift between the .NET function and a future TypeScript port.** Mitigation: one set of golden pairs run by both.
- **No computation in the chart spec** is a rule on the *spec*; a hand-written query can still compute (ad hoc aggregates, transforms), on the server, under the viewer's access and limits. The refusal tests of DBR01 keep the spec closed.
- **Resolution cost:** a dashboard of 12 tiles is 12 queries per viewer per refresh; parallel resolution under the host's limits, the opt-in cache keyed on rules, the refresh floor and partial refresh by changed parameter.
- **Canvas on small screens:** a scaled canvas can be unreadable; `min_scale` and the scroll fallback bound it, the validator checks minimums at scale 1 only, and a phone layout by selector is the cure.
- **Layout combinatorics.** Several layouts per document multiply what has to be checked and kept in step: a widget added later must be placed in the default layout (refused otherwise) and is silently absent from the others; a selector gap leaves a viewer on the default. Mitigations: the default places everything, `selectLayout` has shared goldens, the validator lays each layout out at the sizes its selector allows, warns on unreachable layouts, and the editor (later) lists which layouts omit which widget.
- **Selector surprises.** Specificity-then-order is easy to state and still surprising when two ranges overlap; the validator warns and the selection can be shown (`?layout=` names it, and the page can say which layout and why in a debug view).
- **Two kinds on one core can drift apart** (a key added to one and forgotten in the other, a core change that bumps one kind only). Mitigations: one core schema file referenced by both, one number (`ViewsFormat.Current`), a test that fails on either divergence. That a dashboard can carry a print layout and a report fit layouts is **a feature of layouts**, not a risk; the kind's default-layout rule and the catalog's use of the kind keep each document's intent visible.
- **Bundled fonts cost size and cover little.** About 5 to 10 MB per export component (an estimate); Latin, Greek and Cyrillic only; CJK, Arabic and Hebrew need host fonts an administrator lists and promises, and the page count of such a report can differ between hosts. A licence mistake in a bundled file would be a distribution problem: DBR15b checks every file's licence and keeps the texts.
- **View-spec churn:** GP06 is on a local branch; DBR13 edits it before any release, but if GP06 is released first the removal of `dashboard` is a new `view-spec/2`. Merge order: DBR13 with, or before, the first release that holds `view-spec/1`.
- **Access rules arrive late** (QG2): until then every viewer sees what the data-source permissions give; the two checks of section 5.4 become tests then.
