# Plan 33: Fewer services to install

Status: **in progress** (proposed 2026-11-10, the owner's direction; revised 2026-11-11; audited against the code 2026-11-11: 40 of the 77 slice rows are built, the rest are open as their rows say, SC20g, SC21d and SC22e are on hold until the owner has tested the Workspace's parity). The suite installs as up to eight separate servers today. The owner wants **four service types**:
the **Console**, the **Workspace**, the **Gateway** and the **Runner**, with Store, Sync and Build becoming *authoring* that live in the
console and workspace area and publish to the runner. This plan says what exists, what has to be true so that merging does not weaken security or deployment,
and the slices. Same rules as the other slice plans: one slice, one commit in a batch, "done" is a test, the status goes in the row.

## 1. What exists today (read in the code, 2026-11-10)

| Server | Own install (zip / MSI / Scoop / image) | What only it does |
| --- | --- | --- |
| Console `dbdatakit` | yes / yes / yes / yes (`DbDataKit/dist.json`) | sign-in, users, pairing, the Servers screens, an **embedded runner** (`console-runner`) |
| Gateway `dbdatagateway` | **win-x64 only** / yes / yes / yes (`DbDataGateway/dist.json`; the release workflow builds a Windows zip only) | the serving layer: Flight SQL, the apps host, the semantic route, the `store` module that serves master-data reads and writes |
| Runner `dbdatarunner` | win-x64 and linux-x64 / yes / yes / **no image** | runs the tasks of published packages |
| Sync `dbdatasync` | win-x64 and linux-x64 / yes / yes / image built, not pushed | replication API and its screens (the engine is moving to the runner, plan 28c) |
| Build `dbdatabuild` | win-x64 and linux-x64 / yes / yes / yes | the CLI, and a server over a project (`server run`, a `service` command, screens in the console): models, plans, checks. `dist.json` registers no service |
| Store `dbdatastore` | **none** (a Dockerfile and a compose file only) | authoring and approving `model/1` definitions, structure changes, change requests, publishing models to a Gateway |
| Workspace `dbdataworkspace` | **none** (no `dist.json`, no Dockerfile, no release job) | git workspaces for projects, app builds in a child process with no network, preview, publishing to a Gateway |

What is already shared: every server has the same shape (plan 13: `server run`, `pair`, state module, health), the same pairing with the console, and the
shared libraries (`DbDataKit.Authoring` is used by Build and Workspace; `DbDataKit.Store` is used by the Store server and the Gateway's `store` module).
**The precedent for folding a server into another is the console's embedded runner**: an entry with a fixed id, flagged `embedded`, never paired, served at
`/api/embedded-runner/...` and `/relay/console-runner/...`, the same screens as a paired runner.

## 2. Direction and what it means

1. **Four service types to install:** Console, Workspace, Gateway, Runner. A fifth is allowed only where a security or scale reason is written down here.
2. **The Workspace stays a service** (section 3, decision D1); **the first release for testers does not wait for anything else** (owner, 2026-11-10): the quickest path to a simplified install is the `dbdatakit-full` package (section 6a) with every server that exists as a member, the Store and the Workspace packaged as they are (a zip each, SC16 and SC17). Folds of the other servers happen in small steps, each one dropping a member from the list.
3. **Gateway gets Linux builds** (section 4).
4. **Store, Sync and Build become authoring**: their authoring moves into the console and workspace area (section 5), and what a person authors there (models, replications, projects) is
   *published* as a package. What runs on a schedule runs on the Runner; what is served is served by the Gateway. Their standalone servers keep working
   as they are until their authoring has moved: merging them is lower priority, and only for deployment and maintenance simplicity.

## 3. The Workspace stays a service

The Workspace was to fold into the console as a library it hosts (the engine is now the library `DbDataKit.Authoring.Server`, which the standalone `dbdataworkspace` host uses). The review of the fold (SC04) found one property that cannot be kept in one process: a build child run as the console's account can read that account's files, the console's key ring under `secrets/` included, by path, because nothing gives the child a private file-system view. The owner decided (2026-11-11) that the Workspace stays a separate service, with its own account, folder and state; the embedded hosting, the `workspace` role namespace in the console and the console's `workspace` verbs were built, not kept, and deleted.

The properties SC04 tests hold for the standalone host: the build child's environment is an allow-list (no `DBDATAKIT_*`, key ring or secret), the build has no network, the publisher key is a secret-store reference read only by the publish step, no git hook runs, and the Workspace audits and names the person. The console reaches the Workspace as it reaches any server: pairing, relay, the same Workspaces screen.

## 4. Gateway on Linux

The code is not Windows-only. The Gateway's CI runs Linux and Windows suites and `DbDataGateway/Dockerfile` builds a Linux image that the suite release pushes.
What is missing is the package. What is genuinely Windows-only stays so and says so: Analysis Services (`ssas`) sources, Windows UPN password sign-in, and
the 32-bit ODBC worker (`DbDataGateway.Worker`, x86). On Linux the config that asks for them is refused at start with a message naming the setting
(it already is for `ssas`), and the Linux zip does not carry the worker.

The Runner's release job is the pattern: one Ubuntu job builds `win-x64` and `linux-x64` framework-dependent zips, smoke-tests the Linux zip, and the MSI is built
from the Windows zip. Linux gets the zip, `install.sh` and the systemd unit (`dbdatagateway service unit`); Scoop and MSI stay Windows.

## 5. Store, Sync and Build as authoring

The meaning: *authoring* is the part of a product where a person (or an agent) writes definitions. Its output is a **published package or definition**; the
runtime part is somewhere else.

| Builder | Author in the console and Workspace | Published as | Runs / served by |
| --- | --- | --- | --- |
| Sync | replications, mappings, connections as project files | a `package/1` with a `sync` runtime (plan 28c: E-slices) | the Runner |
| Build | models, tables and views, checks, refreshes | a `package/1` (refresh and quality tasks) and, for serving, `connection/2` and semantic models | tasks on the Runner; serving on the Gateway |
| Store | `model/1` files, change approval | the model, published to the Gateway (plan 20 O10b) | the Gateway's `store` module serves the rows; a scheduled step, if any, on the Runner |

Plan 28c already covers how Sync's and Build's engines run on the Runner; this plan covers only where they are *authored and published from*. Each builder
needs its own slice list (a project kind in the Workspace, plan 27 style) and is sliced in SC20 to SC22 (2026-11-11, owner: the three become authoring in the Workspace, standalone products working until the hand-over rows); what had to be **A fourth authored kind, `integration` (plan 27a IX20), was added on 2026-11-11** beside them: a manifest, job classes (C# files built with no .NET SDK, or a compiled project that needs it) and tests, built by `dbdatarunner package build|test` as a child process and published to a Runner as a package like SC22c's; the page is [`docs/integrations.md`](../integrations.md).
settled first is in the rows.

## 6. Installing and joining on one server

Today each product installs on its own and is joined with a code (`<program> server pair`, then `dbdatakit instance add`) or by announcement
(`DBDATAKIT_CONSOLE_ANNOUNCE_URL`, confirmed in `instance pending`). The compose files use announcement; the Windows installers do not. With three service
types the single-server install is Console, Gateway and Runner, so SC10 makes that case one step per product, without auto-approving anything: the MSI and
`install.*` accept the console's announce address and set it, the server then waits in the console's pending list, and an administrator confirms. A
server that joins itself unasked would be a weaker pairing, so it stays a human click or one command.

## 6a. One Scoop package for a single server

The owner's addition (2026-11-10): a **suite package**, `dbdatakit-full`, for one machine that runs everything. One `scoop install -g` downloads every member's own zip, registers
each service and pairs them, and one `scoop uninstall -g` unregisters the services. It is a fourth route beside each product's own manifest, not a replacement:
the per-product manifests, MSIs and scripts stay for machines that run one product.

**What it is.** One Scoop manifest, pinned to one suite release (every product of a suite release has the same version string, `dist/README.md`), with the members' zips
as a list of `url`s and `hash`es, each extracted into its own folder (`extract_to`: `console`, `gateway`, `runner`, ...) and each program on the path (`bin` with
aliases, so `dbdatakit`, `dbdatagateway` and `dbdatarunner` all work). It is generated by `dist/dist.py` from a new `dist/suite.json` (the member products, in start order) and the
members' own `dist.json`, so a member's service name and register command are written once. It is published like the other manifests: into fixed `dbdatakit-full/dist`, `dist-beta` and
`dist-snapshot` releases, so `scoop install -g https://github.com/<owner>/DbDataKit/releases/download/dbdatakit-full/dist/dbdatakit-full.json` never changes.

**Members, first release (for testers).** Console, Gateway, Runner, Sync, **Store and Workspace as they are**, each its own zip (the last two need SC16 and SC17 first; neither gets an MSI or a Scoop manifest of its own, which the package does not need). **Build is a member too** (SC18): it is a command line *and* a server (`dbdatabuild server run`, with projects added by `server project add`, paired with the console, whose Build screens are shown through the relay; its own `ui web` is gone, plan 13 R09) and it already has a `service` command, but its `dist.json` registers no service, so a package that registers services would leave its screens unreachable. **When a server folds into another** (the Workspace into the console, SC05; later the Store's or Sync's authoring), its line leaves `dist/suite.json` in the same commit, and the install is that much smaller; nothing else about the package changes. The list is the file's, so a member is a line, not code.

**First release: packaging only (owner, 2026-11-10).** The first `dbdatakit-full` (SC11) had the manifest, the zips and the `bin` aliases and **no service install, start or pairing script**; its only `post_install` and `pre_uninstall` set and remove the members' machine variables (`globalEnv`), without which a command run by hand would read a per-user folder, not the one the service uses: `scoop install -g` puts every member's program on the machine, and the manifest's notes list, in order, the commands an administrator runs by hand (`<program> service install`, `server pair`, `dbdatakit instance add`). The owner tests that first, then the install script below (SC12 to SC14) follows. SC11, SC16 and SC17 are this release; SC18 (Build's service block) belongs to the install script, since a package that registers no service has no use for it.

**What the install does (`post_install`).** Only for a global install (`$global`, elevated: a service belongs there; a per-user install stops with a message saying to use `-g`),
and refusing at the start, before it changes anything, when a member's service is already registered from another folder (a product installed by its own MSI or Scoop manifest:
the routes share service names, so one route per machine). Then, in the member list's order:

1. `<program> service install` for each member (registered stopped, as the MSI does);
2. start the console, wait for its health check;
3. for each other member: `<program> server pair --max-role <ceiling>` prints a single-use code, `dbdatakit instance add <address> --code <code>` consumes it (the same two commands
   `dist/tests/msi-pairing-e2e.ps1` already runs), then start the member. **Pairing here is not auto-approval**: whoever runs `scoop install -g` is an elevated administrator of the
   machine and is the person who would have typed those commands; a code is made, used once and never written to a file, the log or the notes, and the console pins the
   member's certificate as in any pairing. The ceilings are what plans 28a R19 and 13 W12 give a console administrator (`viewer,operator,admin` for a Runner and a Gateway; the Gateway and
   the Runner also get a `publisher` pairing for the Workspace);
4. print what an administrator does next: the console's address and the first-run invitation file (`FIRST-RUN.txt`). No state settings are written (the rule in `dist/README.md` stands).

It is **idempotent**: a member whose service is registered is not registered again, and a member the console already lists (`instance list`) is not paired again, so `scoop update` and a
repeat after a failure converge. A failure at one member stops with the member named, what was done and the command that finishes it, and leaves the others as they were.

**What the uninstall does (`pre_uninstall`, only when Scoop is really uninstalling, not updating).** In reverse order: `dbdatakit instance remove` for each member, `server unpair` there, stop the
service, `service uninstall`. Settings and data under `%ProgramData%` stay, as with the MSI (a purge is the administrator's, by hand, and the notes say where). An update stops the services,
replaces the files and starts them again without unregistering them or pairing them again; the services run from Scoop's `current` folder so a new version needs no new registration.

**Not the same as SC10.** SC10 makes separately installed products join by announcement, where nobody has typed a code. The suite package pairs with codes because one administrator
runs the whole install on the machine.

## 6b. Names and folders (owner, 2026-11-10)

**The product is DbDataKit.** "DbDataConsole" and "DbDataKitConsole" go: the program is already `dbdatakit`, the release tag prefix, the package and the image are already `dbdatakit`, so the one service that holds the sign-in, the pairing, the screens and the embedded runner is **DbDataKit**; the Workspace is a service of its own (section 3). "The console" may stay in prose as a plain noun for the web app; it is not a product, folder, project or service name.

**In the repository:** the top-level `DbDataKit/` folder (the shared libraries) becomes **`Shared/`**, and then `DbDataConsole/` becomes **`DbDataKit/`**, so the folder of the same name as the product is the product. The packages keep their names (`DbDataKit.*`, they are the libraries of the suite); the product's projects and namespaces `DbDataConsole.*` become `DbDataKit.Server*` (a name that does not collide with a library package is checked by the build), and `DbDataKit.slnx` keeps its name. The order is fixed: `DbDataKit/` to `Shared/` first, so the second move never meets an existing `DbDataKit/`. About 166 files mention the path `DbDataKit/` and 144 mention `DbDataConsole` (15 of them workflows), so this is a scripted change like the Proxy to Gateway rename (`scripts/rename_proxy_to_gateway.py`), done alone in a batch with nothing else in flight, because every open branch would conflict with it.

**On the machine:** one folder under one root for every service **or module** (a module is a part of a service that keeps files of its own, the Workspace being the case), named for it. Windows `%ProgramData%\DbDataKit\<service or module>`, Linux `/var/lib/dbdatakit/<service or module>`, with the layout `DbDataKit.Hosting.WindowsService.DirectoryLayout` already has inside it (`config`, `data`, `secrets`, `certs`, `logs`):

| Service | Today (Windows) | New |
| --- | --- | --- |
| DbDataKit (the console) | `DbDataKit\console` | `DbDataKit\server` (default; see D9) |
| Gateway | `DbDataGateway` | `DbDataKit\gateway` |
| Runner | `DbDataRunner\server` | `DbDataKit\runner` |
| Sync | `DbDataSync` | `DbDataKit\sync` |
| Build | (a project folder, set by hand) | `DbDataKit\build` |
| Store | `DbDataStore\server` | `DbDataKit\store` |
| Workspace | `DbDataWorkspace\server` | `DbDataKit\workspace`, with its own setting `DBDATAKIT_DATA_WORKSPACE` (section 6c) |

The Workspace folder (`projects/`, `workspaces/` with a git worktree per draft, `builds/`) is the one most likely to be moved on its own, to a bigger or faster volume, so it has a setting of its own (`DBDATAKIT_DATA_WORKSPACE`, section 6c) and nothing outside it refers to its path: the service's state keeps project ids and relative names, never the folder. One root setting (`DBDATAKIT_DATA`, default the root above) moves them all; the variable of one service (`DBDATAKIT_DATA_RUNNER`, `DBDATAKIT_DATA_GATEWAY`, and so on, section 6c) still wins for that one service, and `globalEnv` in each `dist.json` is only `DBDATAKIT_DATA`. The container images keep their `/data` volumes, which is not a path this plan changes.

**No migration (owner, 2026-11-10).** The suite is in the middle of a large clean break, so nothing here builds or keeps a way to move an existing install: the new services use the new folders and the new service name, the old folders and the old `DbDataKitConsole` registration are not read, moved or renamed, and a tester who has one removes it by hand. The one thing kept is the release note (SC31) that names the old and the new folders and the old service name, so nobody looks for their data in the wrong place. A data root that already holds something from an older layout is not touched.

## 6c. Environment variables (owner, 2026-11-10: first, to get the breaking changes in early)

**Today** (read from the code, 2026-11-10): about 60 variable names in six families, one per product: `DBDATASTORE_`, `DBDATARUNNER_`, `DBDATABUILD_`, `DBDATAWORKSPACE_`, `DBDATASYNC_`, `DBGATEWAY_` (and a leftover `DBPROXY_` in docs), `DBDATAKIT_CONSOLE_`, plus `DBDATA_` and `DBKIT_` (secrets, upgrade, children, tests). The same setting has a different name in every product (a data folder is `DBDATASTORE_SERVER_DIR`, `DBDATARUNNER_SERVER_DIR`, `DBDATAWORKSPACE_SERVER_DIR`, `DBDATABUILD_SERVER_DIR`, `DBDATAKIT_CONSOLE_DIR`, `DbDataSync__App__RepoRoot`; the state engine is `DBDATASTORE_STATE_ENGINE`, `DBDATARUNNER_STATE_ENGINE`, ...). About 407 files name one of the product-prefixed variables and 119 a test variable.

**The scheme.** Every variable starts `DBDATAKIT_`; **no product prefix survives** (`DBDATASTORE_`, `DBDATARUNNER_`, `DBDATABUILD_`, `DBDATAWORKSPACE_`, `DBDATASYNC_`, `DBGATEWAY_`, `DBPROXY_`, `DBDATA_`, `DBKIT_` all go). The service or module is a word in the name, not a prefix, so one name means one thing everywhere:

**Rules.** (1) The root moves everything: a service's folder is `DBDATAKIT_DATA_<X>` if set, else `<DBDATAKIT_DATA>\<folder>` (section 6b), else the default root; one machine variable, `DBDATAKIT_DATA`, is all a global install sets (the suite manifest's `globalEnv` shrinks from five variables to one, which is what keeps a command run by hand and the service on the same folder). (2) State: a per-service variable wins over the install-wide one, which wins over the SQLite default. (3) **An old name is refused, not read**: a service started with one of the names above that no longer exists exits with a message naming the new one (one list in one shared place, `DbDataKit.Hosting`), because a machine variable left behind by an older install would otherwise send a service to a new, empty folder without a word. That is the whole of the transition; there is no alias and no migration (D12). (4) One reader: the names are built and read in one shared class, so a product does not spell its own variable. (5) Names that are not settings of ours (ASP.NET's `ASPNETCORE_*`, `DOTNET_*`) stay as they are.

## 6d. Format versions that read forward (owner, 2026-11-10)

Sync refused a `task.yaml` that said `schemaVersion: 1` because the file kind is now 2, although 2 only adds the optional `checks:` section. The strict loader reads **only** the current number of a kind (`StrictConfigFile`), while published definitions already read two (`DbDataKit.State.DefinitionFormats`: the current format and the one before it). One rule for both:

1. **A kind reads `Previous` to `Current`.** `DefinitionFormats` is the one type that says so; a kind's `Previous` is `Current - 1` unless its entry says a longer range is compatible (`DefinitionFormats.Of`). A file whose version is in the range loads as it is.
2. **No check that an older file lacks the newer fields.** A version 1 file that was edited by hand to hold a newer section is read as it is written; that only happens to a person editing by hand, and policing it costs more than it saves.
3. **Every save writes `Current`.** The version is a property of the writer, not a copy of what was read: a file loaded as 1 and saved by Sync, the Console or Build is written as 2.
4. **Older than `Previous`** is refused with the text of what changed and what to do (`HowToMove`); **newer than `Current`** is refused with "update" (unchanged). A reader that only knows 1 still refuses a file of 2 when it loads it: forward compatibility is a property of the newer reader, never of the older one.
5. **A publish writes the current form** (owner, 2026-11-10): the publisher loads the file with the range-reading loader, normalizes it through the typed model, and sends the current-format text it wrote, never the raw bytes of the file on disk. A file that a person left at an older version, or edited by hand so that its version and its fields disagree, therefore never leaves the machine that could read both: everything published is in one format with a consistent version. The file on disk is left as the person wrote it (the normalized copy is only what is published, so comments and layout in the source survive). Readers of published definitions keep the existing rule of plan 24a (a reader reads its current format and the one before, so readers are upgraded before publishers).
6. **A restore from history writes the commit's files as they were** (D18): it does not rewrite the version, and does not refuse a format that is no longer read; the next save writes `Current`, and a restored file below `Previous` fails on load naming the file (`DbDataSync/docs/configuration.md`, "Restoring a replication from its history").
7. `docs/formats.json` keeps `current` and `previous` (the oldest still read) per kind; a bump adds the entry as before, and a kind's compatible range is the span between them.

The first use is Sync's `task.yaml` (reads 1 and 2, saves 2), which removes the need to edit the 67 files that say `schemaVersion: 2` back to 1; the table-mapping and script kinds get the same range from the same helper when their number moves. Every other loader of a versioned kind (connection, library, view spec, app manifest, package, check, model) is audited against the rule in SC50a.
