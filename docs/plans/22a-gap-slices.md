## Direction (decided by the owner, 2026-10-27)

The gaps came from a review of plans 13 to 21 against the data-flow diagram (`docs/suite-data-flow.md`). The seventh gap,
environments and promotion, is plan 21.

### 1. App authoring

Plan 16 described how an app is served, not how it is written, built, tested and versioned.

1. **Shared authoring.** The authoring machinery Build already has moves into a shared library (`DbDataKit.Authoring`), and both Build
   projects and app projects use it. That machinery is plan 13a's W02–W10:
   - git workspaces on the server, one per user (a branch);
   - the console's file tree and editor with diagnostics;
   - diff, commit and merge;
   - the Author role.

   The W slices still to come build it in the shared library instead of in Build.
2. **An apps back-end server** (DbDataApps) owns app repositories, builds and versions. It publishes built versions to the serving
   layer's `apps` module (plan 20), following the same pattern as Build and DbDataStore.
3. **The framework.**
   - Every app starts from one template.
   - The default library set is fixed: `@dbdatakit/shell`, `@dbdatakit/visuals`, and typed clients for DbDataStore and semantic
     queries.
   - Builds run on the server in a child process, offline, from vendored packages.
   - An **allow-list** lets an administrator add further packages. No other `npm install` runs.
4. **Declarative views are part of the framework, not a second kind of app.** The template ships components that render spec files
   (grid, form, detail page, dashboard). A new app can be nothing but spec files, and an author drops into code one page at a time.
   This replaces plan 16's "two kinds of app".
5. **One workflow for people and agents:**
   - create a workspace (a branch);
   - edit;
   - build and preview (plan 21: previews are read-only by default, with sandboxed writes on request);
   - commit and merge;
   - publish.

   A person does this in the console's editor. An agent does the same through MCP, with every step approved by its user as it happens.

### 2. Row- and column-level access rules

Plan 14 deferred row-level security ("not needed now"). With one serving layer, there is now one place to enforce it.

1. **Enforced in the serving layer**, by one policy engine applied to every module: Flight SQL, semantic, store, apps, MCP and feeds.
   Rules are added to the query before it runs and to the result's columns before it is returned. A module cannot bypass them.
2. **Rules are defined with the data's owner and published with it.**
   - Build defines rules on its models and semantic packages.
   - DbDataStore defines rules on its entities.
   - The rules travel with the published definition (plan 20, principle 1), so a promotion moves rules and data together.
3. **Rules are data, not a language (the owner, 2026-11-12, QG2).** Row rules are the rows of a **rules table** that a published Build model builds, in the same
   target as the table it filters, so a rule is a join and never a value list. A rule names the person or group, the column or columns (matched together as a
   tuple) and strict values, no wildcards. Rule groups are `match all` or `match any`, each rule `include` or `exclude`, the top level `match all` or `match any`.
   A group needs at least one include rule; a person with no matching row sees nothing; NULL is an ordinary value matched strictly (`IS NOT DISTINCT FROM`). A check
   lists the values no rule covers. The serving cache key holds a fingerprint of the caller's resolved rules. A rules table's refresh raises `data.changed`; a failed or
   stale refresh serves the last good rules with an alert and denies past the table's maximum age. (The grants entity, per-person attribute values and the rule
   expression of D3 that this section described before are gone; GP04's directory attributes stay for what else uses them.)
4. **An example:** the fact table `sales` has a rule: the rules table `region_access` (built by a Build model from the Store's table of who manages which region) has
   the rows (`east-managers`, `east`) and (`finance`, `east`), (`finance`, `west`); a person in `finance` sees the east and the west rows of `sales`.
5. **Column rules** are the same shape on metadata: (person or group, entity, column, treatment `hide`, `mask` or `null`), resolved when a model is described; a hidden
   column cannot be filtered, sorted, grouped or joined and a measure over it is hidden too. **Scope:** semantic models and Store entities; raw data sources keep their grants (D9).
6. **Later:** limits on non-production channels reading production data (plan 21 section 2b) use this same engine.

### 3. Catalog and search

1. **Built on the lineage graph** (plan 18). Every node is searchable: datasets, columns, jobs, semantic models and members, entities,
   apps.
2. **Descriptions and owners come from the definitions:** Build's model and column descriptions, DbDataStore model text, semantic
   member descriptions, app manifests. Nothing is typed twice.
3. **The glossary is a DbDataStore entity** (**dropped: the glossary is business knowledge per plan 27 decisions 35/36, git `knowledge: 1`; under the owner's 2026-11-08 hold**): terms, definitions, owners and links to nodes, with history and approval like any
   managed data.
4. **Agents use the same search** through the command surface (the `knowledge` commands of plan 27a KN16, which replace `catalog search` and `catalog show`), so "which table has customer
   churn" is a tool call.

### 4. Backup and recovery

| Part of the suite's state | How it is protected |
| --- | --- |
| Definitions (Sync configuration, Build projects, serving-layer configuration, connection definitions without secret values, app source, DbDataStore models) | **git remotes.** Each configuration repository can push to a remote the owner chooses (GitHub, Azure DevOps, any git server) on every commit. Published definitions can be republished from them |
| The secrets store's key | documented as a separate backup (plan 13 section on secrets); never in git; a DPAPI-bound key is machine-specific, so the docs say how to re-key on restore |
| Identity home, pairing and trust, audit, approvals, change requests, run history | on SQL Server or PostgreSQL (required for serving groups), **the database's own backups**. For single-instance SQLite installs, a small command (`<product> state backup` and `state restore`) archives the state database, with a restore test in CI |
| DbDataStore's data, the warehouse | the customer's database backups; Build can also rebuild the warehouse |

### 5. Delivery: alerts and subscriptions

1. **One delivery service**, shared code (`DbDataKit.Delivery`), used by both alerts and report subscriptions.
2. **Channels:** email (SMTP), Teams and Slack webhooks, and a generic signed webhook. Each channel is configured once per install,
   with its secrets in the secrets store.
3. **Alerts** come from monitoring (plan 13 W10): failed runs, late data, approvals waiting, expiring previews.
4. **Subscriptions** deliver a report or a view (plan 32) on a schedule, through the shared scheduler (`DbDataKit.Scheduling`).
   They are rendered under the subscriber's own identity, so access rules (section 2) apply to what is sent.

### 6. External monitoring

1. **OpenTelemetry** from every server and the serving layer: metrics, traces and logs.
   - Off by default, and turned on by one setting.
   - Exported to any OpenTelemetry collector; Prometheus scraping goes through the OpenTelemetry exporter.
2. **Traces follow a request across servers,** for example a query from an app through the semantic module to a database. Identities
   in traces are the user's id, never secrets or query parameters.
3. **The console's own monitoring stays.** OpenTelemetry is for operations teams who already have their own tools.

## The owner's order, and the reason

The owner wants **every breaking change to stored data and definitions done early**, so the slices are in waves and the first wave contains only the ones that fix
a stored format or a definition. Everything else can be built later without breaking what is stored by then.

| Wave | What it fixes or builds | Slices (all three plans) | Stored format changes? |
| --- | --- | --- | --- |
| **1. Formats and definitions** | 22 section 2 (rules travel with published definitions; the grants entity), 24 section 2 (a format version on every published definition; N and N-1 at pairing), 23 section 2 (check definitions stored with datasets; results retention), 24 section 3 (the `cache:` setting in definitions), the spec-file format of declarative app views, the glossary entity | UC01 UC02 GP01 GP02 UC03 FQ01 to FQ06 UC04 UC05 GP03 GP04 GP05 GP06 | **yes, all of them** |

| **3. The rest** | enforcement of access rules, check evaluation and blocking, alerts and subscriptions, backup and recovery, catalog, first-run bundle, upgrades, caching, OpenTelemetry, app authoring | the rest | few and each named in its row |

**One format bump, not three.** Rules (`access`), checks (`checks`) and the cache setting (`cache`) are all new sections of the same definitions (the semantic package, the
DbDataStore model, the serving data source). If each plan raised the format on its own, a definition would change three times. Decision **D1** below makes
them one bump.

## Rules for every slice

- The rules of `CLAUDE.md` ("Making changes") apply: one slice, one commit in a batch, "done" is the test, CI green and independently revertable, behaviour changes named, docs and
  the status line in the same change. A changed stored format is a **clean break** (plan 13 section 3): the old file or database is refused with a message that
  names it, never converted, and a test says so.
- **Wave 1 slices change a definition or a stored structure; their pull request says so in its first line** and lists the format ids it touches, so the owner sees
  the churn before merging.
- A slice with state runs on **SQLite, SQL Server and PostgreSQL** (`testenv/`: `up mssql postgres`, then `eval "$(testenv/testenv.sh env dbdatakit)"`); a screen
  has a Playwright test (`DbDataKit/tests/DbDataKit.Server.Web.Tests`); a library has unit tests.
- New state is a **state module with a declared retention rule** (29a Q05); scheduled work is a **runner task** of a system package (28a, `ConsoleSystemTasks`);
  published definitions go through the **publish API** of plan 30.
- **The editor screen for access rules.** `access/1` is a stored format a person authors; it is not finished until a screen edits it (the rule in `CLAUDE.md`, the row "Access rules" of `docs/ui-editors.md`, state `planned`). GP15's rules and grants screen is the viewer and explainer; the **editor** of a rule document (form and YAML, the loader's diagnostics as you type, save quoting the version, remove) is a slice to add here when GP01 is built, with the row's change to `partial` or `full` in the same commit. The same for the glossary: no slice until the owner's hold of 2026-11-08 ends.

## Risks

- **Format 2 stays open** until the first release that holds any of its sections. If a release ships with only `access`, the other two sections need format 3. The release note and the UC02 check prevent a silent edit of a released format.
- **The grants entity is gone (D9, 2026-11-08):** the data grants are the published definition's `grants` section and need no SQL Server or PostgreSQL storage connection, so a single-machine bundle (plan 23 section 1) on SQLite has them. Per-person values for row rules are rows of a rules table (QG2).
- **Pass-through SQL** cannot be filtered without a parser per dialect; QG3 refuses instead. A user who needs it asks for a semantic model.
- **Rules and the result cache** (plan 24 section 3) must agree: the cache key holds a fingerprint of the caller's resolved rules (GP10 gives it, GP11 wires it); UC12 is built and keys on all of a caller's attributes until then, which never shares across callers with different rules.
- **Plan 22 section 1 versus plan 27:** the Workspace server grows to host agent, integration, skill and knowledge projects. GP31 builds only the shell and the `workspace` module, so plan 27's slices add their kinds without a second break.
- **MailKit and OpenTelemetry are new dependencies** (QG6, QG11); each is added in its own slice with the version check, and OpenTelemetry's exporter packages must be stable releases (a prerelease is refused by the owner's package rules unless listed in `check_package_versions.py`).
- **Offline builds** (GP33) need Bun's cache layout to be stable between versions; `bun.pin` pins it and the slice's test fails when it moves.
