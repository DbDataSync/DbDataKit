Not built: the promotion item and the host of releases, a kind that declares a read slot, Build's channel targets, Sync's trial runs, the callers of the contract guard. This plan holds those.

## Decided, and what binds the slices

1. **Channels in one install**, not an install per environment. Promotion publishes the same version to the next channel; the definition does not change, what it is bound to does.
2. **Sandboxed writes for DbDataStore.** A preview or test channel writes into a **draft layer** only that channel (or that preview) sees; reads show the draft on top of the real data; closing a preview or resetting the channel discards it. Previews are read-only by default; the author turns writes on. **Drafts are never promoted:** "submit as change requests" turns draft rows into ordinary change requests in production, approved like any other.
3. **Promotion is per product, with dependency checks and releases.** A promotion is refused when something it depends on is not in the target channel at a compatible version. A **release** is a named, ordered list of per-product promotions: runs in order, stops at the first failure, says where, can be resumed; a sequence, not a transaction (the console says so). **One approval for a release**, by an approver who holds the approval permission for every item in it.
4. **Expand, then contract.** A change to a shared structure goes in three steps (add, move the consumers, remove later) because channels share databases. Where the suite can see the consumers it refuses the contract step, naming the package and the channel (a Build plan that drops a column a published package in any channel still reads).
5. **Connections per channel: inherit reads, override where needed.** A channel uses production's binding unless it overrides it; **writes are never inherited**: a write binding in a non-production channel is an explicit override that points somewhere other than production, and without one the channel has no write access to that connection (DbDataStore writes go to drafts). Lineage names a dataset reached through an override as its own node marked with the channel. Limits on non-production reads of production (row caps, masking) come with the access rules (plan 22a).
6. **Build, Sync, drafts, lifetimes.** Build's test target is created by an explicit command, never automatically (`channel target create dw --channel test` makes `dw_test` with Build's write login and records the override; `<schema>_<channel>` by default; on Oracle the schema is made by hand, on DuckDB it is a file); it is filled by **deferring to production** (only models changed in this version and their dependents are built, the rest is read from production's target; a sample build is a per-run option). **Sync runs in production only, with trial runs:** additive changes go straight to production through per-product promotion, a risky change gets a one-off, row-limited run into an overridden target in a test channel, never a continuous replication per channel. **Drafts are visible to everything the serving layer answers in that channel or preview** (the app, dashboards, semantic queries through the `store` module, agents) and **not to Build** unless a Build run into an overridden target opts in. A preview lives with its workspace and is removed with its draft when the branch is merged or abandoned; an idle preview expires after 30 days (configurable) with a notice first; a channel's own draft lasts until someone resets it, and a release may include a reset as a step.
