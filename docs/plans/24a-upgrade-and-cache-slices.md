## Direction (decided by the owner, 2026-10-27)

### 1. Upgrades

1. **The console drives upgrades.**
   - The console shows each paired server's version and the versions available.
   - It upgrades servers one at a time, using each product's own installer (MSI, package or image; plan 13 section L).
   - The shelved self-updater (`DbDataKit.Update.*`) stays shelved as a product and a service. Owner decision 2026-11-09: its code is used as code where it fits (UC09: the signed `release/1` manifest, `update-plan/1`, the swap with rollback), without reviving it.
2. **Serving groups upgrade rolling, draining first,** one instance at a time:
   - stop taking new work;
   - finish the queries already running;
   - upgrade;
   - pass the health checks (plan 20, health per module);
   - rejoin the group.

   If an instance fails its health check, the upgrade stops there, and the rest of the group keeps serving on the old version.
3. **State changes during an upgrade** follow plan 21's expand-then-contract rule for the suite's own state databases:
   - a release only adds what the previous release can ignore;
   - it removes what is no longer used one release later.

### 2. Compatibility

1. **N and N-1.** Every part works with the current and the previous release of every other part. This covers the console, the
   back-ends, the serving layer, the identity home and the published definition formats, so parts can be upgraded one at a time.
2. **Checked at pairing.**
   - A pairing, or a reconnection after an upgrade, exchanges release numbers.
   - A pair further apart than N-1 is refused, with a message naming both versions and what to upgrade.
3. **Checked in CI.** A compatibility job runs the previous release of each part against the current one: management API, pairing, publish
   and the serving protocols.
4. **Formats:** a published definition carries its format version. A serving instance reads the current and the previous format and
   refuses anything newer with a message, the same clean-break rule as configuration files.

### 3. Caching

1. **Results are cached in the serving layer, opt-in per dataset.**
   - The cache is off by default.
   - An owner turns it on per semantic model or data source, in its definition, so the setting is published and promoted with it.
2. **The cache key keeps rules and channels safe.** It includes:
   - the query;
   - the values of the access-rule attributes that apply (plan 22 section 2), so users with the same effective access share entries and
     no one sees another's rows;
   - the channel and any preview draft (plan 21);
   - the published version.
3. **Expiry on data change, with a time-to-live as a backstop.**
   - An entry is cleared when something it depends on changes: a Build load, a Sync run, a DbDataStore write, or a new publish. Lineage
     (plan 18) says which entries depend on what.
   - Each cached dataset also has a time-to-live, for changes the suite cannot see (a source written outside it).
4. **Where the cache lives:** in memory per instance, with an optional shared store for serving groups. An instance that misses fetches
   from the database as usual, so a cold or lost cache never changes results.

## The freeze rule of formats (UC02: written 2026-11-07, checked from 2026-11-08)

The rule is held by this section and, in part, by `scripts/check_formats.py` against `docs/formats.json` (UC02): the registry lists the formats of the table below that have a schema or a declared version, and the script fails on an edited frozen format and on a version bump without its entry. The rest is held by review. What the rule says:

1. **Every definition and file format has an id** (`model/2`, `connection/2`, `package/1`, the semantic package's `format` of its definition; the ids today are in the table below), a **current** number and the **previous** number a program still reads (N and N-1, plan 24 section 2.4).
   A program reads those two and refuses any other with a message naming the file or the definition and both numbers (`DefinitionFormat.Refusal`, `DBD-110`). Formats are numbered from 1 per kind.
2. **A format is open or frozen.** Open means it may still be edited: an unreleased format. It is **frozen from the first release that contains a section or a key of it** (the release note says so). Format 2 of the
   semantic package, DbDataStore's `model` and the serving data source is **open** until the first release that holds any of `cache` and `checks` (D5); then it is frozen.
3. **A frozen format is never edited.** Its schema, its loader's behaviour and its loader tests do not change; a change is the next number (N+1), and N stays readable. A change to a frozen format's schema or loader
   without a new number is refused, and so is a new number without a bump of the compatibility generation (`SuiteCompatibility.Generation`, UC04: the generation is what N and N-1 means for the whole suite).
4. **A format that holds nothing of the next format is not bumped.** A file is written in the lowest format that can say what it says (`connection/1` until it has `cache`, `catalog.Format` 1 until it has `cache` or `checks`), so an
   instance that reads only the old format keeps serving what it served, and only a definition that uses a new section needs an instance that reads it. The publish is refused when a live instance of the group cannot read it (UC01).
5. **Additive optional keys.** Keys added later to a section that no released program reads yet (the entries of `checks` until plan 23's check model, 23a FQ01) change nothing a program reads of a released file and need no new
   number. Keys added to a section that a released program does read, and new sections, are a new number once the format is frozen (see QU11).

| Format | Id today | Current / previous read | Status |
| --- | --- | --- | --- |
| Published definition (any kind) | `definition_version.format` | per kind, below | UC01 |
| DbDataStore entity model | `model/2` (`schemaVersion`) | 2 / 1 | open: gains `cache`, `checks` |
| Serving data source (a connection file) | `connection/2` (`schema`) | 2 / 1 | open: gains `cache`, `checks`, `grants` (22a GP03) |
| App view spec (a file under `views`) | `view-spec/1` (`schemaVersion`) | 1 / 1 | open (GP06): a newer one is refused naming kind, file, app and both numbers |
| Semantic package (the catalog) | format 2 of the definition (`Catalog.Format`) | 2 / 1 | open: gains `cache`, `checks` |
| Build model file (a model's `.yml`) | `schemaVersion` (absent is 1; `build-model`) | 2 / 1 | open: gains `checks` (23a FQ02) |
| Runner package | `package/1` | 1 / 1 | frozen by its release |
| Dashboard document | `dashboard/1` (`schemaVersion`, `kind: dashboard`) | 1 / 1 | open: new (plan 32 DBR02, registered as the kind `dashboard` by DBR10, `ViewDefinitions`); **one number with `report/1`** (`ViewsFormat.Current`), the shared core is versioned with both kinds |
| Report document | `report/1` (`schemaVersion`, `kind: report`) | 1 / 1 | open: new (plan 32 DBR02, registered as the kind `report` by DBR10); `docs/formats.json` is not on this base, so these two rows stand in for its two entries (one `version_source`, the core schema file in each `files`) |
| Management API / compatibility generation | `ManagementApi.Version` / `SuiteCompatibility.Generation` | own and one before | UC04 |

## Risks

- **The generation (D1) is a new idea in the suite.** If the owner prefers a rule on CalVer ("the previous stable release"), UC04 changes and UC07's matrix changes with it; the formats and instance rows do not. QU1 is the question to answer before UC04.
- **UC09 is where plan 24 meets the shelved updater.** The service swap with rollback is real work that `DbDataKit.Update.Service` already does. The slice may reuse that code without reviving the updater (QU3); if the owner wants no reuse at all, UC09 grows from L to a second L.
- **Format 2 open** (D5): a release that ships with only part of format 2 needs a format 3 for the rest. UC02's check and the release note guard it.
- **A cache serves wrong rows if a key is incomplete.** UC15 is the guard and has a negative test; UC12 does not turn the cache on for any definition by default (QU7 only sets the default time-to-live of one that opts in).
- **Data-change events (UC13) cross products.** A Build server that cannot reach the serving group falls back to the time-to-live; the console shows "events not arriving" so a long time-to-live is not a silent staleness.
- **Rolling upgrades need the serving layer's O05** (two instances behind a balancer in CI); until it exists UC11's test uses a test balancer and says so.
- **Images and package installs** are not upgraded by the console (QU3); a site that runs only containers sees UC08 and UC10's instructions, not an upgrade.
