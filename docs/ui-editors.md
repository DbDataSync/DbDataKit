# Editors: where a person authors and publishes what the suite stores

The owner's order (2026-11-08): **every feature that can be built and published has an editor screen in the console, the Build or Sync workspace, or the Gateway's screens.** This page lists each thing a person can author, publish or configure by file or command, where its editor is today, how complete it is, and which slice closes the gap. [ui-coverage.md](ui-coverage.md) is the other half: it lists screens and the actions on each object; this page starts from the things (every stored format of `docs/formats.json`, the `publish`, `save` and `set` verbs, the management routes, the plans) and asks whether a screen edits them.

Read as of 2026-11-08 from the code of `Shared/web/*`, `DbDataGateway/src/DbDataGateway.Server/Management`, `DbDataBuild/src/DbDataBuild.Cli/Server`, `DbDataStore/src/DbDataStore.Server`, `DbDataWorkspace/src/DbDataWorkspace.Server`, `Shared/src/DbDataKit.Runner.Api` and the plans' status lines, not from plan prose alone. The screens are shown by the console (`Shared/web/console`) at `/servers/<server>/...`; "Gateway" below is the Gateway's own screens (`Shared/web/gateway`), "Build" and "Sync" are the product screens of `Shared/web/build` and `Shared/web/sync`.

**States.** `full`: a person can create, edit, check and publish (or save) and remove it, from a screen. `partial`: some of that, the gap column says what is missing. `view-only`: the screen shows it and changes nothing. `none`: no screen. `planned`: not built, a plan owns it. A state other than `full` names the slice of the plan that owns the screen in the last column (`DBR27`, `GP18`, `SL12`: the id is a row of a plan in `docs/plans`), or carries its reason in parentheses: `none (reason)`. A "route" below is a management API route; "exists" was checked in the server's code. What a row says is built is evidence in the row: what the screen does, the names of its test ids, components and stories.

**The rule.** A stored format registered in `docs/formats.json` must have a row here with a state. `scripts/check_ui_editors.py` fails, naming the format, when one has none, when a row names a format that is not registered, a screen file (`Name.tsx`) that does not exist under `Shared/web/*/src`, a state that is not one of the five, a state other than `full` that gives neither a slice nor a reason, a `planned` row whose slice is not a row of a plan in `docs/plans`, a reference to a plan that no longer exists (`UEnn`), or a `Counts:` line that is wrong. A format that needs no editor gets the row and `none (reason)`. The same rule is in `CLAUDE.md` (everything built and published has an editor screen).

Counts: full 34, partial 23, view-only 4, none 4, planned 26.

The table is sorted by what blocks "ready to test soon" (apps, dashboards, reports, quality, runner scheduling), then the other gaps, then the planned, then what is complete. The Format column is the id in `docs/formats.json`; `-` means the thing is not in the registry (see "Not in the registry" below).

## How the screens are tested

A console screen has a Playwright story in `DbDataKit/tests/DbDataKit.Server.Web.Tests/tests`, a Sync screen in `DbDataSync/tests/DbDataSync.Web.Tests/tests`. Whether every screen above has one is not audited here (the stories named in the table were found by file name, not run); the Store's screens are the three `store-*.spec.ts` stories, which run the console against a Store server mocked in the page (`store-fake.ts`).

## What a screen delivers

A row is `full` only when the screen has all of this; a screen that lacks some of it is `partial` and the gap column says which.

1. **Where.** The screen lives in the product's own web module (`Shared/web/<product>`), shown by the console at `/servers/<server>/...`: the console's per-server screens (Runner, Store, Gateway) or the Build and Sync workspaces. No product has a web app of its own.
2. **Create or edit, check before saving.** The server's own diagnostics check the thing (never a second validator in the browser that can disagree), then save or publish, and remove where the rules allow. A refusal is shown in the server's words. Writes quote the version they read; a stale one is refused with the current.
3. **Roles as the server decides them** (Viewer, Operator, Author, Approver, Admin). The screen offers what the token allows and the server checks again; a control that is off says why.
4. **Test ids on every control**, `<area>-<thing>-<action>`, as the existing screens have them.
5. **Tests.** A component test (vitest, the screen without its calls, as `PublishView` is tested) and one Playwright story (console: `DbDataKit/tests/DbDataKit.Server.Web.Tests/tests`; Sync: `DbDataSync/tests/DbDataSync.Web.Tests/tests`): create or change the thing in the screen, see the server accept it, see the effect in the screen that reads it. A story contacts no host but its own servers (the pattern of `views-editor.spec.ts`).

The four states other than `full`: `partial` is a screen with some of the above (for example a text editor with the server's diagnostics and no form, or no story run end to end); `view-only` is a screen that shows the thing and changes nothing, by decision or because the thing is made by a machine (`view-only (reason)`); `none` is no screen, with the reason in the state cell when no editor is wanted (`none (generated, never edited by hand)`); `planned` is a screen that a plan owns and has not built. When the screen needs a route the server lacks, the route is part of the same slice (audited, role as the neighbouring routes), never a screen that writes a file around the server.

## Adding or changing a row

A change that adds a stored format, a screen, a route a screen calls, or an editor in a plan's slice changes this page in the same commit:

1. Add the row (Feature, Authored: how a person authors it today, Format: the format ids from `docs/formats.json` in backticks or `-` when the thing is not registered, Editor: the screen file (`Name.tsx`, which must exist), its test ids and its story, State, Gap).
2. Say the state by the definitions above. A `partial`, `view-only`, `none` or `planned` row names the slice of the plan that closes it (an id that is a row of a plan in `docs/plans`) or says why in parentheses in the State cell.
3. Update the `Counts:` line and the matrix of [ui-coverage.md](ui-coverage.md) (the screens and the actions on each object).
4. Run `python3 -I scripts/check_ui_editors.py` and `python3 -I scripts/check_ui_coverage.py`. A new stored format also goes in `docs/formats.json`, and then the check demands its row.

A plan that makes something a person authors, publishes or configures names its editor slice (a row marked as the editor) or the exemption, as plans 14a and 27a do.

## The relay to a runner

The console writes to a remote runner **route by route, as the signed-in person**. `ServerProducts.RunnerRoutes` (`DbDataKit.Server`) is the table of (method, route) to the role the runner itself asks for:

| Role | Calls |
| --- | --- |
| viewer | the reads, and `HEAD artifacts` |
| operator | run, pause, resume, `PUT .../owner` |
| admin | the package life cycle, `PUT artifacts`, `PUT definitions`, `PUT bindings`, `PUT settings/require_signatures`, `PUT .../labels` |

A publisher is also accepted where the runner accepts one. There is no blanket PUT or HEAD pass: a call that is not a row (a product's report of decisions, a webhook, any other path or method) is refused with "the console relays only its management calls". The token the relay signs carries the signed-in person's roles (never a console or service identity). The relay refuses before the runner is asked, with "This needs the <role> role on <server>, and you hold <roles> there", and the runner checks the same roles again from the token. The console's person holds admin, never publisher, and admin is not limited by owner. The embedded runner maps the same writes (`RunnerPublishApi.MapWrite` takes a caller resolver) and audits them. An upload has its own limits (no Kestrel body limit, 30 minutes, the runner's cap decides).

A new screen that needs a runner call adds three things: a row in the route table, its expected line in `ConsoleRunnerTests.Expected`, and its line in `DbDataRunner.Tests/RelayRolesTests.cs`, which pins the role to the real runner.
