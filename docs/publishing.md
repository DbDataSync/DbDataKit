# Publishing: how a definition reaches the serving layer and the runner

What is built of plan 30 ("one way to publish"), read from the code on 2026-11-09. What is left is [plan 30](plans/30-publishing.md). Channels and promotion rules are [plan 21](plans/21-channels-and-previews.md).

Back-end products (Build, the apps back end, DbDataStore, DbDataIntegration) **publish versioned definitions** to a *target group*: a serving group (the Gateway, plan 20) or a runner group (DbDataRunner, plan 28). The target runs from what was published and does not call the publisher. One mechanism, the `definitions` state module, serves both.

## The store (`DbDataKit.State`, `Definitions/`)

| Table | Holds |
| --- | --- |
| versions | every version of a definition, keyed by kind, name and number: the manifest as text, its SHA-256, the format of the manifest (`definition_version.format`, plan 24a UC01), what it depends on (`kind:name@version`), the files (path, SHA-256, size, media type, payload id), who published it, when, a note. Never changed or removed |
| serving | per kind, name and **channel**: the active version, the one before it and a staged version |
| bindings | per channel, kind and name: what each **slot** the definition declares (a connection, a secret, a data source) is bound to there |
| instance status | per instance, kind, name and channel: the version it holds and its state (`preparing`, `ready`, `active`, `failed`), the error; an instance that left the group is marked gone and removed by retention (`InstanceStatusStore`) |
| events | append-only: publish, stage, activate, switch, rollback, retire, bind; followers poll it and it is the audit of what a channel serves |

- **Publish** (`DefinitionPublisher`) validates with the kind's validator, stores the next version and points the channel at it (`serve`) or stores it as the channel's staged version (`stage`), in one transaction. The same content again changes nothing, so a retry is safe. `expected_version` is the optimistic check.
- **Activate** makes the staged version active; `ActivateIfAllReady` does it when every live instance reports `ready`. A failed preparation never activates silently; an administrator may activate anyway as a recorded choice. **Switch** points a channel at any stored version (promotion), **rollback** returns to the previous one, **retire** stops serving and keeps the versions.
- **Checks on every move:** declared slots must be bound in the channel (a missing binding refuses the move and names the slot; a slot declared `access: read` is read from production's binding when the channel has none, a write slot never is (the integration kind declares it per connection of a task in `package.yaml`, `access: read|write`, `ConnectionSlot.Access`; the agent kinds' model slots are all write): `DefinitionPublisher.ResolveSlots` says for each slot whether its binding is the channel's own or inherited); `depends_on` must be active in the target channel; a kind that is trusted code needs an approved version (`RequiresApproval`); a format that a live instance of the group cannot read is refused naming the instance (`DefinitionFormats`, `DefinitionFormat.Refusal`). `PromoteWithDependencies` moves a version with the dependencies it pins, in one transaction, and the matching rollback restores them (plan 32 DBR10).
- **Artifacts** are content-addressed payloads (`PublishArtifacts`, over `PayloadStore`): a file whose hash is stored is not written again. The runner side has the HTTP form: `HEAD` and `PUT /api/v1/artifacts/{sha256}` (refused when the hash differs), `PUT /api/v1/definitions/integration/{name}` with the manifest, the file list, `depends_on`, channel, `serve` or `stage` and `expected_version`, and `POST .../activate|switch|rollback|retire|prune`. Those routes (`DbDataKit.Runner.Api/RunnerPublishApi.cs`) hand every call to the shared library `DefinitionsApi` (`RunnerPublishing.Api`), and what is the runner's own sits in the hook of its kind (below); the runner keeps its own audit verbs (`runner.package.*`) and answer shapes (`already_stored`, `tasks`, `unbound`, a `202` while an activation waits for runs; client `DbDataKit.Runner.Client/RunnerPublishClient.cs`, which also promotes a version from one channel to the next).
- **Followers.** `DefinitionFollower` hands each subscriber (`IDefinitionSubscriber`) what its kind serves and then polls the events; a subscriber builds the new version before replacing the old one, and if it cannot, the old one keeps serving and the failure is reported. The runner's `StagingFollower` prepares a staged version (materialises files into the disk cache by hash, checks hashes) and reports to the instance status.
- **Activation and running work** (`ActivationHolds`): a run in flight finishes on the version it started with; activation of a runner kind holds the definition until its runs in flight end, then migrates the task's progress (plan 29 section 4.3).
- **Signatures.** A publisher signs the message of a version (the manifest and the path and SHA-256 of each file) with an Ed25519 key (`DefinitionSigning`, `ed25519:<key id>:<signature>`). The shared API verifies it against the group's trust store (`DefinitionTrustStore`: the keys each kind trusts; add, revoke; rotation is a new key and a revocation) and stores the signature and signer with the version. Signatures are required for every kind unless an administrator sets the kind optional (`PUT /api/v1/settings/signatures/{kind}`) or marks the group `test` (`PUT /api/v1/settings/group`); an invalid signature is refused wherever they are optional. The runner uses the same trust store (`RunnerPublishing.Trust`, `GET /api/v1/trust/integration`, `PUT .../keys`, `POST .../{keyId}/revoke`) and keeps its own switch: `require_signatures` (off by default) says whether an unsigned version is refused; a signed one is always verified. **Instances verify at preparation** (`VersionSignatureGate`): a version that carries a signature is verified again over the manifest and files as stored, against the trust store (an untrusted key or a signature that does not hold refuses the version; a key revoked since does not unseat what it signed), and an unsigned version is refused only where the host says it needs one: the Gateway for a kind an administrator set to `required` (`SignaturePolicy.RequiredByAdministrator`, not the default for a kind nobody set, because the per-kind routes still publish unsigned versions), the runner when `require_signatures` is on. A refused version is not served; the one served before keeps serving and the host reports why (`DefinitionFollower` `gate`, `GatewayVersionGate`; `StagingOptions.Gate`, `RunnerVersionGate`: the version fails its staging on that instance). The screens: the Gateway's Publishers page (`/trust`, `TrustPage.tsx`) and the runner's Publishing card (`PublishingSettings.tsx`) draw the shared `TrustStore` (`@dbdatakit/shell`): keys per kind, add (a public key is pasted), revoke after asking, the requirement per kind and the group's `test` mode.

**Promotion between groups** (plan 30 PB06). `DefinitionPromoter` (`DbDataKit.State`) moves a version from one group to another over their shared APIs, each reached through an `IDefinitionsLink` (a request relative to `/api/v1/`): it reads `GET definitions/{kind}/{name}/versions/{n}` (the manifest, format, `depends_on`, files by hash and the signature) from the source, asks the target `HEAD artifacts/{sha}` for each file, reads only the missing ones (`GET artifacts/{sha}`) and sends them (`PUT`), then publishes the same manifest in the channel asked (`mode` the kind's default unless `serve` or `stage` is asked) with the signature, which the target verifies against its own trust store. The target's checks decide: a slot its channel does not bind and a dependency that is not active there refuse the move naming it (nothing is stored; the files stay and are not sent again). `PromoteRequest.Bindings` writes the target channel's own bindings first (slot to the name of what it is bound to there). The groups number their versions on their own; the same content again changes nothing and sends nothing. The source is read as a viewer or an administrator (a publisher may not read a runner), the target is written as a publisher or an administrator. `RunnerPublishClient.PromoteToGroupAsync` and `dbdatarunner package promote` are the client and the command for two paired runners (`PromoteAsync` moves a version between channels of one group); tests: `PromotionTests` (two in-process groups) and `PublishPromotionTests` (two runner servers). **The console's action:** `POST /api/promotions` of the console (`ConsolePromotions`) runs the promoter as the signed-in person over two links: a registered runner through `ConsoleRelay.SendAsAsync` (the relay's table and roles apply, the answer stays a stream) and the console's embedded runner in this process; the Packages screen of a runner shown by a console has the **Promote** action. Tests: `ConsolePromotionTests`, `EmbeddedRunnerTests`. **Releases of Gateway definitions** (plan 21 CH02): a release item of product `gateway` promotes a Gateway's `semantic-model`, `data-source`, `entity-model`, `dashboard`, `report`, `report-catalog`, `app` or `app-nav` the same way, between two registered Gateways, as the person who starts the release; the relay passes a Gateway's publish routes with the role each needs (`ServerProducts.GatewayRoutes`, the Gateway's own roles: a viewer reads, an administrator or a publisher writes) and the approval permission of the item is the administrator role on the target Gateway.

**Kind hooks.** What one kind adds to the shared API is an `IDefinitionKindHook` (`DbDataKit.State.Api/DefinitionKindHook.cs`; every member has a default that adds nothing, so a kind without one is published as before): the channel a host serves (`CheckChannel`), checks before a version is stored (`BeforePublish`: names, the trigger loop) and what follows (`AfterPublish`: the task projection, extra answer fields), the life-cycle calls a host does itself (`ActAsync`: the runner's progress migration, the runs in flight, the holds of an activation, the sandbox run), the checks around a binding (`BeforeBind`/`AfterBind`: the posture of a binding that shares production's connection, which answers its own body; `BeforeUnbind`/`AfterUnbind`), its own list and description, whether a publisher may read, the status a refused registry rule answers and whether signatures are required (the runner's `IntegrationKindHook`). The Gateway has hooks too (`GatewayDefinitionsManagement.HooksOf`; `SemanticModelKindHook`, `DataSourceKindHook` and `EntityModelKindHook`, each a thin adapter over the checks of the per-kind route in `GatewaySemanticModels`, `GatewayDataSources` and `GatewayEntityModels`): a check that waits (`BeforePublishAsync`, the data source's test query and the table and column reads of a model), the request body (`PublishHookContext.Body`, where `adopt` is), the owner a definition names in its content when the group's settings hold none (`OwnerOf`: the stamp `managed_by` of the per-kind routes), a read refused by the owner rules (`BeforeRead`), the serving at once on the instance that took the publish and the audit entries of the per-kind route (`semantic-model publish`, `data-source write`, `data-source adopt`). The caller's `Context` is the management caller. The manifest of a publishing client carries its own stamp (it is signed, so the Gateway checks the line and does not add it); a model is published under its lower-case name; the format is read from the content when the body gives none (`DefinitionKind.FormatOf`). While the per-kind routes publish unsigned versions, these kinds ask for a signature only where an administrator set the kind to `required` (the instances' rule), not by the group's default. A hook says no by throwing `DefinitionsRefusalException`; the API audits it as a refused call. A host passes the hooks and its own audit callback to `DefinitionsApi`; the caller's `Context` carries what the host knows of it (the runner's actor).

**The client.** `DefinitionsClient` (`DbDataKit.State.Api`) is the caller's side over an `IDefinitionsLink`: `HEAD` and `PUT artifacts/{sha256}` for the files the group lacks, `PUT definitions/{kind}/{name}` (the manifest, channel, mode, `expected_version`, `depends_on`, format, extra body fields), `PUT bindings/...`, the reads, and the signature: it asks `GET trust/{kind}` and signs when the group trusts its key, goes unsigned when the group does not require signatures, and refuses before sending, naming the key and the administrator's call, when the group requires them and does not trust it. Build's `ProxyPublisher` publishes its data sources and models with it.

## The registry of kinds

`DefinitionKinds.Register(new DefinitionKind(name, targetTypes, defaultMode, requiresApproval) { Formats, FormatOf, slots, validator })`. A publisher built for a target type refuses a kind that does not list it. Registered today:

| Kind | Target | Default mode | Where |
| --- | --- | --- | --- |
| `integration` (runner package, `package/1`) | runner | `stage`, activated when every runner is ready | `DbDataKit.Runner/Hosting/RunnerPackages.cs` |
| `dashboard`, `report` | serving | `serve` | `DbDataKit.Views/Publishing/ViewDefinitions.cs` |
| `semantic-model`, `data-source`, `entity-model` | serving | `serve` | `DbDataGateway.Server/Serving/ServingKinds.cs` |
| `app`, `app-instance`, `app-nav`, `app-approval` | serving | `serve` | `DbDataKit.Apps.Instances/AppDefinitions.cs` |

The Gateway's stores (`PublishedSemanticModels`, `PublishedDataSources`, `PublishedEntityModels`, `AppInstanceStore`) publish through `DefinitionStore.WithRegistry(ServingKinds.All, "serving")`: the kind's validator, its format and the dependencies being active in the channel are checked on every publish. No serving kind declares a slot yet. The shared HTTP API (`DefinitionsApi`, `DbDataKit.State.Api`) is mounted on the Gateway's management listener for these kinds and for dashboards and reports: artifacts by hash, publish, activate, switch, rollback, retire, prune, bindings and reads under `/api/v1/artifacts`, `/api/v1/definitions/{kind}/{name}` and `/api/v1/bindings`. The per-kind endpoints are still there and write the same rows (they go when Sync is operational on the runner, plan 30 PB02).

## Rules that hold for every kind

- **A channel is part of a version's key** (preview, test, prod). Promotion publishes the same version to the next channel; bindings, not the definition, differ between channels.
- **The publisher is a paired Publisher** with an owner scope (plan 13 W12): it sees and changes only what it published.
- **Versions are kept** until an administrator prunes them (owner, 2026-11-04), through an API and a screen that show the active, staged and previous versions, each instance's status and what pruning would remove; an artifact goes when no kept version names it. `DefinitionPublisher.Prune` removes the versions an administrator names (or all but the newest N), never one a channel has active, staged or as its previous, nor one another version pins in `depends_on`; a file goes when no kept version names it. It is `POST /api/v1/definitions/integration/{name}/prune` on the runner and `POST /api/v1/definitions/{kind}/{name}/prune` on the Gateway's management listener (administrator; body `keep` or `versions`, and `dry_run`, which is true unless the call says false). The runner's `PackagesPage.tsx` and the Gateway's models screen show the dry run before the button that removes works. The console's versions panel of dashboards and reports (UE04) uses it too; plan 14a SL07 does not yet.
- **Clean break, not silent:** a version in a format the program does not read is refused naming the kind, the name and both numbers.
