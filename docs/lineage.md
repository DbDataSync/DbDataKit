# Lineage across the suite

Every dependency and data flow in the suite can be traced both ways: **downstream, for impact** (what reads this column, table, measure or entity, and what breaks if it changes) and **upstream, for provenance** (where a number or a row came from). The library is `DbDataKit.Lineage` (README beside the code); the graph view's choice of library is in [lineage-graph-view.md](lineage-graph-view.md).

The rules of the first version, decided by the owner:

- **Best effort.** Column level wherever a product knows it, table level where column level is too complicated or unavailable. **A gap is shown as a gap, never filled by a guess.**
- Manual lineage entries, export to OpenLineage and tracing a value back from a result are later features, not built. The model maps onto OpenLineage so export is an addition, not a redesign.

| DbDataSync | each replication's table mapping as `replicates` edges and column mappings as column edges, with the last run's rows | `SyncLineage`, `SyncLineageRuns`, kept by `LineageKeeper` in Sync's `lineage` state module |

| DbDataGateway | its data sources and the tables they serve, with a per-table summary of reads (count, last read, readers: never per query); the semantic models it serves, their members bound to the columns they read, and `serves` edges to the model and the data source | `GatewayLineageGraph`, `GatewayLineage`, `TableReadStore` |

## The model

**Nodes** (`NodeKind`): `dataset` (a table or view, a file, a Store entity, an extracted table), `column`, `job` (a replication, a load, a copy, an extraction), `semantic_member`, `serving` (a data source, a feed, a semantic package), `consumer` (an app, a dashboard, a report, an agent action), `external_system` (a system outside the suite a task reads from or writes to: `external://<kind>/<name>`, `ExternalSystemLineage`, laid by the runner's lineage route from what tasks report; additive, written `externalsystem` on the wire like the other kinds) and `deployment` (its `deployment` property says package, version, channel, group, instance, runtime or run). A node says when its upstream is unknown (`UnknownUpstream`), so "nothing flows here" and "we do not know" are different.

**Edges** (`EdgeKind`, running upstream to downstream, each at `column` or `table` granularity): `replicates` (source to target through a Sync replication), `derives` (upstream columns to a Build model's column, with the transform as detail; table level for a native model), `copies` (a Build copy's origin to its table), `binds` (a column to a semantic measure or dimension), `serves` (a dataset or semantic model to a data source or feed), `extracts` (a document to its extracted tables), `reads` (a consumer to what it queries), `promotes` (an ad hoc table to the Store entity made from it), `deploys` (package to versions, a version to the channel that serves it, a channel to the instance that holds it, a group or runtime to its instances) and `runs` (a deployed version to a run that named it).

**Confidence**: each edge is `declared` (written in a definition), `derived` (computed, as Build's analysis does) or `observed` (seen in a run).

**Two layers.** Design lineage comes from definitions and is replaced whole when a definition changes. Run lineage (`EdgeRun`: when, outcome, rows) is attached to design edges, only along an existing design edge; its history follows the server's retention of other run detail (`LineageKeeper` calls `PruneRuns` with it; Sync calls it with its 30 days, and the module's own retention rule removes them too). The graph refuses a missing end, a self edge and a cycle, naming them.

## Identity

The same table must be one node everywhere. `LineageIdentity.Dataset(connection, schema, table)` gives the OpenLineage-shaped `namespace` (`engine://server`) and `name` (`database.schema.table`) from a `connection/1` definition: host lower-cased, the machine's own names one, the engine's default port left out, SQL Server's `tcp:` and `host,port` read, a named instance part of the server, names folded by the dialect's case rule, a DuckDB file by its path. Columns add the column name; suite objects (a replication, a model, a measure, an entity) are `suite://<instance>/<kind>/<name>`. A connection with no login in the environment gets a placeholder host of its own name so nothing joins wrongly. The engine's default port comes from the engine registry's `default_port`.

## Where it lives

- **Each server owns the lineage of its own objects**, builds it from its definitions and runs, and serves it: `GET /api/v1/lineage` on a Build server (all hosted projects as one graph, with what was left out in `problems`), on a Runner and on a Gateway, `GET /api/lineage` on a Sync server, all viewer role, in one strict wire form (`LineageJson`; a document of another shape or with an unknown kind is refused saying where). The wire carries design lineage and, optionally, `runs` (the newest `EdgeRun` of each edge: `LineageJson.WriteRuns`); a Sync server and a Gateway send them, the console joins them (the newest per edge) and the Lineage page marks a failed run on its line red, an overdue one amber and the others green. A run may say `late` (additive): the server worked out with the shared rule `Overdue` of `DbDataKit.Monitoring` (`LineageFreshness.Mark`, from an expectation of how often the edge runs) that the edge is overdue; Sync sets it for a replication that loops with a frequency (late after two passes), the Gateway sends the last read of a table as a run of its `serves` edge and has no expectation.
- **Commands** on the shared surface: `DbDataKit.Lineage.Cli` gives the `lineage` noun (`graph [--kind]`, `impact <node> [--depth]`, `provenance <node> [--depth]`, each with a declared schema, so also `--format json` and `ui mcp`). It is mounted on Build's server command line, the Runner's, the Gateway's (over its local channel, so the names of a table's readers are in the answer) and on Sync's command line, over the replications of its repository (offline; the runs are the running server's).
- **The Gateway's graph** (G08, G11b): a `serving` node for each data source and each served semantic model; a `serves` edge from a table to the data source that serves it (*observed* when statements read it, *derived* when a served model names it); for each measure and attribute of a served model a `semantic_member` node, a `binds` edge from the column it reads (the table, with the expression as the detail, when the catalog's column is an expression) and a `serves` edge to the model. The member nodes carry the Gateway's own instance in their id (`suite://<gateway>/semantic/<model>/<member>`), so Build's node for a measure and the Gateway's are two nodes that meet on the column they are bound from, and a measure's path from the source table through the Sync replication and the Build model to the Gateway is a path of that column. The tables of a data source are not listed in the graph (that would read the database on every call): a data source shows the tables something read or modelled. **The run summary** of a table is on its node as properties (`reads`, `last_read`, `reader_count`, `readers` for an administrator): counted from the statement text by a scanner (`SqlTableReferences`), kept in the Gateway's state module `table_reads` as one row per table and reader (never a record per query, which belongs to the Gateway's activity), under the 30 days of run detail the Gateway keeps.
- **Queries** (`LineageQueries`): `Impact`, `Provenance` (breadth-first, by distance, bounded; `Truncated` says it stopped with more to follow), `Path` (the shortest chain, null when data does not flow that way), and the `Gaps` reached, so agents ask "what would break if I drop this column" with the same answers the console gives.
- **The console joins** (`ConsoleLineage`): `GET /api/lineage` asks every reachable Build, Sync and Runner server through the relay as the signed-in person, keeps an answer 30 seconds (`?refresh=true` asks again), joins the graphs by identity and returns it with what each server said (its size, its problems, or why it gave none). A failing server is named and left out; graphs that together would make data flow in a circle are said, not hidden. `?node=&direction=downstream|upstream&depth=` is impact or provenance across all servers.
- **Check results on the graph** (plan 23a FQ16, `LineageQuality`): `GET /api/lineage` on the console also asks the servers that evaluate checks (`ConsoleQuality`) and puts the status of a dataset's checks on its node as properties (`check_status` is the worst of `blocked`, `fail`, `error`, `pass`; `check_count`, `check_failing`, `check_blocking`, `check_blocking_ids`, `check_blocked_since`), matched by the dataset's lineage identity (a result for a dataset the graph does not have is left out). The answer's `blocks` lists, for each blocked node, its checks, since when, and what its block stops: the nodes downstream of it by the same impact walk, columns left out (a warn check stops nothing, D7). `DbDataKit.Monitoring` has the matching rule `HealthRule.CheckFailed` (`HealthEvaluator.EvaluateChecks`, over `CheckReading`; `QualityHealth.Findings(store)` reads the `quality` module with it): an error for a failing check that blocks, a warning for one that only warns or could not run.
- **A store** (`LineageStore`, the `lineage` state module: nodes and edges keyed by hashes of their identities, a version per owner, runs; SQLite, SQL Server, PostgreSQL) exists in the library and is tested; a server that keeps its graph there uses `LineageKeeper` (replace the design only when it changed, lay the newest runs along its edges, prune the runs older than its retention of run detail, read back the graph and the newest run of each edge): Sync does (G07b, G16), so an edge keeps its last run after Sync's own run history was pruned; the others build their graph on request.

## Visualizations

The **Lineage** page of the console (`/lineage`) draws the joined graph with `LineageGraphView` in `@dbdatakit/visuals` (React Flow laid out by dagre). It starts at table level and a dataset opens to its columns; a search by name or id selects a node and marks what feeds it on one side and what it feeds on the other, with the rest dimmed; servers are listed under it with what they left out. Unknown upstream and table-level edges are drawn apart from known and column-level ones, and every view has a list form and the commands' JSON.

## Decisions

- Run lineage history follows the servers' retention of run detail, not a setting of its own.
- Tracing a value back from a result or a visual is later.
- The Gateway's run lineage is a summary per served table, never per query; a per-query record belongs in the Gateway's activity log.
- The graph library: React Flow with dagre; ELK is kept as an option if needed ([lineage-graph-view.md](lineage-graph-view.md)).
