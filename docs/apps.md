# Apps: publishing, navigation and instances

How an app is published, where its code runs, what it may do, how it is addressed and navigated, and how one app or one DbDataStore model is published more than once. The host is the `apps` module of the serving layer ([serving-layer.md](serving-layer.md)); the code is `DbDataKit.Apps.Manifest` (manifest, validation, egress policy), `DbDataKit.Apps.Instances` (apps, instances, approvals, storage) and `DbDataKit.Apps.Host` (the shell, the token broker, the data gateway), hosted by the Gateway's `GatewayAppsModule` (`modules: [apps]`, https, default port 8818).

## Terms

| Term | Meaning |
| --- | --- |
| **App** | the source, the manifest and the built, versioned bundle: the published definition `app/<name>`. It has no address |
| **Instance** | one publication of an app (or of a Store model): a name, the version it runs (a pin, or the channel's current), settings, data bindings, roles. Two instances of one app share code and nothing else: the published definition `app-instance/<name>` |
| **Channel** | the lifecycle stage of an instance (plan 21): preview, test, prod. A channel is *when*, an instance is *who for* |
| **Navigation set** | a named, ordered list of instances shown as one menu (definition `app-nav`) |
| **Portal** | an app of `kind: portal` whose job is to be the shell other apps are mounted into |
| **Host** | a serving group running the `apps` module |

## Where code runs

An app is untrusted UI: the servers it calls check everything. What needs protecting is the person's session on the host, and the browser protects per **origin**.

- **Declarative views** (an app of `views/*.yaml` only, no `entry`) are drawn by the host's own script, which the host serves into the same **sandboxed document** a code app gets (below, "Apps of views only"): the YAML is data, the code is the host's, and it has no more reach than a code app.
- **Code apps** run in a **sandboxed document**, the default: the host serves the app's files under `/apps/<instance>/_app/` with `Content-Security-Policy: sandbox allow-scripts allow-forms allow-popups`, an opaque origin with no cookies, storage or access to the host's pages. The host's **shell page** at `/apps/<instance>/` frames it with `sandbox="allow-scripts allow-forms allow-popups"` (never `allow-same-origin`), runs one script of its own (`/apps/-/shell.js`) and hands the app a short-lived token and storage over `postMessage` (`{dbdata:"app/1", type:"token.request"|"storage"|"route"|...}`; the script answers only the app's own frame). The bundle under `_app/` is not behind the sign-in, because an opaque origin sends no cookie; it is code the group published, and data goes through a token.
- **An origin of its own** (a subdomain or custom domain per instance) is the other option. The manifest accepts `origin: sandbox | own`, but no domain binding exists, so `own` is not served on an origin of its own yet (see plan 26).

Sign-in is the identity home's (`OpenIdClient`, a public PKCE client): nobody signed in is sent to the home, a person with no role on `app:<instance>` gets 403. Sessions are in memory per instance (8 hours, an HttpOnly cookie scoped to `/apps/`, `SameSite=None; Secure` so a portal on another site can frame an instance); the home is asked again every `Apps.RolesRefreshSeconds` (300) so a role taken away stops working, and a refusal (`invalid_grant`) ends the session.

## Apps of views only

An app whose manifest names `views` and no `entry` is declarative: its package holds `app.yaml` and `view-spec/1` files (a grid, a form, a detail page, a dashboard over the entities of a Store model the manifest lists; the format is in the [Apps.Manifest README](../Shared/src/DbDataKit.Apps.Manifest/README.md)). Nothing of the app runs; the host draws it.

- **The page.** `/apps/<instance>/_app/` is generated (`ViewsApp.Document`): `views-app.js` and `views-app.css` (the host's runtime, below) and the app's specs as one JSON element in the page itself (`<script type="application/json" id="views-data">`; a sandboxed document has an opaque origin, so it could not `fetch` them without CORS headers the host does not send; the same JSON is at `_app/views.json`). The first view in the manifest's `views` is the home; the others are a menu (a view with a required parameter, an edit form or a detail page, is reached by a link). A file that does not read is listed on the page with its file, line and column, never a half-drawn screen. The document gets the instance's policy like any app's: sandboxed, `default-src 'self'`, no `unsafe-eval`, only the origins an administrator approved.
- **The runtime** is the web build of `Shared/web/view-app` (`@dbdatakit/view-app`): the shared controls of `@dbdatakit/store-ui` (field controls, the Store client, violations) and the renderers of `@dbdatakit/visuals` (`VegaChart` for a bar or a line, `DataTable` for a table), bundled to one script and one stylesheet. The Gateway serves it from the `apps-views` folder beside the program (`ViewsRuntime`): `dotnet publish -p:BuildViewsRuntime=true` builds and copies it (the Windows publish script and the Dockerfile do), and an ordinary `dotnet build` copies it when it has been built. A Gateway without it answers an app of views with a 503 that names the folder and the build.
- **Data** is read and written the way a code app does: through `/apps/<instance>/_data/api/v1/models/...` with the token the shell page asks for (the identity home's, below), so the manifest's `models` scope, the person's role on the instance and the Store's own validation decide everything. Four calls: `schema` (new for this: `GET .../models/<model>/schema` answers `ModelSchemaJson` for the entities the manifest lists and nothing for a model it does not), rows, one row, changes. A grid and a dashboard read the entity's rows (up to 2000 of one entity; a note says when there were more) and filter, sort, page and total them in the browser; the Store has no query language for it yet.
- **What each kind does.** *Grid*: columns under their labels, a text filter per `filters` attribute, a click on a sortable header sorts, `pageSize` rows a page, `links` (per row or of the page). *Form*: the spec's fields drawn with the model's own control for each (type, length, allowed values), `required`, `readonly` and `help` from the spec; a create form inserts, an edit form (`key` names the parameter that carries the row's key) updates on the version it read; a Store refusal (422) is drawn against the attribute it names, a conflict (409) says to reload. *Detail*: the sections' attributes of one row. *Dashboard*: `metric` (a figure), `bar` (the greatest `limit` groups), `line` (the first `limit` in order), `table`, and `embed` (a report of a report server, below: no entity, no data). A detail or edit view is addressed by one key attribute; an entity with a composite key is refused with that said.
- **Routes.** The shell keeps the address after `#` (`/views/detail.yaml?code=NA`): the runtime tells it the view the person moves to and follows it when the address or the back button changes, the same `route` and `navigate` messages a code app uses.

### Dashboards and reports in an app (plan 32 DBR13)

An app lists a `dashboard/1` or `report/1` file under `views` like any view file (`views/overview.yaml`, [views.md](views.md)): a file whose `kind` is `report`, or `dashboard` with the `layouts` of a dashboard document, is read by the views loader and not as a `view-spec/1` (the mini dashboard of a view spec has no `layouts`). `app validate` and the Gateway's publish check load it with its file and line and check it against the manifest (`AppViewDocuments`, `DbDataKit.Views`; a tool without the views loader warns `DBD-APP-023` for each such file and checks nothing): every semantic model its widgets query is under `semantic`, every Store entity a `store` query reads is listed with `read` (`DBD-APP-024`); every drill and every link leads to a view, report, dashboard, page or form **of this app** (a name is the file's name without folder and extension, a page is a custom page of the manifest) with the names, types and required parameters the target has (`DBD-VIEW-039`, `-044`, `-045`, `-037`); a `type: custom` widget names `<this app>/<Export>` of a widget the manifest declares, gives only the parameters that widget declares, the required ones and each of its type (`DBD-APP-025`). A table column or a matrix value that is an **attribute** may carry a `link` (plan 32 DBR51: `display: icon` with `icons`, `many`, `link: set-status`): the cell is drawn as a button only where the host passes `onLink` to the view (`DashboardView`), which is the hook for the shell's dialog and panel (DBR36) and for an action (DBR53: not built); without a host that follows links the cell is plain text, which is also what print and export draw. `app validate` checks the link names as it checks `on_click` (`DBD-VIEW-036`) and the app's targets (`DBD-VIEW-039`). **Not built:** drawing these files in the app's runtime (`ViewApp` does not draw them yet and the host leaves them out of its menu), the portal home's `dashboard` block, and dropping the mini `dashboard` kind of `view-spec/1` (the template and the territory sample still use it; decision in plan 32 DBR13).

## Starting an app: the template and the library set

`apps new --dir <folder> [--name <app>]` makes a code app from the template (`DbDataGateway/templates/apps/app`, inside the program): `app.yaml`, `index.html`, `package.json` and `src/` with a React entry that draws the Store's own grid and form and the file that connects the app to its host. `apps build` bundles it (Bun) and `apps validate` and `apps publish` take the folder it makes. What an app imports without asking anyone is the **default library set**:

| Package | What it gives an app |
| --- | --- |
| `react`, `react-dom` | the framework the libraries below draw with |
| `@dbdatakit/store-ui` | the Store's controls: a grid of an entity's rows, a form made from the model, history, field controls, the Store client; the server's refusals are shown against the field they name |
| `@dbdatakit/visuals` | the renderers: `VegaChart`, `DataTable`, the dashboard and view components |
| `@dbdatakit/semantic-client` | a typed client for semantic queries (`query(model, {measures, attributes, filters, order, limit})`, `catalog`, `models`) over a `fetch` the host supplies; the apps host serves its route ("The semantic route" below, plan 22a GP35c) |
| `@dbdatakit/view-app` | the app's connection to its host: `connectHost` (the shell's token and route messages), `appStoreClient`, `appSemanticClient` |
| `@dbdatakit/views-sdk` | the code of a custom view (below): `defineWidget`, `definePage`, the props a host gives a view, `useReady`, `PageBreak`, `HostLink`, `useSetParam`, `useOpen`; imports only React |

**Spec files in a code app (GP34).** The template's screens are `view-spec/1` files under `views/`, listed in the manifest's `views`; the library's components draw them (`ViewApp` of `@dbdatakit/view-app`, the same grid, form, detail page and dashboard as the host draws for an app of views only, on the Store controls and the visuals). `apps build` reads the files with the host's own loader and hands the bundle `src/views.generated.json`, so the app draws what `apps validate` checked and a file that does not read is listed on the page, never half drawn. An app can be **only spec files**. One page can be **code**: a component in `src/pages/` registered in `src/pages/index.ts` (`{'pages/quota-report': {title, component}}`, props `client` (the Store client), `params` and `go`) is a menu entry beside the specs, on the same client and token; a code page whose key is a view file is drawn in place of that spec, and to remove a spec for good the author deletes the file and its line in `views:`. The other specs are untouched either way.

`@dbdatakit/shell` is the console's shell (Monaco, router, query cache), not an app's: navigation belongs to the host's shell page (decision 2), so it is not in the default set. The packages come from a **vendored store** (`Shared/web/app-store/build.mjs`), not from a registry (next section).

## Custom views: a widget or a page written as code (plan 32 section 9f, DBR30)

A dashboard or report can place **a component of the app** (`type: custom`, `component: <app>/<Export>`, see [views.md](views.md)), and a whole dashboard or report can be **a page written as code**. Both are app code in the sandboxed document, built offline from the vendored store; the host never lets them fetch data on the paths that print or email: the view **declares its queries**, the host runs them as the viewer (as the subscriber for a subscription) and hands the rows in.

```yaml
# app.yaml: a mapping under `views` is a custom view; a plain path is still a view-spec, a dashboard or a report
views:
  - views/home.yaml
  - name: orders-grid               # addresses the view; lower-case
    kind: widget                    # widget | page
    export: OrdersGrid              # what the code registers
    params: [{name: region, type: string, required: true}]
    queries:                        # run by the host as the viewer; one form each
      orders: {semantic: {model: sales, request: {measures: [orders.net_revenue], attributes: [customers.region], limit: 100}}}
      areas:  {store: {model: territories, entity: territory, limit: 50}}
  - {name: regional-detail, kind: page, export: RegionalDetail, formats: [pdf, png], page: {size: A4, orientation: landscape}, queries: {...}}
```

```tsx
import { defineWidget, startViewFrame, useView, useSetParam, useReady } from '@dbdatakit/views-sdk'
defineWidget('OrdersGrid', function OrdersGrid() { const { data, params, mode } = useView(); /* data.orders.rows ... */ return <table>...</table> })
if (!startViewFrame()) { /* not a view frame: mount the app's own screens */ }
```

`app validate` checks the entries (`DBD-APP-019` shape, `-020` a widget with no declared query, `-021` a query naming a semantic model the manifest does not list, a Store entity without `read`, or a member the model lacks, `-022` an `export` that no `defineWidget('Export', ...)` / `definePage` in the source registers) with the manifest's file and line, and the build refuses an import outside the default library and the allow-list naming file and line. The SDK's messages with the host (`views:hello`, `views:ready`, `views:error`, `views:size`, `views:setParam`, `views:open`; `views:init`, `views:props`, `views:closed`) are the contract the shell and the exporter implement: a widget fires only a **named** link (`open(name, row)`), it cannot choose a target. The entry of the app calls `startViewFrame()` after its registrations (it mounts the registered view when the address's fragment names one, `#view=<Export>&mode=screen`, and does nothing otherwise). How a host resolves the rows and runs the frame on screen is [Custom widgets on screen](views.md#custom-widgets-on-screen); running a custom view in an export and by email is DBR32 to DBR34.

## Offline builds, the package store and the allow-list

An app's packages are not fetched when it is built (plan 22a GP33, QG12). `apps build --store <folder>` (or `apps.packageStore` in `server.yaml`, so every build on that Gateway uses it) builds from a **vendored package store**: a folder with `node_modules/` and `store.json`, made on a machine with a network by `node Shared/web/app-store/build.mjs --out <folder>` (the default library set and what it needs at run time; `--include <package>` adds another package that is installed in `Shared/web`). `store.json` lists every file with its SHA-256, the packages with their versions, and the **library**: the names an app may import with nobody's permission (`react`, `react-dom`, `@dbdatakit/store-ui`, `@dbdatakit/visuals`, `@dbdatakit/semantic-client`, `@dbdatakit/view-app`). The administrator's **allow-list**, `apps.allowedPackages` in `server.yaml` (plan 22a calls it `apps.allowed_packages`; the file's keys are camel case), names further packages an app may import; a package is importable only if it is in the library or on the list **and** the store holds it. Nothing else is installed, ever.

| Setting (`apps:` in `server.yaml`) | Meaning |
| --- | --- |
| `packageStore` | the store's folder; set, `apps build` builds from it (without it, a build installs the app's packages from a registry: a developer's own machine) |
| `allowedPackages` | package names (`left-pad`, `@scope/name`) beyond the library that an app may import |
| `packageStoreSha256` | optional: the SHA-256 of `store.json` (`apps store-verify` prints it), so a replaced manifest is refused too |

What a build from the store does, in order:

1. **The store is checked** against its manifest (`apps store-verify` does the same alone): a file that differs by hash, one that is not listed, a missing file, a link: each is a line naming the file, and nothing is built.
2. **The source is checked**: every literal import (`import`, `export ... from`, `import()`, `require()`, CSS `@import`) and the `dependencies` of `package.json` must be a package in the library or on the list. A package that is not is refused **naming it, the file and the line** (`src/main.ts:3: imports 'lodash', which is not in the default library set (...) and not on the administrator's allow-list (apps.allowedPackages)`); a listed package the store does not hold says so. A path outside the source folder, an address on the network and a path into `node_modules` are refused the same way. `devDependencies` install nothing, so they are not checked.
3. **The build gets its own copy** (a folder under the temporary directory, removed afterwards) of the source without its `node_modules`, hidden files (`.npmrc`) and `bunfig.toml`, and of the store, and **the copy of the store is checked again** before it is used. Bun is told not to auto-install (`install.auto = "disable"`).
4. **Bun runs in a network namespace with no route** (Linux: `unshare --net`, with a user namespace when the caller is not root) with a cleared environment: no secrets of the server's, no proxy variables.

**What the isolation guarantees, and what it does not.**

* It guarantees, on Linux, that the bundler **cannot open a connection to anything**: the namespace has a loopback that is down and no route, so neither the internet nor a service on the machine (a database on 127.0.0.1, the Gateway's own listeners) is reachable. The tests prove it with a listener the process can reach outside the namespace and cannot reach inside it. A package's install scripts are never run (nothing is installed, and Bun is not asked to).
* It does **not** make the build a sandbox for a hostile program. The bundler is a child process of the server **as the same operating-system user**: it can read the files that user can read and write where that user can write (the stage folder is its working directory, nothing stops it going further), and it is not limited in memory or processes beyond the timeout and the size limit of the bundle. The package store is the supply chain: a file in it is trusted as the administrator vendored it, and the hashes detect a change since, not a bad package to begin with. Keep the store's folder writable by the administrator only.
* The import check reads **literal** specifiers. It is a policy and a courtesy (a named refusal before the build), not the barrier: what makes a package that is not in the store unreachable is that the build's `node_modules` is a copy of the store.
* Where a machine cannot make a network namespace (Windows, macOS, a Linux without `unshare` or with user namespaces off) `--isolation auto` (the default) builds anyway and **says so** in the build's output; `--isolation required` refuses the build; `--isolation none` skips it. The Workspace server builds with `required`. Without a namespace the build is still given no installer, no proxy and a cleared environment, but the program could open a socket. On Ubuntu 24.04 and later unprivileged user namespaces are limited by AppArmor (`kernel.apparmor_restrict_unprivileged_userns`); CI turns that off for the job.

## Building, previewing and publishing in the Workspace server

The Workspace server (`DbDataWorkspace`, plan 22a GP35) is where people edit an app in a git workspace; the console's workspace page asks it to **build** the draft, **preview** the build and **publish** it. It does what `apps build` and `apps publish --to` do, through the same code (`DbDataKit.Apps.AppSourceBuilder` and the Gateway's apps API):

- **Build.** `POST .../workspaces/{id}/builds` (the author role). The build runs from the vendored package store with the allow-list and the isolation in the **`apps:` section of the Workspace server's `server.yaml`** (the keys are the Gateway's: `packageStore`, `allowedPackages`, `packageStoreSha256`, plus `isolation: required|auto`, `buildTimeoutSeconds` and `bun`). **The store must exist on the Workspace server's machine** (make it with `node Shared/web/app-store/build.mjs --out <folder>` where there is a network, copy it, point `apps.packageStore` at it); a server without one refuses to build and the workspace page says what is missing (`GET /api/v1/app-build`: no store set, the folder not there, a store that does not match its `store.json`, no Bun, no network namespace). The default isolation is `required`; `auto` builds without a namespace and **says so** in the build's result (`isolated: false`, a note) and on the page. Bun is the child process of a build, with a time limit; each build is a row of the `build` table and keeps its result and its built folder under `builds/<project>/<id>/` of the server's directory. A refused import is reported with its file and line.
- **Preview** (plan 21: read only; the author may turn writes on, see the preview instance below). `GET .../builds/{b}/preview/` serves the built files from the Workspace server, `GET` only, in a document the page frames with `sandbox="allow-scripts"` and whose policy (`connect-src 'none'`, `form-action 'none'`, `default-src 'none'`, `sandbox`) leaves it no network: it cannot write. It shows the app's screens **without data**, on purpose: its document may reach nothing, and the only credential the Workspace server holds for a Gateway is the publisher's key, which is not a viewer's. The semantic route exists (below). **Preview with data** (plan 22a GP35d; `POST .../builds/{b}/preview-data`, the author role, body `{target, instance}`): the server sends the build, with the target's publisher key, to the paired Gateway's `preview` channel (`PUT /api/v1/apps/{name}/channels/preview`, then `PUT /api/v1/app-instances/{instance}/channels/preview`) and answers with the preview's address on the apps host (`/apps/<instance>~preview/`, see "Every instance has the subpath"). The person opens it at the Gateway, signed in as themselves, so the data and the semantic figures are what they may see and a person without a role on the instance sees nothing. It is read only (a preview's changes are refused: plan 21's draft layer, CH01, is not built). The sandboxed preview above stays as it is; no bridge lets its document reach a server. The key is the publisher's, so an author's click uses a high-trust key to write to a channel that only previews: that is why the Gateway refuses a preview of an instance production does not have, and why nothing it sends reaches production.
- **Publish** (the approver role). `POST .../builds/{b}/publish` sends a succeeded build to a Gateway the server is paired with, as the target's **publisher key**: the Gateway checks it (`POST /api/v1/apps/check`, its refusal is shown in its words) and stores the version (`PUT /api/v1/apps/{name}`), and the answer is the app version. The key is in the Workspace server's own secret store; the screen and the API handle only its **reference** (`secret:dbdatakit:workspace:publisher-key:<name>`), read at the moment of publishing and never returned. An administrator makes a target with `dbdataworkspace publisher pair <name> --url <gateway management address> --code <code>` (the code is made on the Gateway with `server pair --max-role publisher`) or on the workspace page; every publish and every change of a key is in the audit with the person's name.

**Sessions in the group** (plan 26 AP29). A person's sign-in at the apps host is a row of the Gateway's `serving` module (`app_session`, migration 7), so an instance of a group accepts a session another instance made and a restart signs nobody out. The cookie holds only a random id; the table holds its SHA-256, the identity the home gave (who, groups, roles, attributes) and the home's refresh token **encrypted with the group's session key** (the secret `dbdatakit:gateway:state:session-key`, the key client sessions already use), never in the clear; a row the group's key cannot read is no session. The memory of an instance is a cache: it asks the table again after 10 seconds, so a session ended at one instance ends at the others within that time; a refresh made at one instance (the home's refresh token is used once) is taken by the others from the table, and when the home refuses a token another instance already used the instance adopts the newer answer instead of ending the session. A session older than its eight hours is removed when the next is made. Tested on SQLite, PostgreSQL and SQL Server (`AppSessionStoreTests`; the server engines run where the shared engines are up; run on both on 2026-11-12) and in a browser (`apps-sessions.spec.ts`: the same cookie opens an app after the Gateway process is restarted, and the shell still gets its token). Only the session id, the person, the expiry and the refresh token (encrypted) are kept; a token for an app is always exchanged again through the home (AP19).

**App tokens are the identity home's (AP19).** The host signs nothing and holds no signing key. When the shell asks (`POST /apps/<instance>/_token`), the host trades the person's refresh token, the one its own sign-in through the home got, for the instance's access token at the home's token endpoint (RFC 8693, `grant_type=urn:ietf:params:oauth:grant-type:token-exchange`, `audience=app:<instance>`; a preview is `app:<instance>~<channel>`). The home checks that the person still holds a role on the instance and that an approved version exists, and makes a token whose audience is the instance, whose `dbdata_roles` are the person's roles on it and whose `dbdata_scope` is the approved manifest's scope narrowed by those roles (a person who may only read gets no write; the scope of a preview is its channel's manifest). The refresh token is not used up by the trade (the host's own refresh keeps rotating it; the trade is done under the same lock, and a token another instance of the group has already replaced is looked for in the group's state once). The data route (`AppDataGateway`) checks the token's signature against the keys the home publishes (`/identity/jwks`, read once and again for an unknown key id at most every 30 seconds), its audience (instance B refuses instance A's token) and the approval of a trusted app on every call, and uses the token's scope, never the manifest's. A token lives 10 minutes (the home's access token), not the 5 of the old host-signed one. **Setting it up:** the home lets only the clients it names exchange: the Gateway's own home names `apps.home.clientId`; a home elsewhere (`apps.home.authority`) must be told its apps host client the same way (`IdentityHomeOptions.AppHosts`; a home that names none refuses with `unauthorized_client`), and each instance needs its client there (made when the instance is saved). The host client may be public (what `identity client-add --public` makes) or confidential (`--secret`, sent with the trade); the allow-list is the gate, and a refresh token is only ever good for the client it was issued to. When the home does not give the token, `/_token` answers 503 with the reason ("The identity home does not give this host tokens for this app (unauthorized_client): the home must let this host's client exchange tokens, and the instance needs its client there"), 403 when the person has no role, 401 when the sign-in is over (the session ends); a home that cannot be reached is 503 and keeps the session. There is no fallback to host-signed tokens. The old secret `dbdatakit:gateway:apps:signing-key` is no longer read and can be removed (`secret delete`).

**The shared shell script.** `/apps/-/shell.js` is the one script every shell page uses: it serves each `iframe[data-instance]` of the page with that frame's own token (`POST /apps/<instance>/_token`), relays its storage calls and the address, and answers only the frame a message came from. A trusted portal's page is on the host's origin with `script-src 'self'`, `connect-src 'self'` and `frame-src 'self'`, so it **loads that script instead of carrying its own**: `<script src="/apps/-/shell.js"></script>` and a frame such as `<iframe data-instance="sales" sandbox="allow-scripts allow-forms allow-popups" src="/apps/sales/_app/">` for each app it mounts (what the approval for its bytes covers is unchanged: the token and storage routes check the mounted instance's own approval). Checked by `AppSiteTests` (the portal page's policy and the script); not run in a browser.

## Trust and egress

Two settings, not the same thing.

**Trust: who vouches for the code.** `trust: sandbox | trusted` in the manifest is a **request**. A `trusted` app (on the host's origin, with the person's session as far as its approval says) is served, given a token, given storage and given data calls only while **an approval stands for its exact bytes**. An approval is a record in the group's state (`app-approval/<id>`): who approved, when, the **content hash** (the built files in path order with their hashes, then the manifest: exactly the bytes a published version contains, so it can be given before publishing), what it was approved for, a note. It is **a new approval for a new version**: any changed byte is another hash. The author cannot approve; the approver must hold the Approver role at the identity home; revoking needs the same role and publishes the record again with the time (nothing is deleted). `apps publish` of a trusted app is refused naming the missing approval and the hash; a revoked approval stops the app at once (the data gateway checks on every call, a token lives five minutes). Commands: `dbdatagateway apps approve --path <folder> --by <approver>` (or `--hash <h> --app <app>`, or `--app --version`), `approval-list`, `approval-revoke --id --by`.

**Audit.** The approval's label goes with every data call a trusted app makes (`AppDataCall.Via`), and the group's Store names it in the audit row of a write: "Ada Lovelace, through sales-portal 3, approved by Grace (apr_...)", cut to the audit column's 200 characters from the person's end. A sandboxed app's rows name the person only. The servers do not change with trust: an app's token is no wider than the person's.

**Egress: no outside requests for any app.** Every answer carries a `Content-Security-Policy` from the instance's effective policy, starting from `default-src 'self'`: it stops outside scripts and styles (so JSONP), fetch, XHR, WebSocket and CORS requests, images, fonts, media, frames and objects from other origins, form posts to other origins and a changed `<base>`. Exceptions are allow-lists: the manifest **requests** them (`egress: {connect: [...], img: [...]}`, or `frame`) and the administrator **approves** them as the standing approval's `Egress` (`approve --egress connect=https://api.x.com,img=https://cdn.x.com`); a request nobody approved is not in the policy, and an approval cannot name an origin the manifest did not ask for. `dbdatagateway apps validate --dir <folder>` checks the manifest and lists addresses of other hosts in the built HTML, CSS and script that the manifest does not request, with file and line. A content security policy is enforced by the browser for that document: it stops accidents and the ordinary routes out, and is not a barrier against hostile code on the same origin; for trusted apps the review and the audit are the control. Approvals exist only for trusted apps, so a sandboxed app cannot be given origins yet.

**A report server in a frame (AP17).** A trusted app that asks for the report server's origin under `egress.frame` and has it approved (`approve --egress frame=https://reports.contoso.com`) may frame it: the policy's `frame-src` lists exactly the approved origins, and an unapproved one is blocked by the browser. A dashboard's `embed` widget (`docs/views.md`, "An embedded report") draws the same way: a frame for an origin the host approves, always with the report's link beside it, and the link plus "Cannot show this report here" when the frame has not loaded within 15 seconds. A cross-origin frame cannot report a failed Windows sign-in to the page, so there is no finer test than that timeout and the link. **In a view of the app.** A dashboard of `view-spec/1` takes the widget `{kind: embed, title, url, link_text}` (no `entity`, no query; `url` is absolute https with no credentials, `schemaVersion` stays 1: the key is new, nothing that was valid changed). `app validate` (and so every publish) refuses an `embed` whose origin the manifest does not ask for under `egress.frame`, naming the app, the view, the origin and the line. When the page is served, the host marks each embed `framed` only when its origin is covered by what the administrator approved (the same list that becomes the document's `frame-src`), so an approved origin is framed and a requested but unapproved one is drawn as the link alone (and the browser would block the frame as well); `EmbedBlock` keeps the link beside every frame and replaces a frame that has not loaded in 15 seconds by the link. The server-level `views.frameOrigins` of the Gateway's `server.yaml` stays for the Gateway's own dashboards and does not apply to an app: an app frames only what its approval allows. Not built: the app host's own `dashboard/1` documents (the `layouts` form) do not resolve `embed` widgets (the views module of the Gateway does, with `views.frameOrigins`); a run on a domain-joined Windows host with a report server is not done.

## App storage

A sandboxed document has no browser storage, so the host provides it on every address (manifest `storage: {user, instance, quota_mb}`; none declared, none given). Keys and JSON values in the group's state (`AppStorage`): `storage.user` (one person in one instance, the owner taken from the session, never the request) and `storage.instance` (everyone in one instance). A value up to 256 KB, a key up to 128 characters, an instance up to its `quota_mb` (1 to 1024, default 10, capped at 50 MB); last writer wins with an optional `ifVersion` (0 = only if new). The shell relays `get`, `set`, `delete`, `list(prefix)` to `POST /apps/<instance>/_storage`. Two instances never share storage. It is not the place for business data: that is a Store model.

## Addresses

Every instance has the **subpath** `https://<host>/apps/<name>/` derived from its name (built). Names follow the Store's rule (`[a-z0-9][a-z0-9_-]{0,63}`); `api`, `admin`, `console`, `identity`, `apps`, `static`, `health`, `version` and `catalog` are reserved. A non-prod channel's subpath is derived (`/apps/acme~preview/`), never the prod address, and it is served: **a preview instance** (plan 22a GP35d) is the instance `acme` as the `preview` channel has it, made with `PUT /api/v1/apps/{name}/channels/preview` (publish the build to the channel) and `PUT /api/v1/app-instances/{name}/channels/preview` (saved only where production has an instance of that name; it takes that instance's settings and bindings unless the call names others; the answer carries its `address`), and removed with the `DELETE`s of the same paths (instance first). The host splits `acme~preview` (`AppInstanceName`), so the shell page, the bundle, the token (audience `app:acme~preview`, so production refuses it and it is refused by production), the data and the semantic routes work on the address unchanged; **who may open it is who may open `acme`** (their roles at the home), it **reads what the instance's bindings name (production's data) and writes nothing** (the changes route answers 403 for a preview: the draft layer that would take its writes is plan 21 CH01, not built), its storage is its own empty copy (keyed by the address), a portal has no preview, and the shell page says it is a preview. No OpenID client is registered for it. **Subdomain and custom-domain bindings are not built**: there is no routing by `Host`, no per-name certificate and no verification of names (plan 26 AP08).

### Names bound to an instance (AP08)

An instance has its subpath and any number of **addresses**: a name and a path an administrator adds to the instance (`addresses` of `PUT /api/v1/app-instances/{name}`, the Apps screen's instance editor). One listener routes by `Host` and path from a table made of every address of every production instance in the group's shared state, so an address added or removed at any gateway is routed by all of them within three seconds (`AppBindings`), with no restart.

- **Kinds.** A **subdomain** is `<instance>.<apps.domain>` (the first label is the instance's name; `apps.domain` of `server.yaml`, such as `apps.example.com`, with a wildcard DNS name and a certificate for `*.apps.example.com` as the host's own); a **custom domain** is any other name, with its certificate in the secret store: `certificate: secret:<name>` holds a base64 PFX and `certificate_password: secret:<name>` its password when it has one. A certificate is a secret reference, never the certificate in the definition.
- **Verified before accepted.** A save is refused, in words, unless a subdomain is the instance's under `apps.domain`; a custom domain is not under `apps.domain`, resolves to an address of the machine (loopback counts: it reaches only this machine) or one listed in `apps.addresses` (a balancer's or public address) **or proves it is the administrator's with a DNS challenge** (below), and its certificate can be read, has a private key, is valid now and holds the name (`AppAddressVerifier`). A name another instance holds at the same path, a path under `/apps/` or one with `..`, an address twice, two primaries, a preview with addresses, and a name that is not a DNS name (an IP address is not) are refused by the store itself. At most 20 addresses; one may be `primary` (the subpath is the primary address when none is).
- **TLS** picks the certificate by the name the client asks for (SNI, `AppCertificates`): a custom domain's own, and the host's own for every other name. A certificate that cannot be read gives the host's, so the browser says the name does not match, and the reason is logged once.
- **Routing.** A request for a bound name is rewritten to `/apps/<instance>/...` before the routes see it, so the shell page, the bundle, the token, the data and the storage routes serve both. On a bound name the host's other pages are 404 (another instance's address, the catalog); the shared shell script and the sign-in callback are served. A binding with a path (`/planning`) takes the longest match. A name that is not bound is served as before.
- **`origin: own`.** An app that declares it is served **only at its names**: at the host's own origin its pages answer 404 naming them, and saving an instance of it with no address is refused naming `origin: own`. A preview of it (served at its subpath, in a sandboxed document) is not asked.
- **Reverse proxies.** `X-Forwarded-Host` and `X-Forwarded-Prefix` say which name and path the browser used, trusted only from the addresses of `apps.trustedProxies` (IP addresses or CIDR ranges); anyone else's are ignored.
- **Sign-in.** A person signs in at the name's own callback (`https://<name>[:<port>]/apps/-/callback`, on the apps host's public port), and the session cookie is the name's own (path `/`). Each address is a redirect URI of the instance's OpenID client, added with the address and removed with it; it is added to the host's own client (`apps.home.clientId`) too when the home is this gateway's, and the answer of the save lists each `redirect_uri` for a home elsewhere, whose host client the administrator adds it to.
- **Format.** An instance with addresses is stored in format 2 of the definition `app-instance` (one without any stays in format 1, so a program that reads format 1 only reads it); a program that finds a newer format refuses the instance naming it.

## Navigation

The host's shell page owns navigation; apps do not draw menus. A navigation set (`apps nav-save`, `nav-list`; refused when it names an instance that does not exist or names one twice) is versioned like any definition. The shell header shows, for each set the instance is in, the members the person holds a role on, so a menu never advertises a refusal. The frame reports its route (`postMessage {type:"route", path}`, a path starting with a single `/`, at most 512 characters); the shell puts it in the address as `#<path>` so the back button and a pasted link work. `chrome: none` (or `?embed`) serves no header. A member bound to another origin would be a plain link.

## Portals

A portal is an app of `kind: portal` with a `portal:` section (identity, theme, layout, navigation, home, mounts, slots, addresses), validated with positions by the manifest loader. It changes how apps look and are reached, never what they may do.

- **Declared** (default): data the shell renders, with no script. `/apps/<portal>/` is its home; `/apps/<portal>/<mount>/` shows a mounted instance in the portal's chrome (a role on the mounted instance is required). The theme is CSS custom properties (light on `:root`, dark under `prefers-color-scheme`) and is also posted to each frame as `{type:"theme", tokens}`. The menu is filtered to what the person may open. The home is a list of view files (`views/home.yaml`: `text` in a small markdown subset with no raw HTML, `links`, `tiles` of the apps the person may open, `dashboard`, `image` and `table`; any block may carry `roles`; codes `DBD-APP-011` to `013`, `026` and `027`; `app validate` and `apps publish` refuse a bad one). **Home blocks** (AP30): a `dashboard: {app, view, height}` block is a mounted app drawn in the block's box as a sandboxed frame of its own, opened at the view file named (`views/board.yaml`), as the person (its token, the portal's theme; a person with no role on that app gets no frame, as no tile); an `image: {file, alt, width}` is a file of the portal's own package (`assets/banner.png`; the host serves a portal's files from its bundle); a `table: {columns, rows}` is text typed in the file (encoded when drawn); `roles` on any block lists the portal's roles that may see it (a role on the portal, and for a dashboard also a role on its app), checked against the manifest's `roles` when published (`DBD-APP-026`). Roles are the identity home's roles on the instance (`viewer`, `operator`, `author`, `approver`, `admin`). `slots.home` and the home view's blocks are drawn together (the slot first). Tested in `HomeViewHtmlTests`, `HomeViewTests` and the Playwright story `apps-home-blocks.spec.ts`. **Slots** (`header`, `footer`, `aside`, `home`) are sandboxed apps in frames of their own, each with a token for its own instance only.
- **Trusted**: a portal with code (`trust: trusted` and an `entry`), on the host's origin with `frame-src 'self'`, only with an approval for its exact bytes; without one the shell shows the default portal with the reason ("Showing the default portal instead") and answers 403 on its files, token, storage and data. It asks for tokens for the apps it frames with the host's shared shell script ("The shared shell script" above). The same guard applies to the files of a trusted app of `origin: own`.
- The host has a **default portal** (the suite's own shell), so nothing is mounted into nothing. A portal is an instance like any other; an instance whose setting `portal` names a portal is framed by it at its own address too.

## External portals

For the organisation's own portal (SharePoint, Teams, an intranet): a stable launch URL `<subpath>/?launch` (signs the person in and opens the app); `GET /apps/catalog` (the signed-in person's session decides; 401 without one) lists the instances she holds a role on with name, title, description, app, version, channel and launch address; `?embed` serves the app without the header, and the instance setting `embed.allowed_origins` (bare origins, no wildcard, validated on save) becomes `frame-ancestors`, `'none'` by default. Browsers that block third-party cookies make a framed instance ask the person to sign in, which the home refuses to frame; such a portal should link with `?launch`. Mounting an app as a web component inside a portal's page is not planned: it would give the app the portal's origin.

## Instances

**An app instance** is a row `(name, app, version pin or latest in the channel, settings, bindings, roles)`. Settings are per instance; roles are per instance (`app:<instance>` in the identity home, `identity assign --app`); a token's audience is `app:<instance>`, so another instance refuses it; versions move per instance (promoting a version moves only the unpinned ones). `apps init` (a new app folder from a sample) and `apps build` (a source tree into a folder that validates; Bun, offline with `--offline`; AP23), `apps validate`, `apps publish --dir`, `list`, `rollback`, `remove`, `instance-save`, `instance-list`, `instance-remove`, `nav-save`, `nav-list`, `nav-remove` are the command line (`publish`, `instance-save`, `rollback`, `list` and `approve` also work against a Gateway on another machine with `--to <address>`, as a paired publisher client: AP26) (a rollback or a removal is a published change, audited, and the record stays; `remove` is refused while an instance runs the app, `instance-remove` while a portal mounts it); the console's **Apps** screen (Gateway module, AP24) shows the same from the management API (`GET /api/v1/apps`, `/apps/<name>`, `/app-instances`, `/app-navigation`, `/app-approvals`, each saying what the caller may do) and does the roll back (serve an older version), pin, approve, revoke (`POST /api/v1/app-approvals/<id>/revoke`: the approver role) and remove (`DELETE /api/v1/apps/<name>`, `/app-instances/<name>`: the store's rules, refusals shown); the app's about page (`GET /apps/<instance>/_about`) lists exactly the manifest's models and operations, the outside origins by directive, the storage kept, who published this version, and the approval that stands; it asks for no consent.

**Data.** An instance's manifest names the models it uses with `read`, `write` or `change request` per entity (`change request` is read plus proposing: the batch always waits as a change request for approval, even where the model would apply a write at once; `write` includes it; the token's scope entry is `model/entity:propose`, and like a write it needs the Author role at the Store, so a person who may only read gets a read entry); its bindings say which model instance each uses. The data route is `/apps/<instance>/_data/api/v1/models/...`, answered **in the host's process by the models published to the group** (`GroupAppData` over `GroupStoreApi`): the app's token is checked per instance, the scope of the manifest (`model/entity:read|write`, write includes read) and the person's role both decide (a viewer cannot write), an app never acts as an agent, and a model outside the manifest is 403 before the group is asked. CORS answers `*` on this route only (the opaque origin; the token is the credential). **The identity home's tokens (AP19).** The data route takes only the home's access tokens (audience `app:<instance>`, `dbdata_scope` the approved manifest's scope narrowed to the person), checked with `JwksTokenVerifier` against the keys the home publishes; "App tokens are the identity home's" above says how the host gets one (a token exchange at the home). The Gateway registers `AppInstanceGrants` for its home and gives each instance a public PKCE client (`AppInstanceClients`: made when an instance is saved through the management API, removed when it is retired, and any missing one when the apps module starts; its redirect URI is the host's callback).

**The semantic route.** `/apps/<instance>/_data/api/v1/semantic/models` (the models the manifest's `semantic:` lists that this server serves), `.../models/<model>/catalog` (`{model, measures, attributes}` with the names a query uses: `orders.net_revenue`, `customers.region`) and `POST .../models/<model>/query` (the query document of `docs/semantic/query.md`, `{spec_version, kind: "query", query}`, a `limit` of 1 to 10,000 required) are what `@dbdatakit/semantic-client` calls. The answer is `{status, columns: [{name, type}], rows (arrays in column order), warnings, request_hash}`; a request the engine leaves steps of is `status: "unsupported"` with its reason, which the client raises as `SemanticError`. The same token and CORS as the Store route; the manifest decides first (a model it does not list is 403 whether or not the server has it; `explain`, `members`, saved queries and semantic SQL are not offered to an app). The query runs **as the person the token names** through the serving layer's `IServingQueries` (`GroupAppSemantic`, `DbDataKit.Serving.Semantic.SemanticRest`): the person is the identity home's user, the data sources they may use are the ones their home groups reach (the principal Flight SQL makes for a home user), and the model's own access rules apply, so **an app never shows a person what they could not ask for themselves**. A sign-in that is no home user (a console administrator) is refused; a refused source is 403 with the server's sentence; 404 is a model this server does not serve. The catalog's `title` is null (the catalog document has none).

**Store model instances.** A model's `storage.instances` says how its instances are kept apart; the server enforces it, never the client.

| `instances:` | Meaning |
| --- | --- |
| omitted | one copy, the `default` instance |
| `schema` | each instance's tables in `<model>__<instance>` on the model's connection |
| `connection` | each instance names its own connection |
| `column` | one set of tables; `_instance` is the first column of every key and of the audit table, stamped on every insert and added to every read, update, delete and rule check (unique, reference, sum, overlap, cycle); a body that names an instance is refused; references resolve inside the instance; no foreign keys are made |

Routes are `/api/v1/models/{m}/instances/{i}/...`; the old paths mean `default`; an administrator registers and forgets instances (forgetting keeps the data). A saved model text is kept under its SHA-256, so a copy runs the version it was made or last migrated at (`GET .../migrations`: `current`, `behind`, `unknown`) and `POST .../migrate` adds what the new version needs and nothing else (see DbDataStore). The Store controls (`@dbdatakit/store-ui`: `StoreClient.withInstance`, `instances`, `InstancePicker`, `EntityEditor instance`) take an instance. A model with instances cannot be published to a group yet (the group serves a model's own copy only).

## Known limits of what is built

Each is a deliberate limit, a gap a slice of [plan 26](plans/26-app-publishing.md) owns (named), or both.

- **DNS challenge** (AP08): a custom domain that does not resolve to this host yet (it is moved over after it is bound) is accepted when the TXT record `_dbdatakit-challenge.<name>` holds `dbdatakit-domain-verification=<hash>`, where the hash is a keyed hash (HMAC-SHA256 with the Gateway's `instanceId`) of the instance and the name, so it is the same every time it is asked for, differs per instance and name and is known only to someone shown it (`AppDomainChallenge`). The instance editor's **Verify** button asks `POST /api/v1/app-instances/<name>/verify-address` `{"host": ...}`, which answers `verified` and `via` (`challenge` or `address`) or `reason`, and always the record to create; the answer changes nothing, and a save runs the same checks (a refusal of an unresolved name ends with the record to create; the certificate is checked either way). The record is read by the host's own DNS client (`DnsTxtResolver`: one UDP question to the resolver in the machine's network settings or `/etc/resolv.conf`; a machine with none, or a resolver that fails, means the proof is not held and the name has to resolve to this host); tests inject the resolver. Default taken (plan 26): a proved name is accepted without resolving to this host, and verification is at save, not stored.
- **Addresses and origins**: bindings are built (above); what is not: a certificate renewed by the host (a custom domain's certificate is the administrator's, replaced by saving the secret and the address again), several ports for one name (every name is on the apps host's public port), and the host's own client at a home elsewhere (its redirect URIs are the administrator's). A sandboxed app cannot be given outside origins, only a trusted app can (decision, plan 26). An app on its own origin calls the host's routes on its own name (`/apps/<instance>/_data/...`, `_storage`), the same as its frame does.
- The storage cap is `apps.storageCapMb` in `server.yaml` (50 by default, 1 to 1024); a manifest's `quota_mb` is limited to it. A preview's storage is its own, empty copy and stays until the preview instance is removed (plan 21's expiry of an idle preview, CH07, is not built).
- **Third-party cookies**: a browser that blocks them makes a framed instance ask the person to sign in inside the frame, which the home refuses to frame; a portal on such a browser links with `?launch`.
- **Shared controls**: the portal header's switcher and search parts are drawn as nothing; the shell fixes the slot sizes (declared sizes would be a manifest addition, not planned). An app of views (and code that uses `ViewApp`) applies the shell's `theme` message: the tokens of the scheme in force become `--*` custom properties on the document, which the controls draw with, and the charts follow the scheme the message names (an optional `scheme: light|dark`, else the person's system setting). An app of plain code reads the message itself (`parseShellTheme` and `applyShellTheme` of `@dbdatakit/store-ui` do it).
- **Portal home dashboard blocks** frame a mounted app (an app of views, or any app), they do not draw a published `dashboard/1` of the semantic layer by name (that waits for the views module being loaded by the Gateway host, plan 32 DBR11); the frame's box is a fixed height, and the dashboard reflows to it.
- **Trust**: `--hash` cannot check that the app asked to be trusted (the gate at run still allows only what the manifest asks). The app's about page lists the outside origins in force and, apart, those the manifest asks for and nobody approved; a change request a trusted app proposes names the app, its version and the approval in its proposer (`proposed_by_name`, as the audit row of a write does). An app has no owner: any publisher client may publish a new version of any app.
- **Remote command line**: `nav-save`, the removals, `approval-list` and `approval-revoke` have no `--to` form; the person of a signed-in console is not passed to a remote verb (the token names the paired client). The Gateway's Apps screen does all of them.
- **Views apps**: reads are up to 2000 rows an entity, with filter, sort and paging in the browser until the Store has a query; a detail or edit view addresses a row by its key: one parameter named by the view's `key`, or for a composite key one parameter per key attribute, named as the attribute (a link supplies all of them); semantic-layer widgets are not built; the Playwright story (list, edit, a refused row) is not written (AP27).
- **Store instances**: `scope: shared` entities in `column` mode, a token scoped to instances, per-instance roles for the Store and moving a model between instance modes are not built (Z12b); the migration's expand step adds only; its **contract step** (`POST .../migrate/contract`, dry run and `?approve=<hash>`) drops the columns the model no longer has and makes the required ones NOT NULL, for one copy at a time, while a copy still at the old version keeps its tables and works; a retype, a change of how rows are kept and the refusal while a published package still reads a column (plan 21 CH06, lineage) are not built (Z13b). A model with instances cannot be published to a group yet (plan 20 O10c).
- **Tests**: the Playwright stories of `apps-host.spec.ts` (and `apps-policy.spec.ts`) (an unapproved fallback with its reason, an approved portal on the host origin with the `_audit` row, a revoked one falls back) is written and has not been run; it needs PostgreSQL, the built Gateway and Store and `npm ci` (AP27).

## Decisions

1. The default for a code app is a sandboxed document under the host's shell page, not a separate origin; because the sandbox has no browser storage, **the host provides app storage**. Sandboxing is a default, not a rule.
2. The shell page owns navigation; apps do not draw menus.
3. A Store model's isolation is declared by the model and enforced by the server.
4. A portal is declared data by default, and may be trusted code with an administrator's approval of that exact version.
5. Trust is an administrative, reviewed and audited decision: the manifest asks, an administrator approves a version, a new version needs a new approval, and every call a trusted app makes carries the approval in the audit.
6. No outside requests for any app, trusted or not, unless an administrator allowed the domain.

Not planned: several tenants inside one app instance (use an instance per tenant).
