# Release notes: what has changed behaviour since the last beta (2026-11-13)

Each entry says what to do about it. Add to it in the pull request that makes the change, one entry per change, without rewriting other entries; a
release moves the entries into its notes and empties this file.

## Servers join the console by a command it prints

- **`dbdatakit setup invite <gateway|runner|workspace>` prints a command to run on the server's machine (`dbdatarunner pair --host ... --token ... --console-thumbprint sha256:...`); the server joins the console at its next start, and the console lists it with the address and certificate it reported.** The token works once and for 15 minutes unless `--minutes` says otherwise; only a verifier made from it is kept in the console's state. The Gateway, the Runner and the Workspace have the new `pair` command and a join step at their start: a refused join stops the start, and its startup-failure file says what the console answered. The console's state gains a table (`join_token` of the `trust` module, under the group `console`), added when the console starts; a console's own state login stays `dbdatakit_console`. Pairing by code (`server pair`, `instance add --code`) still works. What to do: nothing; for a new server, run the printed command instead of exchanging a code. The Gateway joins on its management listener, so its management API must be on (`management.enabled: true`, the default).

- **New: the console's Add a server screen (Servers, Add a server) makes the same command as `setup invite`.** An administrator chooses the server, the role ceiling, a group and how long the command works, and copies the command, which the screen shows once. Below it the screen lists the tokens still waiting, never their values, and Cancel ends one; making and cancelling a token are in the console's audit (`server.invite`, `server.invite.cancel`). The routes are `GET`, `POST /api/join-tokens` and `DELETE /api/join-tokens/<id>`, for administrators only. What to do: nothing.

- **New: `dbdatakit setup single-server` registers, starts and joins every suite service installed beside `dbdatakit` on one machine, and `setup single-server --stop` stops them all.** Run it as an administrator (Windows) or with sudo (Linux). It finds the Gateway, the Runner and the Workspace in the folders next to the console's (`...\gateway\dbdatagateway.exe` beside `...\console\dbdatakit.exe`, or `/opt/dbdatagateway/dbdatagateway` beside `/opt/dbdatakit/dbdatakit`), registers each service as its own `service install` does (on Linux, the system user and the unit `install.sh --system` makes, and the unit enabled), gives its data folder its owner and access list and its program folder an access list only administrators can change, writes each server's join request with a single-use token, and starts it. It prints `registered · started · listening · joined` per service, the startup-failure file of a service that fails, and a summary with the console's address and the first administrator's setup link. A second run leaves what is ready alone. `--skip-folder-permissions-check` puts the switch on each registered command line. Each server's `service install` and `service unit` register exactly what they did before. What to do: nothing; the Scoop package still installs as before.

- **The console trusts its own publisher key in every Runner and Gateway group it manages.** The console makes a publisher key of its own and adds it to the trust store of each group, for every kind the group takes, a few seconds after a server joins and, for groups joined before, after the console starts; a server that does not answer is tried again later. The key is labelled `dbdatakit console <console id>` on the group's Publishers page (the Gateway's `/trust`, the Runner's Publishing card). The shared publish API has a new read, `GET /api/v1/trust`: every kind the group takes with its keys, for a viewer or an administrator. What to do: nothing. A key revoked on the Publishers page stays revoked; a group whose ceiling for the console is lower than administrator refuses the key, and the console's audit says so (`server.trust`).
- **Command lines stop publishing to a Runner or a Gateway: the console deploys.** `dbdatarunner package pair`, `dbdatasync package publish --to runner` with `--server` or `--code`, and `dbdatagateway apps publish --to` exit with code 2 and say so. `dbdatasync package publish --to runner --out` and `--check`, and `dbdatagateway apps publish --dir` (into the Gateway whose data folder it is given), stay. What to do: publish a sync project or an app from the Workspace in the console. A script that sent a package with these commands can still write it with `--out`; a person deploys it from the console.

## The Gateway's HTTP modules share one listener

- **The identity, apps, store, views, feeds and MCP modules answer on one public HTTPS listener, routed by path (`public:` in `server.yaml`, port 8817 by default); a module has a port of its own only when its `port` is set.** Before, each module listened on its own port (identity 8817, apps 8818, store 8819, views 8820, feeds 8821, mcp 8822). Now they have none unless set, and a client set to one of those ports finds nothing. What to do: point the client at the public address with the module's prefix (`https://gateway:8817/feeds/api/v1/query`, `/store/api/v1/models`, `/views/api/v1/...`, `/mcp`; the identity home and the apps host keep the paths they have), or keep the old address by setting the module's `port` (`store: { port: 8819 }`) before you start the new release. A module with `port` set is not under its prefix on the public listener. The compose file `dist/compose/quickstart-apps.yml` sets the identity and apps ports so its addresses stay.

## One `listen` setting for every listener

- **Every service and every listener of the Gateway has one setting, `listen`: an address with its scheme and port (`https://0.0.0.0:7820`), or a list of addresses. `port` and `address` are gone, with no alias.** The console, the Runner and the Workspace already had `listen:`; they now also read a list, in the file and in `--listen` (`--listen "https://127.0.0.1:7841;https://127.0.0.1:9443"`). The Gateway's `listen: { address, port }` (Flight SQL), `management`, `public` and each module's `port` and `address` are replaced by `listen`, `management.listen`, `public.listen` and `<module>.listen` (`rest.listen` for feeds). A file, an environment variable or a command-line setting that still has `port` or `address` stops the Gateway and the message names the file and the setting. What to do: in `server.yaml` write `listen: https://0.0.0.0:8815` for `listen: { address: 0.0.0.0, port: 8815 }`, `management: { listen: https://127.0.0.1:8816 }` for `management: { port: 8816 }`, and the same for each module; in a compose file or a container, `DBDATAKIT_Gateway__Listen=https://0.0.0.0:8815` for `DBDATAKIT_Gateway__Listen__Port=8815`. `https` uses the Gateway's certificate; Flight SQL takes `http` only with `tls.mode: None`.
- **A Gateway's public listener, Flight SQL and management API no longer have fixed ports (8817, 8815, 8816).** A listener with no `listen` takes the first free port of the Gateway's block, 7820 to 7839, at the first start, in the order public, Flight SQL, management, and the Gateway writes it to `config/server.yaml`; a Gateway started with no settings listens on 7820, 7821 and 7822, or the next free ports, and on the same ones after every restart. The public listener now starts in every case. A port you write is never moved: a held port fails the ports step, naming the port and the excluded ranges. What to do: a client set to 8815, 8816 or 8817 is set to the Gateway's pinned address (`config/server.yaml`, or the console's Servers page), or the Gateway is given the old ports in `server.yaml`. The container image and the compose files keep 8815 and 8816, and `quickstart-apps.yml` keeps 8817 and 8818, as `listen` settings.
- **The Gateway's settings screen edits `rest.listen` (REST feeds own address) in place of `rest.port`.** An empty box means the default and saves nothing; a list of addresses is edited in the text view.

## Every Gateway module is under a path of its own

- **On the public listener every module is under a path, set by the administrator: `/identity`, `/apps`, `/store`, `/views`, `/feeds` and `/mcp` by default (`identity.path`, `apps.path`, `store.path`, `views.path`, `rest.path`, `mcp.path`); `/` answers 404.** The identity home moves under `/identity`: its sign-in page is `/identity/sign-in`, the invitation page `/identity/invite` (the first-run invitation and `identity invite` print this address), its calls `/identity/api/auth/...`, `/identity/api/invites...`, `/identity/api/users...` and `/identity/api/access-tokens`, and its issuer is the listener's address with the path, `https://gateway:7820/identity`, with the discovery document at `<issuer>/.well-known/openid-configuration`. `/invite`, `/api/auth/...` and `/.well-known/openid-configuration` at the root answer 404. The apps host's redirect URIs follow the apps path (`https://gateway:7820/apps/-/callback`). What to do: a console, an app host or a script that stored the old issuer `https://gateway:7820` is set to `https://gateway:7820/identity` (a console's `--identity-home`, `apps.home.authority`, the authority of an OpenID client); an identity client registered at the home keeps its redirect URIs, which are the clients', not the home's; a link to `/invite#...` is `/identity/invite#...`; the Entra app registration's redirect URI is `<issuer>/upstream/entra/callback`. A module with a `listen` of its own has no path, and a home that runs on its own (`dbdatakit identity run`) keeps its issuer and its paths. The Gateway's settings screen has a box per module path; an empty box means the default.

## The install is four services

- **The Store server is gone (plan 33 SC23); the install is four services (console, Workspace, Gateway, Runner).** `dbdatastore server`, `service`, `health`, `state` and `secret`
  answer with a sentence that names where each feature went, and the `DbDataStore` service, its MSI, its container image and its place in `dbdatakit-full` are gone. Author a model in a
  store project of the Workspace; deploy and contract its tables from the Deploy tab there (Runner tasks of the model's package, run by `dbdatastore --runner`); write rows on the Rows
  tab against a Gateway's store module and decide change requests on the console's Approvals page. The server's state database and secret store are not read any more: nothing is
  imported. `dbdatastore model put|publish|unpublish`, `storage create` and `gateway add|list|remove` stay, on a folder of models (`--repo`). Unregister the old service
  (`sc delete DbDataStore` or `systemctl disable --now dbdatastore`) before you install this release.
- **The Build server is gone (plan 33 SC23); dbdatabuild is a command line on a project folder and the runtime a Runner starts.** `dbdatabuild server` (with `project`, `proxy`
  and `schedule`), `service`, `health`, `state`, `secret` (with `send --to runner`), `lineage` and `semantic publish|rollback` answer with a sentence that names where each feature went
  (exit code 2), and the `DbDataBuild` service, its MSI, its container image, its compose file, its console screens and its place in `dbdatakit-full` are gone. Author a project in
  a build project of the Workspace and publish it from there to a Runner and a Gateway; its refresh plans run on the Runner from the first activation (`--runner-schedules` is
  accepted and changes nothing; nothing is handed back to a Build scheduler); apply a plan, acknowledge a block or load seeds as the manual Runner tasks `apply_plan`, `ack` and
  `seed` of the operations package; bind the logins on the Runner (the package's `build-login` slots). `semantic describe|query|explain|members` take `--address`; `--gateway` and
  `--server-dir` named the server's pairings and now say so. The server's state database, secret store, projects and pairings are not read any more: nothing is imported.
  Unregister the old service (`sc delete DbDataBuild` or `systemctl disable --now dbdatabuild`) before you install this release.
- **The Sync server is gone (plan 33 SC23); dbdatasync is a command line on a configuration repository and the engine a Runner runs.** `dbdatasync server` (with `pair`),
  `service`, `cert`, `secret` (with `send --to runner`), `config`, `state`, `health`, `gateway`, `update`, `launcher` and `internal` answer with a sentence that names where each
  feature went (exit code 2), and the `DbDataSync` service, its MSI, its launcher and updater, its container image, its compose file, its screens in the console
  (`Shared/web/sync`) and its place in `dbdatakit-full` are gone. Author replications in a sync project of the Workspace (or as the files of a repository) and publish them
  with the Workspace or `dbdatasync package publish --to runner`; run now, pause, bulk loads, verifications, resyncs and the `provision` task are Runner tasks; bind the logins
  on the Runner. The checks stored with a replication (`checks:` of `task.yaml`) are kept and published but not evaluated until the Runner evaluates them. The server's state
  database, secret store, `server.yaml` and pairings are not read any more: nothing is imported. Unregister the old service (`sc delete DbDataSync` or
  `systemctl disable --now dbdatasync`) before you install this release.
  The Runner's own screen sets a connection's run login on a runner package's connections card (*Set the login*), in place of
  `dbdatasync secret send --to runner`; a replication set's Apply (provisioning) runs as its `provision` task on the Runner.
- **Changed: the console, the Runner and the Workspace listen on new default ports, from the suite's range 7800 to 7899.** With no `--listen`, a
  first start takes the default of its service, or the next free port of the service's sub-block, and writes it as the `listen:` line of its settings
  file (`settings.yaml` in the console's folder, `server.yaml` in the Runner's and the Workspace's); later starts use that port. The old and the new
  defaults:

  | Listener | Old default | New default (sub-block) |
  | --- | --- | --- |
  | the console (`dbdatakit server run`) | 8480 | 7800 (7800 to 7819) |
  | the identity home on its own (`dbdatakit identity run`) | 8482 | 7819 (a fixed default, never chosen or written) |
  | the Runner (`dbdatarunner server run`) | 8495 | 7840 (7840 to 7859) |
  | the Workspace (`dbdataworkspace server run`) | 8471 | 7860 (7860 to 7879) |

  What to do: a server started with `--listen` (the container images, the compose files, a service registered with its own address) keeps its
  port. For any other, change what points at the old port: a browser's bookmark, an `instances.yaml` entry or a publisher's paired address (pair
  again on the new address), a firewall rule. To keep an old port, add `listen: https://127.0.0.1:8495` (with the server's own host and port) to the
  server's settings file before you start the new release. `health check` asks the new default address; give `--url` for a server on another port.
  The Gateway's listeners keep 8815 to 8822 for now.
- **The catalog cache of a draft is `catalog-cache/2`.** `catalog-cache.yaml` now records, per connection, where and when it was read (`read`), its databases
  and schemas (the empty ones too) and foreign and unique keys. A draft's `catalog-cache.yaml` of format 1 is refused by the draft's check, the Catalog tab,
  `dbdatasync provisioning plan --from-cache` and `dbdatabuild project import --from-cache`, naming the file: delete it and refresh the catalog of each
  connection (the Catalog tab), then commit the new file.

## Tasks that change table structure start only from the console

- **A task with `capabilities: [ddl]` runs only on the console's signed approval.** A package task that creates, alters or drops tables can declare the capability `ddl`; it must then have no schedule and no trigger but `manual`. The Runner refuses a run of it from its own screens, `tasks run` and any paired client that does not carry the console's approval (403, audited as `runner.task.run`), and its task page shows no Run now button. The console starts it with `POST api/runner-runs/<server>/<package>/<channel>/<task>` after a person approves the exact statements. A dry run needs no approval. Packages that do not declare `ddl` are unchanged. A Runner older than this release ignores the capability, so upgrade the Runner before relying on it.

## Names

- **Breaking, no migration: every remaining product-prefixed environment variable is renamed to `DBDATAKIT_` (plan 33 SC31a).** No product prefix survives (`DBDATA<PRODUCT>_`, `DBGATEWAY_`, `DBPROXY_`, `DBDATA_`); the old names are **refused, with no alias**: a service or command that finds one set stops and names the new one. Rename them wherever you set them (unit files, `.env` files, compose files, the machine's variables, CI):
  - announcing and pairing: `DBDATAKIT_CONSOLE_URL` is `DBDATAKIT_URL`, `DBDATAKIT_CONSOLE_ANNOUNCE_URL` is `DBDATAKIT_ANNOUNCE_URL`, `DBDATAKIT_CONSOLE_ANNOUNCE_LISTEN` is `DBDATAKIT_ANNOUNCE_LISTEN` (`DBDATAKIT_ADVERTISE_URL` and `DBDATAKIT_INSTANCE_NAME` stay);
  - secrets and keys: `DBDATA_SECRET_<NAME>` is `DBDATAKIT_SECRET_<NAME>` (the rest of the name is the secret's name as before: `DBDATA_SECRET_DBDATA_SYNC_CONNECTION_ORDERS` is `DBDATAKIT_SECRET_DBDATAKIT_SYNC_CONNECTION_ORDERS`, because the secret's name changed too: see the entry on secret names), `DBDATA_SECRETS_KEY_FILE` is `DBDATAKIT_SECRETS_KEY_FILE`, `DBDATA_SIGNING_KEY` is `DBDATAKIT_SIGNING_KEY`, `DBGATEWAY_PASSWORD` is `DBDATAKIT_GATEWAY_PASSWORD`, `DBGATEWAY_WORKER_SECRET` is `DBDATAKIT_GATEWAY_WORKER_SECRET`;
  - connection logins of Build: `DBDATA_BUILD_<CONNECTION>_READ` and `_WRITE` are `DBDATAKIT_BUILD_<CONNECTION>_READ` and `_WRITE` (the same rule, `LoginEnvironment`, serves every product: `DBDATAKIT_<APP>_<CONNECTION>[_READ|_WRITE]`);
  - upgrade: `DBDATA_UPGRADE_CHANNEL`, `_MIRROR` and `_REPO` are `DBDATAKIT_UPGRADE_CHANNEL`, `_MIRROR` and `_REPO`;
  - one service's settings: `DBDATARUNNER_CHANNELS`, `_GROUP`, `_MAX_ARTIFACT_BYTES`, `_ACTIVATION_MAX_WAIT_SECONDS`, `_TASK_ENVIRONMENT` and `_CLIENT_DIR` are `DBDATAKIT_RUNNER_<same>`; `DBDATAGATEWAY_CLIENT_DIR` is `DBDATAKIT_GATEWAY_CLIENT_DIR`; `DBDATASYNC_API_URL`, `_RUNNER_TOKEN` and `_STATE_ENDPOINT` are `DBDATAKIT_SYNC_<same>`; `DBDATABUILD_ACTOR`, `_CHECK_RESULTS`, `_DUCKDB_CLOCK_OVERRIDES`, `_POLYGLOT_PATH` and `_STATEMENT_LOG_DIR` are `DBDATAKIT_BUILD_<same>`;
  - the Gateway's settings: the configuration prefix is `DBDATAKIT_`, so `DBGATEWAY_Gateway__Management__Port` is `DBDATAKIT_Gateway__Management__Port` (the section stays `Gateway`; the old `DBPROXY_Proxy__...` spellings are `DBDATAKIT_Gateway__...`). The other `DBDATAKIT_*` variables of the suite are visible to the Gateway's configuration and ignored, because none is under `Gateway`;
  - what a parent hands a child (not refused, a parent sets them): `DBDATA_CHILD_ENDPOINT` and `_TOKEN` are `DBDATAKIT_CHILD_ENDPOINT` and `_TOKEN`, `DBDATA_PARENT_PID` and `_START` are `DBDATAKIT_PARENT_PID` and `_START`, `DBDATA_BUN` is `DBDATAKIT_BUN`; the `DBDATA_<APP>__A__B` configuration form of the shared `DbDataKit.Config` library is `DBDATAKIT_<APP>__A__B`; a Dockerfile written by `DbDataKit.Hosting.Systemd` sets `DBDATAKIT_DATA` (it set `DBDATA_DATA_DIR`, which nothing read).
  `scripts/check_env_names.py` fails on any product-prefixed name in a tracked file (the variables of tests are in the entry below).
- **Changed: the variables of tests, harnesses and CI are `DBDATAKIT_TEST_<NAME>` (plan 33 SC31b).** `DBDATA_TEST_*`, `DBKIT_TEST_*`, `DBDATASYNC_TEST_*`, `DBDATABUILD_TEST_*`, `DBGATEWAY_TEST_*`, `DBDATA_E2E_*`, `DBDATA_REQUIRE_*`, `DBGATEWAY_REQUIRE_*`, `DBGATEWAY_LIVE_*`, `DBDATA_UPDATE_GOLDEN` and the others of the same kind are now `DBDATAKIT_TEST_<same without the product prefix>` (`DBDATA_TEST_SQLSERVER` is `DBDATAKIT_TEST_SQLSERVER`, `DBKIT_TEST_MSSQL` is `DBDATAKIT_TEST_MSSQL`, `DBGATEWAY_REQUIRE_SQLSERVER` is `DBDATAKIT_TEST_REQUIRE_SQLSERVER`); names that meant the same became one (Sync's `DBDATASYNC_TEST_MSSQL_SERVER` is `DBDATAKIT_TEST_MSSQL`, Gateway's `DBGATEWAY_TEST_SQLSERVER` is `DBDATAKIT_TEST_MSSQL_SERVER`). `testenv/testenv.sh env <suite>` prints the new names; `docs/testing-environment.md` has the whole table to translate a shell profile or a CI secret store. - **Changed: the Gateway's Windows service is `DbDataGateway`, and the four services have new descriptions.** `dbdatagateway service install` registers `DbDataGateway`, running as `NT SERVICE\DbDataGateway` (it was `dbdatagateway`). Windows compares service names without case and makes the account's SID from the upper-case name, so a Gateway registered by an earlier release is the same service with the same account, and `Start-Service dbdatagateway` still works. An MSI upgrade keeps the registration as it is; `dbdatagateway service install` from an elevated prompt updates its description, and `dbdatakit-full` registers it again under the new spelling on `scoop update`. The console, Gateway, Runner and Workspace services carry the descriptions listed in `docs/install.md`, "Service names, accounts and descriptions"; run each product's `service install` again to update an existing service. `dist.json` gives no service name for these four products any more: the installers read it from the suite's table.

- **New: `service check`.** In `dbdatakit`, `dbdatagateway`, `dbdatarunner` and `dbdataworkspace`, `service check` checks the service's registration, its account and the permissions of its folders, then prints the startup-failure file of its last start (or that there is none). Its last line is `Check: OK (<n> warning(s)).` or `Check: <n> failure(s).`; it exits with code 1 when a check fails, so a script can run it after `service install`.

- **Changed: a server refuses to start on a data folder another account could change, unless told to skip the check.** At start, the console, the Gateway, the Runner and the Workspace check their data folder: on Linux and macOS it must be owned by the service's account and not writable by every account; on Windows its access list must not let Everyone, Users, Authenticated Users, Anonymous, Guests or Interactive write to it. A folder that fails stops the start at the folder step, and `startup-failure-<program>.txt` names the folder, its owner, what is wrong and the switch. For a test's folder or a checkout, start with `--skip-folder-permissions-check` (also on `service install`, which puts it on the registered command line) or set `startup: { skip_folder_permissions_check: true }` in the server's settings file; the server then warns at every start, `service check` names it, and the console's Bindings page lists it under "Posture choices". A folder `service install` made already passes. Scripts that start a server from a terminal on a shared folder (the CI runner's temporary folder on Windows, for example) give the flag.

## A Workspace project's runs go through the console

- **Changed: the Runs and Provisioning tabs of a Sync or Build project, and the Deploy tab of a Store project, run what the console deployed.** They find the Runner, package, channel and version in the console's record of the newest deploy of a build of the draft, and start runs, read them, test a connection's login and run a Store model's contract through the console as the signed-in person (`POST /api/deploys/<deploy>/runs`, `GET /api/deploys/<deploy>/runs/<run>`, `POST /api/deploys/<deploy>/binding-test`, `POST /api/deploys/<deploy>/contract`). The Deploy tab's dry run stages the model's package through the console's deploy. The person needs the approver role on the Workspace server to start a run, and the Runner's own roles (operator to run, administrator to test a login). The console's audit records `build.run`, `build.binding_test`, `build.contract` and `build.contract.allow_consumer`. A contract step asks every Gateway the console manages who reads what it drops. What to do: publish a build from the Builds tab before you run it; a version the Workspace server published with its own publisher key is not offered on these tabs.
- **Changed: the Catalog tab's refresh from a Gateway goes through the console.** The form offers the Gateways the console manages and the draft's connections; the console asks the Gateway for the data source's tables and columns as the signed-in person (`POST /api/workspace-catalog/<workspace server>/<project>/gateway-read`). The tab shows what changed before **Accept** puts the new cache in the draft as an unsaved edit, as a read from a Runner does; the person saves the draft to keep it. Before, the Workspace server asked the Gateway with its own publisher key and wrote `catalog-cache.yaml` itself, and the console refused that call. A data source made by hand is still read only after the person confirms it. What to do: nothing; the person needs a role on the Gateway that may read the data source's catalog (an administrator reads any; a publisher reads those the console's deploys made).
- **Changed: the Rows tab of a Store project offers the Gateways the console manages that serve the model.** The tab reads the console's list of Gateways and asks each one's store, through the console's relay as the signed-in person, which models it serves; a Gateway paired with the Workspace server under Publisher keys is no longer what it offers. A Gateway that does not answer is named under the pickers with the reason. Rows are read and written through the console's relay as before. What to do: publish the model to a Gateway the console manages (the Builds tab) and deploy its tables (the Deploy tab).
- **Fixed: a task marked `manual: true` runs from a version that is staged and not served.** The Runner refused it as if it had a trigger, so a Sync set's `provision` and a Store model's `deploy` and `contract` could not run before their version was served. A task with a schedule or another trigger is still refused. What to do: nothing.
- **New: a Workspace screen stores a development login's password on a Runner through the console.** `POST /api/workspace-dev-logins/<workspace server>/<project>` (with the Runner, the channel, the project's connection, the user and the password) stores the password in the Runner's secret store as the signed-in person, under `dbdatakit:runner:dev-login:<package>.<channel>.<slot>:password`, for any channel the person picks, `prod` included. The user is not stored as a secret; the answer gives it back as plain text, with the name of the password's secret. The Workspace server is asked only which package the project becomes, and never receives the login. What to do: nothing; the person needs the Runner's admin role to store a secret.
- **Set up for development binds the slot.** `POST /api/workspace-dev-logins/<workspace server>/<project>` takes `draft`, the draft whose connection file is copied. With it, the console stores the password on the Runner as before, puts the draft's connection there as the copy `<package>-<slot>-<channel>` (the user as plain text, the password a reference to `dbdatakit:runner:dev-login:<package>.<channel>.<slot>:password`) and binds the connection's slot of the package in the channel to it, all as the signed-in person. The answer adds `copy`, `file`, `version`, `bound`, `unresolved` and `steps`; a bind the Runner holds for an administrator's confirmation answers 409 with `needsConfirmation`. The channel picker's **Set up for development** sends the draft, so the channel binds the slot without an administrator binding it by hand. A request without `draft` stores the password only, as before. What to do: nothing; the person needs the Runner's admin role, as for storing the login.
- **Changed: deploying a build, and running what it deployed, needs only that you may read the project on the Workspace server.** `POST /api/deploys` and the calls on a deploy (`.../runs`, `.../runs/<run>`, `.../binding-test`, `.../contract`, `.../activate`) no longer ask for the approver role on the Workspace server. The console asks the Workspace server for the project as you, and a person who may not read it is refused in the Workspace server's words ("Workspace does not let you read the project 'orders': This needs the viewer role."). The Runner or Gateway decides the rest from your roles there: publisher to deploy, operator to run, administrator to test a login or activate a version held for its preflight. What to do: give the people who deploy a role on the target. A viewer of a project who holds the publisher role on a Runner can now deploy the project's builds there.
- **New: a draft's connection is tested on a Runner before anything is published.** `POST /api/workspace-catalog/<workspace server>/<project>/binding-test` (with the Runner, the channel, the connection and optionally the login's role) asks the Runner's binding test for the project's package, the channel and the connection's slot, as the signed-in person; no build or version is needed. The answer lists each step (binding, connection, login, connect) as passed, failed or not tried, and never holds a value. The console asks the Workspace server only whether the person may read the project, and audits the test as `build.binding_test`. What to do: nothing; the person needs the admin role on the Runner, as for the test of a deployed version.
- **A draft is read on a Runner before it is ever published.** The channel picker lists every channel the Runner serves, each with the binding it holds for the connection's slot (`GET .../channels`). In a channel that holds no version of the package, the Runner's `discover` and `describe` read any slot the channel binds for it, whatever other channels hold; a channel that holds a version reads only the slots that version declares. So after **Set up for development** binds it, **Refresh**, **Describe columns** and **Test** read the draft's connection with nothing published. The Runner has a new read, `GET /api/v1/metadata/channels?package=<package>` (the viewer role): the channels it serves, the bindings it holds for the package, and whether it holds a version. What to do: nothing; an older Runner lists only the channels that hold a version of the package, and there a build of the draft published to the channel still comes first.
- **Set up for development offers `prod` like any other channel that does not bind the connection's slot.** The picker lists the unbound channels, those other than `prod` first, and shows the warning a read in `prod` shows when `prod` is picked. The console stores the login for `prod` as it does for `dev`, under `dbdatakit:runner:dev-login:<package>.prod.<slot>:password`, and binds the slot in `prod` to the copy `<package>-<slot>-prod`. What to do: nothing; the person needs the Runner's admin role, as for any channel. A package already served in `prod` runs with the login stored this way once the slot is bound to the copy.
- **New: the console takes over what a Workspace server's publisher key published on a Gateway.** An administrator of the Gateway asks `POST /api/deploys/handover` with `{"gateway": "<name>"}` once per Gateway; the console asks the Gateway, as that person, to hand each client whose id starts with `workspace-` to the console (`PUT /api/v1/settings/handovers/<client>` with `{"to": "<console id>"}`, new on the Gateway's shared publish API with `GET /api/v1/settings/handovers` and `DELETE .../<client>`). The Gateway records the hand-over and each definition whose owner changes in its audit (`definition.handover`, `definition.owner`); the console audits `gateway.handover`. Afterwards the console's deploys publish over those data sources, models and views with no adoption, and the Workspace server's key can no longer change them. What to do: run it on each Gateway the Workspace server published to before its publisher keys are removed.

## A sync project's Designer edits a replication

- **New: a replication's page in the Designer of a Workspace sync project.** It has the tabs Overview (the source and target connections and databases, the schedule) and Table Mappings (the source's tables with **Create mappings**, and a mapping's two sides and **Column Mapping**), with **Enabled**, **Save settings** and **Delete** in its chrome. The databases, tables and columns are those of the draft's `catalog-cache.yaml`. Each change is an unsaved edit of the draft's file, the same one Files shows, and keeps the file's comments and the keys the page does not show. What to do: nothing; everything the page does not offer is still edited in Files.
- **New: the Workspace answers a sync draft's authoring questions in its own process.** `GET .../sync/script-slots`, `POST .../sync/capabilities`, `POST .../sync/inferred-columns` and `POST .../sync/bulk-create` (author) answer the script slots, what a connection's driver offers with the key each reader and writer needs, a mapping's inferred target types and natural key, and the files Create mappings makes, from Sync's libraries and the draft's `catalog-cache.yaml`, with no database. A question may carry the person's unsaved edits. What to do: nothing.
- **New: the rest of a table mapping in the Designer.** A mapping's editor has the source filter, **Custom query, not a table**, and the tabs Notes, Column Mapping, Custom Transforms, Bulk Load, Provisioning (the mapping's part of the replication's plan, its number of statements on the tab), Pipeline, Diagnostics and Verify. **Create mappings** asks the Workspace for the files (`sync/bulk-create`) and lists what is inferred for each new mapping; Column Mapping shows each target type nobody set as the inferred one, in grey, and the type is not written into the file. A mapping named in the replication's provisioning plan opens that mapping's Provisioning tab. What to do: nothing; the column pairs of a query source are still written in Files.
- **New: the draft's check warns when an engine's own reader or writer would refuse a mapping for want of a key.** `MsSqlChangeTracking` and `PgLogicalSlot` need the source's primary key in `catalog-cache.yaml`, `MsSqlMerge` and `MsSqlMergeReconcile` the target's. Before, the check said it could not tell. What to do: add the key, or pick a reader or writer that needs none.
- **New: the Designer's live reads of a replication: Test, Set up for development, Describe columns and the newest preflight.** Each endpoint card has **Test**, the Runner's binding test of its connection in a channel picked there, with each step and no row; where a channel other than production does not bind the connection's slot, the picker offers **Set up `<connection>` for development**. A mapping whose source is a query has the card **Query columns** on Column Mapping: **Describe columns** asks the Runner to describe the query, and **Use these columns** writes them into the mapping's `sourceColumns`, so Column Mapping lists them and the Runner reads them. The replication's and each mapping's Provisioning tab show the newest `preflight` run of a channel the draft was published to, with its link and what it found per mapping. Everything is read through the console as the signed-in person. What to do: describe the query of a query source in the Designer before you publish the set; its column pairs no longer need to be written in Files.
- **New: the Tracking card follows the target's driver.** `sync/capabilities` answers `keepsStateTable`: true for SQL Server and PostgreSQL, false for every other driver, a driver the draft carries in `drivers/<folder>/driver.yaml` among them. On a target whose driver keeps no state table (MySQL, MariaDB, Oracle, DuckDB), the Tracking card on a replication's Overview disables **Target** and **Both** and says why; a file that already asks for one of them keeps it shown, with the reason as a warning, and the draft's check refuses it as before. What to do: nothing.
- **Changed: the Designer's provisioning plan includes the draft's unsaved edits.** `POST .../provisioning-plan` takes an optional `unsaved` object (a path of `catalog-cache.yaml`, a file under `config/` or a `drivers/<folder>/driver.yaml`, and its text), the same as the `sync/` routes, and plans the draft with those edits over it; nothing is written. The replication's Provisioning sub-tab and a mapping's Provisioning tab and its number ask with the edits, so a mapping that is not saved yet is planned. A request without `unsaved` plans the saved files as before. **Apply** still runs the version on the Runner: save, build and publish an edit before applying what it adds.

## A Sync set is checked before it is served in production

- **Every Sync package has a manual, read-only task `preflight`, which the console runs on a version staged in `prod` before it serves it.** It reads each mapping of each enabled replication with the run logins the channel binds: the source and target tables and columns, the source filter (a read that returns no row), the logins' privileges on SQL Server and PostgreSQL, the change capture the reader needs, types, keys, and the state table of a replication that keeps its state on the target. It writes nothing. An error (a missing table or column, a filter the database refuses, a login that may not read or write, change tracking or CDC off where the reader needs it) keeps the version staged until the person confirms it; **Re-check** on the Runs tab runs it on the version served. A replication may no longer be named `preflight`, as it may not be named `provision`. What to do: rename a replication named `preflight` before you build the set again; a set deployed to `prod` from now on waits for its preflight before it is served (`docs/authoring-metadata.md`, "A sync project").

## A mapping's rows and a strategy's trial, read on a Runner and kept nowhere

- **New: Preview rows of a mapping and Try of a segmenting strategy in the Sync Designer.** Every Sync package has two more manual, read-only tasks: `preview` reads the first rows of a mapping's source (20, or up to 100) with the run login the channel binds, and `try-strategy` runs a segmenting strategy, saved or as it is being edited, over a mapping and a column as a reload would. The console starts them as the signed-in person (`POST /api/deploys/<deploy>/runs` with `"answer": true`, then `GET /api/deploys/<deploy>/runs/<run>/answer` for a run longer than 10 seconds) and passes the rows or candidates to the screen. The Runner keeps them in memory for that console and that person only, at most 10 minutes, and never in its state, a step, the run's log or the audit (`GET /api/v1/runs/<run>/answer?on_behalf_of=<person>`, the operator role; the runner protocol's new call `Answer`). A replication may no longer be named `preview` or `try-strategy`. What to do: rename a replication with one of those names before you build the set again; publish a build of the draft to a Runner before you preview its rows.
- **Preview rows and Try read the mapping as the draft has it, unsaved edits included.** The Sync Designer sends the mapping's file with the run (the new input `mapping_text` of the set's tasks `preview` and `try-strategy`), and the task reads it with the deployed version's replication, connections and drivers. A filter typed and not yet saved is in the rows. The run's record keeps the mapping's text as an input. A run started without `mapping_text` reads the mapping the version has, as before. What to do: build and publish the set again. On a version built earlier, Preview rows and Try fail with "The input 'mapping_text' is not declared".

## A Sync script is tested on a Runner

- **Changed: Test on the Scripts tab of a Workspace sync project runs the script on a Runner.** It builds the saved draft, stages the build in the Runner and channel chosen beside the button through the console (never `prod`), and runs the replication set's new manual task `script-test` there, which compiles the script and runs it against generated sample input with no connection; the tab shows the cases with a link to the run. A set's package has the task `script-test`, and a replication named `script-test` is refused. What to do: have a Runner the console manages with the slots of the set bound in a channel other than `prod` (`dev` with **Set up for development** is enough); the person who tests needs the publisher and operator roles there.

## A Sync connection on a driver of Sync's own is read by the set's own package

- **New: a Sync package has the manual, read-only tasks `discover` and `describe`, which read a connection whose driver is Sync's own.** A
  connection on a YAML driver or another driver the set carries, on DuckDB or Flight SQL, or one that binds a `metadataProvider` script, is read by them
  instead of the Runner's built-in package. They answer what the built-in package answers: the connection's tables and columns as `catalog-cache/2`, and
  a query's columns. The console runs them in the newest build of the set that the channel holds (`POST /api/workspace-catalog/<workspace>/<project>/read`

  again; build and stage the set in a channel before you read such a connection there.

## Column types: one set of answers for every product

- **Fixed: Sync no longer reads SQL Server's `tinyint` (0 to 255) as a signed 8-bit integer, nor MySQL's unsigned integers as signed ones.** A
  replication into MySQL or DuckDB created a signed `tinyint`, and values from 128 to 255 failed on write; MySQL `int unsigned` and `bigint unsigned`
  became `int` and `bigint`, and values above their signed maximum failed. Sync now writes `tinyint` on SQL Server, `tinyint unsigned` on MySQL and
  `utinyint` on DuckDB, and the next wider signed type on PostgreSQL and Oracle. A target made before shows a type change in its next provisioning
  plan (for example SQL Server `smallint` to `tinyint`); apply it or leave it. DuckDB's `UTINYINT` to `UBIGINT` are written back as the same type
  where the target has unsigned types, where Sync wrote `smallint` to `decimal(20,0)`.
- **Fixed: a decimal with no stated precision (PostgreSQL's `numeric`) is no longer rounded to a whole number.** Sync created `numeric(18,0)` or
  `decimal(18,0)`, so 12.75 arrived as 13; Transfer and the Store created `decimal(18,0)` on SQL Server and `decimal(10,0)` on MySQL. Every product now
  writes PostgreSQL's `numeric` on PostgreSQL and `decimal(38,9)` (`number(38,9)` on Oracle) elsewhere, with a note. A Sync target made before shows a
  type change in its next provisioning plan.
- **Changed: a time or timestamp with no stated precision is `time(6)`, `datetime(6)` or `timestamp(6)` on MySQL in every product**, where Transfer
  and the Store wrote whole seconds (Sync already wrote microseconds).
- **Changed: SQL Server's and MySQL's `binary(n)` stay fixed-length in Transfer and the Store too** (Sync already kept them): a `binary(16)` copied to
  SQL Server or MySQL is created as `binary(16)`, where it was `varbinary(16)`. The catalog shows such a column as `binary(fixed,16)`, and the
  Gateway reads an Arrow fixed-size binary column as one, with no note.
- **Changed, for authors of Sync scripts and `driver.csx` files: a column type is the shared `DbDataKit.Dialect.CanonicalType`; Sync's own
  `CanonicalType` and `CanonicalTypeKind` are gone.** A lifecycle hook, a `driver.csx` provisioner (`ProvisioningColumn.Type`) and a `driver.csx`
  dialect that used them no longer compile until they are changed; the namespace `DbDataKit.Dialect` is imported for every script, so no `using`
  is needed. What to change: `CanonicalTypeKind.X` becomes `CanonicalKind.X` (`CanonicalTypeKind.Unmappable` is `CanonicalKind.Unmappable`);
  `IsUnicode` becomes `Unicode == true`; `IsMax` becomes `Length is null`; `IsFixed` becomes `Fixed == true`; `CanonicalTypeKind.TimestampTz`
  becomes `CanonicalKind.Timestamp` with `TimeZone == true` (written `timestamp(tz)`); a reading's note (`SourceNote`) is no longer on the type.
  A `driver.csx` dialect implements `ReadColumnType` and `WriteColumnType` in place of `ToCanonicalType` and `RenderColumnType`. A hook's
  `IScriptDialect.ToCanonicalType` and `RenderColumnType` keep their names.
- **Changed: a generic Arrow Flight SQL target gets `TIME(6)` and `TIMESTAMP(6)`** for a time or timestamp with no stated precision, where Sync
  wrote `TIME` and `TIMESTAMP`; an Oracle target gets `timestamp(s)` for a time in Transfer and the Store too, where they wrote an interval.
- **Changed: Sync's JDBC driver reads and writes PostgreSQL's types through the same table as the PostgreSQL driver**, so a `bytea` or `time`
  column it refused before is provisioned, and a `varchar` with no length becomes `text`, where it was `varchar(255)`.

## Since the last release before the 2026-11-13 beta

These entries were written before the 2026-11-13 beta and are in no release note: the beta's release carries only the install text. They describe
programs that still exist and matter to a person upgrading from an older release. Entries about the deleted Build, Sync and Store servers and about the
Proxy's name are left out (their deletion and the rename are noted above). Each is as it was written; a later entry above wins where they differ (for
example the variable names of plan 33 SC31a).

### DbDataSync (the command line and the engine a Runner runs)

- **Connections are `connection/1` files, and the old form is refused.** `config/connections/<name>.yaml` is now the shared connection format that the Proxy and Build use: `schema: connection/1`, `name`, `engine`
  (`sqlserver`, `postgres`, `mysql`, `oracle`, `duckdb`, `flightsql`, or a driver id), `address` (host, port, database) or `connection_string`, `auth` (`sql` with `user` and
  `password_secret: secret:dbdatakit:sync:connection:<name>`, `integrated` or `none`), `timeouts`, and Sync's own settings (`segment_order`, `properties`, `scripts`, `hooks`, `test_query`, `connect_timeout_seconds`, `command_timeout_seconds`, and `database` with a `connection_string`)
  under `extensions.sync`, spelled snake_case like the shared keys (a camelCase key such as `testQuery` is refused as an unknown key, with the new spelling suggested). A repository that still has the earlier files (`driverType`, `host`, `authMode`, `schemaVersion`) fails to load its connections, with a message that names every such file and the new form
  (`dbdatasync config check` and the Connections page show it). **Rewrite each file by hand, or delete it and create the connection again**; nothing is converted, and the stored passwords keep their names so none needs setting again.
  A connection name must now start with a letter and be at most 64 characters (it was any letters and digits). The API and the screens are unchanged. See `DbDataSync/docs/configuration.md`, "Connection files". (E01)
- **Every config file needs a `schemaVersion`, and unknown keys are an error.** (Connection files carry `schema: connection/1` instead, see the entry above.) A file without one, or with an older one, is refused with a
  message naming the file. The retired per-stage `parallelism` keys under `reader` and `writer` in a replication's `task.yaml` are refused,
  naming each key: delete them. (A02, A03)
- **Column types for some engines changed.** Oracle `uuid` stays `varchar2(36)`. Oracle `NUMBER(n,0)` up to 18 digits is read as an integer
  type. MySQL's time-zone timestamp is created as `timestamp(s)` (it ends in 2038). Postgres creates `timestamp(6) with time zone`.
  DuckDB's unsigned integers are read as the next wider signed type. (A07)
- **The dotnet tool package is gone.** `dotnet tool install -g DbDataSync` and `dotnet tool update` no longer work for a new release: no `DbDataSync.<version>.nupkg` (and no `.sha512`) is built, attached to a release or pushed anywhere, and `DbDataSync.Cli` is no longer a packable tool. Install the Windows installer (`.msi`), the zip with `install.ps1` / `install.sh`, the Scoop manifest, or the container image instead (`DbDataSync/docs/install.md`, `dist/README.md`), and upgrade the same way. `dbdatasync update` reads those packages from the release, so **it finds no new version from this release on** (it still lists older ones); use the same route you installed with. A machine that was installed as a tool keeps working: install the zip or MSI over `%ProgramFiles%\DbDataSync` / `/opt/dbdatasync` (the installers replace the program files and keep the service registration), or remove the tool (`dotnet tool uninstall`) and install again. `tools/install-local-tool` (the developer's pack-and-install loop) is gone: run the build output, or install a zip built with `dotnet publish`. (Dist)
- **SQL Server and PostgreSQL connections verify the server certificate by default.** The built-in `TrustServerCertificate=true` is gone: SQL Server connections are encrypted (`Encrypt=Mandatory`) and the
  certificate is checked, and PostgreSQL uses `SSL Mode=VerifyFull` (Npgsql's default was `Prefer`, which did not verify). A server with a self-signed certificate needs `TrustServerCertificate=True` in the
  connection string or in the connection's properties; a PostgreSQL server without TLS needs `SSL Mode=Disable` (or `Require`, which encrypts without verifying). `Encrypt`, `SSL Mode` and `Root Certificate` in a
  connection string or in properties are still honoured. A connect timeout in properties still wins. Any other property the shared policy reserves (credentials, host and database keys, `Application Intent`,
  `Multi Subnet Failover`, `Options`, `Search Path`, command timeouts) is now refused with a message naming it; put it in the connection string instead. (A08)
- **Sync commands accept `--format json`.** `server`, `service`, `cert`, `secret`, `library`, `driver`, `config` and `health` print one JSON document (`schema`, `command`, `exit_code`, `ok`, `data`, `messages`, `errors`); an unknown command now exits 2 with "'x' is not a command" (it was 1 with "Unknown command 'x'"). (C07)
- **Database errors show a fixed message and the engine's code, not the driver's text.** A failed connection test, run, preview, provisioning step or reconcile now reports for example
  `The login was rejected. [sqlserver 18456]` or `The server could not be reached. [postgres 08006]`; a run's stored error detail is empty for a driver failure. The driver's own text, with
  secrets scrubbed, is written to the server log. Set `Diagnostics:DriverDetails` to `true` (environment `Diagnostics__DriverDetails=true`) to append it to the response and keep it in the run
  detail again. Sync's own validation messages are unchanged. (A10)
- **MySQL, MariaDB and Oracle connections are verified and encrypted by default.** Like SQL Server and PostgreSQL before them, they are built by the shared composers. MySQL and MariaDB now use `SSL Mode=VerifyFull`
  unless the connection string or `properties` name another `SSL Mode` (`None`, `Preferred`, `Required`, `VerifyCA`); `SSL CA` is the root certificate. An Oracle connection given as a host, port and service name is written as
  `tcps://host:port/service`; put `Encrypt` = `false` in `properties` for a listener that has no TLS. A connection string is still the base and its own data source (an alias, a descriptor, a wallet) is not rewritten.
  Credential, host, port, database and timeout keys in `properties` are refused with a message naming the key (Oracle's `Data Source` included). Failures from these engines now show the shared classified message. (A09)
- **`dbdatasync ui mcp` serves the commands that read to an agent** (Model Context Protocol on standard input and output). Each command that only reads is a tool that returns its `--format json` document; `--allow-writes` also offers the ones that change files. Secrets cannot be set and installed libraries cannot be loaded through it. (C08)
- **MySQL, MariaDB and Oracle table columns are read by the shared catalog readers.** MySQL and MariaDB column types now carry the full engine type (`bigint unsigned`, and MariaDB's `bigint(20) unsigned`; `text` instead of `text(65535)`), so an unsigned column is no longer mistaken for a signed one. Oracle reports the same types as before. (A12)
- **New: whether a reload's segments run one at a time or together is a setting.** `segmentOrder` (`oneAtATime`, the default and what Sync has always done, or `together`) can be set on a connection (the one the mapping writes to), a replication or a table mapping, and a bulk load request may carry it; the most specific wins. Nothing changes until it is set; there is no screen for it yet. (M03)
- **A load into SQL Server or PostgreSQL that used to store a reinterpreted value now fails.** Sync's staging refuses, before writing, a value whose type the
  target would store as something else, with a message naming the table, the column, its type and the value's type (never the value): `Staging into public.invoices: column 'Due' (date) cannot take a value of type System.Int32 from the source ...`.
  The pairs: PostgreSQL `date` from `int` or `ushort` (stored as days since 2000-01-01), `time`, `timestamp` and `timestamptz` from `uint` or `long` (microseconds since 2000-01-01), `text` and
  `character varying` from `byte[]` or a stream (the bytes as characters); SQL Server `tinyint`, `smallint`, `int` and `bigint` from a character (its code point, `'a'` as 97), and SQL Server `varchar` and `nvarchar` from a `DateTime` or `DateOnly` (the client formats the date as text such as `03/17/2024 09:41:22`: lossy, and dependent on the culture of the machine that runs Sync; decided 2026-10-30). **To fix a date sent into a text column,** add a Transform to the mapped source column that formats the date or time as the text you want (for example `yyyy-MM-dd HH:mm:ss`). **To fix the others,** change the mapped source
  column, or its `Transform`, to a type the column takes (a date or timestamp for a date column; `CAST(... AS ...)` or a conversion in the Transform; text for a text column). What is still stored as before:
  anything that is only a question of the value, such as `1.5` into an integer column (rounded on SQL Server, truncated on PostgreSQL), a number out of range, a string that parses as a date or a number, and a
  string too long for its column. Cost: one type comparison per cell, as before; no change in speed. (A14b)
- **Package hashes of scripts are pinned in the configuration repository.** A `.csx` script's `#r "nuget: Id, 1.2.3"` packages are recorded, with their SHA-512, in `scripts/<name>.lock` beside the script (a library's are in `libraries/<id>/library.lock`
  already, and a compiled driver's in `drivers/<id>/driver.lock`; same file format). A configuration repository without lock files keeps working: the first time a script with packages is compiled (validated, saved, tested or run) its lock file is created, and saving the script
  commits it; a lock file created by a run is not committed by Sync, so **commit the new `scripts/*.lock` files** of an existing repository. From then on a package whose bytes differ (another machine, or the feed changed under the same id and version) is refused with a message naming the package, the version
  and the lock file; if the change is expected, delete that package's line from the lock file and validate again. A stored package that matches its pin needs no network. The lock reader is strict: a key other than `schema` and `packages` stops the load,
  naming the file and the key. Deleting a script deletes its lock file. (S12)
- **Changed: a primary key update at the source now reaches a `TriggerAudit` target as a delete of the old key and an insert, and a pass over an old trigger fails until it is replaced (plan 28c CW02a).** Before, `UPDATE orders SET id = 2 WHERE id = 1` on a PostgreSQL, MySQL, MariaDB or Oracle source left the row with id 1 in the target for good (the trigger recorded the new key only) and nothing reported it; SQL Server's trigger already recorded it correctly and is unchanged. The generated triggers now record the old key as a `D` row when an update changes a key column (the audit table's shape is the same: no new column). **A trigger already installed in your database is the old text:** each `TriggerAudit` pass on PostgreSQL, MySQL, MariaDB and Oracle now checks it and **fails naming the table** until you replace it. Open the replication's Provisioning card (or `POST api/replications/{replication}/provisioning/apply`) and apply *Enable source change capture*: it lists the replacement as a step (PostgreSQL replaces the capture function only; MySQL/MariaDB and Oracle drop and create the trigger again) and keeps the shadow table and the stored position. A trigger you wrote yourself is not checked on a descriptor (ODBC/JDBC) driver. `Watermark` still cannot see a key update (see Replication concepts, "A key change"). The read also treats a `D` shadow row whose source row still exists as the update of that row. Nothing in a stored file changes: no format version moves.
- **New: `reconcile.afterEveryPasses` and a "cannot see a key change" note for `Watermark` (plan 28c CW02b).** A `Watermark` (or `ScriptedQuery`) reader reads only rows that exist, so a primary key update at the source (`UPDATE orders SET id = 2 WHERE id = 1`) leaves the row with the old key in a target keyed by the source's key until a reload or a delete-reconcile sweep removes it; nothing is refused and nothing fails, as before. What is new: the reader picker marks these readers "cannot see a key change" and the Pipeline screen warns under the reader stage; and the delete reconciliation of a replication or mapping takes `afterEveryPasses: N` (off when left out, at least 1, no cadence needed) which runs the sweep after every N successful change passes since its last sweep, so the old key is gone within N passes without a hand-run reload. An existing file is unchanged (the key is optional; `schemaVersion` stays 2); a Sync older than this release refuses a `task.yaml` that has the key as an unknown key. The API's reader capabilities carry the new `detectsKeyChanges` flag.

### DbDataBuild (the command line and the runtime a Runner runs)

- **New: a built model can declare `foreign_keys:`, and a semantic model reads them as relationships.** The keys are a claim about the data, never created in a database. A key that does not match its target (`references.table` not a model of the project, a column the target lacks, columns that are not its `grain`) is DDB-618. A semantic file reads a key as a many-to-one relationship named like the key when both models are used and the file writes none between them (roles stay in the semantic file). `connection check` tests each key: rows whose key the target lacks, and a target grain that is not unique (`project tests list --kind semantic` lists them). (J29)
- **A PostgreSQL connection is a `postgres` source of a semantic model, not a `sqlserver` one.** The catalog Build compiles from `semantic/` files is now validated and emitted as PostgreSQL for a PostgreSQL connection (it was validated as SQL Server). (D13)
- **A copy now stops on two values it used to let through.** A copy converts values with the shared converter, and writes them with the shared bulk writers. A `DateTime` that has a time of day, copied into a column the model declares `DATE`, used to lose its time silently; it is now an error that names the column. A string longer than a declared `VARCHAR(n)` is refused at the copy, naming the column, where the destination used to refuse it. Declare the type the origin really holds (`TIMESTAMP`, a longer `VARCHAR`) or cut the value in the read. Nothing else changes: the same rows arrive in the same tables, and the statement log is as before. (B08)
- **Login variables are `DBDATA_BUILD_<CONNECTION>_<READ|WRITE>`.** The old `DBDATABUILD_*` names are not read, and the
  `secret:dbdatakit:build:connection:...` fallback is gone. A connection name with characters other than letters and digits has underscores in
  its variable (`my-dw` is `DBDATA_BUILD_MY_DW_READ`). A connection with no variable set is DDB-501, naming the variable. (B02)
- **Connections are files, `connections/<name>.yaml`, and a `connections:` in `dbdatabuild.yml` is refused.** Each is a `connection/1` document (`schema: connection/1`, `name` equal to the file name, `engine` the driver alone, optional `dialect` and `access: readonly`, and the tool's own settings under `extensions.build`: `version`, `parameters`, `max_parallel`, `tracking`, `title`, ...). A project whose `dbdatabuild.yml` still has `connections:` stops with `DDB-621` naming `dbdatabuild.yml` and every connection in it; nothing is converted. Move each entry: `shop: { engine: readonly postgres, parameters: { store_id: E01 } }` becomes `connections/shop.yaml` with `engine: postgres`, `access: readonly` and `extensions: { build: { parameters: { store_id: E01 } } }` (keywords of the old `engine` other than the driver are `access` and `dialect`). A file that is not right is `DDB-620` naming the file and line; a connection file holds no address, login, TLS or timeout setting, and the login is still `DBDATA_BUILD_<NAME>_<READ|WRITE>`. The five templates are rewritten, so a project made from one before needs the same move. `dbdatabuild project agent-kit` writes `schemas/connection.schema.json`. (E03)
- **The statement log has a new line format, and still holds the values.** `.dbdatabuild/statement-log/*.jsonl` is written by the shared write gate's log: each parameter of a line is `{"name":..., "type":..., "hash":..., "value":...}` where it was `{"Name":..., "Value":...}`. The `value` is still the value in the clear, as before (nothing was changed to hashes; `hash` is an extra, salted per run, that matches equal values within a run). The file is created readable by its owner only on Linux and macOS. The lines for a lock and for the rollback after a failed statement have the kinds `Lock` and `Control`, and the rollback line has no text. Tools that read these files by the old keys need the new ones; retention (`retention.statement_logs_days`) is unchanged. (B06, B07)
- **`connection status` and `connection monitor` decide overdue and slow by exact time** (the shared health rules) where they compared whole seconds, so a run that began 3600.5 seconds ago is now overdue under `expected_every: 1h`. (M09)
- **Build secures its connections the way every product does: encrypted, certificate verified, unless the connection file says otherwise.** A SQL Server or PostgreSQL login string from `DBDATA_BUILD_<NAME>_<READ|WRITE>` used to be taken as written, so `Encrypt=False` or `TrustServerCertificate=True` in it was enough. Now the connection file's `tls:` block is applied over the string, and a file with no `tls:` (or a connection named after its engine with no file) encrypts and verifies. A server with a self-signed certificate needs `tls: { trust_server_certificate: true }` in `connections/<name>.yaml` (and one without encryption `tls: { encrypt: false }`); the keys are `encrypt`, `verify`, `trust_server_certificate` and `ca_file`, and the connection file's schema lists them. Without it Build reports a TLS or certificate failure when it connects. A read login also asks for read-intent and is named `dbdatabuild-read` (write: `dbdatabuild-write`) as before. ODBC, DuckDB and Flight SQL logins are unchanged. (B02)
- **`scripts/test-engines.sh` is gone; the slow conformance engines are profiles of `testenv/`.** Start them with `testenv/testenv.sh up mssql postgres mssql2025 oracle spark bigquery flight flight-tls` (`up all` starts every engine there is) and read the variables with `eval "$(testenv/testenv.sh env dbdatabuild)"`. Ports are fixed: SQL Server 2025 14332, Spark 10000, the BigQuery emulator 9050, Flight SQL 31337 and 31338 (TLS); Oracle is the shared one (user `dbkit`, not `system`). The ODBC driver exports that `test-engines.sh env` printed are now `eval "$(DbDataBuild/scripts/psqlodbc-env.sh)"`. Only developers and CI are affected. (F16)
- **`project compile --format json` and `project show metadata` no longer fail for a mapped model on a read origin** (DDB-900, "Unknown target `duckdb`"). `project import` writes such models (`connections=: [origin]`), so the first import into a project used to break the console's check. (W07)

### DbDataGateway

- **A Gateway now listens on `127.0.0.1:8816` by default (its management API), https with its generated self-signed certificate.** Before, the management API was off unless `management: { enabled: true }`. It is reachable only from the machine until `management.address` says otherwise, and every call needs a token a pairing issued, so a console pairs with a fresh install at `https://localhost:8816` (`dbdatagateway server pair`, then `dbdatakit instance add https://localhost:8816 --code <code>`). **To keep the old behaviour set `management: { enabled: false }`** (`DBDATAKIT_Gateway__Management__Enabled=false`). A configuration with `tls: { mode: none }` that says nothing about management is now refused at start; add `management: { enabled: false }` or use a TLS mode. Another program on the machine that uses port 8816 must move (`management.port`). The compose files no longer set `Management__Enabled` (it is the default) and still set the address to `0.0.0.0` so a console in another container can reach it. (SC40)
- **The Gateway has a linux-x64 zip, and a Linux server refuses the Windows-only settings (plan 33 SC01 to SC03).** The release now carries `dbdatagateway-v<version>-linux-x64.zip` beside the Windows one (one `SHA256SUMS`): framework-dependent, so it needs the .NET 10 runtime (ASP.NET Core), with no 32-bit ODBC worker; `install.sh` installs it and `dbdatagateway service unit` prints the systemd unit (data in `/var/lib/dbdatakit/gateway`). The Scoop manifest, the MSI and `install.ps1` stay Windows. **On Linux a configuration is now refused at start, naming the setting, when it uses `Auth: { windows: true }` (Windows password sign-in), a `Bitness: x86` ODBC source (was a warning) or an Analysis Services source (already refused)**: remove it, or run that Gateway on Windows. (SC01, SC02)

### DbDataGateway, as it was named DbDataProxy before the beta (each entry describes the Gateway today)

- **New: a management API for a console (off unless asked for), and `server pair|clients|unpair`.** `management: { enabled: true }` in `server.yaml` opens an https listener on port 8816 (loopback unless `management.address` says otherwise) that is never the Flight port; a console pairs with a single-use code from `dbdataproxy server pair` and then reads the server's identity, its effective configuration (secrets masked, with where each value came from) and validates a candidate configuration without writing it. `management.localChannel` also answers the command line on this machine. `server.yaml` gains `instanceId` and `pairedClients`, which the pairing verbs write; leave them to the verbs. (P03)
- **Proxy's settings are YAML files, and `appsettings.json` is refused.** The settings are in the `config` folder of the data directory: `server.yaml`, `proxy/auth.yaml`, `proxy/users.yaml` and one `connections/<name>.yaml` per data source (keys in camelCase, except the data sources, which are `connection/1` files with snake_case keys and the proxy's own settings under `extensions.proxy`; `config.example/` beside the executable shows each file). A data source file in the earlier layout (`provider:`, `connectionString:`, no `schema:`) is refused with a message naming it: rewrite it as a `connection/1` file, with the password as `auth.password_secret` (a reference such as `env:ERP_DB_PASSWORD`) instead of in the connection string. An `appsettings.json` in the data directory, its `config` folder or beside the executable stops the server (exit 2) with a message that names it; nothing is converted, so move the `Proxy` section's keys into the new files and delete the old one. Environment variables and the command line override as before. `config check|show --file` takes a config folder or the path of its `server.yaml`. (P01)
- **Parameterised queries work from the Apache .NET Flight SQL client.** A prepared-statement handle was random binary data, which that client turns into a string and back, so the proxy no longer recognised it and answered `NotFound: Unknown or closed prepared statement`. Handles are now 32 hexadecimal characters; clients need no change. (A18)
- **`dbdataproxy ui mcp` serves the commands that read to an agent**, the same way. Secrets and `query run` (which returns rows) are never offered. (C08)
- **New: semantic queries.** A `semantic:` section in `server.yaml` names catalogs (semantic models) and the data source for each of their sources; a client then sends a JSON semantic request or semantic SQL as a statement with `x-datasource: semantic:<model>` and gets the combined result as an Arrow table, with the engine's status, warnings and remaining steps in the schema metadata. The scans run as the signed-in client against the mapped data sources, under the same access, classifier and limits as their SQL. SQL Server, PostgreSQL and DuckDB sources; Analysis Services (DAX) sources run on Windows when the model gives their connection (`ssas:` under the model; the connection is the server's, not the caller's, so the access rules of the data sources do not apply to it). Nothing changes for a server with no `semantic:` section. (J10)
- **New: publish semantic models to a running Proxy.** `PUT /api/v1/semantic-models/<name>` (administrator, or a paired Build server for its own models) validates the catalog and its source mapping, keeps every version, switches atomically and rolls back with `POST .../rollback`; published models survive a restart. Also fixed: a catalog source with several fact tables ran its second and later facts against a data source of the wrong name. (J13)
- **The Proxy serves PostgreSQL (`engine: postgres`).** A data source of `engine: postgres` takes an Npgsql connection string (`Host=...;Database=...`; the `address:` form stays SQL Server only) and answers queries, catalog metadata and parameters like the others, with the read-only classifier (the PostgreSQL deny list: `COPY`, `DO`, `pg_read_file`, `lo_import`, `dblink`, `set_config`, and the rest) and the concurrency limits applied, and a source that cannot write also sets `default_transaction_read_only=on` on its session. It can pass the caller's own database credentials through (`pass_through: true`). TLS is `SSL Mode=VerifyFull` unless the string says otherwise; a string with `SSL Mode=Require` or `Disable` is named in the startup warning like a SQL Server opt-out. Behaviour to know: a `?` is a marker, so PostgreSQL's `jsonb` `?` operator must be written `jsonb_exists(...)`; an array column arrives as its JSON text; a `numeric` wider than .NET's `decimal` fails the query (cast it). Build's publish now accepts PostgreSQL connections, and the console's Build Publish page says so; `fabric` connections are still refused with the 409 that names the engines a Proxy serves (plan 13a, P12, which records why). Nothing to do for an existing install: no setting changes. (P12)
- **The Proxy serves an upstream Flight SQL server (`engine: flightsql`).** The data source's connection string is the Flight SQL login value Build already uses (`grpc+tls://host:port;token=...`, or `;user=...;password=...`, with `header.x-datasource=<name>` to choose a data source of an upstream Proxy), read by the shared `DbDataKit.Connections.FlightSql` client. It is read only (`allow_writes` is refused at load), takes no pass-through credentials, and a statement is checked with the ANSI deny list; the read-only classifier and the concurrency limits apply as for any source. `token_command` and `token_env` are **refused** in a Proxy data source (a program or variable the data source's author named must not run or be read on the Proxy's host); put the token in `token=` as a secret reference. Metadata is read with `INFORMATION_SCHEMA` queries on the upstream server. Build's publish now accepts Flight SQL connections whose login follows that rule and refuses others in a sentence before anything is sent. (P12)
- **New: `dbdataproxy datasource adopt <name> <client id or name>`** hands a data source made by hand, or by another client, to a paired server client (a Build server), the same call as `POST /api/v1/data-sources/{name}/adopt`, over the running proxy's local channel (`management.localChannel: true`); the audit line names the operating-system user. `--format json` works. A new `GET /api/v1/clients` (administrator) lists the paired server clients. The console's Proxy data sources page shows who manages each data source and has a Hand over button, and the Build Publish tab's adopt offer has a button for administrators. (T13)
- **Changed (breaking): Proxy's own users are gone; clients sign in with the identity home, and data source files name the home groups that may use them.** Proxy no longer has users or Windows accounts of its own. A configuration that still lists them (`users:` in `proxy/users.yaml` or `server.yaml`, `Proxy:Users` in the environment or on the command line, a Windows `AuthType` entry) **stops the server** with exit code 2 and a message naming the file and line (or the layer) and the key `Proxy:Users`; an empty `users: []` is accepted. `dbdataproxy secret hash` is removed with them, and `PUT`/`DELETE /api/v1/users/{name}` answer `410 Gone`. To move over: (1) make the people home users (the identity home's people screens or invitations, or `dbdataproxy identity service-account-add --name <name>` for unattended work); (2) a client signs in with its **home user name (the person's address, a service account's name) and a personal access token as the password** (a person makes theirs at the identity home, a service account's with `dbdataproxy identity token-create --account <name> --name <label>`), or sends the token alone as `authorization: Bearer <token>`, or, with `windows: true` in `proxy/auth.yaml`, signs in with their UPN and Windows password (resolved to the home user who holds that address); (3) **name the home groups that may use each data source in its file**, under `extensions.proxy`:

  ```yaml
  extensions:
    proxy:
      groups: [finance-reporting, auditors]   # members of these home groups may use this data source
      # everyone: true                         # or: every user of the identity home may use it
      # default: true                          # the source a person gets when their client names none (one at most)
  ```

  **A data source that names no group and is not `everyone` is used by no home user**: after the move nobody reaches it until you name a group, and the configuration check warns about each such source (a pass-through data source needs neither: the database decides there, with the caller's own credentials, unchanged). `groups` takes the place of the retired `Users[].DataSources`, and `default: true` the place of `DefaultDataSource`. A refused person is told which data source and why. The log, the session list and the running-query list name the home user (`Query by Ada Lovelace on erp`), never the token. A failed password that has the shape of a token (`ddk_...`) is refused, not tried as a database login. A data source a Build server publishes to the Proxy names no group either, so open it with its file in `connections/`. (P13)

### dbdatakit (the console) and the suite

- **New: the `dbdatakit` console.** One web interface for the DbData servers, a separate program from them: `dbdatakit server run` serves it over https (a self-signed certificate it makes in its directory; `--listen https://localhost:8480` by default), the first administrator redeems the invitation in `FIRST-RUN.txt` by making a passkey, and `dbdatakit user list|invite` manage who can sign in. `dbdatakit instance add <address> --code <code>` pairs it with a server (the code is made on the server with `server pair`); `instance list|remove|rotate-key` manage the pairings, and the Servers page shows each server's state. Calls to a server go through the console's `/relay/<server>/api/...`, which signs a short-lived token naming the person. Nothing is on unless you start it. (U07, U12, U08)
- **Staging loads go through the shared bulk writers; nothing to do.** SQL Server's `SqlBulkCopy` staging and PostgreSQL's binary `COPY` staging now run in `DbDataKit.Transfer.SqlServer` and `DbDataKit.Transfer.Postgres`.
  The staging tables, their names, their columns, the error text for a value `COPY` cannot write, and the speed (measured within noise of before, see `DbDataSync/architecture/benchmarks/staging-baseline.md`) are unchanged; no file, log
  or wire format changes. One difference: SQL Server `date` and `time` values that a source delivers as `DateOnly` and `TimeOnly` are converted to `DateTime` and `TimeSpan` by the shared writer before `SqlBulkCopy` sees them. (A14, A15)
- **A staged value of a type the target column never takes now fails with one message.** On the SQL Server and PostgreSQL bulk staging paths, a value whose type the target engine refuses for every column of that kind (a `Guid` into an `int`
  column, a `DateTimeOffset` into `varbinary`) fails before it is written, with `Staging into <table>: column '<name>' (<declared type>) cannot take a value of type <type> from the source ...`, naming the table, the column and the type, never the value.
  Before, the same run failed with the provider's own message. What is stored and what is refused is unchanged for every value measured (the 1,900-cell tables in `DbDataSync/architecture/staging-value-types.md`); a run that failed still fails, a run that
  succeeded still succeeds; only the text and the exception type (`StagingValueException`) differ. (A14a)
- **Sync scripts are `.csx` files.** A script `config/scripts/<name>.cs` with an `entryType` in its manifest is no longer read: Sync stops with a message naming the file. Rename the code to `<name>.csx`, remove `entryType:` from `<name>.yaml`, and end the script with an expression that is the implementation, **with no semicolon after it**: `new MyTransform()`. A script may now `#r "nuget: Id, 1.2.3"` packages and `#load` other scripts of `config/scripts/`. (S07)
- Servers can announce themselves to a console (`DBDATAKIT_CONSOLE_ANNOUNCE_URL`, `DBDATAKIT_ADVERTISE_URL`) and wait to be confirmed (`dbdatakit instance pending|confirm|reject`); the console takes announcements on a private plain-http port (`--announce-listen`, `DBDATAKIT_CONSOLE_ANNOUNCE_LISTEN`) that must not be published. `dist/compose/build.yml` runs a console with a Build server this way. The Servers page of the web app lists the waiting servers (name, address, when each last announced) with a Confirm and a Reject button each, for administrators; Confirm pairs with the certificate the server presents, so confirm only a server you recognise.
- The console's and the Proxy's state database can live on SQL Server or PostgreSQL: `--state-engine` and `--state-connection` (or `DBDATAKIT_CONSOLE_STATE_ENGINE` and `_CONNECTION`) for the console, `state:` in `server.yaml` for the Proxy. SQLite stays the default. Give each its own database; the password is a secret reference.
- **A console with an identity home refreshes roles inside a session and ends the home's session at sign-out.** The home's OpenID provider now issues refresh tokens (scope `offline_access`) and has an end-session endpoint (`end_session_endpoint` in discovery). A console signed in through a home asks it for the person's roles again every 5 minutes (a removed role applies without a new sign-in; the console's ceiling still lowers them), keeps the last roles for 10 more minutes when the home does not answer and then grants no role on any server, and signing out of the console sends the browser to the home to end their session there (which ends their other consoles' sessions at their next refresh). Register the console's `<public address>/` as a post-logout redirect address of its client at the home so the browser comes back. Local users are kept and unaffected. Two new state tables are added by append (`RefreshTokens`, `OidcClientLogout` at the home; `FederatedSessions` at the console); nothing to migrate. (U17)
- **The identity home maps Entra and Windows groups to roles (component only).** `HomeDirectory.MapExternalGroup` gives everyone whose last sign-in through a source (`entra`, `windows`) carried a group the roles you map it to on a server, a Build project of it or an app, added to what they hold otherwise; a removed mapping removes the role. Groups are compared ignoring case. **Nothing to do yet:** no host performs the Entra sign-in or administers mappings (serving layer, O06), so no install has mappings. The home's schema gains `GroupMappings` and `ExternalMemberships` (a new schema entry, appended; created at the next start). An unmapped group gives nothing. A person removed from an Entra group keeps the role until their next sign-in through Entra (open question D24). `OpenIdClient` now also accepts RS256 id tokens. (U18)
- **One account per person across every way of signing in; a new account needs an email address.** The address is the account's key (a Windows account's is its user principal name, `user@domain`), compared without regard to case: a local passkey user, a Windows account and a person who signs in through the identity home with the same address are one user (the same roles, and the same user id in a server's audit). A sign-in that would take an address another account already holds is refused with a message. **What changes for you:** (1) an invitation for a new user must say whose it is: `dbdatakit user invite --email <address>` (or `--user <id>` to give an existing user another way in), `dbdatasync invite --email <address>`, `POST /api/invites` with `email`, and the Users page asks for it; before this an invitation made without one now fails with a message naming `--email`, and the person's own entry at redemption is no longer used (only the first-run invitation, which nobody made, keeps what is typed, for display). (2) **Existing users keep signing in and keep their roles**, but their addresses were typed by whoever redeemed the invitation and nobody checked them, so none is matched on: the Users page marks them "unverified", and `dbdatakit user set-email --user <id> --email <address>` (or the Set button) sets the address an administrator vouches for; until then such an account is not joined to a Windows account or the home, and the same person signing in that way gets a second account. (3) A Windows account whose domain gives no user principal name cannot be a new account (a `DOMAIN\user` name is never turned into an address); one that already has an account signs in by its SID as before. (4) A person the identity home knows, whose verified address a local or Windows account holds, becomes that account **under the home's user id** (their passkeys, Windows accounts and sessions move with it), and then holds what the home gives them on every way in. The state database gets two new columns (`Users.EmailKey`, `Invites.Email`) and a unique index when the product starts; older databases are upgraded in place, nothing is rewritten. (U16)
- **New: the identity home can run on its own, `dbdatakit identity run`.** It serves the OpenID Connect provider and the shared sign-in (passkeys, invitations, users) with a state and a directory of its own (`--repo` or `DBDATAKIT_IDENTITY_DIR`; `--state-engine sqlite|mssql|postgres` with `--state-connection`; default address `https://localhost:8490`; `--public-url` is the issuer every console and app knows it by and must not change when the home moves). The first administrator redeems the invitation in `FIRST-RUN.txt` (the console's web app, installed as `wwwroot`, serves the invitation and Users screens). Register each console with `identity client-add --name <name> --redirect <console address>/api/identity/callback --logout-redirect <console address>/` (the secret is shown once: give it to the console as the variable `--identity-secret-env` names), give people roles with `identity assign --user <id> (--server <id> [--project <name>] | --app <id>) --roles <list|none>` and external groups with `identity map-group`. **To move a home, stop it and move its directory (and keep its address)**: the signing keys are protected by the key ring in `dataprotection/` of that directory, so a copy without it will not start (the message is a cryptographic error). The sign-in page needs a browser with passkeys; it is not covered by a Playwright run yet. Not yet: running it as a Windows service or a systemd unit, the serving layer forwarding its public endpoints, screens for its administration. (U15)
- **A global Scoop install sets the products' data folders, and betas and snapshots have Scoop manifests.** After `scoop install -g` the manifests set machine variables: `DBDATAKIT_CONSOLE_DIR=%ProgramData%\DbDataKit\console` for the console (so `dbdatakit instance` and `user` commands find the folder `server run` serves, instead of a per-user one) and `DbDataSync__App__RepoRoot=%ProgramData%\DbDataSync` for Sync (its default); uninstalling removes them only while they still hold that value. A per-user install sets nothing. Open a new terminal after installing. The newest beta and snapshot of each product have fixed manifest URLs, `.../releases/download/<product>/dist-beta/<product>.json` and `.../dist-snapshot/<product>.json`; a snapshot (`<CalVer>-snapshot.g<sha>`) can be cut from any branch. (L10)
- **Breaking, no migration: one data root, a folder per service, and new variable names (plan 33 SC31).** Every service keeps its folder under one root, named for it: Windows `%ProgramData%\DbDataKit\<service>`, Linux `/var/lib/dbdatakit/<service>`, with `<service>` one of `server` (the DbDataKit console), `gateway`, `runner`, `sync`, `build`, `store`, `workspace`, `identity`. **The old Windows service folders are not read, moved or renamed**: `DbDataKit\console` is now `DbDataKit\server`, `DbDataRunner\server` is `DbDataKit\runner`, `DbDataStore\server` is `DbDataKit\store`, `DbDataWorkspace\server` is `DbDataKit\workspace`, `DbDataSync` is `DbDataKit\sync` and `DbDataGateway` is `DbDataKit\gateway` (Build had no default; it is `DbDataKit\build`). A Linux unit's folder is `/var/lib/dbdatakit/<service>` instead of `/var/lib/<program>`. Move the old folder by hand (stop the service, move it, start it) or set the service's variable to the old place; nothing does it for you, and an existing service registration keeps passing its old `--repo` until you run `service install` again. **New variables:** `DBDATAKIT_DATA` (the root), `DBDATAKIT_DATA_<SERVICE>` (one folder, which wins), `DBDATAKIT_STATE_ENGINE` and `DBDATAKIT_STATE_CONNECTION` (the state database of the whole install) and `DBDATAKIT_STATE_<SERVICE>_ENGINE` and `_CONNECTION` (one service's, which wins); `--repo` and the state flags still beat all of them. **Old variables are refused, with no alias:** a service or command that finds one set stops and names the new one. They are `DBDATAKIT_CONSOLE_DIR`, `DBDATAKIT_IDENTITY_DIR`, `DBDATARUNNER_SERVER_DIR`, `DBDATASTORE_SERVER_DIR`, `DBDATAWORKSPACE_SERVER_DIR`, `DBDATABUILD_SERVER_DIR`, `DbDataSync__App__RepoRoot` (now `DBDATAKIT_DATA_SYNC`), `DBGATEWAY_Gateway__DataDirectory` (now `DBDATAKIT_DATA_GATEWAY`; `--Gateway:DataDirectory` still works), and `DBDATA<PRODUCT>_STATE_ENGINE` and `_CONNECTION` for the runner, store, workspace and build, `DBDATAKIT_CONSOLE_STATE_*` and `DBDATAKIT_IDENTITY_STATE_*`, `DBGATEWAY_Gateway__State__Engine` and `__Connection` (now `DBDATAKIT_STATE_<SERVICE>_ENGINE` and `_CONNECTION`). Container images keep their `/data` (Sync `/var/lib/dbdatasync`) volumes; only the variable's name in the image changed. A global Scoop install of any product now sets the one machine variable `DBDATAKIT_DATA=%ProgramData%\DbDataKit` (and the old per-product variables are no longer set); **uninstalling a product does not remove it**, because the other products read it too. (SC31)
- **Changed: Sync reads a replication file of the previous format (plan 33 SC50).** A `task.yaml` that says `schemaVersion: 1` loads again (format 2 only adds the optional `checks:` section) and every save of it, from a screen, the API or the checks tab, writes `schemaVersion: 2`; a file of 3 is still refused as newer and one of 0 as invalid. Table-mapping and script files are unchanged (1).
- **Breaking, no migration: the Windows service of the console is named `DbDataKit` (plan 33 SC32).** `DbDataKitConsole` is gone: the service name and the display name are `DbDataKit` (the account is `NT SERVICE\DbDataKit`), the MSI registers that service, and the console protects its secrets with a new DPAPI entropy. A machine that has the old service **uninstalls it by hand before installing this release** (`sc.exe delete DbDataKitConsole`, or `dbdatakit service uninstall` with the old build) and sets its secrets again; nothing is moved or converted. The console's CI workflow is `DbDataKit CI` (`dbdatakit-ci.yml`) and the libraries' own is `Shared CI` (`shared-ci.yml`). A new check, `scripts/check_product_name.py`, keeps `DbDataConsole` and `DbDataKitConsole` out of the repository.
- **Changed: what is published and saved is in the current format (plan 33 SC50a).** Build's publish of a data source to a Gateway is always `schema: connection/2` (it was `connection/1` unless the connection had `grants`), the connection files in a package Build publishes to a runner are written as `connection/2`, Sync's package for a runner carries `task.yaml` as `schemaVersion: 2` and its connection files as `connection/2`, the Store publishes a model as `schemaVersion: 2` (and its data source as `connection/2`), and a model saved in the Store and a connection saved in Sync are written in the current format; the files in the project or repository are not changed by a publish. A Gateway that reads only format 1 of a data source or a model refuses these: upgrade the Gateway before the tools that publish to it.
- **Changed: a .NET package's task runs with the machine's culture data.** The task host (`dbdatakit-taskhost`) no longer runs in invariant globalization mode, so a package can open SQL Server (Microsoft.Data.SqlClient refuses to open a connection in that mode). A job that formats numbers or dates without naming a culture now uses the culture of the runner's service account: name `CultureInfo.InvariantCulture` where the output is read by a program. A Linux runner already needs ICU (`libicu`) for the server itself; nothing else is to be installed.
- **New: the Runner's built-in package `dbdatakit-metadata`.** Its tasks `discover` and `describe` read the shape of a database (schemas, tables, columns, keys; a query's columns) through a project package's slot, with the login the channel binds to it, for a person a console names (`POST /api/v1/metadata/<channel>/<task>`). The runner adds the package to a channel the first time a read is asked there; it appears on the Packages page beside the published packages. Its files are in `builtin/dbdatakit-metadata/` beside the program.
- **New: the console reads a connection's shape for a Workspace project from a Runner channel.** `POST /api/workspace-catalog/<workspace>/<project>/read` (with the Runner, the channel, the connection and optionally one schema or table) starts the Runner's `discover` as the signed-in person, waits up to 10 seconds and answers the connection as a `catalog-cache/2` file; after 10 seconds it answers the run, and `GET .../read/<run>` follows it. `GET .../channels` lists the channels of the project's package on that Runner and which bind the connection's slot. The Workspace answers a new call, `GET /api/v1/projects/<project>` (the project and the package it becomes on a Runner), which the console asks as the person. What to do: nothing; a person needs the operator role on the Runner to start a read.
- **New: Refresh from a Runner on the Workspace's tab Catalog.** A `build` or `sync` draft reads a connection, or one of its cached tables, in a channel of a paired Runner that binds the connection's slot; the channel picker offers the channel the cache was last read in, else the first one that is not `prod`, and warns before a read of `prod`. The difference (tables and columns added, removed, retyped) is shown before anything is replaced, and the accepted cache is an unsaved edit of the draft until it is saved. What to do: nothing; the Gateway refresh stays beside it.
- **New: Set up for development, Test, Describe columns and the newest-check card on the Workspace's screens.** The channel picker of **Refresh from a Runner** offers **Set up `<connection>` for development** where a channel other than `prod` does not bind the connection's slot: the login goes to the console, which stores it on the Runner, and the line says what an administrator binds until the channel binds the slot. **Test** on the tab **Catalog** runs the Runner's binding test of the draft's connection in the picked channel and shows each step. The console describes a query's columns through the Runner's built-in `describe` (`POST /api/workspace-catalog/<workspace>/<project>/describe`, and `GET .../describe/<run>` to follow it); `@dbdatakit/workspace` exports **Describe columns** (`QueryDescribe`) for a kind's Designer to place. The Runs tab shows, per Runner and channel the draft was published to, the newest `preflight` run with its findings and link, read through `GET /api/deploys/<id>/runs?task=preflight` (new: the newest run of a task in a deploy's channel).
