# Authoring parity: what the standalone screens do and what the Workspace does

The owner's decision (2026-11-11): **no standalone authoring screen or route is retired until the Workspace has feature parity with it and the owner has tested it in a snapshot release.** The three hand-over rows of [plan 33](plans/33-fewer-services.md) (SC20g Build, SC21d Store, SC22e Sync) are on hold for that reason: first parity, then the owner's snapshot test, then the owner's go. The standalone products keep working unchanged meanwhile (decision D3).

This page is the list that parity is measured against: every thing a person can do on a standalone authoring screen (`Shared/web/build`, `Shared/web/store`, `Shared/web/sync`), what the Workspace (`Shared/web/workspace`, with the console's Approvals page for the Store) does for it today, and the plan row that owns each gap. Read from the code as of 2026-11-11, not by clicking through every screen. Keep it current in the same commit that builds a row.

**States.** `built`: a person can do it in the Workspace. `partly`: some of it, the Workspace column says what. `missing`: not built, a plan row owns it. `not planned`: the Workspace will not do it, with the reason in the Workspace column; each is a decision the owner confirms before the hand-over, because the standalone screen is where the feature lives today and removing the screen removes the feature.

**What the Workspace does differently on purpose.** It authors files in a git draft and publishes artifacts; it holds no connection, login or row (D20), and it does not run anything against a database (a run is the Runner's task, plan 28c). So a standalone screen that reads or changes a database is `not planned` here unless the answer can come from a committed cache (D20, SC20i), which has the shape of tables and never their rows.

## What the hand-over rows must keep

Removing the standalone screens with these still `not planned` loses the feature, so the owner decides for each group before SC20g, SC21d and SC22e are released:

- **Runs and the database-facing Build views** (SC20o: tests, status, refresh run, compare, initialise). Decided 2026-11-12: the Runner does the work and the console shows it in one screen with the authoring screens; the Build server keeps none of these routes.
- **The Store's storage and rows** (`StorageTab.tsx`, `EntityPage.tsx`): acts on a database and data, not authoring. SC21d's hand-over removes only the authoring screens and keeps these.
- **Sync's run, monitoring and verification screens** (SC22l): decided 2026-11-12: the Runner does the work and the console shows it in one screen; the Sync server keeps its run routes until Sync runs fully on the Runner (plan 28c).
- **Publish of Build's models to a Gateway** (SC20e, SW01; owner decision 2026-11-12: it goes through plan 30's one way to publish): Build has the offline verb `project publish --to gateway --out <dir>` (models and data-source documents, no login, kept until SW01's tests have run for a while and it is retired in its own slice); the Workspace sends that folder through the shared publish API (`WorkspaceGatewayPublish`: `DefinitionsClient`, the data source documents then the models, signed with the publisher key when the group trusts it, bindings for the data sources a model needs as slots). The login of a data source stays with Build's server or a Gateway administrator (D20). Tested against a fake Gateway and a stand-in `dbdatabuild` in the Workspace's suite, and against a real Gateway's hooks, owner rules, slot refusal, signature policy and audit in the Gateway's suite (`ManagementWorkspacePublishTests`); not run against a real Gateway process with a real Workspace server.

## Gaps and their rows

Every `missing` and `partly` has a row in plan 33: SC20h (Build load graph), SC20k (cache-backed preview and import), SC20l (offline compile, lowered SQL and sample), SC20m (forms for model, connection and semantic files), SC20n (dashboards and reports of a project), SC20o (the decision on database-facing Build screens), SC21e (restore an earlier text), SC22f (error counts), SC22g (mapping columns from the cache), SC22h (connection test), SC22i (transform, segmenting and pipeline forms, the run login), SC22j (provisioning plan), SC22k (checks, scripts, library), SC22l (the decision on Sync's run and monitoring screens). The cache itself is SC20i (format, readers, checks) and SC20j (the paired Gateway's call that writes it: built; a Sync server's own call is not).

**Audited 2026-11-12 (authoring pass 3).** Why the open rows are still open, each with its smallest design in its plan row: SC20h (built 2026-11-12: column lineage from `project show graph --columns` run on the draft, its shape read from the real tool), SC20k (built 2026-11-12: `project import --from-cache`, the route and the import form of the Catalog tab), SC22h (no Sync pairing: the Workspace pairs with Gateways and Runners; the Runner's slot binding test is the nearest paired call), SC22j (built 2026-11-12 as designed for the target side: `provisioning plan --from-cache`, the route and the Provisioning tab; the source's change-capture state is the live server's and is shown as not known), SC22k (built 2026-11-12: `script list|test --json`, the route, the template folder and the Scripts tab; the library and platform setting stays open with SC22c).
