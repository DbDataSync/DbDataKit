# DbDataKit.State.Cli

The shared `state` noun of every product's command line (plan 29b, M7). A product lists `StateVerbs.Create(new StateVerbContext(...))` with its other nouns and passes its program name, how to find its state from the command's options (`Locate`), its module list (or `null` when it has none yet) and its scope.

* `state show [--offline]`: engine, connection (secrets masked, references shown as written), where each module's tables are, each module's version in the registry against this binary, what is pending. Read-only: it opens no `StateDatabase`, so nothing is created or migrated; a missing SQLite file stays missing.
* `state test`: settings, connection, registry, rights (`StateRights`), engine version (`EngineSupport`), schema clash and refusals, pending migrations the login may not apply. Stops at the first failure with one sentence that names the fix. Exit codes (`StateExit`): 0 ok, 2 wrong use, 10 settings, 11 unreachable or no such database, 12 login refused, 13 registry unreadable, 14 rights missing, 15 engine too old, 16 schema clash, 17 pending migrations this login may not apply, 18 the service would refuse the database, 19 `state init` would leave data behind, 20 `state init --apply`: the administrator's connection or a statement failed.
* `state grants --login <name> [--migrate]`: the `GRANT` statements of `StateGrants` for the product's layout.
* `state init --topology service|group|install [--engine mssql|postgres --connection <connection>] [--login <name> [--migrate]] [--admin-connection <reference> --apply] [--group <name>] [--settings <file>]` (plan 29b C03, `StateTopology`): puts the state in one of the three places of plan 29 section 5 and reports each step. `service` is a SQLite file per service (today's default; nothing is written when the settings already say so, otherwise `engine: sqlite`). `group` is one SQL Server or PostgreSQL database for a serving or runner group, `install` one for every service of the install, each service's modules in namespaces of their own (a schema per module, the scope's name added for per-group and per-service modules). The connection's password must be a reference (`Password=secret:state-db`, `Password=env:NAME`, or the whole `--connection env:NAME`); a literal password is refused with the fix named. In order: the arguments are checked; a product whose state holds data is refused another place (exit 19; `state move` carries data over); on a server engine the schemas and, with `--login`, the login's rights (`StateGrants`) are printed, or with `--admin-connection` and `--apply` run through the administrator's connection (which also applies the service's modules first: a grant on a table needs the table; exit 20 when the administrator's connection or a statement fails); the `state` section of the settings file is written with `StateSettingsWriter` (the product's `server.yaml` where it has one, else `--settings`; nothing when it already says so); then the checks of `state test` run on the new settings and print. Printing is the default and executes nothing. Running it again changes nothing. Where the settings file is read by the product is each product's business: a product that has not adopted the `state` section yet keeps reading its own flags or variables.

Verbs added later (the snapshot verbs) go in files of their own and are added to the list in `StateVerbs.Create`; the four above do not change.
