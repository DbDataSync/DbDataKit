# DbDataKit.Identity

The identity home (plan 13a U13): who people are and what they may do, for every server, console and app of an install. A component, not a host: the serving layer hosts it (plan 20, O06), and `dbdatakit identity run` (U15, in `DbDataConsole.Server`: `IdentityHost`) runs it on its own with the shared sign-in, its own state and directory.

- **`HomeSchema`**: the tables, over `DbDataKit.State`'s users, credentials and sessions: groups, members, role assignments, OpenID Connect clients, authorization codes, signing keys. SQLite, SQL Server and PostgreSQL by the state dialect.
- **`HomeDirectory`**: groups, and roles assigned to a user or a group on a server, on one Build project of a server, or in an app. What a user holds is the union of their own and their groups'.
- **`OpenIdProvider`** and **`MapOpenIdProvider`**: discovery, JWKS, `authorize`, `token`, `userinfo`, `end-session`. Authorization code with PKCE (S256 only), ES256 id tokens and access tokens; **refresh tokens** (scope `offline_access`; the `refresh_token` grant reads the roles again, rotates the token on each use, revokes the family when a used token comes back or the user is disabled, and expires 12 hours after the sign-in); **OpenID Connect RP-Initiated Logout** (`end_session_endpoint`: the id token hint names the person, every refresh token of theirs is revoked, the host's `EndSession` callback ends its own session, and the browser goes back only to a `post_logout_redirect_uri` the client registered). `sub` is the home's user id; `groups` and `dbdata_roles` (`server:<id>`, `server:<id>/<project>`, `app:<id>`) carry what the home says. The host signs the person in (its session) and tells the endpoints who that is.
- **Addresses** (plan 13a U16): the id token carries `email` with `email_verified`, true only for an address an administrator entered at the home (the state store's `EmailKey`); a client links people on the address only when it is verified. `OpenIdClient` reads it into `HomeIdentity.EmailVerified` (a JSON `true` and nothing else), and `FederatedUsers` hands it to `AccountLinker` (`DbDataKit.State`), which joins the sign-in to the local or Windows account that holds the address.
- **`SigningKeys`**: ES256 keys, the private half protected by the host's `ISigningKeyProtector` (there is no default, so there is no unprotected key); rotate, retire.
- **`OpenIdClient`** and **`FederatedUsers`** (U14, U17): the relying party and what a console keeps for people who sign in through the home: the mirrored user, the home's last word on their roles, and per session the protected refresh token. `RefreshAsync` asks again when the interval has passed; the roles lapse after the interval plus a grace when the home cannot be asked.
- **`HomeTokens`**: the request for the console's token to a server (plan 13 T01) with the home's user id as the subject and the roles the home holds for that user there.

- **External groups** (plan 13a U18): `HomeDirectory.MapExternalGroup` maps an Entra group (the id token's `groups` claim) or a Windows group to roles on a server, a Build project or an app; `ExternalSignIns.SignIn` finds or makes the home user for an upstream sign-in (U16's rules) and records the groups the sign-in carried, replacing the last ones. What a person holds is their own assignments, their groups' and their external groups' mappings added together. `OpenIdClient` validates ES256 (the home) and RS256 (Entra) id tokens.

- **Upstream sign-in at the home** (plan 20 O06b, `UpstreamSignIn`): `IdentityHomeOptions.Entra` (an `EntraUpstream`: the tenant's issuer, the home's app id and secret, whether its addresses are trusted) makes the home a confidential OpenID Connect client of an Entra tenant: `/identity/upstream/entra` sends the browser there, `/identity/upstream/entra/callback` (the redirect URI to register) checks the RS256 id token with `OpenIdClient`, hands it to `ExternalSignIns` and starts the home's session. `IdentityHomeOptions.Windows` adds `/identity/upstream/windows`, negotiated (`AddNegotiate`): the SID (else the Kerberos name) is the credential, the UPN the address, the group SIDs (and on Windows their `DOMAIN\group` names, or on Linux an LDAP lookup's role claims) the groups. The sign-in page offers each one that is configured; a refused sign-in, an unknown state, a token that does not check out, an account conflict or a disabled person signs nobody in and the page says why (403).

- **Personal access tokens and service accounts** (plan 13a U20, `AccessTokens`): a token is `ddk_<id>_<secret>`, shown once, kept as a SHA-256 hash; a person's lasts `AccessTokenPolicy.DefaultLifetime` (90 days, or the install's lower maximum) unless asked otherwise and never more than `MaxLifetime` (at most 365 days); a service account (a home user with no credential, `ServiceAccounts`) may have one that never expires. `Verify(userName, token)` takes the person's address, the service account's name or the user id with it, and refuses a revoked or expired token, another person's name and a disabled user. The home registers it as the shared `IPasswordCredentials`, so `SessionAuthenticationHandler` signs a request with `Authorization: Basic` in as that user, with the same id as any other way in. `/api/access-tokens` is a person's own list, make and revoke at the home (a request signed in with a token cannot make another). Administration at the command line: `service-account-add`, `-list`, `-remove`, `token-create` (a service account's), `token-list` and `token-revoke` (anyone's).

Not here yet: administering mappings through an API (13a U21; the command `identity map-group` exists), Entra's group overage, an Entra sign-in that comes back to another instance of a group than the one that started it (the attempt is in memory until O02), the serving layer forwarding a home that runs on its own (O07).
