# Sample apps

Sample apps to publish while you try app publishing end to end ([docs/apps-testing.md](../../../docs/apps-testing.md) is the script; [docs/apps.md](../../../docs/apps.md) is the design).

| Folder | Kind | What it shows |
| --- | --- | --- |
| `territory-notes/` | a code app: `index.html`, `app.js`, `app.css`, no build step | a sandboxed document: a token from the host's shell over `postMessage`, data calls to the Store model `territories` through the host (`/apps/<instance>/_data/...`), app storage, and no outside request |
| `front-portal/` | a declared portal (`kind: portal`): data the host renders, no script | a home page from `views/home.yaml` (text, a link, a tile for each mounted app the person may open), a menu and a mount of the instance `notes` |
| `territory-views/` | an app of views only (`view-spec/1`, no `entry`, no script) | a grid with a filter and sortable columns, an add form and an edit form (the Store's refusals are drawn against the field), a detail page and a dashboard (two figures, a bar chart, a table) over the model `territories`; the host draws all of it (AP25) |
| `app/` | the template `apps new` starts from: a code app on the default library set (plan 22a GP32) | `views/` holds three `view-spec/1` files over the model `territories` (a grid, an edit form, a dashboard); `src/main.tsx` draws them with the library's `ViewApp`; `src/clients.ts` connects the app to its host (`connectHost`) and makes the Store client and the semantic client; `src/pages/index.ts` is where a page of code is registered beside the specs (none to begin with); `package.json` lists the packages it imports. `apps build` bundles it into `main.js` (a plain script) and `main.css`, and makes `src/views.generated.json` from the view files for the bundle |
| `territory-notes-src/` | the same code app as a source tree: `src/main.ts` (TypeScript), `index.html`, `app.css` | what `apps build` takes: it bundles `src/main.ts` into `main.js` (a plain script, which is what the sandboxed page loads) and copies the rest |
| `territories.yaml` | a Store `model/1` | the model the code app uses; `storage: {connection: mdm}` is the connection the quickstart's Store has |

`apps new --dir <new folder> [--name <app>]` starts an app from the template `app`; `apps init --template <app|territory-notes|territory-notes-src|front-portal|territory-views> --dir <new folder> [--name <app>]` copies any sample (they are inside the program, so no repository or network is needed) and `apps build --src <folder> --out <folder>` builds a source tree; `publish-samples.sh` runs `apps validate`, `apps publish`, `apps instance-save` and `apps nav-save` for the three that need no build (instances `notes`, `front` and `views`). `territory-notes` has no build step on purpose, so a tester needs nothing but the Gateway; `territory-notes-src` is the one to build (needs Bun: `scripts/fetch-bun.sh` fetches the pinned, hash-checked one).

`territory-views` needs the host's views runtime (`apps-views` beside the Gateway, the web build of `DbDataKit/web/view-app`; the Dockerfile and the Windows publish script include it). The instance's people need the `author` role to add or edit and any role to read.

**The template builds from a vendored package store.** `app/` imports React, `@dbdatakit/store-ui`, `@dbdatakit/visuals`, `@dbdatakit/semantic-client` and `@dbdatakit/view-app` (the default library set). They are not installed from a registry: `node DbDataKit/web/app-store/build.mjs --out <folder>` (run in the repository after `npm ci` in `DbDataKit/web`) copies them and what they need at run time into a store folder (`node_modules/` and `store.json`, which lists every file with its SHA-256). `@dbdatakit/shell` (the console's shell, which pulls in Monaco) is not part of the default set; `--include @dbdatakit/shell` adds it to a store and the administrator's allow-list decides whether an app may import it. `apps build --src <folder> --out <folder> --store <store folder>` builds from it with no network and installs nothing (set `apps.packageStore` in `server.yaml` to make it the default); `apps store-verify` checks the store against its `store.json`; an import that is not in the library or the administrator's allow-list (`apps.allowedPackages`) is refused by name. What the isolation guarantees and does not is in [docs/apps.md](../../../docs/apps.md).
