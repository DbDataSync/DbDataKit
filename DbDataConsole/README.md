# dbdatakit, the console

The one web interface for the DbData servers (plan 13, U07). It signs people in, holds the users, and (in the slices that follow) manages the Sync, Gateway and Build servers paired with it.
It is a separate host from the servers: a server runs without it, and it is not needed to run one.

```
dbdatakit server run [--repo <console directory>] [--listen https://localhost:8480]
dbdatakit user list [--repo <console directory>]
dbdatakit user invite [--role admin|viewer] (--email <address> | --user <id>) [--url <address>]
dbdatakit user set-email --user <id> --email <address>
dbdatakit instance add <https address> --code <code> [--name <label>] [--repo <console directory>]
dbdatakit instance list [--offline] [--repo <console directory>]
dbdatakit instance remove <id or name> [--repo <console directory>]
dbdatakit instance rotate-key [--repo <console directory>]
dbdatakit state grants --login <database role or user> [--migrate] [--engine mssql|postgres] [--repo <console directory>]
dbdatakit state init --topology service|group|install [--engine mssql|postgres --connection <connection with Password=secret:NAME or env:NAME>] [--login <role or user> [--migrate]] [--admin-connection <reference> --apply] [--group <name>] [--settings <file>]   # one SQLite file per service (the default), one database per group, or one for the install; prints (or with --apply creates) the schemas and the console's rights
dbdatakit state show [--offline] [--engine mssql|postgres] [--repo <console directory>]   # engine, masked connection, namespaces, versions, pending migrations; creates nothing
dbdatakit state test [--engine mssql|postgres] [--repo <console directory>]   # connection, registry, rights, engine version, schema clash, pending migrations; stops at the first failure with the fix
dbdatakit state export --to <directory> [--include-secrets-check] [--engine mssql|postgres] [--repo <console directory>]   # the whole state as a snapshot; stop the console first
dbdatakit state import --from <directory> [--migrate-after true|false] [--engine mssql|postgres] [--repo <console directory>]   # into an empty state database
dbdatakit state verify --snapshot <directory> [--db] [--rehash-payloads] [--engine mssql|postgres] [--repo <console directory>]   # the snapshot against itself, or the state against it; also --other-engine ... or --against <settings file>
dbdatakit state move --to-engine mssql|postgres --to-connection "<connection string with secret references>" [--yes] [--keep-snapshot] [--repo <console directory>]   # export, import, verify, then write settings.yaml; the old database is untouched
dbdatakit service install|uninstall|status|start|stop|restart|doctor|unit
dbdatakit health check [--url <url>]
```

The console's directory is `--repo`, or `DBDATAKIT_CONSOLE_DIR`, or a folder under the user's local application data (`%ProgramData%\DbDataKit\console` for the Windows service). It holds `state.db`
(users, sessions, invitations, notifications), the self-signed certificate (`tls.pfx` and its password file, readable only by the account that runs the console) and `FIRST-RUN.txt`.

## First run

With no user yet, the console writes an invitation to `FIRST-RUN.txt` and the log. Open `https://localhost:8480/invite#<code>` once and register a passkey: that person is the first administrator.
**The state database** is SQLite (`state.db` in that directory) unless you name another engine: `--state-engine mssql|postgres --state-connection "<connection string>"` on `server run`, or `DBDATAKIT_CONSOLE_STATE_ENGINE` and `DBDATAKIT_CONSOLE_STATE_CONNECTION` (the commands that open it, such as `user invite`, read the variables too). The password belongs in a reference, not in the string: `Password=env:STATE_DB_PASSWORD` (the console has no secret command yet, so its own store holds only its keys). The `state:` section of `settings.yaml` in the console's directory (the section every DbData product reads: `engine`, `connection`, `namespaces`, `retention`; nothing creates the file but `state init` and `state move`) names it when no flag or variable does, setting by setting: the first place that names the engine, and the first that names the connection, wins (flag, then variable, then file, then SQLite). A setting in the file that is not one is refused with the file named and the nearest setting that is. `dbdatakit state show` says where each value came from (a flag, an environment variable, the file, the default), and `dbdatakit state init --topology service|group|install` writes `settings.yaml` with no `--settings`. **To move the state to another engine** (an upgrade, a bigger database), stop the console and run `dbdatakit state move --to-engine postgres --to-connection "Host=db;Database=console_state;Username=svc;Password=secret:state-db"`: it exports the state, imports it into the empty target, verifies the copy against the snapshot and the old database, and only then writes the new `state:` section to `settings.yaml` (the old file is kept as `settings.yaml.before-state-move`); the old database is not touched, so going back is putting that file back. Restart the console afterwards. A flag or a `DBDATAKIT_CONSOLE_STATE_*` variable overrides the file, so remove it for the move to take effect. `state export` and `state import` do the same in two steps (a backup, or an install onto a new machine). The console has to be stopped for all of them: an export of a state a running console uses is refused, naming it. The console needs a database of its own: the Gateway's state database has tables of the same names.

`dbdatakit user invite` prints a fresh invitation when that one has expired or scrolled away (it opens the state database directly, so it works when nobody can sign in).

## One account per person

A person is one user however they sign in: a local passkey, a Windows (Negotiate) account, or the identity home (plan 13a U16). The **email address is the account's key** (for a Windows account, its user principal name, `user@domain`): it is
trimmed and compared without regard to case, and one address is one account. The first sign-in by a way no account has seen joins the account that holds the person's address, so they have the same id (the audit's) and the same roles;
a person the home knows takes over the local account with the home's id, and everything the account had (its passkeys, Windows accounts, sessions) moves with it. A sign-in that would take an address another account holds is refused with a message.

What is trusted to say whose an address is: an **administrator's entry** (the invitation is made for an address: `user invite --email`, or the Users page; `user set-email` or the Set button changes it), the **user principal name the domain issued**
(never a `DOMAIN\user` name, which is not an address and is never guessed into one: a Windows account with no UPN signs in by its SID if it already has an account, and is refused as a new one), and the identity home's **verified** id token
(`email_verified`; without it nothing is linked). What a person types when redeeming an invitation is never used (only the first-run invitation, which nobody made, keeps it, for display). An address nobody vouched for, including every
address of an account made before this slice, is shown (marked unverified) and never links; those accounts keep signing in as they did, and an administrator sets their address to link them.

## Servers

**Signing in through an identity home** (plan 13a U14): `server run --identity-home https://home.example --identity-client <id> --identity-secret-env HOME_SECRET [--identity-app console] [--identity-home-cert <file>]` makes the console an OpenID Connect client of the home. It keeps no passwords or passkeys and writes no first-run invitation; people sign in at `/api/identity/sign-in` (the sign-in screen's **Sign in with the identity home** button), are the same user id here as everywhere, may sign in only if the home gives them a role on `app:<identity-app>` (`admin` makes them an administrator here), and reach each server with the roles the home holds for them there, never above the ceiling this console was paired with. A console with a home **keeps local users** (the way in when the home is missing): local sign-in is not closed, and a local session is never refreshed from or ended at the home.

The home is usually the serving layer's (`identity:` in a Gateway's `server.yaml`, plan 20 O06; register the console there with `dbdatagateway identity client-add --name <name> --redirect https://<console>/api/identity/callback --logout-redirect https://<console>/`), or one that runs on its own (`dbdatakit identity run`). `--identity-home-cert` names a certificate file (PEM or DER) to trust for the home's address besides the machine's own trust: the home's certificate itself (a Gateway's self-signed certificate is the `.cer` beside its PFX in the data directory) or the CA that issued it. The host name is checked either way.

Inside a session the home stays the authority (plan 13a U17). Each session holds a refresh token (kept protected in the console's state database, never as the home gave it). The first request after the **refresh interval** (5 minutes) reads the person's roles at the home again, so a role removed there applies within the interval without a new sign-in, and the console's ceiling for each server lowers them exactly as at sign-in; a person the home no longer gives a role on `app:<identity-app>`, a disabled person, or a sign-in the home ended is signed out of the console. When the home cannot be asked, the last roles are kept for a **grace** of 10 more minutes, then the person holds **no role on any server** (the servers refuse the call) until the home answers; their sign-in to the console itself stays. Signing out of the console ends the person's session at the home (OpenID Connect RP-Initiated Logout: the sign-out answer carries `redirectTo`, the home's end-session address, and the web app goes there), which also ends their other consoles' sessions at their next refresh. The interval and the grace are not flags yet. The home must register the console's `post_logout_redirect_uri` (`<public address>/`) for the browser to be brought back; without it the home shows its own page.

**The identity home on its own** (plan 13a U15): `dbdatakit identity run [--repo <dir>] [--listen https://<name>:<port>] [--public-url https://<name>:<port>] [--state-engine sqlite|mssql|postgres --state-connection <string>]` runs only the home (the OpenID Connect provider and the sign-in with passkeys), with a state and a directory of its own (`DBDATAKIT_IDENTITY_DIR`; default address `https://localhost:8490`), so it can sit behind the firewall. `--public-url` is the issuer: keep it when the home moves. The first administrator redeems the invitation in `FIRST-RUN.txt`. `identity client-add --name <name> --redirect <uri>[,<uri>] [--logout-redirect <uri>] [--public]` registers a console or app (a confidential client's secret is shown once; a console takes it through `--identity-secret-env`), `identity client-list` lists them, `identity assign --user <id> (--server <id> [--project <name>] | --app <id>) --roles viewer,operator,author,approver,admin|none` gives a person roles, and `identity map-group --source entra|windows --group <group> (...) --roles ...` maps an external group. **To move the home**, stop it, move its directory (it holds `state.db` and `dataprotection/`, the key ring that protects the signing keys; a copy without the ring does not start) and run it again at the same address: every console's session, refresh token and client, and every token, keeps working. The sign-in page is `/identity/sign-in` and the invitation page `/invite`. **To administer it** (plan 13a U21), pair a console with it like any server: `dbdatakit identity pair --max-role viewer,operator,admin [--repo <dir>]` prints a code, which the console's Servers page takes with the home's address; **Open** shows the Identity home screen through the relay: people (invite, disable), role assignments, Entra and Windows group mappings, groups, consoles and apps, service accounts and tokens. The same calls are the home's management API, `/api/v1/identity/...` (`people`, `groups`, `assignments`, `clients`, `group-mappings`, `tokens`, `service-accounts`), every one for the admin role in the console's token. `identity clients` and `identity unpair` list and forget paired consoles. The home serves no web app of its own any more: `--web-root` is refused with a message, and the console's Users and invitation screens are no longer copied there.

`dbdatakit instance add` pairs the console with a server (Sync, Gateway, Build, Store or Runner) using the single-use code that server's administrator made with `<program> server pair`; the server's certificate is pinned and the pairing is recorded in `instances.yaml`
in the console's directory. `instance list` shows each server with its product, version and whether it answers, `instance remove` forgets one (it keeps listing the console until `server unpair` is run there) and `instance rotate-key` moves every server to a new signing key.
A server started with `DBDATAKIT_CONSOLE_ANNOUNCE_URL` (and `DBDATAKIT_ADVERTISE_URL`, `DBDATAKIT_INSTANCE_NAME`) and not yet paired announces itself to the console's private `--announce-listen` port and waits: `instance pending` lists the waiting servers (never their codes),
`instance confirm <id or name>` pairs with one and `instance reject` forgets it. In the web app the Servers page shows the same list above the paired servers, for administrators only: each waiting server with its name, product, advertised address and when it last announced,
and a Confirm and a Reject button. The list refreshes every few seconds, Confirm moves the server into the list below (a failure, such as the server not answering or its code having expired, is shown under that server in the console's own words) and Reject removes it until it announces again (every half minute while it waits).
In the web app, `/instances` lists them and `/servers/<id>/...` opens a server's own screens (Sync's replications and configuration so far), whose calls the console relays at `/relay/<server>/api/...` and `/relay/<server>/hubs/...`.

**Runners** (plan 28a R19). A `dbdatarunner` is paired like any server (`dbdatarunner server pair --max-role viewer,operator,admin`, then `instance add` or the Servers page, or it announces itself) and its product is `dbdatarunner`. Its screens are at `/servers/<id>`: **Tasks** (the group's instances, each live or gone, with host, version, labels marked as set by an administrator or reported by the machine, and the capabilities that matter for routing: memory and cpu limits enforced or only watched, network; then every task with package, channel, version, next due, last run, running, queued, paused, and the reason when it waits, such as a required label no runner has; run now, pause and resume for an administrator), **Runs** (filtered by package, channel and outcome, with a run's detail) and **Packages** (what each channel serves, a package's versions and history; a staged version with how far each runner is in preparing it; activation, which lists the progress the dry run would lose and needs it confirmed, or goes ahead anyway with a reason; roll back, serve another version, retire). The Monitoring page lists a runner's tasks (a failed last run, a task that waits, a hold) and a runner that is gone, with the other servers' rows. A signed-in administrator holds the runner's operator and admin roles there (what the pairing's ceiling allows); a viewer reads. The runner decides and audits every act, naming the person; the console's relay passes a runner's management calls only (status, instances, runs, task run, pause and resume, definitions and their activate, switch, rollback and retire): its publisher calls (artifact upload, publish, bindings, settings) and webhooks are not relayed. Publishing stays with `dbdatarunner package publish`.

## Connections across servers

**Lineage** (plan 18, G09): `GET /api/lineage` joins the design graphs of the paired Build and Sync servers by identity (a table Sync writes and a Build model reads is one node), with what each server said or why it gave none; `?node=<id>&direction=downstream|upstream&depth=<n>` is the impact or provenance of one node across all of them, and `?refresh=true` asks the servers again instead of using what was kept for 30 seconds.

**Data quality** (plan 23a, FQ17): `GET /api/quality` joins the results of the checks that the paired Sync (`/api/quality`) and Build (`/api/v1/quality`) servers evaluate, by dataset identity: every dataset with its checks, the latest result and the block of each, and what each server said (or why it gave none, `can_run`, and how a server that cannot evaluate on request does). The page `/quality` reads the history of a check from the evaluating server through the relay (`.../api/quality/history`) and evaluates on request (`POST .../api/quality/run`, a Sync server, admin); the console holds no results and decides no block.

The Connections page (`/connections`, in the rail) lists the connections of every Sync server and the data sources of every Gateway the console manages, each asked of its server through the relay (a server that does not answer, or whose list it refuses, is named above the list and the others still show).
A Sync connection and a Gateway data source are the same `connection/1` file, so a connection on one server can be **copied to another**: *Copy to...* on a row, choose the server and the name it will have there (the same name when it is another server).

The console makes the copy as the person signed in: it reads the file from the first server (`GET /api/connections/<name>/file` on Sync, `GET /api/v1/data-sources/<name>` on a Gateway), changes only what belongs to that server, and creates the file on the second
(`PUT` with no version, so a name the target already has is a conflict and the file there is never overwritten). The target reads it with its own strict loader, and what it refuses comes back on the page with the line of each fault, and nothing is written.
What changes in the file, and what the page tells the person:

- `name` is the new name; `managed_by` is dropped (it names a client of the source's server); `extensions.<product>` of another product is dropped (the target does not read it), the target's own kept (Sync to Sync, Gateway to Gateway). The rest of the file, its comments and its layout, stay as they were.
- **A password is never copied.** It is a reference in the file (`password_secret`); the copy names the reference the target is to hold and says so. Sync reads one reference only, `secret:dbdata:sync:connection:<name>`, so a copy to Sync names that for the new name; a copy of a Sync connection to a Gateway names
  `secret:dbdata:gateway:connection:<name>`, not Sync's store; every other reference (`env:ERP_DB_PASSWORD`) is kept as written. For a Sync target the page asks for the password (optional, for a connection that logs in with one): it is sent to that server only, in the same call, stored there under the copy's own reference
  as Sync's own Connections page stores one, and kept nowhere else; without it Sync refuses a user-and-password connection, naming the reference. A Gateway takes its secrets from its own store, so no password is accepted for a Gateway target.
- What the target does not support is its refusal, in its words: the Gateway serves `sqlserver`, `odbc`, `duckdb`, `postgres` and `flightsql` and refuses another engine; Sync refuses `tls`, `read_login`, `write_login`, `connection_string_secret` and `access`.
- What a person may do is each server's decision from the token (the roles the console grants that person there, never above the server's ceiling): a Gateway takes a copy from an administrator only.

## The embedded runner

The console can host **a copy of the runner engine** (`DbDataKit.Runner`) as a runner group of one, `console` (plan 28 section 6a, plan 28a R20), with its own state in the console's state database (the scope becomes group `console`; the `runner`, `runner_progress`, `definitions`, `scheduling`, `payloads` and `trust` modules are added, and a console that does not turn it on has none of them). **It is off by default**, per install: a console that is updated gains no tables, no child processes and no dependency on the task host until an administrator writes this in `settings.yaml` in the console's directory:

```yaml
runner:
  enabled: true
  channels: [dev, preview]        # the non-production channels it serves (the default); the channel `system` is always served
  max_concurrent: 2               # runs at once (the default), so a heavy run cannot slow the console's screens
  data_directory: runner          # cache, scratch and socket; default: `runner` in the console's directory
  require_separate_account: false # true: packages of its own are refused while their tasks would run under the console's account
  retention_every_minutes: 60     # how often the console's own state-retention task runs
```

What it runs: the tasks of packages published to a channel it serves, each **in a process of its own** with the time and memory limits of any runner, and the console's own system tasks (package `console-system`, channel `system`), which run in the console's process: `state-retention` (the shared retention job over the console's state, on its schedule) and `evaluation`, a placeholder for plan 27's evaluation runs. A product's own housekeeping stays with the product. The runner's version is the console's.

**Production is an administrator's recorded choice.** Until then publishing or activating into the production channel (`prod`) is refused with a message that names the choice, and the runner serves no production channel. `dbdatakit runner accept-production --yes [--note <text>]` records it (audited: who and when; so does `POST /api/embedded-runner/accept-production` with `{"confirmed": true}` for an administrator) and the console then logs, and the runner screens show, the warning that **production schedules stop when the console stops**. `dbdatakit runner revoke-production` takes it back.

In the web app the runner is the first entry of the Servers page (id `console-runner`, flagged `embedded`, never paired and not forgettable) and opens the same runner screens as a `dbdatarunner`: the calls are the runner's own management API, served in the console at `/api/embedded-runner/...` and at `/relay/console-runner/api/v1/...` for people signed in (a viewer reads, an administrator runs, pauses, resumes, activates, switches, rolls back and retires); every other call under that id is 403. Stopping the console stops the runner: running tasks are cancelled, given their grace period, and no run is left running. The task host is published beside the console (`taskhost/`) as it is beside `dbdatarunner`.

## What is served

`/api/auth`, `/api/invites` and `/api/users` are the shared sign-in controllers of `DbDataKit.Web` (the same ones Sync serves), `/health` and `/version` answer without signing in, and everything else under `/api` is closed
to anyone who is not an administrator unless an endpoint says otherwise. The web app is the build of `@dbdatakit/console` in `wwwroot` beside the program; without it the console serves the API and says the app is not installed.

## State databases and moving a server's state (plan 29b, C06)

**Connections** lists, below the connections of Sync and Gateway servers, the console's **state databases**: connections of kind `state` (engine `postgres`, `mssql` or `sqlite`, the last a file on the console's machine). A connection holds the connection string with its password as a secret reference; the password is typed once and kept in the console's secret store as `dbdata:console:state:<name>` (a server needs the same secret under the same name to resolve it: `dbdatabuild secret set dbdata:console:state:<name> --stdin`, likewise `dbdatagateway` and `dbdatastore`). **Test** runs the checks of `state test` through the shared library (connect, registry readable or empty, the rights to create the tables, engine version, features) and answers with one sentence naming the fix; the list shows which paired servers use each database and the module versions found there. The API is `GET /api/state-connections`, `PUT|DELETE /api/state-connections/<name>`, `POST /api/state-connections/<name>/test` (administrators).

**Servers > State** is the STATE panel of a paired Gateway, DbDataStore or Build server (and, read-only, of this console at `/state/console`): the engine, the connection as the server shows it, each module's version against the binary, the migrations pending, where each setting came from, the other instances, and the maintenance mode, which an administrator puts on (with a reason) and off through the relay, audited by the server. Under it the **Move wizard**: choose a state connection, **Check** (the server reports its state; the target is reachable and empty, with the rights, the engine version and the features; it is not the server's own database; the server itself can resolve the password reference and write its settings file, else the check names the `secret set` command to run on that server), then the steps with progress: maintenance on, wait for idle, and the move, which the server runs in its own process (`POST /api/v1/state/move`, see `DbDataKit.State.Api`): export, import, verification against the snapshot and the old database, and only then its settings. At the end it shows the restart instruction and the way back; a failure says what was kept (the settings are unchanged). Nothing is restarted from the console. A server too old to have the call is told the command line way (`<program> state move ...`). The console's own state is moved with `dbdatakit state move` (it cannot stop itself).

## The state and the maintenance mode

For the people signed in to the console: `GET /api/v1/state` (a viewer: the engine, the connection with secrets masked, each module's version in the registry against this binary, the migrations pending, where each setting came from) and `GET`/`POST /api/v1/state/maintenance` (an administrator puts the console into maintenance with `{"enabled": true, "reason": "..."}`: everything but the sign-in, the web app's files, the health endpoints and an administrator's own requests answers 503 with `Retry-After` and the reason, and `idle` says when what was in flight has finished). Every change and every refusal is in the audit as `state.maintenance`. Nothing is persisted: a restart leaves maintenance, which a move of the state needs anyway (`dbdatakit state move`). The same endpoints are on a paired server's management API; the shared component is `DbDataKit.State.Api`.
