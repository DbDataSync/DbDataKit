# DbDataWorkspace

The server where people (and, later, agents) author projects in git workspaces (plan 22a GP31, decision D8; plan 27). A project is a git repository of some kind (an app today; a Build, Store, Sync and integration project beside it, see [`docs/integrations.md`](../docs/integrations.md); plan 27 adds agent, skill and knowledge projects); a **workspace** is one person's draft of it, a git worktree on its own branch in a folder the server owns, so a draft never changes what is published. The server lists, creates and abandons workspaces, shows their changes, commits, pushes and merges them (the shared library `DbDataKit.Authoring`, which Build serves its workspaces with too), and keeps a record of what was done in its state database. It has no web page of its own: a console pairs with it and shows its screens (Servers, then the Workspace server, then Workspaces).
**Built:** editing a draft's files, commit, push and merge (GP35a); an app project starts as the app template (GP32); builds from a vendored package store and a read-only preview (GP35b, below); the console reads a build and deploys it as the person ([docs/publishing.md](../docs/publishing.md#deploying-a-build-from-the-control-service)), and the Workspace server never calls a Runner or a Gateway. **Not built:** a preview with live data (the semantic route and the apps host's preview channel), a git remote for a project. The builds write the `build` table of the state module.

```
dbdataworkspace server run [--repo <server directory>] [--listen https://127.0.0.1:7860] [--state-engine sqlite|mssql|postgres --state-connection <connection string>]
dbdataworkspace server pair --max-role <roles> [--repo <server directory>]
dbdataworkspace pair --host <console address> --token <token|-> --console-thumbprint sha256:<hex> [--address <https address>] [--repo <server directory>]   # the command the console prints (dbdatakit setup invite): joins it at the next start
dbdataworkspace server clients | unpair <client> [--repo <server directory>]
dbdataworkspace project create <id> [--title <text>] [--kind app|build|store|sync|integration] [--template <name>] [--repo <server directory>]   # a git repository in projects/<id> with a first commit
dbdataworkspace project add <id> --path <repository folder> [--title <text>] [--kind app|build|store|sync|integration] [--template <name>] [--repo <server directory>]   # host a repository that is already on this machine, in place
dbdataworkspace project list [--repo <server directory>]
dbdataworkspace workspace list [--project <id>] [--repo <server directory>]
dbdataworkspace service install|uninstall|status|start|stop|restart|check|unit
dbdataworkspace state init --topology service|group|install [--engine mssql|postgres --connection <connection with Password=secret:NAME or env:NAME>] [--login <role or user> [--migrate]] [--admin-connection <reference> --apply] [--group <name>] [--settings <file>] [--repo <server directory>]   # writes the state section of server.yaml (a SQLite file per service is the default)
dbdataworkspace state show [--offline] [--engine mssql|postgres] [--repo <server directory>]      # the state database: engine, where each setting came from, namespaces, module versions, pending migrations; creates nothing
dbdataworkspace state test [--repo <server directory>]                   # opens it read-only and checks rights, engine version and clashes; stops at the first failure with the fix
dbdataworkspace state grants [--login <database role or user>] [--migrate] [--repo <server directory>]
dbdataworkspace state export --to <directory> [--include-secrets-check] [--repo <server directory>]   # the state as a snapshot; stop the server first
dbdataworkspace state import --from <directory> [--migrate-after true|false] [--repo <server directory>]   # into an empty directory's state
dbdataworkspace state verify --snapshot <directory> [--db] [--rehash-payloads] [--repo <server directory>]   # the snapshot against itself, or the state against it
dbdataworkspace state move --to-engine sqlite|mssql|postgres [--to-connection <string with secret references>] [--yes] [--repo <server directory>]   # offline: export, import into the empty target, verify, then write the new settings
dbdataworkspace secret set|list|delete|... [--repo <server directory>]   # the server's own secret store (the shared secret verbs)
dbdataworkspace health check [--url <url>] [--repo <server directory>]
```

Merging a draft of a project that has a git remote pushes the draft's branch there, and the person opens the pull request where the remote is hosted;
the Workspace gives the link. A project without a remote is merged in the Workspace, under the author's name.

## A project's two areas: Files and Designer

A draft is edited in two areas, the same two for every kind of project, each with its own address and its own entries in the project's navigation:

- **Files** is the stock editor every kind has: the file tree, each file as the form generated from its format's schema or as YAML in the code editor, and the draft's tabs (Changes, Check, the kind's own tabs, Builds, History). Every file of every project can always be read and changed here. Its addresses are `/:project/:draft/files/...` (a file's path after `files/`).
- **Designer** is the kind's own designed screens: pages laid out around what the person authors rather than around files (for a sync project, each replication's page with its tabs and the table mappings with the source and target side by side). A Designer reads and writes the same files of the same draft; it adds no format of its own. Its addresses are `/:project/:draft/designer/...`, and its navigation entries are the kind's own (for a sync project, the project's replications and **New replication**).

The person moves between the two by clicking: a file in the Files tree, a replication or a mapping under Designer, or a link one area gives to the other. Nothing is remembered per person and there is no switch to set: the address alone says which area and which place is open, so a reload or a shared link opens the same one. A kind without a Designer shows only Files; a draft of a kind with one opens on its Designer, always: the landing page is fixed by the kind, not a choice stored per person or per draft (a person who wants Files clicks it, or keeps a link to a `files/` address).

Both areas edit one draft: an edit not yet saved in the Designer is still there, not saved, when the person clicks into Files, and the reverse; the draft's chrome (**not saved** with **Save**, the check's count, **Commit…**) is the same in both, and the check runs on the files whichever area changed them. A file the Designer cannot show (it does not parse, or it is of a format version newer than the screens know) is shown in the Designer as a line naming the file with a link that opens it in Files, never as an empty or partial screen. History, diffs and earlier texts of a file are the Files area's (History, Changes, a file's earlier texts); a Designer does not repeat them.

Why: one way to move between designed screens and raw files for every kind, so a person who learned it on one kind knows it on the next, and the stock editor is always there as the fallback for whatever a Designer does not offer yet (a key the screens do not show, a file they cannot read, a part of the project the Designer does not cover yet).

Example: in the sync project `erp-sync`, an engineer opens the draft `add-order-lines` and lands on the Designer, on the replication `erp-to-dw`. On the mapping `customers` she ticks two key columns, then wants `relationshipColumns`, which the Column Mapping tab does not offer: under Files in the navigation she clicks the mapping's file, it opens as a form with her two key columns already in it (not saved), she sets the key in YAML, clicks `customers` under `erp-to-dw` in the Designer's entries and is back on the mapping's Column Mapping tab, saves once and commits.

A kind's Designer is a web package of its own, registered with `@dbdatakit/workspace` (a component, its routes and its navigation entries), built and tested on its own; components any product uses go to `@dbdatakit/shell`. The sync Designer is `@dbdatakit/sync-ui` (`Shared/web/sync-ui`, an npm workspace like `store-ui`): the Sync server's authoring screens of a replication, restored, with everything that watched or operated a running replication left out. Why a package rather than a folder of the Workspace's: the Workspace's own package stays the frame and Files, and a later pass can put the screens that watch a replication beside the authoring ones for the console's Runner pages.

The sync Designer's server calls are answered in the Workspace's own process, from Sync's libraries under `Shared/src/DbDataKit.Sync.*`, so the column picker can ask as the person types. No call opens a database, and none runs a child process. Each is a route of a sync draft, `/api/v1/projects/{project}/workspaces/{id}/sync/...`:

| Route | Role | What it answers |
| --- | --- | --- |
| `GET script-slots` | viewer | the script slots a binding can name, each with the levels it binds at (`metadataProvider` binds only at a connection) |
| `POST capabilities` `{"connection"}` | viewer | what the connection's driver offers: its readers, staging providers and writers, their settings, and the key each needs (`SourceKey`, `TargetKey`, `NaturalKey` or `None`). A built-in driver answers from the table `BuiltInDriverCapabilities`, which Sync's tests hold equal to what each driver registers; a driver the draft carries as `drivers/<folder>/driver.yaml` answers what the file declares. A compiled driver is not known offline: the answer is 404 with the reason. |
| `POST inferred-columns` `{"replication", "mapping"}` | viewer | the type each source column would get on the target, and the natural key the SCD Type 2 writer would derive, worked out by the code provisioning and a run use, over the source's columns in `catalog-cache.yaml` |
| `POST bulk-create` `{"replication", "tables": [{"schema", "table"}]}` | author | the mapping files Create mappings makes, one per table, with the columns of both sides from the cache and the columns of the same name paired, plus what would be inferred for each. Nothing is written into the draft: the caller saves the files. |

A question may carry the person's unsaved edits as `"unsaved": {"<path>": "<text>" or null}`, for `catalog-cache.yaml`, files under `config/` and `drivers/<folder>/driver.yaml`. The answer then reads the draft as the person sees it. Example: a cache refreshed and not saved yet goes with `bulk-create` as `"unsaved": {"catalog-cache.yaml": "..."}`, and the files that come back map the columns of the refreshed tables.

In `@dbdatakit/sync-ui`, one module asks these routes: `api/syncApi.ts`, with the hooks of `api/hooks.ts` over it. It sends every unsaved edit of those files with each question, at most 500. The package's test `boundary.test.ts` fails when another module calls a server, or when that module names any other route.

The databases, tables and columns are not a server call: the screens read the draft's `catalog-cache.yaml` in the browser through the Workspace's route that reads a draft's file, a refresh not yet saved included ([docs/authoring-metadata.md](../docs/authoring-metadata.md), "A sync project"). The Workspace server never runs a script a person wrote. **Test** on the Scripts tab runs the script on a Runner, as the replication set's task `script-test`, after the console stages the draft's build there ([docs/authoring-metadata.md](../docs/authoring-metadata.md), "A script's test runs on a Runner").

A sync project's engines come from the suite's engine registry (`DbDataKit.Connections.Descriptor`'s `engines/*.engine.yaml`, read into the web build), one list that the Files area's Sync forms and the Designer's screens both read (`useSyncEngines` of `@dbdatakit/workspace`): as a source the engines whose `sync_source` role is `supported` or `unverified`, as a target those whose `sync_target` is, each with the role's note; a role that is `planned` is shown as planned and not offered, and an engine with no Sync role is not listed. A driver the project carries itself (`drivers/<id>/driver.yaml` or `driver.csx`) is listed as custom and offered as both a source and a target, with the note that what it reads and writes is checked when the draft is checked; once the Workspace answers a connection's capabilities from the driver registry (as the old Sync server did), such a driver is offered only in the roles it has. Example: the new-connection form of Files offers `postgres: source and target` and `flightsql: source`, and a connection naming `flightsql` says under its form that it may be a source and not a target; a project's `drivers/legacy/driver.yaml` that lists readers and no writer is offered as `legacy (custom): source and target`, and the draft's check says it cannot be a target.

The registry is read into the web build, and no server is asked: the console's build is the list. A release that marks `sync_target` of `duckdb` as `supported` makes the console of that release offer DuckDB as a target, whatever version the Workspace or the Runner runs. This holds while the console and the Workspace of an install run the same release; when they can run different ones, a Workspace route answering its own build's registry takes over, so the list follows the server that checks and packages the draft.

The sync Designer's navigation lists the draft's replications and ends with **New replication**, the last entry, which opens a dialog asking only a name and a schedule (the old Replications page's form); the replication is made in the draft and its Overview opens, where the person picks the source's and the target's connections. With no connection in the draft the dialog says so and links to `config/connections/` in Files.

The frame is built (`WorkspacePage.tsx`, `draft.tsx`, `designers.ts` of `@dbdatakit/workspace`): the two areas, their addresses, the navigation and the chrome; the draft's unsaved edits are held by the frame (`useDraft`, `useDraftFile`), and a file's editor in Files saves on its own (the live check of a form) only what was typed in that editor, so an edit made in the Designer stays not saved until **Save**: a look should not save. Example: Ana turns **Enabled** off on a replication's page, then opens its `task.yaml` in Files to look; the form shows `enabled: false` marked not saved and leaves it so, and the check beside the form is about the saved text until she presses Save or types in the form.

What makes, moves or deletes a file writes into the draft at once, as the Files area always did: **New file**, the forms that make a file (New connection and New replication of Sync's set overview, New model, New script), **Move** and **Delete**; a file made only as an unsaved edit is deleted by dropping the edit. The Designer's own edits (a field, **Enabled**, a mapping) are unsaved edits until **Save**. Example: Ana makes the connection `crm` from the set overview in Files, and it is in the draft at once; she then picks `crm` as the source on a replication's Overview, and that change is marked not saved. The navigation always shows the Designer's entries and the Files tree, and a kind's overview cards (Sync's set overview, an integration's package) stay in the Files area.

A kind registers its Designer with `registerDesigner` (a `Navigation` and a `Page` component, the page routing the address after `designer/` itself). An address with only `?tab=<tab>` (where the Runner's screens link back) opens that tab of Files. Sync is the first kind with a Designer, and it covers what lives inside a replication; a sync project's connections and scripts are edited in Files. Its navigation lists the replications and ends with **New replication**. A replication whose files have errors in the draft's check shows the number of errors beside its name; the check reads the saved files. A replication's page (`designer/replications/<name>`) has three tabs:

- **Overview**: the source and target cards side by side the schedule and the tracking settings (`tracking:`). A card's connection is one of the draft's connection files; its database is one the draft's `catalog-cache.yaml` lists for that connection, with the line saying which server and channel read it and when. The tracking modes **Target** and **Both** keep a state table on the target, so they are offered only when the target connection's driver keeps one (`keepsStateTable` of the Workspace's `sync/capabilities`: SQL Server and PostgreSQL); otherwise they are disabled and the card says why. Example: Ana picks the MySQL connection `mart` as the target; Target and Both turn grey, the card says that `mart` (driver MySql) keeps no state table and to choose State only or Default, and a `task.yaml` that already says `mode: target` keeps it shown with that reason as a warning, which the draft's check also refuses.
  Under them are five sub-tabs, each with its own address:
  - **Notes** (the replication's own address): the replication's `notes`, in Markdown.
  - **Pipeline** (`.../overview/pipeline`): the Reader, Staging and Writer stages of `changeProcessing`, each with its kind and settings, and the delete reconciliation (`reconcile:`) under them. The readers are those of the source connection's driver; the staging providers and writers are those of the target connection's driver (the Workspace's `sync/capabilities`).
  - **Provisioning** (`.../overview/provisioning`): what every mapping may do to its target unless the mapping says otherwise (`provisioning:`), and the replication's plan below it, grouped by connection and side.
  - **Custom Transforms** (`.../overview/transforms`): the scripts bound to the replication's slots. The slots are the Workspace's `sync/script-slots`, and the scripts offered are the draft's enabled scripts of each slot.
  - **Bulk Load** (`.../overview/segmenting`): the named segmenting strategies a mapping's reload can use. **Try** in a strategy's editor runs it as it is written over one of the replication's mappings and a column, on the Runner the draft was last published to, and lists every candidate it proposes; nothing of them is kept (`docs/authoring-metadata.md`, "Rows and trials are answered, never kept").
- **Table Mappings** (`.../mappings`): a sidebar of the replication's mappings with the count of mapped columns of each, and **+** for a new one. Its overview lists the tables of the source database from the catalog cache, how many mappings read each, and **Create mappings** for the ticked tables. A mapping's editor has the two sides, each inheriting the replication's endpoint unless **Override for this table** is on, and under them the source filter (`filter:` of the source, a SQL predicate the reader adds to its `WHERE` clause), open with **FILTERS APPLIED** when the mapping has one. Under the filter, **Preview rows** shows the first rows of the source (20, 50 or 100), read on the Runner the draft was last published to, with the mapping as the draft has it (unsaved edits included) and the login its channel binds; nothing of them is kept. **Custom query, not a table** on the source side replaces the schema and table with a query (`query:`), edited in a dialog with whether it may be wrapped as a subquery; no row of it is read. Below are eight tabs, each at `.../mappings/<mapping>/<tab>`:
  - **Notes** (`notes`): the mapping's `notes`, in Markdown.
  - **Column Mapping** (`columns`, where the sidebar opens a mapping): **Auto-map by name**, each target column's source column, target type and transform, the primary key, the relationships, and the columns the mapping records of its tables compared with the catalog cache.
  - **Custom Transforms** (`transforms`): the scripts bound to the mapping's slots, each inheriting the replication's binding, else the source connection's.
  - **Bulk Load** (`segmenting`): how the table divides for a reload (`defaultSegmenting:`): the whole table, buckets of a column, a fixed list of ranges or values, or one of the replication's segmenting strategies with this table's column.
  - **Provisioning** (`provisioning`): what the mapping may do to its target, each setting the replication's unless set here, and the mapping's part of the replication's plan. The tab's name carries the number of statements that plan would run.
  - **Pipeline** (`pipeline`): the mapping's own Reader, Staging and Writer in place of the replication's, for Change Processing and for Bulk Load, the natural key of the SCD Type 2 writer, and the mapping's own delete reconciliation.
  - **Diagnostics** (`diagnostics`): **Trace stage timing** (`traceTiming:`), which records how long each stage of a pass took onto the run.
  - **Verify** (`verify`): the mapping's verification checks (`verification:`): a row count, a sum, two statements of your own or a script, each comparing the source and the target.
- **Quality Checks** (`.../checks`): the replication's `checks:`, listed with their kind and severity. **Add check** opens a form for one of the seven kinds, and **Add to the list** puts it in `task.yaml` as an unsaved edit. The draft's check then reads it as a Runner would.

The page's chrome has **Enabled** (it takes effect on a Runner when the set is published), **Save settings** (it saves `task.yaml`) and **Delete**, which asks twice and then removes the replication's folder from the draft. Each change on the page is an unsaved edit of the file it belongs to, written as a change of that value only, so comments and keys the page does not show stay in the file. **Create mappings** asks the Workspace for the files (`sync/bulk-create`, with the draft's unsaved edits) and puts them in the draft as unsaved edits, one per ticked table, named `schema.table`: the columns of the same name are paired, both sides' columns from the cache are recorded, the mapping states no key of its own (the source's key is used), and no target type is written (the target's types are inferred when it is provisioned). A target table the catalog cache does not have gets every source column. The overview then lists what was made: for each mapping, how many target types are inferred and the natural key the SCD Type 2 writer would derive, or why there is none, what could not be captured of a side, and the tables skipped because a mapping of that name exists.

Column Mapping shows a target type nobody set as the type the Workspace infers from the source column (`sync/inferred-columns`, the code provisioning runs), in grey; typing a type writes it into the mapping, and it then stays as typed when the source changes. Example: Ana ticks `dbo.Lines`, which has no primary key, and `dbo.Customers`, keyed on `id`, for a PostgreSQL target, and clicks **Create 2 mappings**. The overview says `dbo.Lines` has 3 target types inferred and no primary key to derive a natural key from, and `dbo.Customers` has the natural key `id`. On `dbo.Lines`, Column Mapping shows `date` in grey as the type of `shipped_on`, and `targetType` is not in the file; on the Pipeline tab the natural key says the table has no primary key, and **Enter it by hand** takes one.

A mapping's editor changes the mapping only when the person changes something on it. Opening a saved mapping leaves its file as it is, so looking at a mapping never marks the draft not saved. Picking a side's table writes that side's columns from the catalog cache into the mapping (`sourceColumns` or `targetColumns`) at once, as an unsaved edit. While nobody has edited the column pairs, picking a table also pairs the columns that have the same name on both sides. A table the catalog cache does not have removes that side's columns from the mapping. Example: Ana opens the saved mapping `dbo.orders`, whose column pairs are empty, and the draft stays saved. She picks `dbo.order_lines` as its source table: `sourceColumns` now lists that table's columns from the cache, the columns with the same name on both sides are paired, and the mapping is marked not saved.

The schedule on the Overview keeps only the settings of the mode it shows, because Sync reads one set of settings for each mode:

- **Continuous**: the replication runs every `frequencySeconds`, and its worker stops after `idleTimeoutSeconds` without a changed row.
- **Periodic**: the replication runs on `cronExpression`.

Switching the mode removes the other mode's settings from `task.yaml`. Switching to Periodic writes the cron expression the replication had, or `*/15 * * * *`. Switching to Continuous writes `frequencySeconds: 60` and no idle timeout. Example: the replication `orders` runs Continuous with `frequencySeconds: 60` and `idleTimeoutSeconds: 120`. Ana switches it to Periodic, and `task.yaml` now has `cronExpression: "*/15 * * * *"` and neither of the other two. When she switches it back to Continuous, the file has `frequencySeconds: 60` and no cron expression, and she types the idle timeout of 120 again if she wants it.

The pickers, the overview and Column Mapping read the catalog cache as the draft holds it. A connection the cache has nothing for shows a line saying so, and its pickers stay empty until its catalog is read into the cache. Three buttons read a database again through the console, which starts the read on a Runner as the person:

- **Refresh catalog** on an endpoint card whose connection is one of the draft's and has nothing in the cache: the whole connection.
- **Refresh** on the Table Mappings overview: the replication's source connection.
- **Refresh** beside each side of a mapping's cached-metadata card: that side's table.

Each opens the channel picker of the Files area's Catalog tab, reads in the channel chosen, and lists the tables and columns added, removed or retyped before anything is replaced ([docs/authoring-metadata.md](../docs/authoring-metadata.md), "The catalog cache"). **Accept** puts the new cache in the draft as an unsaved edit of `catalog-cache.yaml`, which the pickers and Files show at once; **Save** keeps it. Accepting a read does not change any mapping: the cached-metadata card then compares the mapping's own columns with the new cache. Example: on the mapping `dbo.Invoices`, Ana presses **Refresh** beside Source, keeps the channel `dev` and presses **Refresh**. The panel says "1 column added" and lists `App.dbo.Invoices.segment`. She presses **Accept**, and the card now says "the catalog cache has 1 column added (segment)"; she adds the column to the mapping on Column Mapping.

A Runner runs the build that was published, never the draft. The page's rail has **Build and publish…**, a link to the Builds tab of the same draft in Files (`.../files?tab=builds`). There the person makes the build and publishes it from its panel, which deploys it through the console ([docs/publishing.md](../docs/publishing.md), "Publishing from the Builds tab"). The browser's **Back** returns to the replication. A build reads the files the Workspace server holds, so the card says when the draft has edits that are not saved and that the build leaves them out. Example: Ana turns **Enabled** off on `orders`, and the card says "One edit of this draft is not saved, so a build leaves it out." She presses **Save**, then **Build and publish…**, makes the build, stages it on the Runner `plant` in `dev` with `source-db=erp` bound, and presses Back to return to `orders`.

The rail also says what a Runner does not run yet. When the console has deployed a build of the draft to a Runner, the card **Unpublished changes** names that version and channel and counts what came after it: the draft's commits after the commit the build was made from, the unsaved edits of this replication's files, and the unsaved edits of the files every replication uses (connections, scripts, drivers and `catalog-cache.yaml`). The console's deploy record, the build and the draft's history are read through the console; no Runner is asked. Example: version 1 of `plant` is staged on `dev` of the Runner `plant`. Ana turns **Enabled** off on `orders`, and the card says "Version 1 on dev of plant was built before unsaved edits of 1 file of this replication." On `customers` the card does not appear, because that edit is not one of its files.

The Provisioning sub-tab asks the Workspace for the replication's plan (`provisioning-plan`), made from the catalog cache and the draft as the person sees it: the request carries the unsaved edits, as the `sync/` questions do. While the person edits, the plan is asked again once the edits have stayed the same for a moment (300 ms), and the previous plan stays on screen until the new one arrives. The tab says how many unsaved edits the plan includes. The Files area's Provisioning tab asks with the same unsaved edits when the person presses **Plan from the catalog cache**, and says how many it included. **Apply** runs the version on the Runner, so a statement that comes from an unsaved edit is applied only after the edit is saved, built and published. **Plan again** asks again, and a save asks again too. Each statement is shown once, with the mappings that need it, and **Copy** copies a group's statements as a script. **Apply** on a mapping runs the set's task `provision` of the version the console last deployed to a Runner, through the console as the person, as the Files area's Provisioning tab does, and shows the run's outcome and each statement it ran. Without a build of the draft on a Runner the tab says so and offers no **Apply**. Example: Ana opens **Provisioning** on `orders`; the group `target-db · target` shows `CREATE TABLE "public"."orders" ...` for the mapping `orders`, and **Apply** `orders` runs it on the Runner `plant`, which reports "Done: Create the table of orders".

Each mapping named in the replication's plan is a link to that mapping's Provisioning tab, which shows the same plan for that mapping alone, with its settings above it. The plan is the replication's, asked with the draft's unsaved edits, so a mapping that is not saved yet is planned too. The tab's name carries the number of statements, and the number follows each edit. Statements are applied from the replication's Provisioning tab.

The plan of a target table that is missing always holds its `CREATE TABLE`, and says who runs it, as a pass of the run decides:

- **Create target table if missing** is on: the first pass creates the table with that statement.
- The setting is off: a pass does not create the table and fails until it exists. The person applies the statement, creates the table another way, or turns the setting on.

**Alter target columns if missing or changed** is said the same way for an `ALTER TABLE`. Example: Ana creates the mapping `dbo.Lines`, whose target table `dw` does not have, and does not save it. Its Provisioning tab reads **Provisioning 1**, shows the `CREATE TABLE` the target would run and says that a pass does not create the table. She turns on **Create target table if missing**; the tab still reads **Provisioning 1**, now says that the first pass creates the table, and the hint says the mapping's unsaved edits are included. On the replication's Provisioning tab, the name `dbo.Lines` beside that statement opens the same tab.

A query source has no columns in the catalog cache, so the mapping records them itself (`sourceColumns`), as the Runner reads them. When the source is a query, the Column Mapping tab starts with the card **Query columns**, which lists the columns the mapping records. **Describe columns…** opens the channel picker, and **Describe columns** asks the Runner to describe the query in the channel picked, with the login that channel binds; the query is described and never run, so no row comes back. **Use these columns** writes the columns into the mapping as an unsaved edit. While nobody has edited the column pairs, the target's columns of the same name are paired with them. A query that changed is described again. Example: Ana turns on **Custom query, not a table** on `orders`, writes `SELECT id, total FROM dbo.Orders`, and presses **Describe columns** in `dev`. The panel says "2 columns: id int, total decimal(12,2) null"; she presses **Use these columns**, Column Mapping lists `id` and `total`, and **Save mapping** writes both under `sourceColumns`.

Each endpoint card on the Overview has **Test**. It opens the channel picker and runs the Runner's binding test of the card's connection in the channel picked, through the console as the person: the binding, the connection, the login and the connect, each with its state and the Runner's reason. No row comes back, and the draft needs no build. A channel that does not bind the connection's slot cannot be tested. When a channel does not bind it, production as any other (with the production warning), the picker offers **Set up `<connection>` for development**: the console stores the login on the Runner, copies the draft's connection file there and binds the slot in the channel ([docs/authoring-metadata.md](../docs/authoring-metadata.md), "Before anything is published: Set up for development"). The same picker is used by every Refresh button and by **Describe columns**. Example: Ana picks `target-db` as the target and presses **Test**. `dev` does not bind its slot, so the panel offers **Set up target-db for development**; she types the login `dw_dev` and its password, the console binds the slot in `dev`, and the picker then offers `dev` with **Test**.

Below the provisioning plan, the replication's Provisioning sub-tab shows the card **Newest preflight**: the newest run of the set's `preflight` in a channel the draft was published to (the newest deploy first, the others in a picker), read through the console. It shows the run's version, outcome and time, its link on the Runner, and what the run found for each mapping of the replication and for where the replication keeps its state. A mapping's Provisioning tab shows the same card with that mapping's findings only. A preflight runs when a version is served in production, and on **Re-check** on the Runs tab in Files; before the draft is published the card says that no channel has a version with a preflight. Nothing of the run is committed. Example: Ana stages `plant` on `dev` and presses **Re-check** on the Runs tab. On `orders`, the Provisioning sub-tab then says "preflight of version 1, succeeded" with a link to the run, and lists under `orders` the error "The run login of 'target-db' may not UPDATE dw.public.orders."

Example: on `dbo.Lines`, Ana opens **Verify**, clicks **Add check**, names it `rows` and keeps the kind Row count. On **Bulk Load** she picks **Custom: a segmenting strategy**, keeps the replication's strategy `by-month` and types the column `shipped_on`. She presses **Save mapping**: the file has a `verification:` list with the row count and `defaultSegmenting: [{mode: custom, strategyName: by-month, column: shipped_on}]`.

Example: on the replication `orders`, Ana picks the target `dw` and the database `warehouse` on the Overview, opens Table Mappings, ticks `dbo.customers` and `dbo.invoices` and clicks **Create 2 mappings**. Two files appear under `config/replications/orders/table-mappings/` marked not saved; `dbo.invoices` has no key in the source, so on its Column Mapping tab she ticks `invoice_no` under Primary key, presses **Save mapping**, then **Save** in the chrome for the rest.

## Reading a database while authoring

The Workspace holds no login of a customer database and never opens one. What a project's databases hold is read on a Runner, as a task run as the person who asked, with the login a channel binds to the project's slot: discovery of databases, schemas, tables and columns, a query's columns, the connection test, and each package's `preflight` before it is served in production. Before anything is published, **Set up for development** binds a slot in a non-production channel on the Runner with a login the person types once (it is sent to the Runner and kept nowhere in the Workspace). What discovery finds is committed in the draft as `catalog-cache.yaml` with the channel and Runner group it was read from, refreshed only on request with the difference shown, and read offline by the pickers and the draft's check; no row, sample, value statistic, login or address is kept. The design, with what is built and examples: [docs/authoring-metadata.md](../docs/authoring-metadata.md).

## The server's directory

| Path | What |
| --- | --- |
| `server.yaml` | the `state:` section (engine and connection) and the `apps:` section (how an app is built: `packageStore`, `allowedPackages`, `packageStoreSha256`, `isolation: required\|auto`, `buildTimeoutSeconds`, `bun`; a server with no `packageStore` does not build) |
| `state.db` | the state database on SQLite (the default); `DBDATAKIT_STATE_WORKSPACE_ENGINE` and `DBDATAKIT_STATE_WORKSPACE_CONNECTION`, or the `state:` section, name SQL Server or PostgreSQL |
| `projects/<id>/` | a project the server made (a git repository); a project added by path stays where it is |
| `workspaces/<project>/<id>/` and `<id>.json` | a workspace's worktree and the record that says whose it is (the layout Build's server has always had; `DbDataKit.Authoring`) |
| `builds/<project>/<id>/` | a build: `app/` (the built folder) or `artifact/`, and `result.json` |
| `secrets/` | the server's own secret store: the login of its state connection, when the state is on SQL Server or PostgreSQL |
| `management-audit.log` | who made a project, requested a build or changed a draft, never a value |

`DBDATAKIT_DATA_WORKSPACE` (or the folder `workspace` under `DBDATAKIT_DATA`) names the directory for every command; the service's own is `%ProgramData%\DbDataKit\workspace` (`/var/lib/dbdatakit/workspace`).

## The state module `workspace`

Kept per service in the state database (`DbDataKit.State`, `WorkspaceModule`): `project` (id, kind, repository folder), `workspace` (the drafts that exist now), `workspace_event` (created, committed, pushed, merged, abandoned, with who; kept a year), and `build` (kept 90 days). Version 2 of the module drops the table `publisher_key`, which an earlier version used for its publisher keys. The retention rules are the shared job's.

## The management API

Every call needs a token a paired console issued; the roles are the suite's (`DbDataKit.Web`).

| Call | Role |
| --- | --- |
| `GET /api/v1/info` | any |
| `GET /api/v1/project-kinds` | viewer (the kinds of project, what each publishes as and to which product; plan 33 SC20a) |
| `GET .../{id}/check` (under `/api/v1/projects/{project}/workspaces`) | viewer (the draft checked by its kind's validators: diagnostics with file and line) |
| `GET /api/v1/projects` | viewer (a token scoped to some projects lists those) |
| `POST /api/v1/projects` `{id, title?, kind?}` | admin |
| `GET\|POST /api/v1/projects/{project}/workspaces`, `DELETE .../{id}` | viewer; author to make one; the owner abandons theirs |
| `GET .../{id}/files`, `GET .../{id}/files/{path}`, `GET .../{id}/changes`, `GET .../{id}/history`, `GET .../{id}/events` | viewer |
| `PUT .../{id}/files/{path}` `{content}`, `DELETE .../{id}/files/{path}`, `POST .../{id}/move` `{from, to}` | author, the owner (text files of at most 1 MiB; a path stays inside the draft and never names `.git`; saves are not history, the commit is) |
| `POST .../{id}/commit`, `POST .../{id}/push` | author, the owner |
| `POST .../{id}/merge` | approver (a project that follows a git remote is pushed to, never merged here) |
| `GET .../{id}/builds/{build}/contents`, `GET .../{id}/builds/{build}/files/{sha256}` | viewer (what a build holds to send, its record and each file by hash: what the console reads to deploy it) |
| `GET /api/v1/state` and the maintenance calls | the shared state API (`DbDataKit.State.Api`) |

A build of a project whose kind produces something to publish (`build`, `sync`, `store`, `integration`) is the kind's check followed by its artifact in `builds/<project>/<id>/artifact/` (`package.yaml` and `files/` for a Runner, `models/` for a Gateway); the console deploys it to a Runner or a Gateway as the person (`POST /api/deploys`). The calls that sent a build, ran its tasks, read a Gateway's catalog or kept publisher keys answer `410 Gone` with the console's call to use instead ([docs/publishing.md](../docs/publishing.md#deploying-a-build-from-the-control-service)), and the former command `publisher` answers the same way.

The `integration` kind (IX20) is a manifest (`package.yaml`), job classes in `src/*.csx` (or a `.csproj` for a compiled project), and test scripts in `tests/`: the check is `dbdatarunner package build` into a scratch folder (no .NET SDK needed for csx), a build runs `package test` first and then writes the package, and a compiled project is built with `dotnet publish` only where the SDK is installed (a server without it says so, `DBD-WS-INTEGRATION-SDK`). The programs are `dbdatarunner` and `dotnet`, found beside the server or on PATH (`RunnerExecutable`, `DotnetExecutable`, `IntegrationSources` and `IntegrationCache` name them and the NuGet feeds otherwise); see [`docs/integrations.md`](../docs/integrations.md).

The console relays an explicit table of these (`ServerProducts.WorkspaceRoutes` in `DbDataKit.Server`: 45 routes, each with its role, checked at the relay against what the person holds, in the route's project too, and by the server again), not the whole API.

## Build and test

From this folder: `dotnet build`, then `dotnet test --project tests/DbDataWorkspace.Tests` (xunit v3). The server tests run on SQLite always and on PostgreSQL and SQL Server when `DBDATAKIT_TEST_POSTGRES` and `DBDATAKIT_TEST_SQLSERVER` are set (`testenv/testenv.sh up mssql postgres`, then `eval "$(testenv/testenv.sh env dbdatakit)"`); `DBDATAKIT_TEST_REQUIRE_POSTGRES=true` makes a missing engine a failure, not a skip. The module's own convention, layout and retention tests are `WorkspaceStoreTests` in `DbDataKit.State.Tests`.
